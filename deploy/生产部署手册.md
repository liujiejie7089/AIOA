# AIOA 生产部署手册（单机 Docker Compose · 应用机 10.0.0.12）

> 目标：把 AIOA 的**应用侧**部署到 **10.0.0.12**，由本仓库的 `deploy/docker-compose.yml`
> 起 `server` / `agent`（**本次不用边缘 nginx、也不用 MinIO**，理由见 ⑥⑦）。  
> **MySQL / Redis / Milvus / MinIO 都不在这台机上、也不由本 compose 托管**，全部按外部地址直连。  
> 配置模板：`deploy/.env.production`（地址已按本次环境填好，只需补口令 / Key，见 §4.0）。

> ### ★ 2026-09-21 现场复核结论（照下文执行前先读这四行）
>
> ① **应用机拉不到 Docker Hub**（`failed to resolve reference "docker.io/minio/minio:latest" … i/o timeout`、
>    `ping baidu.com` 100% 丢包）⇒ 镜像**不能直接 pull**，按 **§5.0** 在「国内加速器」与「离线搬运包」之间二选一。
>
> ② 上一轮 `.env` 里 **MySQL / Redis 口令根本没写进去**：自检打印的 `22` / `25` 是**占位符本身的长度**
>    （`CHANGE_ME__db-password` = 22 字符、`CHANGE_ME__redis-password` = 25 字符），**不是你的口令长度**；
>    `MINIMAX_API_KEY` 也仍是空 —— 旧检查 `grep -c '^MINIMAX_API_KEY=.\+'` 把该行 `=` 后面的**填充空格**
>    当成了值，是**假通过**（本次已换成会真报错的自检）。
>
> ③ **写口令不要再用 `sed -i "s|^KEY=.*|KEY='${P}'|"`**：值里含 `|` 会让整条命令失败
>    （`sed: -e expression #1, char NN: unknown option to 's'`，屏幕上只有一行报错、值**静默没写**）；
>    值里含 `&` 更糟 —— sed 会把 `&` 展开成「匹配到的整段原文」，**不报错但值被改坏**。
>    统一改用 `deploy/ops/set-secrets.py`（按行整体重写，`$ | & # ! ' " \` 与空格、中文全都安全）。
>
> ④ **三台机器的角色**：本地（改代码 / 推代码）→ **隧道机 `219.151.186.24`**（唯一能碰到真实服务器的跳板）
>    → **真实服务器 `10.0.0.12`（无外网）**。公网直连 `10.0.0.12:22` 不通，下面的命令都在**真实服务器自己的 shell** 里跑。
>
> ⑤ **真实服务器上已有 5 个容器，但一个都不是本项目要的**（2026-09-21 `docker ps` 实测）：
>    `milvus:v2.6.14` / `etcd:v3.5.25` / `mongo:latest` / `apache/rocketmq:4.9.6` ×2。
>    其中只有 **Milvus 有用**（外挂复用，`AIOA_MILVUS_URI=http://10.0.0.12:19530`；`v2.6.14 ≥ 2.5` ⇒
>    `AIOA_MILVUS_ENABLE_BM25=true` 可保留）；`etcd` 是 Milvus 的配套；
>    **`mongo` 与 `rocketmq` 属别的系统** —— 本项目源码里搜不到任何 mongo/rocketmq/kafka 依赖，别去动它们。
>    这些容器占的是 10909/10911/9876/19530/2379/2380/27017，**与我们本次要用的 8080/8000 不冲突**。
>
>    ⚠️ **`docker ps` 只列「运行中的容器」，不是「镜像清单」** —— 机器上可能有没在跑的 `nginx`/`minio` 镜像。
>    判断够不够**只能**看 `docker images`（见下方清单 A 的 ① 与 ⑤）。
>
> ⑥ **本次入口「不用边缘 nginx」**（你已有的 nginx 在别的机器上）：叠加 `deploy/docker-compose.backend.yml`
>    把 `server:8080` / `agent:8000` 发布到宿主，其余交给你的 nginx 反代 `/api/`。
>    ⇒ 只起 **2 个容器**（server + agent）、只搬 **2 个镜像**（`aioa-server` + `aioa-agent`）。
>    ⚠️ 代价要认清：**80 = 用户端 H5 / 81 = 管理端** 这两份静态就没人托管了 ——
>    它们各有明确出处，见 **§5.2「静态前端放哪」**（H5 是单文件、管理端需要构建产物）。
>
> ⑦ **MinIO 应用代码根本不读**（2026-09-21 全仓 grep：Java/Python/前端里没有 `minio` 字样，
>    也没有 S3 客户端）。文件上传落的是 **server 容器内 `/app/uploads`**（本次已挂命名卷
>    `serveruploads` 做持久化），元数据落 `sys_file` 表。
>    ⇒ 别处那台 MinIO（`172.16.8.249`，控制台 `:9001`）**与本项目无关：不需要接、不需要搬镜像**；
>    compose 自带的 `minio` 服务已归入 `profile: [minio]`，默认 `up` 不再起它
>    （历史包袱：它曾被 `server.depends_on: minio(healthy)` 强制拉起，该依赖**已移除**）。
>
> ⑧ **本次不部署 Ollama，知识库照样能落进 Milvus**（2026-09-21 定案）：
>    嵌入走 `aioa.kb.embedding-provider=local`——**维度固定 256**（写死在 `EmbeddingProvider.local()`），
>    进程内计算、零依赖、不需要任何嵌入服务。因此：
>    - `AIOA_MILVUS_DIMS` **必须 = 256**，集合名必须是 **256 维的新集合**（本次用 `kb_chunk_v1_256`）——
>      Milvus 集合维度创建后不可改，已有 512 维集合只能换名，不能原地改；
>    - 后端启动会**硬校验**「嵌入维度 == 集合维度」，不一致会**直接启动失败**并告诉你该改成什么
>      （`MilvusConfig.assertDimsAgree`）。这道校验是必须的：配错时 Milvus 会**静默**一条不收、
>      检索永不命中，接口却全部成功——属于最难查的一类问题；
>    - 本次**首次启动必须手动回填一次**（`AIOA_MILVUS_BACKFILL=true`），把 MySQL 里已有的切片灌进新集合，
>      否则 Milvus 是空的、只有此后新上传的才进得去（见 D5 与 §6 第 9 条判据）；
>    - ⚠️ 代价要认清：local 是 char n-gram 哈希，**无语义**——向量腿等价于「字面重叠」，
>      召回质量主要靠 `AIOA_MILVUS_ENABLE_BM25=true` 的原生 BM25 关键词腿兜住。
>      将来真接了语义嵌入服务（Ollama / vLLM），按 `.env` §7.0 的 http 档切回
>      （**必须连集合名一起换 + 重算向量**，`dims` 也要跟着改）。

## 全流程执行清单（照顺序打勾）

镜像怎么进来是唯一的不确定项，所以**先做 A，再按 A 的结果决定走 A1 / A2 / C**。

### A · 真实服务器：先体检（**只读**，整段粘贴，不依赖仓库是新是旧）

```bash
echo "=== ① 已有镜像 ==="; docker images --format '{{.Repository}}:{{.Tag}}  {{.Size}}' | sort
echo "=== ② docker 实际生效的 registry 镜像源 ==="; docker info 2>/dev/null | sed -n '/Registry Mirrors/,/^[A-Z]/p' | head -8
echo "=== ③ daemon.json ==="; cat /etc/docker/daemon.json 2>/dev/null || echo '(无)'
echo "=== ④ 出口通断（200/301/302 = 通；000 = 不通）==="
for u in https://www.baidu.com https://mirrors.aliyun.com https://registry-1.docker.io/v2/ \
         https://docker.m.daocloud.io/v2/ http://172.16.8.249:3000; do
  printf '  %-44s %s\n' "$u" "$(curl -sS -m 6 -o /dev/null -w '%{http_code}' "$u" 2>/dev/null || echo 000)"
done
echo "=== ⑤ 缺哪些镜像（★ 本次「后端档」只需要下面这 2 个）==="
for i in aioa-server aioa-agent; do
  docker image inspect "$i" >/dev/null 2>&1 && echo "  ✅ $i" || echo "  ❌ $i   ← 本次必需"
done
for i in ollama/ollama:latest aioa-web nginx:1.27-alpine minio/minio:latest; do
  docker image inspect "$i" >/dev/null 2>&1 && echo "  ✅ $i" || echo "  ⚪ $i   ← 本次不需要（不部署 Ollama / 不用边缘 nginx / 代码不读 MinIO）"
done
echo "=== ⑥ .env 占位符残留（这一行应无输出）==="
grep -nE 'CHANGE_ME__' /opt/aioa/deploy/.env 2>/dev/null | grep -v ':#' || echo "  (无残留)"
echo "=== ⑦ 本次要用的端口是否空闲（8080 后端 / 8000 agent）==="
ss -lntp 2>/dev/null | grep -E ':(8080|8000)\b' || echo "  (全空闲 ✅)"
```

> ⚠️ **① 与 ⑤ 看的是 `docker images`（镜像），不是 `docker ps`（容器）** —— 机器上可能有没在跑的
> `nginx` / `minio` 镜像，用 `docker ps` 判断会误判成「什么都没有」，白搬一个包。
> `aioa-server` / `aioa-agent` 这两个是本项目代码构建出来的，**任何机器上都不会现成存在**。
> 而 `aioa-web` / `nginx` / `minio` 三张镜像**本次根本不需要**（见头部 ⑥⑦）。

仓库若已是最新，等价于跑 `bash deploy/ops/host-check.sh`（更全：git 版本、加速器逐个通断、镜像齐备度）。

**按 ②③④ 的结果定路**：

| 情况 | 走法 |
| --- | --- |
| ②③ 里有**内网 registry**（harbor / nexus / `registry-mirrors` 指向 `172.x`/`10.x`），且探得通 | **最省事**：能直接 pull 基础镜像 ⇒ 在应用机 `docker compose -f docker-compose.yml -f docker-compose.backend.yml build server agent`（`--build` 也能用了），跳过 C 与 D1–D2 |

- [ ] **D5** **首次回填 Milvus（必做一次；不做则 Milvus 是空的）**：

```bash
# 首次接入时新集合是空的 —— 这步把 MySQL 里已有的切片按 256 维灌进 Milvus。
# ⚠️ 不回填**不会报错**，只是「Milvus 里没有历史数据、只有此后新上传的才进得去」，
#    非常容易被误判成"没落库"。所以它是一次性必做步骤，而不是可选项。
cd /opt/aioa/deploy
AIOA_MILVUS_BACKFILL=true docker compose -f docker-compose.yml -f docker-compose.backend.yml up -d server
docker compose -f docker-compose.yml -f docker-compose.backend.yml logs --tail=300 server \
  | grep -E 'Milvus (回填完成|集合|连接成功)'
# 期望：
#   Milvus 连接成功：uri=http://10.0.0.12:19530 collection=kb_chunk_v1_256
#   Milvus 集合创建完成：kb_chunk_v1_256 bm25=true
#   Milvus 回填完成：写入=N 跳过(无向量)=0 跳过(维度不符)=0 collection=kb_chunk_v1_256
# 跑完把 .env 的 AIOA_MILVUS_BACKFILL 改回 false 再重启 server（否则每次重启都重灌一遍）。
```

- [ ] **D6** 知识库端到端：管理端 → 知识库 → 上传 `.txt` → 切片完成 → 检索命中关键词（判据见 §6 第 9 条）

## 2. 上服务器做一次体检（先做，别跳）

> **一条命令代替本节全部**（只读，不改任何东西，含外网/加速器通断与镜像齐备度）：
>
> ```bash
> cd /opt/aioa && bash deploy/ops/host-check.sh
> ```
>
> 下面是它覆盖的逐项手工版本，想单独看某一项时用。

```bash
# 2.1 应用机现有容器与端口（MySQL / Redis 不在本机，这里看不到它们）
docker ps --format 'table {{.Names}}\t{{.Ports}}'
ss -ltnp | grep -E ':(8080|8000|19530|9000|9001)\b' || true
# ↑ 本次真正要用的只有 8080（后端）/ 8000（agent）；19530 在别的机器上（外部 Milvus）。
#   80/81/9011 是「自带 nginx 完整档」才占用的端口，本次与你无关。

# 2.2 Docker 与 compose 版本（需要 compose v2）
docker version --format '{{.Server.Version}}'; docker compose version

# 2.3 资源余量（建议可用内存 ≥ 8G、磁盘 ≥ 20G）
free -g; df -h /var/lib/docker 2>/dev/null || df -h /

# 2.4 ★ 外部 MySQL：连通性 + 版本必须 ≥ 8.0
#     ⚠️ 本机没有 mysql 容器，**别用 `docker exec -it mysql`**（会报 no such container）
mysql -h 10.0.0.5 -P 13049 -u aioa -p -e "SELECT VERSION(), @@sql_mode\G"
# 只看端口通不通（不需要客户端）：nc -z 10.0.0.5 13049 && echo 'MySQL 13049 可达'

# 2.5 ★ 外部 Redis：**本次有口令**，-a 后面填你的口令
redis-cli -h 10.0.0.7 -p 6379 -a '<你的Redis口令>' ping        # 期望 PONG
# 只看端口：nc -z 10.0.0.7 6379 && echo 'Redis 6379 可达'

# 2.6 ★ Milvus：先确认 19530 可达（这是后端真正要连的端口）
nc -z 10.0.0.12 19530 && echo 'Milvus 19530 可达'

# 2.7 Milvus 版本（原生 BM25 需要 ≥ 2.5）。
#     ⚠️ 若 9091（健康检查 / WebUI）没发布出来，下面这条会失败 —— **不影响后端**，跳过即可
curl -s --max-time 3 http://10.0.0.12:9091/healthz; echo
```

> 应用机若没装 `mysql` / `redis-cli`，可以借一次性容器探（**不会**在应用机起服务）：
>
> ```bash
> docker run --rm mysql:8.0 mysql -h10.0.0.5 -P13049 -uaioa -p -e 'SELECT 1'
> docker run --rm redis:7 redis-cli -h 10.0.0.7 -a '<你的Redis口令>' ping
> ```
>
> ⚠️ **但本机拉不到 Docker Hub 时这两条会挂住**（卡在 `Unable to find image … locally` 然后超时，正是本次现场遇到的）。
> 这种情况下**不要**用容器探，改用纯 socket 探，不依赖任何镜像：
>
> ```bash
> for hp in 10.0.0.5:13049 10.0.0.7:6379 10.0.0.12:19530; do
>   h=${hp%:*}; p=${hp#*:}
>   timeout 3 bash -c "cat < /dev/null > /dev/tcp/$h/$p" 2>/dev/null \
>     && echo "✅ $hp 可达" || echo "❌ $hp 不通"
> done
> ping -c2 10.0.0.5 >/dev/null 2>&1 && echo 'ICMP 10.0.0.5 通' || echo 'ICMP 不通（不代表 TCP 不通）'
> ```

**体检结论要满足**：**8080 / 8000** 空闲（本次入口）；MySQL `10.0.0.5:13049` 连得上且 ≥ 8.0；  
Redis `10.0.0.7:6379` 回 `PONG`；Milvus `19530` 可达。

> Milvus 版本拿不到时，先按默认 `AIOA_MILVUS_ENABLE_BM25=true` 起；若后端日志出现  
> 「不支持 BM25 / 退回纯稠密」之类告警，把该键改 `false` 再 `docker compose up -d server`。

> ⚠️ **不要**用 `--profile milvus` 起本项目的 Milvus 栈 —— 本环境用的是**外部现成的 Milvus**，  
> `AIOA_KB_STORE=milvus` 指的是「连过去」，不是「在本机起一套」。起了会白拉镜像、并与外部实例混淆。

| ------------- | -------------------------------------- | -------------------------- |

| MySQL 库 / 账号  | `aioa` / `aioa`（**非 root**）            | §1                         |

**两条路径，二选一**：

- **路径 1（推荐，零手填）**：直接用它已填好的 `deploy/.env` —— rsync（方式 B）会自动带上，  
  或 `scp deploy/.env root@10.0.0.12:/opt/aioa/deploy/.env`。⇒ **跳过 §4.1~§4.4**，只跑 §4.5 自检。
- **路径 2（在服务器上从模板手填）**：`cp .env.production .env`，再按 §4.1 → §4.2 → §4.3 → §4.4 逐节填。

**生效键 vs 无效键**（分不清会白改）：

| 你要填什么               | 生效键（改这些）                                                                  | 所在节    | 说明                                                |
| ------------------- | ------------------------------------------------------------------------- | ------ | ------------------------------------------------- |
| MySQL 主机/端口/库/账号/口令 | `MYSQL_HOST` `MYSQL_PORT` `MYSQL_DB` `MYSQL_USER` `MYSQL_PASSWORD`        | **§1** | compose 用这 5 个键**现拼**出后端要用的 `SPRING_DATASOURCE_*` |
| Redis 主机/端口/口令/库号   | `REDIS_HOST` `REDIS_PORT` `SPRING_REDIS_PASSWORD` `SPRING_REDIS_DATABASE` | **§2** | 本次**有口令**，必须填                                     |
| Milvus（已填好，无需你改）    | `AIOA_MILVUS_URI` + `AIOA_MILVUS_TOKEN`（**留空**）                           | §7.1   | 填了 Token 反而认证失败                                   |

| 看起来像、但本 compose **不读**（别浪费时间）                           | 原因                                                                                       |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD`（§1） | server 服务的同名变量被 `${MYSQL_*}` **现拼覆盖**；仅当**不走 compose、直接 `java -jar`** 时才有效               |
| `MYSQL_ROOT_PASSWORD` / `MYSQL_DATABASE`（§1）            | 本 compose **不含 mysql 服务**（MySQL 在外部主机），没有服务读它们；本次也没拿到 root 口令 ⇒ `MYSQL_ROOT_PASSWORD` 留空 |
| `SPRING_REDIS_HOST` / `_PORT`（§2）                       | 同样被 `${REDIS_*}` 现拼覆盖                                                                    |

> ⚠️ **值里的特殊字符**：含 `$` **必须加单引号**（`$` 是 compose 的插值符，裸写或双引号会把口令吃掉）；  
> 含 `!` 建议也单引号（交互式 bash 会做历史展开）；含空格 / `&` / `<` `>` / `|` / `*` 用双引号。

### 4.1 复制模板 + 自动生成随机密钥

```bash
cd /opt/aioa/deploy
cp .env.production .env        # .env 已被 .gitignore 忽略

# 生成随机密钥并就地写入（JWT / 服务间密钥 / 令牌加密键）
# 说明：这里**可以用 sed** —— `openssl rand -base64` 只会产出 [A-Za-z0-9+/=]，
#       不可能出现 `|`（会让 sed 报 unknown option）或 `&`（会被展开改坏值）。
#       用户提供的口令（含 $ ! | & 空格）**必须**走 §4.2 的 set-secrets.py。
J=$(openssl rand -base64 48)
S=$(openssl rand -base64 48)
G=$(openssl rand -base64 48)
sed -i \
 -e "s|^JWT_SECRET=.*|JWT_SECRET=${J}|" \
 -e "s|^AIOA_JWT_SECRET=.*|AIOA_JWT_SECRET=${J}|" \
 -e "s|^SERVICE_JWT_SECRET=.*|SERVICE_JWT_SECRET=${S}|" \
 -e "s|^AIOA_SERVICE_JWT_SECRET=.*|AIOA_SERVICE_JWT_SECRET=${S}|" \
 -e "s|^AIOA_GITEE_TOKEN_ENC_KEY=.*|AIOA_GITEE_TOKEN_ENC_KEY=${G}|" \
 -e "s|^AIOA_GITEA_TOKEN_ENC_KEY=.*|AIOA_GITEA_TOKEN_ENC_KEY=${G}|" \
 .env
```

> **不需要再给 MinIO / Grafana 生成口令了**：本次不用 MinIO（头部 ⑦），Grafana 属 `profile=ops` 不启。
> 模板里这两个键已留空，留着空值即可。


### 4.2 填 MySQL（`deploy/.env` 的 §1 小节）

要点（**端口 13049**、账号 `aioa`）：

```ini
MYSQL_HOST=10.0.0.5
MYSQL_PORT=13049            # ★非默认端口，最容易漏
MYSQL_DB=aioa
MYSQL_USER=aioa             # 非 root ⇒ 需对 aioa 库有 DDL 权限
MYSQL_PASSWORD='你的口令'    # ★唯一真正生效的口令键；含 $ 必须单引号
```

一键写入 + 回读校验（**用脚本，别用 sed** —— 原因见文首现场结论 ③）：

```bash
cd /opt/aioa

# 方式一：交互式，逐项输入（输入不回显，两次确认）
python3 deploy/ops/set-secrets.py --only mysql

# 方式二：先把口令读进环境变量（不进 shell 历史、不进 ps），再由脚本写入
read -rsp 'MySQL 口令: ' MYSQL_PASSWORD; echo

python3 deploy/ops/set-secrets.py --only mysql --from-env
```

脚本会：按行整体重写 `MYSQL_PASSWORD` 与 `SPRING_DATASOURCE_PASSWORD`（同名值一并改，避免残留占位符）、
自动加最稳的引号、**回读校验长度是否与输入一致**，最后用 `docker compose config` 核对**容器真正会收到的值**：

```
  MYSQL_PASSWORD               写入 len=17   读回 len=17   ✅ 一致
  MYSQL_PASSWORD               ✅ 容器将收到 len=17（服务 server）
```

地址三项（`MYSQL_HOST/PORT/DB/USER`）模板里**已经是对的**（`10.0.0.5` / `13049` / `aioa` / `aioa`），
不用改；想核对一眼：

```bash
grep -nE '^MYSQL_(HOST|PORT|DB|USER)=' deploy/.env
```

顺带把 §1 里**不生效**的那三行也改成一致值（可选；只为「日后不经 compose 直接 `java -jar`」时也对）：  
`SPRING_DATASOURCE_USERNAME="aioa"` / `SPRING_DATASOURCE_PASSWORD='你的口令'` /  
`SPRING_DATASOURCE_URL` 里的 `IP:端口` 改为 `10.0.0.5:13049`  
（URL 含 `&`，用 sed 要写成 `\&`，嫌麻烦就 `vim .env` 手改这两处）。

> `MYSQL_ROOT_PASSWORD` / `MYSQL_DATABASE` 本 compose **不读**（无 mysql 服务）⇒ 留空即可。

**账号权限自检**（本次 `aioa` 非 root，Flyway 首启要建表 DDL）：

```bash
docker run --rm mysql:8.0 mysql -h10.0.0.5 -P13049 -uaioa -p -e "SHOW DATABASES LIKE 'aioa';"
docker run --rm mysql:8.0 mysql -h10.0.0.5 -P13049 -uaioa -p -e "SHOW GRANTS FOR CURRENT_USER();"
```



> 库不存在且账号无建库权限时，先在 MySQL 侧建库：  
> `CREATE DATABASE aioa DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`

### 4.5 自检：还有哪些没填（**一条命令**）

```bash
cd /opt/aioa
python3 deploy/ops/set-secrets.py --check      # 退出码 0 = 全就绪，1 = 还有没填的
```

它会打印三张表，一眼看出问题：

```
【体检】文件里的值
  MYSQL_PASSWORD               ✗ 仍是占位符（len=22，占位符本身就是这个长度，别当成已填）
  SPRING_DATASOURCE_PASSWORD   ✗ 仍是占位符（len=22，占位符本身就是这个长度，别当成已填）
  SPRING_REDIS_PASSWORD        ✗ 仍是占位符（len=25，占位符本身就是这个长度，别当成已填）
  MINIMAX_API_KEY              ✗ 空（此项必填）

【体检】compose 渲染后容器真正会收到的值
  MYSQL_PASSWORD               ✅ 容器将收到 len=17（服务 server）
  ...
```

> **长度对照速查**：`22` = 占位符 `CHANGE_ME__db-password`；`25` = 占位符 `CHANGE_ME__redis-password`。  
> 看到这两个数就说明**这一项压根没写进去**，不是「口令短了」。
>
> ⚠️ **不要用 `bash -c 'set -a; . ./.env; …'` 去校验含单引号的项** —— 那种值只能写成双引号 + `$$`，
> compose 会还原成 `$`，而 **bash 会把 `$$` 当成 PID**，两边结论不同。以 `set-secrets.py`
> 或 `docker compose config` 的渲染结果为准。

需要更全的机器侧事实（镜像齐不齐、外网通不通、git 到哪个提交）时，再跑一次总体检：

```bash
bash deploy/ops/host-check.sh          # 只读，不改任何东西
```

> 模板共 **12 处真占位**：9 处随机密钥（§4.1 一次 sed 全替换）+ 3 处口令  
> （`MYSQL_PASSWORD` ★生效 / `SPRING_DATASOURCE_PASSWORD` / `SPRING_REDIS_PASSWORD`）。  
> `MYSQL_ROOT_PASSWORD` 本部署**留空**（compose 不读，且本次也没拿到 root 口令）。  
> 用**路径 1**（已填好的 `.env`）时，本节应当直接全绿。

## 5. 镜像怎么进来（先解决这个，否则 §5.1 必然失败）

应用机拉不到 Docker Hub。**本次（后端档）只需要 2 个镜像**：

| 镜像 | 来源 | 用途 | 本次是否需要 |
| --- | --- | --- | --- |
| `aioa-server` | **本地构建** | 后端（版本由 `name: aioa` 决定，两台机同名） | ✅ 必需 |
| `aioa-agent` | **本地构建** | FastAPI agent | ✅ 必需 |
| ~~`ollama/ollama:latest`~~ | 外部 | 语义嵌入（512 维） | ⚪ 本次不部署：嵌入走 local（256 维） |
| ~~`aioa-web`~~ | 本地构建 | 管理端静态站 | ⚪ 不跑容器；**但 §5.2 要用它取静态产物** |
| ~~`nginx:1.27-alpine`~~ | 外部 | 80=H5、81=管理端 的边缘网关 | ⚪ 不用边缘 nginx |
| ~~`minio/minio:latest`~~ | 外部 | 附件 / 知识库原文 | ⚪ 代码不读它（头部 ⑦） |

> 要「完整档」（自带 nginx、80/81 直接可用）时再补搬后三个 —— 见本节末尾的对照。

先跑 `bash deploy/ops/host-check.sh`，看 §⑤ 的通断结果，再按下面二选一：

### 5.0-A 应用机能上国内网（`baidu.com`/`mirrors.aliyun.com` 返回 200/301）→ 配加速器

说明只是 Docker Hub 被挡 / DNS 被污染，**这是最省事的一条**：

```bash
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.net",
    "https://hub-mirror.c.163.com",
    "https://mirror.ccs.tencentyun.com"
  ]
}
EOF
systemctl daemon-reload && systemctl restart docker
docker pull python:3.11-slim          # 试拉一个验证（agent 的基础镜像，体积小）
```

若仍超时，再把 DNS 换成公共 DNS（`/etc/resolv.conf` 里加 `nameserver 223.5.5.5` /
`nameserver 119.29.29.29`）后重启 docker 再试。**注意：这些加速器本身也可能不通** ——
`host-check.sh` §⑤ 会给每个加速器单独打一个通断，哪个是 200 就用哪个。

⚠️ 这条路上**应用镜像仍要在这台机上构建**（`docker compose build server agent`），构建期还要 Maven Central /
npm registry；若这两个也不通，就直接走 5.0-B。

### 5.0-B 应用机完全出不去（全部 000）→ 离线搬运包

思路：在**能上外网 + 有 Docker** 的机器上把镜像（含构建结果）打成一个包，搬过来导入。
**本次只用 `--backend-only`，包里就 2 张镜像。**

```bash
# ── 在能上外网的机器上（首选隧道机）──────────────
git clone <你的仓库> && cd aioa
```

## 6. 验收（9 条，全过就是部署成功）

```bash
# 1) 容器状态（本次后端档：期望只有 aioa-server / aioa-agent 两个）
cd /opt/aioa/deploy && docker compose -f docker-compose.yml -f docker-compose.backend.yml ps

# 2) 后端健康（★ 本次 server 的 8080 已发布到宿主，可直接 curl）
curl -s -o /dev/null -w 'health    %{http_code}\n' http://127.0.0.1:8080/actuator/health
docker inspect --format '{{.State.Health.Status}}' aioa-server   # 期望 healthy

# 3) 后端登录接口（本次入口是 :8080；返回里应含 accessToken）
curl -s http://127.0.0.1:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Admin@123"}' | head -c 200; echo

# 4) 知识库档位（应为 store=milvus + embeddingProvider=local + embeddingDims=256）
TOKEN=$(curl -s http://127.0.0.1:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Admin@123"}' | sed -n 's/.*"accessToken":"\([^"]*\)".*/\1/p')
echo "token 长度=${#TOKEN}"        # 必须是 200+ 的正常长度；空 = 登录没通
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/kb/store
# 期望：{"code":0,...,"data":{"store":"milvus","embeddingProvider":"local","embeddingDims":256}}
#   · embeddingDims=512 ⇒ 你还在 http 档但没起 Ollama，上传会没有向量（见头部 ⑧ 与 §9.2）
#   · store=mysql       ⇒ .env 的 AIOA_KB_STORE 没生效，数据不会进 Milvus

# 5) ★ 前端（H5 / 管理端）——**走你自己的 nginx**，不是 80/81 容器
#    H5：宿主 nginx 的 / 应指向你拷过去的 user-client/index.html
curl -s http://<你的nginx地址>/ | grep -q 'aioa_session' && echo 'H5 内容 OK' || echo 'H5 内容异常'
#    管理端：应指向 §5.2 取出的 /opt/aioa/webroot
curl -s -o /dev/null -w 'admin-ui  %{http_code}\n' http://<你的nginx地址>:81/
#    ⚠️ 别用 200 当「页面正常」的判据：H5 那个 location 常是 try_files 回退，
#       任意路径都会回 200。要判内容（上面那句 grep）。

# 6) 容器 → **外部服务**连通性（MySQL 10.0.0.5:13049 / Redis 10.0.0.7:6379 / Milvus 19530）
#    ← 这三处任一不通，后端必然起不来（fail-fast）。注意 MySQL 端口是 13049
docker compose exec server bash -c '
  for hp in 10.0.0.5:13049 10.0.0.7:6379 10.0.0.12:19530; do
    h=${hp%:*}; p=${hp#*:}
    timeout 3 bash -c "cat < /dev/null > /dev/tcp/$h/$p" && echo "$hp OK" || echo "$hp FAIL"
  done'

# 7) 上传目录已持久化（本次新加的命名卷；应为 /dev/... 挂载点，不是容器内的 /app/uploads）
docker inspect --format '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{"\n"}}{{end}}' aioa-server

# 8) 浏览器：H5 用 admin/Admin@123 或 zhangsan/User@123 登录；管理端能进工作台、菜单完整

# 9) ★★ 证明「数据真的落进了 Milvus」（不是只落进 MySQL）
#    为什么必须单独验：kb_chunk（MySQL）是权威底座，切片与向量**先落 MySQL**；
#    Milvus 只是索引副本，写入失败**只告警不阻断**。所以「上传成功」完全不能说明 Milvus 有数据。
#    唯一确定的判据是**走 Milvus 稠密腿检索**：mode=vector 命中且 score 非 null ⇒ Milvus 里确有这些向量。
echo "--- A) 回填日志（D5 那次）---"
docker compose -f docker-compose.yml -f docker-compose.backend.yml logs server \
  | grep -E 'Milvus (连接成功|集合创建完成|回填完成)'
#   期望「回填完成：写入=N」N>0 且「跳过(维度不符)=0」；维度不符 >0 说明存量向量是旧 provider 的，
#   需开 AIOA_KB_REEMBED_ON_START=true 重算一次（后端同时会打 WARN）。

echo "--- B) 稠密腿检索（权威判据）---"
TOKEN=$(curl -s http://127.0.0.1:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Admin@123"}' | sed -n 's/.*"accessToken":"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $TOKEN" -G http://127.0.0.1:8080/api/v1/kb/search \
  --data-urlencode "q=验收要点" --data-urlencode "mode=vector" --data-urlencode "topk=3"
#   期望：data 非空，且每条 score 是一个非 null 的小数
#   data=[] ⇒ Milvus 里没有数据（或维度不符被跳过）：回去查 D5 有没有跑、日志里有没有维度告警。
#   score=null ⇒ 走成了关键词腿，不是稠密腿，不能作为「Milvus 有数据」的证据。

# 对照实验（区分「MySQL 有 / Milvus 空」这把最隐蔽的坑）：
#   同一条 q 分别打 mode=bm25 与 mode=vector
#     · 两个都空        ⇒ 这条链路整体没走通（可能压根没入库）
#     · bm25 有、vector 空 ⇒ **典型「MySQL 有、Milvus 空」** —— 就是本机要防的那类静默失效
#     · 两个都有        ⇒ Milvus 正常（vector 腿只能来自 Milvus）
#   注意 bm25 腿只有在集合成功建出 BM25 稀疏列时才查 Milvus；集合建 BM25 失败会回落到 MySQL，
#   所以 bm25 命中**单独不足以**证明 Milvus 有数据 —— vector 腿才是权威判据。
```

## 7. 常见故障对照

| 现象                                          | 根因                                                            | 处置                                                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `server` 容器反复重启，日志有 **`Milvus 不可用，应用拒绝启动`** | Milvus 不可达 / URI 错                                            | `nc -z 10.0.0.12 19530`；确认 `.env` 的 `AIOA_MILVUS_URI`（**容器内不能用 localhost**，必须用 IP）                                                |
| 日志 `Access denied for user 'aioa'`          | 口令错 / 账号对该库无权限                                                | 重填 §4.2 的 **`MYSQL_USER` / `MYSQL_PASSWORD`**（不是 `SPRING_DATASOURCE_*`），并跑 §4.2 的权限自检                                             |
| 日志 `Communications link failure`            | **13049** 不可达                                                 | `docker compose exec server bash -c 'cat < /dev/null > /dev/tcp/10.0.0.5/13049'`；不通就查防火墙 / 安全组 / 端口是否真的是 13049                    |
| 日志 `Unknown database 'aioa'`                | 库不存在且账号无建库权限                                                  | 见 §4.2 末尾的建库语句                                                                                                                    |
| 口令明明填了却仍鉴权失败                                | 值里的 **`$` 被 compose 当变量插值吃掉了**（裸写或双引号）                        | 用 `python3 deploy/ops/set-secrets.py --check` 看**容器实际收到的长度**；不对就重跑 `--only mysql` / `--only redis` 重写                    |
| 自检显示口令长度 **22 / 25**                        | 那正是占位符 `CHANGE_ME__db-password`(22) / `CHANGE_ME__redis-password`(25) 的长度 ⇒ **口令压根没写进去** | 跑 `python3 deploy/ops/set-secrets.py --only mysql,redis --from-env` 真正写入；别把 22/25 当成「口令短了」                     |
| `sed: -e expression #1, char NN: unknown option to 's'` | 用 `sed` 拼口令时，**值里含分隔符 `|`** ⇒ 整条命令失败、值静默没写（那个 char 号就是出问题的位置） | 别用 sed 写口令，改用 `deploy/ops/set-secrets.py`；值里含 `&` 时 sed 更会**不报错地改坏值** |
| `grep -c '^MINIMAX_API_KEY=.\+'` 返回 1 但 Key 其实是空的  | 模板该行 `=` 后有对齐**空格**+行尾注释，`.\+` 匹配到的是空格 ⇒ **假通过**          | 改用 `grep -nE '^MINIMAX_API_KEY=[^[:space:]]'`（应有输出）或 `set-secrets.py --check`                                            |
| `failed to resolve reference "docker.io/…" … i/o timeout` | 应用机拉不到 Docker Hub（无外网 / DNS 污染）                                | 见 **§5.0**：能上国内网就配加速器（5.0-A），完全出不去就用离线包（5.0-B）；**离线导入后启动不要加 `--build`**                                                  |
| Redis 报 `NOAUTH` / 认证失败                     | 没填口令，或 `!` 触发了 bash 的历史展开                                     | 见 §4.3；口令用单引号                                                                                                                     |
| 页面能开但所有接口报 502                              | server 未 healthy                                              | 看 `docker compose logs server`，先修后端                                                                                               |
| **对话一直回「回声」**                               | 模型 Key 没填（或 Key 与 `MODEL_DEFAULT` 不配对）⇒ 网关**静默降级 echo**（不是报错） | 按 §4.4 填**与 `MODEL_DEFAULT` 同名**的 Key（本模板默认 `MINIMAX_API_KEY`），再 `docker compose up -d agent`（**不是 restart**，见 §8）                |
| 上传成功、切片也有，但**检索什么都查不到** | **最隐蔽的一种**：Milvus 里没有向量。可能原因：① 新集合没回填（漏了 D5）；② `AIOA_MILVUS_DIMS` 与嵌入维度不符 ⇒ 向量被**静默跳过**；③ 还在 http 档但嵌入服务不可达 | 按 §6 第 9 条定位：看日志有无「Milvus 回填完成：写入=N」，再打 `mode=vector` —— **vector 空而 bm25 有**即确诊「MySQL 有、Milvus 空」；维度不符则后端本就该启动失败（有硬校验），若没失败说明改的是运行时环境不是 `.env` |
| 启动直接失败，日志含「嵌入 provider 与 Milvus 集合维度不一致」 | 嵌入维度 ≠ `AIOA_MILVUS_DIMS`（如 local 是 256，配置写了 512） | **这是刻意的**（没有它就会静默写错维）。按日志给的两条出路改：local ⇒ `dims=256` + 换集合名；http ⇒ `dims=模型维度` |
| 启动失败，日志含「Milvus 不可用，应用拒绝启动」 | `AIOA_MILVUS_URI` 不可达（Milvus 必须在线，刻意 fail-fast） | `docker compose exec server bash -c 'timeout 3 bash -c "cat < /dev/null > /dev/tcp/10.0.0.12/19530" && echo OK'`；不通就先修 Milvus |
| 检索报 embedding 错误 / `fetch failed`/超时 | 你在 `provider=http` 档，但嵌入服务没起或地址不对 | 出路二选一：① 起嵌入服务并核对 `AIOA_KB_EMBEDDING_URL`（容器内服务名，如 `http://ollama:11434/api/embeddings`），见 §9.2；② **直接改回 `AIOA_KB_EMBEDDING_PROVIDER=local`**（零依赖，本次默认档） |
| `port is already allocated`                 | 端口被占                                                          | 本项目已避开 19530/9091/9000/9001；若 **80 或 81** 被占，改 compose 里 nginx 的 `"80:80"` / `"81:81"`（冒号左边是宿主端口，右边必须保持 80/81，否则容器内 nginx 没有对应监听） |
| 管理端菜单里没有「仓库/项目」模块                           | `AIOA_GITEE_ENABLED=false`（内网预期）                              | 见 §9.3                                                                                                                            |
| 换嵌入模型后检索命中异常                                | 集合维度不可改                                                       | 必须换新集合名（`kb_chunk_v2`）+ 开 `REEMBED`/`BACKFILL`，见 §9.2                                                                             |

## 8. 日常运维

```bash
cd /opt/aioa/deploy

$COMPOSE logs -f --tail=100 server agent

# 升级：**先判断这台机能不能 pull**（见 §5.0）

# 能上外网/已配加速器时才：git pull && $COMPOSE up -d --build
```


### 8.1 ⚠️ 改了 `.env` 之后：用 `up -d`，不要用 `restart`

```bash
docker compose up -d server agent       # ✅ 会按新变量**重建**容器
docker compose restart server           # ❌ 无效：只重启进程，环境变量还是旧的
```

原因：`docker compose restart` 是「把同一个容器停掉再启动」，**不重新读取 `.env`、也不重新渲染服务定义**，  
容器里的环境变量保持原样。而 `docker compose up -d` 会把渲染后的服务配置与运行中容器做哈希比对，  
**发现变化就自动重建**（这才是你要的效果）。

- **不需要** `--force-recreate`：上面的哈希比对已经能识别 `.env` 变化；`--force-recreate` 只是在  
  「配置哈希没变但你想强制换一个容器」时用（例如容器内文件被手工改脏了）。
- 判断是否真的生效：`docker exec aioa-server printenv <变量名>`，或直接看 `docker inspect` 的  
  `Config.Env`。**只看「容器重启成功了」不算生效。**
- 换了 DB / Redis / Milvus 地址、模型 Key、`AIOA_KB_*` 档位等**任何环境变量**都走这条。

```bash
# 备份（三件套：库 + 上传文件 + 配置）
# MySQL 在**外部主机** ⇒ 用远端 mysqldump；口令从 .env 读，避免落到 shell 历史里
set -a; . /opt/aioa/deploy/.env; set +a
mysqldump -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u "$MYSQL_USER" -p"$MYSQL_PASSWORD" \
  --single-transaction --routines "$MYSQL_DB" > /root/aioa-$(date +%F).sql
# 应用机没装 mysqldump 时，借用一次性容器（口令用 -e 传入，不写进命令行）：
# docker run --rm -e PW="$MYSQL_PASSWORD" mysql:8.0 \
#   sh -c 'exec mysqldump -h10.0.0.5 -P13049 -uaioa -p"$PW" --single-transaction aioa' > /root/aioa-$(date +%F).sql

tar czf /root/aioa-env-$(date +%F).tgz -C /opt/aioa deploy/.env

# ★ 上传的文件在命名卷 aioa_serveruploads（= 容器内 /app/uploads），**必须备份**：
#   它是本地磁盘存储（MinIO 未被使用），丢了就是真丢。
docker run --rm -v aioa_serveruploads:/data -v /root:/backup alpine \
  tar czf /backup/aioa-uploads-$(date +%F).tgz -C /data .
# Milvus 索引**不必备份**，可从 MySQL 的 kb_chunk 重建（见下方回滚）
```

**回滚向量库**：把 `.env` 里 `AIOA_KB_STORE` 改回 `mysql` 再 `docker compose up -d server`  
（MySQL 始终保存文档与切片，Milvus 只是可重建的索引副本）。

## 9. 这次没做 / 以后怎么做

### 9.1 本地大模型（可选，需要 GPU）

`docker compose --profile model up -d` 会额外起 vLLM（镜像大、需 GPU）。没有 GPU 就别开，  
用云端 Key（DeepSeek/通义）即可。

### 9.2 从「哈希向量」升级为「语义向量」（**本次是哈希档，想升级看这里**）

本次 `.env` 是 `AIOA_KB_EMBEDDING_PROVIDER=local` + `AIOA_MILVUS_DIMS=256` —— 因为**不部署 Ollama**，
用的是进程内 char n-gram 哈希向量：零依赖、确定性，但**无语义**，向量腿只等价于「字面重叠」。
检索质量目前靠 `AIOA_MILVUS_ENABLE_BM25=true` 的原生 BM25 关键词腿兜住。

**什么时候值得升**：用户会用近义/改写说法提问，而关键词腿检不到时。

升级要动 **4 个键 + 1 次重算**，缺一步就会静默失效（或不给启动）：

```bash
# ① 起一个嵌入服务（示例：Ollama 只拉嵌入模型；也可用 vLLM）
cd /opt/aioa && bash deploy/ops/offline-images.sh import ollama-image.tar.gz        # 有外网则可直接 pull
cd deploy && docker compose -f docker-compose.yml -f docker-compose.backend.yml --profile ollama up -d ollama
docker exec aioa-ollama ollama pull quentinz/bge-small-zh-v1.5      # 512 维

# ② 改 .env 的 4 个键（sed 在这里可用：模型名/集合名都不含 | & 等特殊字符）
sed -i -e 's|^AIOA_KB_EMBEDDING_PROVIDER=.*|AIOA_KB_EMBEDDING_PROVIDER=http|' \
       -e 's|^AIOA_KB_EMBEDDING_MODEL=.*|AIOA_KB_EMBEDDING_MODEL=quentinz/bge-small-zh-v1.5|' \
       -e 's|^AIOA_KB_EMBEDDING_DIMS=.*|AIOA_KB_EMBEDDING_DIMS=512|' \
       -e 's|^AIOA_MILVUS_DIMS=.*|AIOA_MILVUS_DIMS=512|' \
       -e 's|^AIOA_MILVUS_COLLECTION=.*|AIOA_MILVUS_COLLECTION=kb_chunk_v2_512|' \
       -e 's|^AIOA_KB_REEMBED_ON_START=.*|AIOA_KB_REEMBED_ON_START=true|' \
       -e 's|^AIOA_MILVUS_BACKFILL=.*|AIOA_MILVUS_BACKFILL=true|' .env

# ③ 跑一次：先按新 provider 重算历史切片向量，再回填进新集合
docker compose -f docker-compose.yml -f docker-compose.backend.yml up -d server
docker compose -f docker-compose.yml -f docker-compose.backend.yml logs --tail=300 server \
  | grep -E '嵌入端点|切片重算|Milvus 回填完成'
# ④ 跑完把 REEMBED_ON_START / BACKFILL 改回 false 再重启（否则每次启动都全量重算一遍）
# ⑤ 验收：§6 第 4 条档位应为 milvus + http + 512；第 9 条 vector 腿应命中且 score 非 null
```

⚠️ 三条硬约束（违反任一条都会掉进坑里）：

1. **`AIOA_MILVUS_DIMS` 必须等于嵌入模型的真实输出维度**。不符时后端**直接启动失败**并告诉你该改成什么
   （`MilvusConfig.assertDimsAgree`）—— 这不是"多此一举"：维度不符时 Milvus 会**静默**一条不收、
   而接口全都成功，属于最难查的一类问题。
2. **集合名必须换新的**。Milvus 的集合维度**创建后不可改**，所以「改 dims + 沿用 kb_chunk_v1_256」
   一定起不来。旧集合先留着（可回滚），确认新档检索正常后再删。
3. **不要用 `docker compose restart`** 让新 `.env` 生效 —— 它不会重读 `.env`，必须 `up -d`（见 §8.1）。

> 想彻底跳过「语义模型」这一档、又要更好的中文召回，也可以只把 `AIOA_MILVUS_ENABLE_BM25` 保持 true
> 并把 `AIOA_MILVUS_INDEX` 调成 `AUTOINDEX` 观察效果 —— 但那是**关键词路线的调优**，
> 与语义召回是两件事，不要混为一谈。

### 9.3 启用 Gitee / Gitea 仓库联动（需要公网 HTTPS 域名）

1. 准备公网域名（如 `aioa.example.com`）并解析到网关，配好 HTTPS（可在前面再放一层 nginx / 宝塔）。
2. 在托管方（Gitee「设置→第三方应用」/ 自建 Gitea）创建 OAuth 应用，回调地址填  
   `https://<域名>/api/v1/gitee/bind/callback`。
3. `.env` 里改：`PUBLIC_BASE_URL` / `AIOA_GITEE_REDIRECT_URI` / `AIOA_GITEE_WEBHOOK_BASE_URL` /  
   `AIOA_GITEE_BIND_RETURN_URL` 四处改成新域名，填 `CLIENT_ID`、`CLIENT_SECRET`，  
   再把 `AIOA_GITEE_ENABLED=true`、`AIOA_GITEE_SYNC_ENABLED=true`。
4. `docker compose up -d server`。⚠️ Webhook 地址必须**托管方能访问到**，否则回调静默失效。

### 9.4 HTTPS

**本次（后端档）compose 只发布 `8080`（后端）/ `8000`（agent）**，不含任何对外 Web 端口 ⇒
TLS **在你自己的 nginx 上终止**（最省事，也符合你已有 nginx 的现状）：把 `proxy_pass` 指到
`http://10.0.0.12:8080/`，证书由它统一管理。

若改走完整档（自带 nginx，暴露 80/81），同样建议由**前置** nginx / 宝塔 / Cloudflare 终止 TLS，
或把证书挂进 `deploy/nginx/` 并在 `nginx.conf` 里加 `listen 443`。
