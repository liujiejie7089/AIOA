## 三、新增模块的设计思路与代码实现

### 3.1 能力层：统一注册 / 加载 / 生命周期（为 skills、connectors 预留扩展点）

#### 3.1.1 四个设计约束

1. **不推翻现有框架**：能力层是「新增一层」，旧的工具装配逻辑被收敛而不是被替换。
2. **零回归**：注入顺序 = 注册顺序 = 与旧手工拼接**逐项同序**（K1 断言锁死）。
3. **失败隔离到能力粒度**：一个能力加载失败不许拖垮整轮对话。
4. **不许假绿**：停用的能力重新启用时回到 `REGISTERED`，必须重新加载才 `READY`。

#### 3.1.2 生命周期状态机

```
REGISTERED ──▶ RESOLVED ──▶ READY
     │             │
     │             └──▶ ERROR ──▶（可重试）RESOLVED
     ├──▶ DISABLED（跨注册存活）
     └──▶ UNRESOLVED（能力不可用，不算故障）
```

迁移合法性由纯函数 `can_transit(src, dst)` 判定，非法迁移抛 `IllegalTransition`——
状态机逻辑因此可脱离 Spring/LLM 单独单测。

#### 3.1.3 关键代码

`agent/aios_ai/capabilities/models.py`：

```python
class CapabilityKind(str, Enum):
    BUILTIN = "builtin"; MCP = "mcp"; PLUGIN = "plugin"; SKILL = "skill"

class LifecycleState(str, Enum):
    REGISTERED = "REGISTERED"; RESOLVED = "RESOLVED"; READY = "READY"
    DISABLED = "DISABLED"; UNRESOLVED = "UNRESOLVED"; ERROR = "ERROR"

def can_transit(src: LifecycleState, dst: LifecycleState) -> bool:
    return dst in _ALLOWED_TRANSITIONS.get(src, frozenset())
```

`agent/aios_ai/capabilities/registry.py` 的 `load(ctx)`：

- 按**注册顺序**逐个加载 ⇒ 注入顺序确定且可预测；
- 失败隔离：单个 provider 抛异常 ⇒ 只有它进 `ERROR`，其余能力照常 `READY`；
- `available() == False` ⇒ `UNRESOLVED`（不算故障，不刷错误日志）；
- 成功路径：先 `RESOLVED` 再 `READY`（中间态可观测，便于 health 区分「已解析」与「就绪」）。

`agent/aios_ai/capabilities/providers.py` 的四个 provider：

| Provider | 提供工具 | 来源 | 现状 |
|---|---|---|---|
| `HitlProvider` | `ask_user` / `request_form` / `request_confirm` | 内置 | 生效（受 `settings.agent_hitl` 开关） |
| `WebProvider` | `web_search` / `web_fetch` | 内置 | 生效（受 `web_search_enabled`） |
| `McpProvider` | `mcp__*` | 运行时 manifest（`ctx["mcp_tools"]`） | 生效 |
| `SkillProvider` | （待接入） | skills 注册表 | **扩展位**：`skill_registry_enabled=False` ⇒ `UNRESOLVED`、零工具、零回归 |

`build_default_registry()` 的注册顺序固定为 **HITL → Web → MCP → Skill**，即最终注入顺序。

#### 3.1.4 接入新 skills / connectors 需要做什么

只需新增一个 `CapabilityProvider` 实现并 `registry.register(provider)`：
注册、加载、失败隔离、停用/启用、health 上报**全部复用**，不需要改 prepare 逻辑。
这就是「预留统一扩展点」的具体含义。

### 3.2 日程 / 会议模块：端到端全链路打通

#### 3.2.1 起点：为什么此前是「死模块」

`V94__portal_modules.sql` 只建了三张表 + 只读查询，
而全仓 `/api/v1/portal` **零调用方**（连管理端都改走表单了）；
H5 的「日程」面板则是用「请假起止 + 数字员工排班」在**前端本地合成**的假数据。

即：**数据层建好了、业务层没有入口、前端没有真源**。

#### 3.2.2 四层落地

| 层 | 文件 | 内容 |
|---|---|---|
| 数据 | `V94__portal_modules.sql` | `portal_schedule` / `portal_meeting` / `portal_meeting_attendee`（已存在） |
| 服务 | `server/aios-resource/.../service/PortalService.java` | 补齐写链路：日程 CRUD、发起会议、取消、应答 |
| API | `server/aios-resource/.../controller/PortalController.java` | 新增 6 个端点，每端点 `AuthUserContext.require()` |
| 前端 | `user-client/index.html` | 日程面板改读真实接口 + 内联新建卡 + 会议接受/谢绝 |

新增端点：

```
POST   /api/v1/portal/schedules              创建日程
PUT    /api/v1/portal/schedules/{id}         更新（仅本人）
DELETE /api/v1/portal/schedules/{id}         删除（仅本人，逻辑删）
POST   /api/v1/portal/meetings                发起会议（含参会人 + 房间冲突校验）
POST   /api/v1/portal/meetings/{id}/cancel    取消（仅组织者）
POST   /api/v1/portal/meetings/{id}/respond   应答（仅受邀人）
```

#### 3.2.3 三条业务硬口径

1. **租户隔离**：可见 = 本租户 + `tenant_id=0`（平台公共）；**写必须落在用户自己的租户**，
   公共数据只可读不可改（否则普通用户能改平台数据）。实现为 `writeTenant()`（写）/`tenantScope()`（读）分离。
2. **归属**：日程只能改自己的（`user_id` 不符即 **404**，不告知「存在但无权」，避免探测他人数据）；
   会议只有组织者能取消，只有被邀请人能应答。
3. **逻辑删除**：统一置 `deleted_at`，绝不物理删（审计口径）。
   ⚠️ 必须用 `LambdaUpdateWrapper.set(...)`：`updateById(entity)` 因 MyBatis-Plus 的 NOT_NULL 策略
   会**静默跳过 null 值**——mcp_server 清 `lastError` 时踩过同一条坑。

#### 3.2.4 会议冲突校验

同租户 + 同地点 + 时间区间重叠 + 未取消 ⇒ 拒绝，且**只校验有地点的会议**
（无地点的线上会议判了会误伤）。重叠判据：`start < 已有.end AND end > 已有.start`（端点相接不算冲突）。

## 四、实现过程中发现并修复的真实缺陷

### 4.1 业务校验失败被包成 500「服务内部错误」★ 本轮关键修复

**现象**：真服务端到端跑出 7 条失败，空标题 / 时间倒序 / 时间格式非法 / 房间冲突 /
非法应答值 / 已取消会议再应答，全部返回 **HTTP 500「服务内部错误」**。

**根因**：`GlobalExceptionHandler` 只把 `BizException` 与 Spring 参数类异常映射成 4xx，
其余全部落到 `@ExceptionHandler(Exception.class)` 兜底 ⇒ 500。
而我在 `PortalService` 里用 `IllegalArgumentException` 表达业务校验失败 ⇒ 直接命中兜底。

**修复**：改用仓库既有约定 `BizException.badRequest(msg)`。

**顺带澄清一条容易踩的认知**（docs/36 §、docs/38 §均有记载）：

> 本项目对业务校验失败的约定是 **HTTP 200 + 信封 `code=400`**；
> 只有 `BizException` 的 401/403/404 才映射成对应 HTTP 状态码。
> 所以「标题为空 ⇒ 400」的正确判据是 `body.code == 400`，**不是** `http_status == 400`。

e2e 首版按 HTTP 状态码断言 ⇒ 6 条假红，已改为按信封 `code` 断言。

### 4.2 e2e 参会人期望值写错

首版写死 `attendeeIds=[2,3]`，而 `zhangsan` 的真实 uid 恰为 2（组织者本人会被跳过）⇒ `invited` 期望 2 实际 1。
**这不是产品缺陷**。已改为：从登录响应取真实 uid，用同租户真实账号 `admin`(uid=1) 作受邀人，
期望值按「真实受邀人集合」动态计算。

### 4.3 后端启动口径：Flyway 校验

本机库的 `flyway_schema_history` 里 V89–V95 的 checksum 为 NULL、V100 已应用但本地文件被 revert
（`d5974af` revert 了 `cd79d79`），因此**直接 `java -jar` 会启动失败**（Validate failed）。
项目既有口径是 `start-all.sh` 启动后端时带 `-Dspring.flyway.validate-on-migrate=false`
（`server/aios-boot/.../application.yml` 里 `validate-on-migrate: true` 仅在不传该参数时生效）。
本轮启动后端已按此口径执行。
