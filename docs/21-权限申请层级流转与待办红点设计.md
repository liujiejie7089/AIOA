# 21 · 权限申请层级流转 / 待办红点 设计与根因分析

> 场景来源：租户「某某智能科技有限公司」→ 机构「研发中心」→ 部门「算法部 ZN-SFB」，
> 以成员身份向上级发起权限申请，**机构管理员收不到该申请**。
> 本文先给实测根因，再给需求应答与落地方案。
> 结论均以库表数据与接口实测为准，代码位置精确到「文件 : 方法」。

---

## 0. 结论速览

| # | 问题 | 结论 |
|---|---|---|
| 1 | 机构管理员为何收不到？ | **权限申请的审批流模板里根本没有「机构管理员」这一级**。租户 9 的 `PERMISSION_GRANT` 流程定义为 `[部门负责人 → 租户管理员]` 两级固定链，与申请人自身层级无关。 |
| 2 | 为什么有时又「像是能收到」？ | 算法部 `leader_user_id` 为空，引擎的**兜底**把本应给部门负责人的第 1 级改派给了机构管理员。这是偶然的兜底副作用，不是设计意图；一旦按用户描述把负责人配上，机构管理员立刻从链上消失（已实测复现）。 |
| 3 | 需求「所有人向上级的上一级申请」能否表达？ | **当前不能**。引擎只按 `approval_flow_def.steps_json` 展开固定节点，不做「按申请人层级推导上一级」的递推，也没有自审防护。 |
| 4 | 菜单右上角未处理红点 | **完全未实现**。`MainLayout.vue` 无任何 badge；前端没有待办计数接口。 |
| 5 | 各层级管理员的配置权 | 审批流配置**只有租户管理员入口**（`/tenant/approval-flow-defs`）且**没有界面**；部门负责人角色**没有被授予** `ROLE_DEPT_LEADER`。 |

## 1. 现状事实（实测）

### 1.1 组织与账号

| 层级 | 名称 | 账号 | user_id | 角色 |
|---|---|---|---|---|
| 租户 | 某某智能科技有限公司（`MYQY-DEMO`）| `znkj_admin` 傅宸 | 3142 | `ROLE_TENANT_ADMIN` |
| 机构 29 | 某某智能科技有限公司研发中心（`ORG-ZNKJYF`）| `znkjyf_admin` 傅宸 | 3143 | `ROLE_ORG_ADMIN` |
| 机构 30 | 某某智能科技有限公司市场部（`ORG-ZNKJSC`）| `znkjsc_admin` 简宁 | 3151 | `ROLE_ORG_ADMIN` |
| 部门 101 | 算法部（`ZN-SFB`），机构 29 | `znsfb_ldr` 祁野 | 3144 | **`ROLE_MEMBER`** |
| 部门 102 | 工程部，机构 29 | `zngcb_ldr` 路遥 | 3148 | **`ROLE_MEMBER`** |
| 部门 103 | 销售一部，机构 30 | `scxsyb_ldr` 简宁 | 3152 | **`ROLE_MEMBER`** |

两处与描述不符的库内事实（重要）：

- `org_department.id=101` 的 **`leader_user_id` 为 NULL**、`leader_name` 为 NULL。
  「算法部负责人」只体现在 `org_member.job_title = '算法部负责人'`，**不是**引擎读取的字段。
- 祁野 / 路遥 虽为部门负责人，**角色仍是 `ROLE_MEMBER`**，未授予 `ROLE_DEPT_LEADER`
  （`sys_user_role` 实测）。即「负责人」这一层在**权限体系里不存在**。

### 1.2 审批流定义（`approval_flow_def`）

租户 9 只有一条权限申请流程：

```json
{ "id": 31, "tenant_id": 9, "institution_id": 0, "biz_type": "PERMISSION_GRANT",
  "name": "租户默认权限申请审批流（部门负责人 → 租户管理员）",
  "steps_json": "[{\"seq\":1,\"approver_type\":\"DEPT_LEADER\"},{\"seq\":2,\"approver_type\":\"TENANT_ADMIN\"}]" }
```

**没有 `ORG_ADMIN` 节点。** 其它业务类型（`LEAVE` / `QUOTA_EXPAND` / `RESOURCE_OPEN`）
在租户 9 **完全没有定义**（只有 `PERMISSION_GRANT` 一条）。

### 1.3 复现实验（决定性证据）

**实验 A — 维持库现状（部门负责人为空），以算法部成员 `znsfb_m01` 提交：**

```
orderId=218  nodeCount=2
  seq 1  DEPT_LEADER   -> id 3143 傅宸  PENDING
        note: 「第 1 级『部门负责人』未解析到（部门未设置负责人），已改由企业管理员审批」
  seq 2  TENANT_ADMIN  -> id 3142 傅宸  PENDING
```

→ 机构管理员**由兜底**拿到第 1 级。此时 `/workflow/tasks?scope=todo` 以 `znkjyf_admin`
查询**能查到**该单；而 `/approvals?scope=todo`（legacy 单级池）返回
`403 审批中心仅租户管理员可访问`（该池仅租户管理员可读，机构管理员 403 属预期）。

**实验 B — 按用户描述把算法部负责人配成祁野（3144）后再提交：**

```
orderId=219
  seq 1  DEPT_LEADER   -> id 3144 祁野   PENDING
  seq 2  TENANT_ADMIN  -> id 3142 傅宸   PENDING
>>> 机构管理员(3143)是否在链上: False      ← 复现「机构管理员无法收到」
>>> 租户管理员(3142)是否在链上: True
```

实验结束后已还原 `leader_user_id=NULL`，并清理了 218/219 两单（备份
`scripts/_diag_v40_backup.json`）。

> 注：3142 与 3143 的 `nickname` **都是「傅宸」**，在待办列表里无法区分是租户级还是机构级，
> 会加剧「到底谁收到了」的误判。建议演示数据里把两人姓名区分开。

## 2. 根因

### 根因 A（主因，结构性）审批链是「固定模板」，不是「按申请人层级递推」

`ApprovalFlowService.expandNodes()`（`aioa-org/.../service/ApprovalFlowService.java` L158-229）
只做一件事：取 `approval_flow_def.steps_json`，逐条把 `approver_type` 解析成具体人。
**它完全不看申请人是成员、部门负责人、还是机构管理员** —— 同一个模板对所有人展开出同一条链。

因此：
- 模板 `[DEPT_LEADER, TENANT_ADMIN]` ⇒ 成员申请走「部门负责人 → 租户管理员」，
  机构管理员**永远不在链上**；
- 要让机构管理员入链，只能靠改模板或靠兜底（见根因 B）。

### 根因 B（掩盖主因）兜底逻辑会把「解析不到」静默改派，制造「有时能收到」的假象

`expandNodes()` L206-214：

```java
if (approverId == null && !ApprovalTask.TYPE_ORG_ADMIN.equals(type)) {
    approverId = orgAdminId;                 // 先退机构管理员
    if (approverId == null) approverId = tenantAdminId;  // 再退租户管理员
    ...
}
```

而 `resolveDeptLeader(institutionId, departmentId)`（L231-246）在
「部门未设置负责人」时会退化为「本机构第一个有负责人的部门」；若本机构所有部门负责人都为空，
则返回 `null` → 触发上面的改派。

算法部与工程部的 `leader_user_id` **同时为空**，于是第 1 级被改派给机构管理员 ——
问题被**偶然掩盖**。一旦负责人被正确配置（如实验 B），机构管理员立即脱离审批链。

附带缺陷：被改派后的节点 **`approver_type` 仍是 `DEPT_LEADER`**，
与真实审批人（机构管理员）不一致，前端会显示成「部门负责人 · 傅宸」，语义错误。

### 根因 C（能力缺口）「未处理提醒」与「按层级配置」都没有载体

- `MainLayout.vue`（L71-74「审批中心」菜单）**没有 `el-badge` / 红点**；
  `web/apps/shell/src/api/*.ts` 中**没有任何待办计数接口**。
- 后端只有 `notification` 表与 `NotificationController`（通知列表），**没有「待我处理数」的聚合端点**。
- 审批流配置端点 `/tenant/approval-flow-defs` 有 `requireTenantAdmin()` 门禁，
  且 `api/org.ts` 里虽已封装 `listApprovalFlowDefs` / `saveApprovalFlowDef`，
  **没有任何视图引用它们** → 配置无界面。

## 3. 需求应答

### 3.1 权限层级（三层模型，必须分清）

| 维度 | 内容 | 载体 | 决定什么 |
|---|---|---|---|
| **组织层级** | 租户 → 机构 → 部门 → 个人 | `sys_tenant` / `org_institution` / `org_department` / `org_member` | 「谁属于谁」——审批链的递推基准 |
| **角色层级** | `ROLE_ADMIN`(平台) > `ROLE_TENANT_ADMIN`(租户) > `ROLE_ORG_ADMIN`(机构) > `ROLE_DEPT_LEADER`(部门) > `ROLE_MEMBER`(个人) | `sys_role` + `sys_user_role` | 「能做什么」——功能与审批入口门禁 |
| **数据范围** | `ALL` / `TENANT` / `ORG` / `DEPT` / `SELF` | `sys_role.data_scope` | 「能看到谁的数据」 |

**关键纪律：审批链由「组织层级」递推，不能由「角色清单」硬编码。**
现在的实现恰恰把两者混同了 —— 模板写死角色类型，于是组织层级一变（部门负责人没配、
某人兼两级）就断链。

### 3.2 申请与审核的传递路径

**现状（可实现的部分）**

```
① 提交  POST /api/v1/org/permissions/apply            PermissionGrantService.apply (L80-174)
   ├─ 落 permission_grant(PENDING)  带 tenant/institution/department
   └─ 调 ApprovalFlowService.submit (L76-151)
        ├─ 落 approval_order(PENDING)
        ├─ expandNodes 展开 N 条 approval_task（seq 升序）
        └─ notify(第 1 节点审批人) → notification 表

② 取链  POST 无；读取 GET /api/v1/workflow/tasks?scope=todo    ApprovalFlowService.todo (L279-306)
   条件：approver_id = 我 AND status = PENDING AND 我是 seq 最小的 PENDING 节点 AND 单据仍 PENDING

③ 决策  POST /api/v1/workflow/tasks/{taskId}/decide           ApprovalFlowService.decide (L373-457)
   ├─ 通过 → 推进下一节点（并 notify 下一审批人）；末节点通过 → order=APPROVED
   │        → 回调 PermissionGrantService.onApproved → grant=ACTIVE + granted_by/at + expire_at
   └─ 驳回 → order=REJECTED，其余节点 SKIPPED，回调 onRejected（驳回人/时间/意见回查 approval_task）
```

**目标（需求要求：所有人向上级的上一级申请，逐级审）**

```
成员            → [部门负责人] → [机构管理员] → [租户管理员]
部门负责人       → (跳过自己)  → [机构管理员] → [租户管理员]
机构管理员       → (跳过自己)  →                [租户管理员]
租户管理员       → 无上级（直达平台 / 或自动生效）
```

**两条必须写进引擎的规则：**

1. **递推起点 = 申请人的「上一级」**，逐级向上直到租户管理员（或配置的终止层）；
2. **自审防护**：任何节点解析出的审批人 == 申请人本人时，该节点必须 `SKIPPED`
   （`skip_reason = '申请人本人，按回避规则跳过'`），**且不允许出现「全部被跳过」** ——
   此时应自动上抬到再上一级。

现有引擎已具备「跳级」机制（`threshold_days`）与 `SKIPPED` 状态，**自审防护可复用同一套**。

### 3.3 未处理提醒的触发条件

**语义**：只有「此刻轮到我、且我还没处理」才点亮红点。**不能只数 `PENDING` 任务** ——
一条 3 级单据在 1 级审批时，2/3 级任务的 `status` 也是 `PENDING`，会重复计数，
让第 3 级审批人在还没轮到他时就看到红点。

**判据（四条件全部满足才计数）：**

| # | 条件 | 说明 |
|---|---|---|
| 1 | `approval_task.approver_id = 当前登录用户` | 指派给我 |
| 2 | `approval_task.status = 'PENDING'` | 我这一级未处理 |
| 3 | `approval_task` 是该单据 **`seq` 最小的 PENDING 节点** | 「当前节点」才轮到我（与 `isCurrentNode()` 同口径）|
| 4 | `approval_order.status = 'PENDING'` | 单据未终态（不被驳回/撤销的残留计数）|

**触发与熄灭时机：**

| 事件 | 红点 |
|---|---|
| 新申请提交 / 上一级通过 → 轮到我 | 计数 +1，点亮 |
| 我通过或驳回 | 计数 -1，归零则熄灭 |
| 前序被驳回 → 单据终态 | 我这一级不会亮 |
| 相同 `order_id` 重复通知 | 计数按**单据去重**，不按消息条数 |

**刷新策略**：新建 `GET /api/v1/workflow/tasks/summary` 返回
`{ todo: n, mine: m, generatedAt }`；管理端 `MainLayout` 在登录后拉一次 +
**路由切换后刷新** + 60s 轮询兜底（演示场景无需 WebSocket）。
红点挂在「审批中心」菜单项上；点击进入即视为已查看，但仍以「实际待办数」为准
（不引入「已读」状态，避免与「已处理」语义混淆）。

### 3.4 各层级管理员的配置与审核职责

| 层级 | 配置权（对本级及下一级） | 审核职责 | 现状 |
|---|---|---|---|
| **平台管理员** `ROLE_ADMIN` | 全平台只读运维；审核租户级内容 | 内容审核台（`/admin/content-reviews`）| ✅ 已有 |
| **租户管理员** `ROLE_TENANT_ADMIN` | **审批流模板**、假种、额度包、机构与人员、专家 | 权限申请**终审**；额度扩容 / 资源开通终审；授权回收 | ⚠️ 审批流**有接口无界面** |
| **机构管理员** `ROLE_ORG_ADMIN` | 本机构：部门、成员、额度、知识库、审计；专家 | 本机构上行的权限申请；额度/资源一级审批 | ❌ **不在权限申请链上**（根因 A）|
| **部门负责人** `ROLE_DEPT_LEADER` | 本部门：数字员工（仅本部门可见的） | 本部门成员的权限申请（第一级）| ❌ **角色未授予**；且 `leader_user_id` 未配 |
| **机构成员** `ROLE_MEMBER` | 仅本人数字员工（`visible_scope=SELF`）| — | ✅ 可提交申请、查进度 |

## 4. 落地方案

### 4.1 后端：引擎支持「按层级递推 + 自审防护」

**改动点：`ApprovalFlowService.expandNodes()`（核心，唯一必改的方法）**

1. 新增节点类型 `APPLICANT_MANAGER`（或复用现有类型 + 新增模板开关 `derive_from_applicant: true`）；
2. 解析出**申请人的组织层级**：查 `org_member`（部门 / 机构）+ `org_institution.admin_user_id`
   + `selectFirstUserIdOfRole(tenant, ROLE_TENANT_ADMIN)`；
3. 生成候选链 `[部门负责人, 机构管理员, 租户管理员]`，**从申请人所在位置的上一级开始**取；
4. 逐节点过滤：解析不到 → 跳过；**== 申请人本人 → 跳过（回避）**；
5. 若过滤后为空 → 上抬到租户管理员；再为空 → 上抬到平台管理员（或直接生效并留痕）；
6. 兜底改派时，**`approver_type` 必须一并改成实际生效的类型**（修掉根因 B 的语义错误）。

**保持兼容**：模板仍可为 `[DEPT_LEADER, ORG_ADMIN, TENANT_ADMIN]` 这类显式链；
`derive_from_applicant` 只影响「展开起点」，不影响既有单据
（`approval_task` 已固化 approver_id，历史单不受影响）。

### 4.2 后端：待办计数端点

新增 `GET /api/v1/workflow/tasks/summary`（`WorkflowController`，`guard.requireApprover()`），
内部按 §3.3 的四条件聚合，返回 `{todo, mine}`。

### 4.3 前端：管理端红点

- `web/apps/shell/src/api/resource.ts` 新增 `workflowTodoSummary()`；
- `MainLayout.vue` 的「审批中心」菜单项包一层 `<el-badge :value="todoCount" :hidden="!todoCount">`，
  登录后 + 路由切换 + 60s 轮询刷新。

### 4.4 数据修复清单（不改代码也能先让演示跑通）

| # | 对象 | 现状 | 建议 |
|---|---|---|---|
| D-a | `approval_flow_def`（tenant 9, `PERMISSION_GRANT`）| `[DEPT_LEADER, TENANT_ADMIN]` | 补为 `[DEPT_LEADER, ORG_ADMIN, TENANT_ADMIN]` |
| D-b | `org_department.id=101`（算法部）| `leader_user_id=NULL` | 设为 3144（祁野），`leader_name='祁野'` |
| D-c | 祁野 3144 / 路遥 3148 / 简宁 3152 | 仅 `ROLE_MEMBER` | 补 `ROLE_DEPT_LEADER`（否则部门负责人无任何管理功能）|
| D-d | tenant 9 的 `LEAVE`/`QUOTA_EXPAND`/`RESOURCE_OPEN` | 无定义 | 播种默认流程（否则请假链路不可用，即既有缺口 D-8）|
| D-e | 3142 / 3143 `nickname` | 都叫「傅宸」 | 改为可区分（如「傅宸(租户)」「傅宸(研发中心)」）|

> ⚠️ D-a 单独改数据**只解决「机构管理员收不到」这一条**；若不做 §4.1 的递推改造，
> 部门负责人申请自己那一层时仍会出现**自审**（seq1 解析成他自己）。
> 两者应一起做。

## 5. 验收口径

| 用例 | 期望 |
|---|---|
| 成员（算法部成员）申请 | 链 = `[祁野(部门负责人), 傅宸(机构管理员), 傅宸(租户管理员)]`，三者依次可见待办 |
| **部门负责人**（祁野）申请 | **seq1 不得是祁野自己**；链从机构管理员起（回避免疫）|
| **机构管理员**（3143）申请 | 链从租户管理员起 |
| 部门未配负责人 | 第 1 级**跳过**（而非改派给机构管理员），可直接从机构管理员起，且节点类型与实际审批人一致 |
| 红点 | 新单到达 → 对应审批人红点 +1；处理完 → 归零；**未轮到我的下级节点不点亮** |
| 终态 | 末级通过 → `permission_grant.status=ACTIVE`、`granted_by/at` = 终审人/时间 |

## 6. 风险与兼容

- **历史单据**：`approval_task` 已固化审批人，引擎改造不回改历史数据；仅新单生效。
- **模板语义**：引入递推后，仍保留「显式模板优先」——租户管理员显式配了链就按链走，
  避免既有租户（tenant 2 的四个机构各有专属流程）行为突变。
- **回归**：`e2e_v24_*`（审批链）、`e2e_v36_grant_expert_review`、`e2e_full_system` 的

### 7.3 遗留与待确认

1. **tenant 管理员作为申请人（链的 `start=3`）当前无提交入口可触达**：
   `PermissionGrantService.apply` 要求「该权限码可申请且我未持有」，而租户管理员
   已按角色持有全部 3 个可申请权限码（`worker:manage`/`expert:manage`/`approval:leave`），
   且 `QUOTA_EXPAND`/`RESOURCE_OPEN` 的提交入口在 `/api/v1/org/**`（需机构成员身份）。
   `superiorLadder` 的 `start=3` 分支已实现且链条第 4 级（平台管理员）已在成员用例中实测解析成功，
   但该分支本身缺端到端用例。若要覆盖，需要先给平台级能力定义一个可申请权限码。
2. **链长语义已选定为「整链逐级上报」**（部门负责人 → 企业管理员 → 租户管理员 → 平台管理员）。
   定这样而非「只上一级审一次」的依据：用户报的原始缺陷是**「成员申请权限，机构管理员收不到」** ——
   若只审一级，成员的申请只会落到部门负责人，机构管理员依然收不到，缺陷不闭环。
   若某租户确实只要一层，把该租户的 `steps_json` 改成 `[{"seq":1,"approver_type":"DEPT_LEADER"}]`
   即可（引擎数据驱动，零代码改动）。
3. cosmetic：tenant 9 的 3142 / 3143 昵称同为「傅宸」，演示时链条上会出现两个同名审批人。
4. `scxsyb_ldr`(3152, 机构 30) 仍未授 `ROLE_DEPT_LEADER` —— **故意**，避免打破
   `e2e_admin_personnel_scope` C3/C4 的「机构 30 成员档位」断言，待该套件期望值同步后单独处理。
