## 2. 三条契约（跨层，改任一键名都会断链）

### 2.1 `available_forms`（Java → agent）
```json
"available_forms": [
  {"code": "leave_request", "name": "请假申请", "module_code": "leave", "biz_type": "leave"}
]
```
- 只带 4 键，**不带** `schema_json`（单一事实源仍在 DB，agent 不持字段定义）。
- 清单为空 ⇒ 字段不下发 ⇒ agent 系统提示与改动前**逐字一致**（可做负向对照）。

### 2.2 `rules`（表单定义内，JSON Schema 根键）
```json
"rules": [
  {
    "id": "sick_need_proof",
    "when": {"field": "leave_type", "op": "in", "value": ["sick"]},
    "then": {
      "action": "require",
      "require_fields": ["proof"],
      "message": "病假需上传诊断证明",
      "target_field": "leave_type",
      "options": [{"value": "annual", "label": "改为年假"}]
    }
  }
]
```
| 键 | 语义 |
|---|---|
| `when.op` | `eq / ne / in / not_in / gt / gte / lt / lte / empty / not_empty`（`eq/ne` 宽松字符串比较；`gt` 系列两边可转 double 才比；`in/not_in` 的 `value` 必须是数组） |
| `then.action=block` | 条件成立即拦截 |
| `then.action=require` | 条件成立 **且** `require_fields` 任一为空才拦截 |
| `then.target_field` | 选项回填目标字段，缺省回落 `when.field` |
| `then.options` | H5 渲染为可点选按钮，点选后写回字段并重走校验+汇总 |

- `x-rules` 兼容；两者都有时 `rules` 优先。
- 无 `when`、未知 `op`、未知 `action` 运行期一律跳过（不抛）；**配置期**在 `validateSave` 就拒写库，避免坏配置静默失效。
- 不引入脚本求值（只做声明式判定）。

### 2.3 `rule_violation`（Java → H5）
命中时 **HTTP 200**（与 `BizException(400)` 的既有惯例一致，H5 只看 `body.code`）：
```json
{"code": 40090, "message": "病假需上传诊断证明",
 "data": {"rule_violation": {"rule_id": "sick_need_proof", "field": "leave_type",
          "target_field": "leave_type", "message": "病假需上传诊断证明",
          "options": [{"value": "annual", "label": "改为年假"}]}}}
```
H5 读取的键 `{field, target_field, message, options}` 是 Java 输出键的**严格子集**（`rule_id` 保留给审计，前端不依赖）。

## 3. 行为变化（谁会被影响）

1. **提交多一步**：所有 `need_form` 表单与独立入口 `window.oaOpenForm` 都走「提交 → 汇总确认 → 确认提交」。这是**故意**的统一行为，若某表单不希望汇总，需要单独加开关（当前未提供）。
2. **汇总回显可读值**：`select`/`multiselect` 显示选项名（`annual` → 「年假」）；命中不到选项时**原样显示**原值（不吞成「—」）。
3. **脏字段不再入库**：schema 未定义的 key 被丢弃并 `log.warn`（此前会原样进 `form_submission.data_json` 与审批快照）。
4. **`API.req` 的 Error 多了 `data`**：向后兼容（只新增属性）。
5. **模型可能拒绝猜表单**：清单未列出的表单不调 `request_form`；若某数字人应能办理的表单 `module_code` 隔离得过窄，会表现成「模型说办不了」——届时检查清单是否包含该表单。

## 附：跨层哨兵为什么必要

三层各测各的只能证明「本层自洽」：Java 单测证明 DTO 有字段，agent 单测手工构造 `RunRequest` 证明提示词有清单——**两者用的键名可以不一样而测试全绿**，线上却是清单悄悄丢失。
`scripts/_check_form_contract.py` 用 Java 源码里的 `@JsonProperty` 值与 pydantic 字段名做**同一字符串**比对，并用驼峰变体做负向对照，才真正钉住「改名必断链」这一事实。

## 6. 复盘（2026-10-17 23:40）：上线后数字人**仍然**不调用表单

用户实测输入「办公用品报销」，数字人回了一篇「进入报销系统 → 选择类型 → 填写 → 提交 → 查询进度」的通用操作指南，没有出表单卡。

### 6.1 根因（决定性证据，不是推测）

`agent/aios_ai/config.py:68` — `AIOS_HITL` 的**代码默认值是 `false`**；全仓启动脚本（`start-all.sh` / `start-backend.bat` / `deploy/*.yml`）**没有任何一处**设置它。

于是 `graph/nodes.py:166` 的注入条件不成立：

```python
if _hitl_enabled():                      # ← false，整块不执行
    tools = [ASK_USER_TOOL, REQUEST_FORM_TOOL] + list(tools)
```

`request_form` **从来没有出现在模型的工具表里**。模型即便「想」请求表单，也无工具可调，只能输出文字步骤 —— 与用户看到的现象完全一致。

实测证据（`logs/agent.log`）：

| 时刻 | 日志 | 含义 |
|---|---|---|
| 23:25:55（修复前，用户那次对话） | `tools=7` | 7 个业务工具，**无**内置工具 |
| 23:38:12（修复后） | `tools=9` | 7 + `ask_user` + `request_form` |
| 全历史 | `grep -c "request_form\|need_form" logs/agent.log` → **0** | 该工具**一次都没被调用过** |

> 这也解释了为什么之前的哨兵全绿却没发现：`_verify_form_confirm.py` / `_verify_form_invoke_e2e.py` 都是**伪造** `need_form` 帧，只验「帧到了前端怎么渲染」，从不验「模型会不会主动请求」。**假帧测试通过 = 只证明了下半段。**

### 6.2 三个叠加因素

1. **HITL 未开启**（决定性，见上）。
2. **后端是 17:26 的旧 jar**，而 `available_forms` 注入是 21:16 才写的 ⇒ 即便开了 HITL，模型也不知道系统里有 `expense_form`（清单为空 ⇒ 按提示词「清单未列出不要调」直接放弃）。
3. **提示词只有「别乱调」，没有「该调必须调」**：原文只写「清单未列出的表单一律不要调用」「改为文字说明业务入口」，模型面对「办公用品报销」这种**清单里没有同名表**的诉求，自然会退回文字教程。

| 层 | 改动 |
|---|---|
| agent 配置 | `agent/.env` 新增 `AIOS_HITL=true`（含注释，说明关闭时的现象）。⚠️ **`.env` 是持久配置**，此后任何方式启动 agent 都生效 |

### 6.5 这条复盘的可迁移教训

- **「假帧测试全绿」不等于功能可用**：凡是「模型主动发起」的能力（`ask_user` / `request_form` / 任何 tool-calling 行为），都必须有一条**真实 LLM 的端到端哨兵**，否则开关关着也能全绿。
- **开关类配置要能被观测**：`tools=N` 这一行日志就是最便宜的判据 —— N 少了 2，内置工具就没注入。以后排查「模型不调用某工具」，先看这个数字。
- **`mvn package` 不够，必要时 `clean`**：本机 target 里残留过 ECJ 编译的 class，`package` 会打出启动即 `Unresolved compilation problem` 的坏包；判据是启动日志里的 `Caused by: java.lang.Error`，而不是「构建成功」。
