# 58 · 用户端「插件-技能」拆分为插件 / 技能 / 连接器 与连接器授权方案

> 版本：2026-10-20 · 状态：**已实施**（后端 V96 + H5 三分 + 连接器两枚）
> 需求原话：「在用户端『插件-技能』里面新加一个连接器，前改名插件-技能-连接器，插件、技能、连接器分开；
> 连接器先新增 QQ 邮箱、企业微信，像 WorkBuddy 一样，会让用户去自行连接。」

---

## 0. 一句话结论

抽屉入口 **「插件-技能」→「插件-技能-连接器」**；同一页内用**三段分段控件**把三块分成三个独立子项，
各自独立取数、独立空态；**连接器**是**新增的一等能力**（新表 + 新接口 + 新授权流程），
两种授权模式：**QQ 邮箱 = 用户填授权码并做真实 IMAP 校验**，**企业微信 = OAuth2 扫码授权**。
连接状态**由服务端唯一判定**（H5 不自己拼状态），并区分「未连接 / 已连接 / 未通过校验 / 待管理员配置」四种可见态。

（`odSkills` 的 id、`META.skills` 的 key、`v-skills` 的 section id **一律不改**——改名只改可见文案。）

### 2.2 各面板的数据源与展示

| 子项 | 数据源（真实） | 行内字段（展示） | 当前实况 |
|---|---|---|---|
| **插件** | `tool_definition` 表（可被数字员工调用的工具） | `name` / `description` / `domain` / 风险徽标（`requiresApproval` → 「需审批」） | **64 行**（真实数据） |

**插件不暴露** `endpoint` / `auth_ref` / `input_schema` 等内部字段——只给用户看「叫什么、能干什么、要不要审批」。

### 2.3 连接器的分组与卡片

```
连接器
├ 邮箱
│   └ QQ 邮箱        [未连接]        ［连接］
└ 协作与办公
    └ 企业微信       [待管理员配置]   ［连接］(禁用)
```

卡片状态 chip 与文案**唯一映射**（后端给 `status`，前端只做字典）：

| status | chip 文案 | chip 样式 | 主按钮 |
|---|---|---|---|
| `NEED_AUTH` | 未连接 | `chip.done`（灰） | 连接 |
| `CONNECTED` | 已连接 | `chip.due`（绿） | 断开 |
| `UNVERIFIED` | 未通过校验 | `chip.wait`（琥珀） | 重新检测 |
| — （catalog `configReady=false`） | 待管理员配置 | `chip.wait` | 连接（禁用） |

卡片副行：`CONNECTED` 显示绑定的账号（如 `zhangdd@qq.com` / 企业微信 `ZhangDD`）+ 连接时间；
`UNVERIFIED` 显示 `lastError` 原文（不吞错、不改写）。

## 3. 连接器的连接流程

### 3.1 两种授权模式（同一条状态机的两个入口）

| 模式 | 适用 | 用户操作 | 服务端做什么 | 校验依据 |
|---|---|---|---|---|
| `CREDENTIAL` | **QQ 邮箱**（腾讯未提供 IMAP 的 OAuth，只有「授权码」） | 弹层填「QQ 邮箱地址」+「IMAP/SMTP 授权码」 | 用授权码**真实登录 `imap.qq.com:993`（TLS）**，登录成功才落库 | IMAP `LOGIN` 返回 `OK` |
| `OAUTH2` | **企业微信**（扫码授权） | 点「去企业微信授权」→ 扫码 → 回跳 | `state` 防伪 + 换 `access_token` + 取 `userid` | `auth/getuserinfo` 返回 `userid` |

> 企业微信需要**已注册的自建应用**（corpid / agentid / secret）才能发起授权。
> 未配置时该卡显示「待管理员配置」，连接按钮禁用并说明缺哪个键 —— **绝不用假数据假装已连接**。

### 3.2 QQ 邮箱（CREDENTIAL）时序

```
H5 点「连接」→ 弹层（说明：QQ邮箱→设置→账户→开启 IMAP→生成授权码）
  → 填 邮箱 + 授权码 → POST /v1/connectors/qq_mail/connect/credential
      → 服务端：TLS 连 imap.qq.com:993 → 读问候 → `a1 LOGIN "邮箱" "授权码"`
          ├─ `a1 OK`      → 授权码 AES-256-GCM 加密落库 → status=CONNECTED（200）
          └─ `a1 NO/BAD`  → 400，message=服务端原文（如「授权码无效」），**不落库**
      → H5：成功则关弹层 + 卡片转「已连接」；失败则弹层内红字显示原因（弹层不关，用户可改）
```

### 3.3 企业微信（OAUTH2）时序

```
H5 点「连接」→ POST /v1/connectors/wechat_work/connect/start {returnPath}
  → 服务端生成 state（一次性、10 分钟过期、绑定 tenant/user/connector/origin）→ 返回 authUrl
  → H5 window.location.href = authUrl（整页跳转，移动端最稳，不用弹窗）
  → 用户扫码授权 → 企业微信回跳 GET /api/v1/connectors/wechat_work/callback?code&state
      → 服务端：校验 state（未用过且未过期）→ gettoken → auth/getuserinfo → userid
          ├─ 成功 → status=CONNECTED + 存 userid/nick → 302 回 `${origin}${returnPath}?connector=wechat_work&result=ok`
          └─ 失败 → 302 回同一地址 + `result=fail&message=<原因>`
  → H5 启动时读 query：toast 结果 → history.replaceState 清掉参数（避免刷新重放）
```

**为什么用 302 而不是 postMessage**：手机浏览器（本系统 H5 的主场景）普遍拦截弹窗，
且 iOS Safari 的跨窗口 `postMessage` 在整页跳转后 opener 会丢；302 回原页是唯一稳的路径。

`returnPath` 只接受**同站相对路径**（以 `/` 开头、不含 `//`），并与 start 请求的 `Origin` 主机名比对，
防开放重定向。

### 3.4 状态机（唯一判定点：`ConnectorConnectionService`）

```
            connect(credential|oauth 回调成功，且已校验)
NEED_AUTH ───────────────────────────────────────────────► CONNECTED
    ▲                                                          │
    │ disconnect（用户主动断开，删凭据）                        │ verify 失败 / token 失效
    └──────────────────────────────────────────────────────────┤
                                                               ▼
                                                          UNVERIFIED
                                          （凭据仍在，但校验未过；带 lastError）
```

- `CONNECTED` **只在一次成功校验之后**写入；不存在「先标记已连接再后台校验」。
- `UNVERIFIED` 只允许出现在「凭据已保存但校验不可用」（如 IMAP 端口被网络策略拦）——
  并**必须**把 `lastError` 显示给用户，不允许静默降级成已连接。
- `disconnect` = 删凭据 + 置 `NEED_AUTH` + 记 `disconnected_at`（留痕，不物理删行）。

## 4. 接口契约（冻结）

前缀 `/api/v1`，全部走既有 `ApiResponse` 信封；`code=0` 为成功。

| 方法 | 路径 | 用途 | 关键字段 |
|---|---|---|---|
| GET | `/plugins` | 插件清单（`tool_definition`） | `code,name,description,domain,riskLevel,requiresApproval` |
| GET | `/connectors` | 连接器清单 + 我的连接状态 + 配置就绪度（一次拿全，避免 N+1） | 见下 |
| GET | `/connectors/{code}` | 单个详情（用途 / 授权说明 / 需要填什么 / 帮助链接） | `mode`,`fields[]`,`helpText`,`helpUrl` |
| POST | `/connectors/{code}/connect/start` | 开始连接 | 入 `{returnPath}`；出 `{mode:'OAUTH2',authUrl}` 或 `{mode:'CREDENTIAL',fields:[…]}` |
| POST | `/connectors/{code}/connect/credential` | 提交凭据（CREDENTIAL） | 入 `{values:{email,authCode}}`；出 `{status,accountLabel}` |
| GET | `/connectors/{code}/callback` | OAuth 回调（浏览器直跳） | 出 302 |
| POST | `/connectors/{code}/verify` | 重新检测 | 出 `{status,lastError}` |
| POST | `/connectors/{code}/disconnect` | 断开 | 出 `{status:'NEED_AUTH'}` |

`GET /connectors` 单条形状：

```json
{ "code":"qq_mail", "name":"QQ邮箱", "group":"邮箱", "icon":"mail", "summary":"接收/发送邮件",
  "authMode":"CREDENTIAL", "configReady":true, "status":"NEED_AUTH",
  "accountLabel":null, "connectedAt":null, "lastCheckedAt":null, "lastError":null,
  "isPlatformManaged":false }
```

**硬约束**：`status` 只能由服务端算；`configReady=false` 时 `status` 恒为 `NEED_AUTH` 且附 `configHint`（缺哪个键）。

## 5. 数据模型（Flyway V96，`server/aios-boot/src/main/resources/db/migration/`）

| 表 | 作用 | 关键列 |
|---|---|---|
| `connector_def` | 连接器目录（平台级，tenant_id=0） | `code` `name` `group_name` `icon` `summary` `auth_mode` `config_keys`(JSON) `help_text` `help_url` `sort` `status` |
| `connector_tenant_config` | 租户级应用凭据（管理员配） | `tenant_id` `connector_code` `secret_json`（**加密**）`enabled` `updated_by`；唯一键 `(tenant_id, connector_code)` |
| `connector_connection` | **用户级**连接状态 | `tenant_id` `user_id` `connector_code` `status` `account_label` `credential_json`（**加密**）`expires_at` `last_error` `connected_at` `last_checked_at` `disconnected_at`；唯一键 `(tenant_id, user_id, connector_code)` |
| `connector_oauth_state` | OAuth 防伪 | `state`(PK) `tenant_id` `user_id` `connector_code` `return_path` `origin` `created_at` `used_at` |

种子：`qq_mail`（group=邮箱，auth_mode=CREDENTIAL）、`wechat_work`（group=协作与办公，auth_mode=OAUTH2，
`config_keys=["corpId","agentId","corpSecret"]`）。

**凭据加密**：新增 `aios-common` 的 `SecretCodec`（AES-256-GCM，密文 `enc:` 前缀，格式与 `GiteeCrypto` 同口径），
密钥取 `aios.connector.secret-key`。**不改** `GiteeCrypto`（避免动已验证的仓库联动链路）。

## 7. 验收判据

**接口层哨兵** `scripts/_verify_connectors.py`
1. `GET /v1/connectors` 返回两枚、字段齐全、`qq_mail` 的 `configReady=true`。
2. `qq_mail` 用**错误授权码**连接 → 400 且 message 非空，**`status` 仍为 `NEED_AUTH`**（负向对照：证明「没连上就不许显示已连接」）。
3. `qq_mail` 用**格式非法**邮箱 → 400（参数守卫生效）。
4. `disconnect` 后 `status=NEED_AUTH`、`accountLabel=null`。
5. `wechat_work` 未配置时 `connect/start` → 400/`configReady=false`，message 指出缺哪个键；**不得**返回假 authUrl。
6. `callback` 用**伪造 state** → 不写任何 connection（防 CSRF）。
7. `GET /v1/plugins` 条数 = `tool_definition` 中该租户可见行数，且**不含** `endpoint`/`auth_ref` 字段。

**浏览器层哨兵** `scripts/_verify_oa_connector_ui.py`（Playwright，file:// 或 :5181）
8. 抽屉项文案 = 「插件-技能-连接器」。
9. 三个分段按钮存在且可切换；「插件」面板行数 > 0；「技能」面板显示空态而非空白。
10. 连接器面板两张卡 + 状态 chip；点 QQ 邮箱「连接」出现弹层（含授权码输入），**弹层在 body 下且样式生效**（`getComputedStyle` 判据，防 `.oa` 作用域失效）。
11. 空授权码提交 → 前端拦截且**无网络请求**。

## 8. 已知边界（如实记录，不粉饰）

1. **企业微信**必须有真实的 corpid/agentid/secret 才能完成授权；本环境未提供，故只验证「未配置时的诚实提示 + state 校验」，
   端到端扫码授权**未验证**。配好后同上链路即可用（代码不区分环境）。
2. **QQ 邮箱**的 IMAP 校验依赖 `imap.qq.com:993` 可达（本机实测 345ms 可达）。没有真实 QQ 授权码，
   故只验证「错误授权码被服务端拒绝且不落库」，**未验证**成功连接的真实邮箱。
3. 连接器**当前只做「连接 + 状态 + 断开」**，不做「代表用户收发邮件/推送消息」的业务动作（那是下一步）。
4. 管理员配置企业微信凭据的**管理端 UI 未做**，当前支持平台级配置（`aios.connector.wechat-work.*`）与
   `connector_tenant_config` 表直配；管理端页面属后续需求。

### 9.2 缺陷一：OAuth 回调被安全链拦成 401（**功能性，已修**）

- **现象**：`GET /api/v1/connectors/wechat_work/callback?code=..&state=..` → **401**。
- **根因**：回调是**浏览器从企业微信 302 跳回**，天然不带 `Authorization`，而 `SecurityConfig.PUBLIC_ENDPOINTS`
  只放行了 `/api/v1/gitee/bind/callback`，连接器回调漏了 ⇒ 生产环境扫码授权永远回不来。
- **修法**：加 `/api/v1/connectors/*/callback`（只放行这一个子路径；目录/详情/连接/断开仍须登录态），
  注释写明身份由一次性 state 承载、校验失败绝不写库。
- **判据**：`_verify_connectors.py` C10 —— 伪造 state 必须 **302** 到本站失败页（修复前是 401，实测红→绿）。

### 9.3 缺陷二：弹层标题图标被压成「残字」（**视觉，已修**）

- **现象**：连接器弹层左上角多了一个像 "S" 的小方块（`conn_e2e_3_dialog.png` 修复前）。
- **根因**：又是**弹层作用域陷阱**。`.oa-up-ico` 的 32×32/底色只写在
  `.notif-modal.oa-upload-dlg` 作用域下，而连接器弹层的类是 `.oa-conn-dlg` ⇒ 拿不到尺寸；
  且 `.ic` **没有全局尺寸规则**（各处上下文各自声明），里面的 `<svg>` 落到默认尺寸被裁。
- **修法**：`_oa_extra.css` 把 `.oa-conn-dlg` 并列进 `.oa-up-hd` / `.oa-up-ico` 规则，
  并新增 `.notif-modal.oa-dlg .oa-up-ico .ic{width:18px;height:18px}`。
- **判据**：`_verify_oa_connector_ui.py` **S8** —— 砖块 32×32 + 底色非透明 + svg 宽 18px。
- **纪律**：以后任何用 `.oa-up-hd` 新弹层，**必须把类名加进这条并列选择器**（已写进 CSS 注释）。

### 9.4 与设计草案的偏差（语义未变，如实记录）

1. `isPlatformManaged` = 「企业微信凭据来自平台级 `aios.connector.wechat-work.*` 而非租户级」，不是「平台托管连接」。
2. OAUTH2 的 `verify` 不重新校验（只存 userid、无 refresh token），仅回当前状态 + `lastError`。
3. 伪造/过期 state 的回调一律 302 到 **`/`**（无 state 时拿不到可信 origin，防开放重定向），
   有 state 时回到 `origin + returnPath`。
4. `connector_def` 额外加了 `uk (tenant_id, code)`（原设计只写 PK），防重复种子。
5. `config_keys` 存 JSON 字符串而非 JSON 列（与 `secret_json` 同口径）。
6. 未新增权限码：连接是**用户维度**数据（`tenant_id + user_id` 唯一键），越权由 `AuthUserContext` 天然隔离。

### 9.5 判据口径提醒（避免下次误判）

- 业务错误是 **HTTP 200 + body `code != 0`**（`GlobalExceptionHandler.handleBiz` 只在 401/403/404 才改 HTTP 状态），
  断言必须读 `body.code`，不能只看状态码。
- `authMode` 的合法取值就是 `"CREDENTIAL"`：**不要对整串 JSON 做敏感词扫描**（会自造假阳性），
  只扫键名 + 查 `enc:` 密文前缀与提交过的明文值。
