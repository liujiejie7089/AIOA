### C-4. 工具调用网关零 `@Transactional`，幂等 / HITL 存在 TOCTOU 竞态

- **位置**：[server/aioa-bridge/.../service/ToolInvocationService.java](server/aioa-bridge/src/main/java/cn/aioa/bridge/service/ToolInvocationService.java) 整文件
- **证据**：`grep -r '@Transactional' server/aioa-bridge` → **0 命中**。
  `invoke()` 走「SELECT-then-INSERT」模式
  （line 100 查 `findByIdem` → 后续 `persist`），而 V59 迁移建的
  `UNIQUE(tenant_id, tool_code, idempotency_key)` 在并发下抛
  `MySQLIntegrityConstraintViolationException`，**未被 catch**，直接 500 给客户端。
- **更严重的子问题**：
  - line 111：`if (prev != null && !ERROR_PENDING_APPROVAL.equals(prev.getErrorCode()))`
    显式**跳过 PENDING 行**的幂等——结果「同一幂等键 + 第一次还在审批中」会**创建第二个
    PENDING_APPROVAL 行 + 第二张审批单 + 最终两次外部 HTTP 调用**。
  - `resume()`（line 192-231）从 `PENDING_APPROVAL` 选行后直接 `dispatchAndFinalize`，
    无锁。审批回调网关重试一次 → **外部副作用被执行两次**。
  - `submitForApproval`（line 150-181）：先持久化 PENDING_APPROVAL，再调网关；若网关
    超时，**PENDING_APPROVAL 行残留**且 `approvalId = null`，第二次同键调用会再造一份。
- **危害**：在 HITL（人机协同）路径下，**外部系统的副作用可能执行两次**
  （扣款、发邮件、建仓库…）；普通幂等键场景下，并发 500。
- **修复**：(a) 整个 aioa-bridge 加 `@EnableTransactionManagement` 并把
  `invoke/resume/submitForApproval` 都 `@Transactional(isolation=READ_COMMITTED)`；
  (b) 把 SELECT-then-INSERT 换成 `INSERT ... ON DUPLICATE KEY UPDATE` 或显式 catch
  唯一键冲突转 `status=DEDUPED`；(c) PENDING 行用 `SELECT ... FOR UPDATE` 抢锁或加
  `version` 列乐观锁；(d) `resume()` 自身加幂等键。

### C-5. 审批任务 `decide()` 没有行级锁，并发审批会重复执行

- **位置**：
  [server/aioa-org/.../service/ApprovalFlowService.java:1201](server/aioa-org/src/main/java/cn/aioa/org/service/ApprovalFlowService.java#L1201) 的
  `decide()`、line 1248/1267/1305/1420/1496-1516 的 `taskMapper.updateById(task)`
- **证据**：`UPDATE approval_order SET status=? WHERE id=?` 缺 `AND status='PENDING'`
  守卫；两个并发的「同意」+「驳回」都读到 PENDING → last-writer-wins。结果
  `approval_order.status='APPROVED'`，但同一 approvalId 关联的
  `tool_invocation_log.error_code='APPROVAL_REJECTED'`，**两张表状态自相矛盾**。
  当这张审批单驱动工具桥 `resume()` 时，**两次外部调用**。
- **危害**：HITL 双调用、审计回溯时无法解释谁是真、跨租户场景下 `role` 与实际决策人
  不一致。
- **修复**：加 `version` 列 + `WHERE id=? AND version=?`；或事务内 `SELECT ... FOR UPDATE`；
  或把 `decide` 改成 `UPDATE ... WHERE id=? AND status='PENDING' AND affected=0 THEN 409`。

### H-3. Python 沙箱 `r'''…'''` 包装可用 DATA 逃逸

- **位置**：[agent/app/tools/sandbox.py:128-142](agent/app/tools/sandbox.py)
- **证据**：
  ```python
  wrapper = "import json\nDATA = json.loads(r'''__DATA_JSON__''')\n...".replace(
      "__DATA_JSON__", data_json.replace("'", "\\'"))
  ```
- **危害**：AST 白名单只对用户 `source` 跑过（line 63-93），**没跑过 wrapper**。
  `r'''…'''` 是 raw 三引号字符串，`\\'` 在 raw 串里**不会被消耗**
  （两个字符：`\` 和 `'`），所以只要 DATA 里有 `'''` 就能关闭原始字符串、注入任意 Python
  绕过白名单（`os`, `subprocess`, `__import__`）。此外 `pandas`/`numpy` 允许属性访问 →
  `pandas.read_pickle` 在 DATA 受控时可执行任意代码。
- **修复**：(a) 整个 wrapper 用 `subprocess.run([sys.executable, "-"], input=source)`
  通过 stdin 传入（**绝无字符串拼装**）；(b) `ast.Attribute` 收敛到精确子集
  （`pandas.DataFrame.*`、`numpy.ndarray.*` 等）；(c) 全局禁用 `pickle`/`allow_pickle=True`。

  （如 `Ordered.HIGHEST_PRECEDENCE`）使其先于 Spring Security 过滤器链执行；
  参照 `AioaWebPrefixConfig.java:15-26` 的注册方式。

## 五 · 设计不合理之处（架构层）

1. **「工具调用 / 审批 / 幂等」三个网关层都裸奔**。aioa-bridge 整体零 `@Transactional`、
   审批 `decide()` 没锁、ToolDispatcher HttpClient 每调用重建。这不是疏漏，是**架构级的
   认知偏差**：默认了「工具调用是请求级别，单飞一次就完事」，但 HITL 把这件事切成
   「挂起-恢复-重放」三段，每段都需要持久化 + 锁。
   [docs/04-接口契约](docs/04-接口契约) 与 [ADR-001](docs/adr/ADR-001-工具调用走定义驱动网关.md)
   应明确把「resume 必须幂等 / decide 必须加锁 / invoke 必须 read-committed」写进接口契约，
   而不是只写代码注释。

2. **「服务间令牌」与「用户身份」分离的设计**，默认安全模型是「agent 服务可信」。
   一旦 agent 服务被攻陷，C-3 的通道就开了。应当在服务 JWT 里强制带 `tid/uid/roles` claim，
   server 端拒绝「声明与 token claim 不一致」。

3. **多租户完全靠约定**（H-1）。MyBatis-Plus 自带 `TenantLineInnerInterceptor` 已经在生态
   里成熟，**不用白不用**。继续靠人写 `.eq(tenant_id, ?)` 等于把跨租户安全寄托在每个
   开发者的纪律上 —— 这是 12 个模块的开发者总和，不是「资深技术负责人」。即便引入拦截器
   还要做 ignore list（`sys_*` 平台表），但成本远低于泄漏一次。

4. **aioa-resource 上帝模块**（M-2）。一个模块里 10 个域，单是改一处安全策略就要扫 24 个
   controller，审计成本失控。

5. **配置管理「Spring profile 是 no-op」**（C-1 + M-4）。
   [application.yml:8](server/aioa-boot/src/main/resources/application.yml) 写了
   `profiles.active: dev`，但**根本没有 `application-dev.yml`**。
   `start-backend.bat` 自己都承认 `--spring.profiles.active=local` 是 no-op。
   这种「假装做了环境隔离」的假象比「什么都没做」更危险 —— 运维以为切了 profile 就变了，
   其实啥都没变。

6. **「声明存在但不生效」的字段**（H-6）。`rateLimit` / `circuitBreaker` 在 DB 和实体里都
   建了，文档也写了，但运行时不读。比直接删掉更糟。

7. **文档与代码严重漂移**（H-5, H-9, H-10, M-4, M-9）。README、docs/05、docs/33、deploy/k8s、
   application.yml 之间的不一致已经达到「任何一处都不能单独信任」的程度。这是项目最大的
   隐性成本 —— 每次新人上手都要打三个电话才能问清真实情况。

8. **Python agent 的安全边界**（H-3 + H-4）设计粗糙：沙箱与提示词两道防线都有标准做法
   （subprocess + stdin / 强转义 + 角色覆盖过滤），代码里偏偏选了最脆弱的两种实现。

## 六 · 不完善之处（功能 / 工程）

1. **没有审计失败路径的设计**。DbTokenRevocationChecker fail-open、ApprovalService.submit
   无事务、AsyncConfig 无 TaskDecorator —— 几乎每条「跨进程/跨线程/跨事务」的边界都是
   「成功路径写得漂亮，失败路径走 fallback」的风格。
2. **没有可观测性**。`actuator/prometheus` 没接、logback 没 JSON、traceId 进了 MDC 但没传进
   appender（且 Filter 没注册 — 见 H-13）。
3. **没有备份 / 密钥轮换 / 容量规划 / DR 演练**剧本。`deploy/ops/` 里有 compose-lint /
   host-check / offline-images / prometheus / set-secrets，唯独缺这四项。
4. **CI 不跑端到端**（L-28）。README 自己说「判据是端到端套件，不是单测覆盖率」，但 CI 实际
   只跑编译 + pytest。合并到 `main` 的回归门槛是「开发者手动跑过」，无任何机器保证。
5. **e2e 脚本清理不彻底**。多套套件 `approve / create project` 后没有 teardown；
   累计的 demo 数据已成为「基线」（user-clients 的 MEMORY 里已经记载「E2E 造的 9 个机构
   被长期当成机构总数 22 的基线」）。
6. **frontend UX 不闭环**（M-7, M-8, L-12, L-13, L-14）。错误处理 5 套、404 静默重定向、
   无 error boundary、auto-scroll 不尊重用户位置 —— 整个 SPA 看起来能用，但每个细节都在扣分。
7. **`scripts/_e2e_*` 与 `scripts/_check_*` 不入库**（L-23）。本地手工探针成了不可重现的
   「实验台账」。

## 八 · 验证过且**确认安全**的项（避免不必要的怀疑）

为节约后续评审时间，下列面已被实测验证为 PASS：

- **MyBatis SQL 注入**：14 个 mapper 共 144 处 `#{}` 参数化绑定，**0 处 `${}` 字符串拼接**，
  **0 个 XML mapper**（`server/**/mapper/*.java` 与 `resources/mapper/`）。
- **Webhook 验签**：[GiteeClient.java:476-484](server/aioa-gitee/src/main/java/cn/aioa/gitee/client/GiteeClient.java)
  用 `MessageDigest.isEqual` 常量时间比较、空 secret 拒绝；
  [GiteaProviderClient.java:480-567](server/aioa-gitee/src/main/java/cn/aioa/gitee/client/GiteaProviderClient.java)
  正确实现 HMAC-SHA256。GiteeWebhookController 总返 200 + `accepted=false`，避免 Gitee 重试风暴。
- **CSRF**：JWT + 无 cookie 架构下经典 CSRF 不适用；OAuth 回调用一次性 `state` + DB 校验；
  Webhook 用签名。
- **多租户隔离（OrgGuard）**：[OrgGuard.resolveScopeTenant](server/aioa-org/src/main/java/cn/aioa/org/support/OrgGuard.java) 跨租户访问返 404（不泄漏存在性），TenantController / Gitee 端点都正确委派给它。
- **`/actuator/health`**：只暴露 health，`show-details: never`。
- **模块依赖 DAG**：12 模块无环（`aioa-common → security+tool-sdk → 域 → 集成 → aioa-boot`）。
- **JDBC 连接**：0 处手工 `DriverManager.getConnection`，全部走 HikariCP + MyBatis-Plus。
- **流式资源**：除 M-1 / H-11 提到的两处外，无其他资源泄漏；所有 `HttpClient`
  （除 ToolDispatcher）都是 final 字段单例。
- **`AuthUserContext` ThreadLocal 清理**：`JwtAuthenticationFilter` 在 try/finally 中清理，
  覆盖全部 /api/** 路径。
- **`LocalToolRegistry.byCode`**：`ConcurrentHashMap`，线程安全。
- **`AioaToolScanner`**：只在 `afterSingletonsInstantiated()` 单线程跑，自身无需线程安全；
  单工具失败不拖垮启动。
- **`PlatformConfigOverlay` 自实现 volatile+`Map.copyOf`**：故意不引入 spring-cloud，
  自管动态配置。
