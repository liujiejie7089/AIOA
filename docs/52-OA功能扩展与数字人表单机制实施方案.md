**链路 B · 动作意图 → H5 写死窗口（不可扩展，仅作字段词汇参考）**

`intake.py`（加动作规则）+ Java（新提交端点）—— **四处**，且字段不可配。

## 1. 结论先行

> **一句话架构**：把「每个功能」表达为**一份可配置的表单定义（JSON Schema）**，把「数字人」表达为
> **一组「任务 → 表单 → 工具 → 审批」的能力声明**；用户创建数字人 = 给数字人装上若干能力；
> 数字人干活时通过**扩展后的 HITL 链路**把表单**推给用户填**，提交后按声明**分流**到「台账 / 审批 / 回填对话」。

两条改造主线：

1. **表单：从「代码」搬到「配置」** —— 现状「一个表单 = 改 4 个文件」→ 目标「一个表单 = 一条 `form_template` 数据」。
2. **数字人：从「4 个硬编码角色」升级为「模板 + 能力声明」** —— 保留 4 个内置角色作为模板，
   但新增「能力声明」使其可声明「我处理这类任务时，用哪张表单收哪些字段」。

**扩展点选择（基于 §0.4 的实测）**：**扩展链路 A（HITL），而不是链路 B**。
理由：A 已有完整的「暂停 → 渲染 → 回填 → 续跑」状态机与断点，语义正好是「数字人发起交互、收集输入、继续办」；
B 的结果不回填对话，语义不符。但 A 的载荷字段太弱，所以要**借 B 已验证的字段词汇**（文本/日期/下拉/金额/附件）
并**新建 H5 通用渲染器**——这正是 `docs/19/20/30` 早就规划、一直没做的那块。

## 3. 四大核心能力

### 3.1 数字人管理（谁去办）

**保留**：`WorkerRole` 四角色作为**内置模板**（`GENERAL`/`LEAVE_APPROVER`/`KB_ASSISTANT`/`DOC_DRAFTER`），不动枚举语义。

**新增：能力声明** `worker_capability`（`worker_id, task_code, task_name, form_code, tool_names_json, approval_biz_type, sort, enabled`）

- 语义：「这个数字人会办 `task_code` 这件事；办的时候用 `form_code` 这张表收字段；需要 `tool_names` 这些工具；提交后走 `approval_biz_type` 审批（可空=不审批）」。
- 为什么用表而不是 JSON 大字段：要能**按任务/表单反查**（「哪些数字人用这张表？」），且便于管理端分项编辑。
- 与既有 `formFields` 的关系：`agent/aioa_ai/intent/intake.py:_ROLES` 里那串中文（`["假种","起止时间","请假事由","证明材料"]`）
  **改为引用 `form_code`**，由表单定义提供字段与话术 —— 满足铁律 1「话术与事实同源」，消灭两处各写一份。

**用户自建数字人流程（现状已通，补齐能力选择）**
`POST /api/v1/workers` → 六项 `precheck`（既有）→ 新增第 7 项**能力自检**：
声明的每个 `form_code` 必须存在且 ACTIVE、每个 `tool_name` 必须已注册、每个 `approval_biz_type` 必须有 ACTIVE 审批流定义；
否则创建即阻断并给出 `nextAction`（沿用现有 precheck 的三态 PASS/WARN/BLOCKED 输出形状）。

**分配**：沿用既有三条路径，不新建概念 —— 会话绑定 `chat_conversation.worker_id`、项目绑定 `pm_project_worker`、
个人自建 `visible_scope=SELF`。

### 3.2 表单定义（收什么）

**`form_template`**（JSON Schema 承载，范式照抄 `approval_flow_def`：大字段 + 版本 + 作用域 + 状态）

| 字段 | 说明 |
|---|---|
| `code` | 全局唯一，如 `leave_request`；数字人与工具都用它引用 |
| `name` / `module_code` | 中文名 / 归属功能模块（对应清单 43 项的稳定 code，如 `leave`、`expense`） |
| `biz_type` | 提交后进审批时的 `bizType`（复用既有引擎，如 `LEAVE`；无审批则空） |
| `schema_json` | **JSON Schema Draft 2020-12**（与 `tool_definition.input_schema` 同版本、同口径） |
| `layout_json` | 可选，分组/栅格/顺序（渲染用，缺失则按 schema 顺序） |
| `submit_policy` | `LEDGER` / `APPROVAL` / `RESUME`（可组合，如 `APPROVAL+RESUME`） |
| `receipt_json` | 声明式回执（标题模板 / 展示哪些字段 / 按钮组） |
| `tenant_id` / `institution_id` / `status` / `version` | 作用域与生效态；ACTIVE 唯一 |

**字段类型词汇（冻结，与既有前端控件对齐，避免新造词）**
`text | textarea | number | amount | date | datetime | select | multiselect | file | boolean`

**字段选项的两种来源（关键设计）**
- 静态：schema 里内联 `enum` + `enumNames`；
- 动态：schema 写 `x-options-ref: "leave_types"`，由**后端在发帧前解析并内联为 enum**
  （复用既有 `GET /api/v1/leave/types` 与项目文件夹树两处先例），**前端不做任何取数决策**（铁律 1）。

**校验一份、三处同源**：同一份 `schema_json` 同时用于
① LLM function calling 参数定义（照 `docs/03` 既有约定）、② H5 渲染、③ 后端提交校验。
后端校验为**唯一权威**（前端校验只为体验）。

### 3.3 表单调用（怎么让用户填）

**新增 agent 内置工具 `request_form`**（与 `ask_user` 并列，共用 `clarify` 的 `interrupt()` 底座）

```
入参：{ "form_code": "leave_request", "reason": "需要请假信息才能送审", "prefill": {...} }
```

**新增 SSE 帧 `need_form`**（与 `need_clarification` 并列，**不污染**既有单选链）

```
event: need_form
data: {
  "form_code": "leave_request",
  "version": 3,
  "title": "请假申请",
  "submit_label": "提交",
  "fields": [ {"name","label","type","required","options?","placeholder?","validation?","default?"} ],
  "prefill": { "startDate": "2026-10-18" },
  "origin": { "kind": "worker", "worker_id": 86, "worker_name": "请假助手" }
}
```

**三层改动（全部复用既有底座，不新建状态机）**

| 层 | 改动 |
|---|---|
| agent | 新增 `request_form` 工具 + `need_form` 出帧；`clarify` 节点的 `interrupt` 机制、断点、`facade._pause_events` 与 `resume` **原样复用** |
| Java | `RunService.forward` 增加 `need_form` 分支（与 `need_clarification` 同样写入 `clarificationRef`）；`completeRun` 的暂停保护、`markWaitingInput`、`WAITING_INPUT` 拦截、`proxyAgentRun`、`resume` 端点**全部原样复用**；`resume` 的 `answer` 由标量**兼容升级**为对象 |
| H5 | 新增 `renderForm(schema, prefill)` 通用渲染器，**经典与 OA 共用一份**（范式照 `leaveFormHtml` 两形态共用）；`mountClarCard` 保留给纯单选澄清；`while(clar)` 回填循环改为可回填**对象** |

**必须同时支持的两种入口**（不能只做对话内）
1. **对话内**（数字人发起）：`need_form` → 渲染 → 提交 → `resume` 回填；
2. **独立入口**（用户自己点进去填）：`GET /api/v1/forms/{code}` 取定义 → 同渲染器 → `POST /api/v1/forms/{code}/submit`。
   理由：清单里大量模块（工作日志、问卷调查、资产盘点…）不以对话为主入口，若只做对话内，「每个功能自定义表单」就落不了地。

### 3.4 数据流转（填完去哪）

```
用户提交（resume 回填 / 独立 submit）
      ↓  后端按 schema_json 校验（唯一权威）
   form_submission 落库（真源：template_id + template_version + data_json + status）
      ↓  按 form_template.submit_policy 分流
  ┌───────────┬──────────────────────┬─────────────────────────┐
  │ LEDGER    │ APPROVAL             │ RESUME                  │
  │ 只落台账   │ + ApprovalFlowService│ 结构化答案回填给数字人续跑 │
  │（工作日志）│  biz_type→steps_json │（"办完了，接着办下一步"）  │
  │           │（请假/报销/采购/合同）│  可组合：APPROVAL+RESUME  │
  └───────────┴──────────────────────┴─────────────────────────┘
      ↓
  回执：按 receipt_json 渲染结果卡 → 既有范式 showLeaveResultCard
      ↓
  留痕：approval_order（审批）+ tool_invocation_log/agent_run_step（对话执行）
```

**状态机（`form_submission.status`）**
`DRAFT → SUBMITTED →（APPROVING → APPROVED/REJECTED）| DONE | CANCELED`
- 无审批（`LEDGER`）：`SUBMITTED → DONE`；
- 有审批：`SUBMITTED → APPROVING → APPROVED/REJECTED`，`approval_order_id` 回写；
- **终态失败必须回写**（铁律 2）：审批被拒 → submission 置 `REJECTED`，并回填对话说明原因。

## 6. 对现有系统的优化点

> 这一节回答「可以优化目前的系统」。按**收益**排序，前三条是本次架构的立身之本。

**6.1 消灭「新增一个表单要改 4 个文件」**
现状：新增表单 = 改 `_oa_app.js`（OA 写死表单）+ `index.html`（经典再写一份）+ `intake.py`（加动作规则）+ Java（新端点）。
目标：**一条 `form_template` 数据**。这是把 43 个模块从「不可能铺开」变成「可铺开」的唯一前提。

**6.2 `formFields` 从「文案」变成「定义」**
现状：`agent/aioa_ai/intent/intake.py:99-124` 的 `["假种","起止时间","请假事由","证明材料"]` 只是给 LLM 看的字符串，
与实际表单（`leaveFormHtml`）各写一份，**改一处忘一处**（违反铁律 1）。
目标：改为 `form_code` 引用，话术与渲染同源。

**6.3 两形态共用一套渲染器**
现状：经典 `index.html` 与 OA `_oa_app.js` 各写一套表单（请假已用 `leaveFormHtml` 共享，属正确做法，应推广到全部表单）。

**6.4 接通 `expert_settings`（数字人专属调参，已就绪但未接线）**
调研发现：`ExpertSettings`（temperature/topK/threshold/kbScope/tools/systemPrompt，多层 merge）**已存在**，
agent 侧 `graph/nodes.py:140-157` 也已解析，但 `RunService` **从不注入** `expert_settings`
（`aioa-chat` 内 grep `expertSettings` 零命中）⇒ **数字人当前拿不到自己的专属设置，全走默认值**。
用户自建的数字人若连调参都带不上，「协助完成工作」就是空话。建议在 P3 一并接通。

**6.5 统一「提交回执」**
现状：上传/花费是 toast + 气泡，请假是结果卡，口径不一致。目标：由 `receipt_json` 声明式决定。

**6.6 `form_submission` 与 `approval_order.form_data` 的真源关系（必须钉死）**
现状：`approval_order.form_data` 是「谁提交了什么」的唯一留存，且**由各业务 service 硬编码字段拼 JSON**
（`LeaveService.java:344-351`、`PermissionGrantService.java:230-237` 等）。
目标：`form_submission` 为**唯一真源**，`approval_order.form_data` 只存**引用 + 提交时快照**。
否则同一份数据两处各存一份、口径必然漂移（铁律 1）。**这是迁移期最容易出的缺陷。**

**6.7 `tool_definition` 表零装载，顺手盘活**
该表由 `aioa-bridge` 的 `ToolRegistryService` **实时读写**（非死表），但**行数为 0**（框架就绪、零装载）。
既然 §3.2 决定用 JSON Schema 做同源，可让工具与表单共用装载链路（`docs/03` 已埋伏笔），
在 P6 顺带把工具定义也纳入配置化。

**6.8 修掉「新表单必须写死前端」带来的双形态漂移**
H5 是单文件产物（`index.html` 由 `_build_oa.py` 拼装，**不可手改**）；通用渲染器落在源里后，
新增表单**不再需要重建产物**，从根上消除「改了源忘了重建」这类静默失效。

## 7. 风险与已知边界（不粉饰）

1. **`need_form` 与既有 `need_clarification` 共存期**：两条链共用 `WAITING_INPUT` 状态与 `resume` 端点。
   必须保证「一个 run 同时只挂一个待填交互」，且 `resume` 能按挂在 run 上的类型分派；
   否则会出现「填了单选却被当表单」的口径错配。（P0 必须把这个分派规则写进契约。）
2. **断点存储默认是内存档**（`checkpoint.py:52`，`AIOA_CHECKPOINT_URL` 为空即 `InMemorySaver`）：
   agent 重启即丢断点，此时「数字人发起表单 → 用户还没填 → agent 重启」会退化为 `run.failed`。
   生产必须配 Redis（且需 Redis Stack，普通 Redis 会失败）。**这是既有限制，不因本次改造而消失。**
3. **额度/配额**：本演示环境单个账号有**每日免费词元上限**（实测会返回「今日免费额度已用完」）。
   端到端验收必须考虑跨账号/跨日安排，**不得把额度耗尽的失败当作代码缺陷**（应记为 ENV）。
4. **表单定义是权限敏感面**：`schema_json` 若允许任意内容，可能被用作注入载体（H5 渲染器必须转义，
   且动态选项接口需鉴权）。渲染器必须**只认白名单字段类型**，禁止渲染任意 HTML。
5. **43 个模块 ≠ 43 个表**：多数模块是一组表单 + 一条审批流，不应每个模块造一套独立表结构；
   能复用 `form_submission` 的全部复用，避免退化成「每个模块一套硬编码表」（那等于回到现状）。
6. **`pm_project_worker` / `chat_conversation.project_id` 的迁移位置**：调研中一度出现「仅在构建产物、源码缺失」的说法，
   **经 team-lead 亲自复核为误报** —— 源码 `db/migration/` 确有 82 个文件至 `V82`。此处记录在案，避免后续重复踩。

## 8. 验收判据（沿用本仓库铁律）

1. **禁止恒真断言**（铁律 7）：每条新断言必须能用「删掉被测实现」的方式证明它会变红。
2. **判据不得与被测对象同源**（铁律 12）：验证「H5 渲染了某字段」时，判据回到 `GET /api/v1/forms/{code}`
   与库里的 `form_submission`，**不得**读渲染器自己的数据副本。
3. **P1 起每个阶段配套哨兵**（`scripts/_check_*` / `_verify_*`，属本仓库约定长期回归面）：
   - `_check_form_definition.py`（模板 CRUD / 版本 / 作用域 / 校验器，含负向：非法 schema 必拒）
   - `_verify_form_invoke_e2e.py`（对话内发起→渲染→提交→续跑；含负向：无表单定义时必不渲染）
   - `_verify_form_flow.py`（三条分流 + 审批拒绝时的终态回写）
   - `_check_form_renderer_discriminating.py`（删除渲染分支应全红）
4. **改权限/可见性/生效态后**：全局搜既有套件的旧口径断言并**连跑两次**（铁律 8）。
5. **P5 每上架一个模块**，必须能让「新增该模块」只改数据、不改前端 —— 若不满足，回到 P2/P3 返工。

### 9.2 本轮修掉的缺陷（共同特征：**不修也不会报错**，只会静默退化）

1. **回执契约漂移**（P4 核心）：`V86` 种子写 `{"title","display_fields"}`，后端只认 `{"title","lines":[{"label","value"}]}`
   ⇒ `lines` 恒空 ⇒ 43 张表单的回执全部退化成兜底「提交单号」。修：`V87` 改数据 + 生成器 `build_receipt` 改结构 +
   `renderReceipt` 三条兜底路径补 `log.warn`（原先 `catch (Exception ignored)`，配置错了永远没人知道）。
2. **字段展示名口径漂移**：`FormSchemaValidator.labelOf` 只读 `def.label`，而种子用 JSON Schema 的 `title`
   ⇒ 报错话术是「必填字段「today_work」不能为空」。修：统一走 `FormFieldMeta.label`（label → title → name），
   并去掉服务层「英文键名 + 中文名」的重复前缀。
3. **按钮文案塞策略串**：`RunService` 把 `submitPolicy` 塞进 `submit_label` ⇒ 提交按钮显示「LEDGER」/「APPROVAL+RESUME」。
   修：按策略给中文文案（`提交审批` / `提交`），单测已做**变异验证**（改回旧写法 → 2 条变红）。
4. **Flyway 占位符**：迁移里出现 `${field}` 会被 Flyway 当自己的占位符，**后端启动直接失败**
   （报错不说是哪个文件）。修：迁移文本用 `§` 代替 `$` + `REPLACE(...,'§',CHAR(36))` 落库，生成器同步；
   已验证「把两行数据还原成旧形状 → 启动 → 转成新结构且 `$` 正确还原」。
5. **agent 把调用方错误报成 500**：`GuardError`（如 `text 不能为空`）只被 `Exception` 兜底处理器接住 ⇒ 500，
   调用方 Java 只能当「agent 故障」降级，真实原因被埋进 ASGI traceback。修：新增 `GuardError` 处理器（`BAD_REQUEST`→400，
   其余护栏→429），`agent/tests/test_internal_http_errors.py`（5 条，含正常链路负向对照）。
6. **HITL 单测反射签名过期**：`RunServiceHitlTest` 用 `getDeclaredMethod("forward", 9 参)`，产品侧 `forward` 早已加到 12 参
   ⇒ 4 条用例 `NoSuchMethodException`（测试一直红着，没人跑就没人知道）。修：签名与调用同步。
7. **审批列表缺 `decidedAt`/`decisionNote`（顺带发现，与表单域相邻）**：`ApprovalFlowService.mine()`/`deptSubjectOrders()`
   只回 `timeline`，而 OA 审批列表直接读订单级 `decidedAt`（`_oa_app.js:733`「审批时间」整行）与 `decisionNote`（`:749`「审批意见」）
   ⇒ 已办单永远看不到审批时间、意见恒显示「（未填写意见）」。修：终态单把**最后一个已决节点**的时间/意见提升到订单级；
   同时把 `_check_dto_fields.py` 的判据按语义分档（PENDING 单本来就没有这两个键，按首行 keys 一律判定属**错误前提**）。

### 9.4 已知边界（不粉饰）

- **`request_form` 由模型自主调用**这一段没有自动化：真实 LLM 是否决定调工具不可确定，
  故用两侧单测钉契约（Python 出帧形状 + Java 补全形状），中间用首帧仿真跑浏览器链路。
- **43 个模块里只有请假是 `APPROVAL+RESUME`**，其余 `LEDGER`；报销/出差等要接审批，需要为对应 `bizType`
  注册审批流定义（`approval_flow_def`），当前数据里没有。
- **H5 表单卡「取消」**只是让本地循环收口，服务端 run 仍是暂停态；再次提问会新建 run（不复用暂停断点）。
- P6 的拖拽式设计器 / 模板导入导出 / `tool_definition.input_schema` 统一装载未做。
