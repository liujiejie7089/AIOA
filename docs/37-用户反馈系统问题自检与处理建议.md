## 1. 机构分配额度失败

**入口**：租户与机构 → 机构管理 → 行内「配额」→「机构配额分配」弹窗 → 保存
`InstitutionView.vue:366 submitQuota()` → `POST /tenant/org-quotas` → `QuotaService.allocateOrgQuota()`

**三道门禁**（`QuotaService.java:204-239`）：

| 门禁 | 条件 | 报错 |
|---|---|---|
| 租户归属 | 机构必须属本租户 | `机构不存在于本租户：{id}`（HTTP404） |
| 资源池存在 | 该周期 `tenant_resource_pool` 必须有行 | `周期 {p} 的资源池尚未交付，无法分配机构配额（请先执行入驻第 1 步）` |
| 总量不超 | Σ其他机构配额 + 本次 ≤ 资源池总量 | `分配超额：其它机构已占 {others}，本次 {quota}，超过资源池总量 {total}（FR-C2）` |

**实测数据（当前库）**：

```
tenant_resource_pool:  tenant 2 / 2026-09 / total 5,000,000 ; tenant 3 / 2026-09 / total 800,000
org_quota:             (2,机构1)=2,000,000 (2,机构2)=1,800,000 (2,机构3)=900,000  ⇒ 已分配 4,700,000 → 仅剩 300,000
                       (3,机构4)=  600,000                                     ⇒ 已分配   600,000 → 仅剩 200,000
```

⚠️ **结论 A（体验缺陷，非代码 bug）**：租户 2 只剩 30 万可分配。把「某某区发展和改革局」从 200 万调到 300 万 → `2,700,000 + 3,000,000 = 5,700,000 > 5,000,000` → 必然报「分配超额」。门禁按设计工作，但**弹窗里不显示"剩余可分配"**，用户只会看到"分配失败"。

✅ **结论 B（真缺陷：统计期取自浏览器时钟）**：`InstitutionView.vue:270 currentPeriod()` 用 `new Date()` 推导 `YYYY-MM`，页面**没有周期选择器**；种子只有 `2026-09`。只要本机月份 ≠ 2026-09，资源池卡片变「暂无资源池数据」，且分配一律报"…资源池尚未交付，**请先执行入驻第 1 步**"——把**系统状态**问题说成**操作员步骤**问题。
> 补充：后端 `allocateOrgQuota` 已有 `Vals.nowPeriod()` 兜底，但前端**总是**显式传浏览器周期，兜底永不生效。

**处理建议**（按性价比排序）
1. 弹窗内显示 `pool.allocatableTokens`，`quotaTokens > 剩余 + 本机构现值` 时**前置禁用保存**并给出明确文案（避免"填了才被拒"）。
2. 统计期提升为**页面级选择器**，默认值改为**服务端当前周期**（新增 `GET /tenant/current-period`，或让 `?period=` 缺省由后端裁决）。
3. 重配演示数据比例（当前 5,000,000 里已占 94%），给"分配成功"留出可见余量。
4. 「资源池尚未交付」文案改为**状态陈述 + 双动作**：`周期 2026-10 尚未交付资源池` + 直达「池扩容 / 调参」按钮。

## 2. 权限可见性 + 「选择机构后页面和数据随之改变」

**现状**：右上角 AI 助手左侧的控件是**租户**选择器，且只对平台管理员渲染
（`MainLayout.vue:10-28`：`v-if="showTenantMenu && canSwitchTenant"`；`tenantState.canSwitch` 对租户管理员恒为 false → 只显示一个 tag）。

**它的作用范围**：`tenantScope.ts:35,116-125` 的请求拦截器**只对 URL 以 `/tenant/` 开头**的请求附 `?tenantId=`。

| 页面 | 请求前缀 | 是否随顶部选择变化 |
|---|---|---|
| 机构管理 / 入驻进度 / 资源授权 / 费用分摊 | `/tenant/*` | ✅ 会 |
| 组织与部门 | `/org/*` | ❌ 不会 |
| 人员管理 | `/admin/personnel` | ❌ 不会 |
| 数字员工 / 专家配置 / 知识库 / 经营数据 | 其他 | ❌ 不会 |

对**平台管理员**更明显：`OrgAdminController.institutions()` → `guard.selectableInstitutions()`，其注释明写「平台管理员返回**全局全部启用机构**（只读运维视角）」——所以换租户后该页机构选择器**仍是跨租户全集**，即用户说的"机构未改变"。

❌ **用户三点要求逐项裁定**
- 「平台管理员只能看到不同租户」→ ✅ 已具备（顶部租户选择器）。
- 「租户管理员只能看到自己下级的单位」→ ⚠️ 顶部无机构级切换器；租户管理员需进「组织与部门」页内用机构选择器。
- 「选择机构后页面内容和数据随所选机构动态改变」→ **未实现**：控件是租户级，且不入 `/org/*`。

**处理建议**
1. **先定语义**：顶部选择器到底是"租户"还是"机构"？建议做成**两级联动**（平台管理员选租户→再选机构；租户管理员只有机构下拉）。
2. **要落地"随之改变"，就必须有请求注入点**：把当前机构提升为全局态（与 `tenantState` 同构的 `institutionState`），并把注入从"仅 `/tenant/`"扩展为**声明式**——即由各接口显式声明"我吃 tenantId / institutionId"，而不是靠 URL 前缀猜。
3. 若短期内不做全站联动，就把顶部控件文案与 tooltip 写实（"当前操作租户"），并**不要**在其它页面承诺"随选择变化"（铁律 #1：展示必须与事实同源）。

## 3. 组织与部门：切换租户机构未变 + 员工账号不显示

**(a) 切换租户机构未变** —— 同 §2：`/org/institutions` 不吃 `tenantId`，平台管理员拿到的是跨租户全集。租户管理员 `canSwitch=false`，顶部本无切换器。

**(b) 员工账号不显示** —— ✅ **确认缺陷**

```
OrgTreeService.listMembers()  :275-312  →  out.put("items", rows)   // rows 是 List<OrgMember> 实体
OrgMember.java                          →  字段: id/tenantId/institutionId/departmentId/userId/

OrgStructureView.vue:116                →  <el-table-column prop="username" label="账号" />  ⇒ 恒为空
```

**对照反例**：`PersonnelService`（`/admin/personnel`）用 SQL `SELECT u.id, u.username, u.nickname, …`（:88）并显式 `row.put("username", …)`（:303-304）→ 人员管理页账号正常。
⇒ 两个"人名单"页面口径不一致（铁律 #1 的典型形态）。

**处理建议**：`listMembers` 按 `user_id` **批量 IN 查一次 `sys_user`** 补 `username`（勿逐行查，避免 N+1），与 `PersonnelService` 同源；并抽一个共用的"成员视图组装"函数，杜绝第三处再分叉。

## 6. 专家配置：可见范围选「指定机构/部门/用户」应出现对应内容

✅➕ **确认：这是能力缺口，不只是 UI 缺口**

**前端**（`ExpertConfigView.vue`）：下拉有 5 个选项（:75-83 `ALL/TENANT/INSTITUTION/DEPT/USER`），但**模板里没有任何 `v-if` 分支**去渲染机构/部门/人员选择器；`form` 只承载一个字符串 `visibleScope`（:361 回填、:381 保存、:506 默认 `'ALL'`）。

**后端**：
- 能存取：`ExpertSettings.visibleScope`（`ExpertSettings.java:21`，解析见 :87），`ExpertConfigService` 也回吐（:345）；
- **但过滤逻辑没有"目标清单"概念** —— `ExpertConfigController.visible()`（:538-552）只做一件事：

```java
case "INSTITUTION" -> user.getInstitutionId();
case "DEPT"        -> user.getDepartmentId();
case "USER"        -> user.getUserId();
...
return v != null && v > 0;      // 只判断"当前查看者有没有该维度归属"
```

⇒ `INSTITUTION/DEPT/USER` 的**实际语义退化为**"凡有该维度归属的人都可见"，与"仅对指定对象可见"完全不同。

**DB 实证**：`expert_config.config_json` 现存行只含
`{topK, model, enabled, threshold, temperature, systemPrompt, retrievalMode, knowledgeScope}` —— **无 `visibleScope`、更无目标清单**。

**处理建议（全链路）**
1. 数据：`api_expert.visible_scope` 已有；**目标清单**建议写入 `config_json` 的 `visibleInstitutionIds / visibleDeptIds / visibleUserIds`（或复用 `expert_config(scope_type, scope_id)` 一行一目标存多行）。
2. 后端：`visible()` 改为**目标集合命中判定**（当前用户所属机构/部门/自身 id ∈ 目标集合），集合为空时**明确不通过**（而不是退化成"全员可见"）。
3. 前端：按 `form.visibleScope` 渲染 **机构树 / 部门树 / 人员选择器**，并把选中项随表单一起提交。
4. 断言（铁律 #5）：新增可配置维度 ⇒ 必须为"指定机构 A"配 A 可见 / 配 B 可见 两种组合各补断言。

## 7. 编辑员工保存失败（提示"姓名与登录账号必填"）

✅ **确认缺陷 —— 与 §3(b) 同一根因**

```
OrgStructureView.vue:404  openMemberDlg(row) { memberForm.value = row ? { ...row } : {} }
OrgStructureView.vue:410  if (!memberForm.value.name || !memberForm.value.username) {
                              ElMessage.warning('姓名与登录账号必填'); return }
```

`row` 来自 `listMembers`，**没有 `username`** ⇒ 守卫恒为真 ⇒ **任何员工都编辑不了**，且报的是"必填"这种**归因错误的提示**（明明是后端没给字段）。

**附加**：表单里「登录账号」在编辑态被 `:disabled="!!memberForm.id"`（:178）禁用 —— 意图是"账号不可改"，但当前**连值都没有**，用户看到的是一个空的禁用框。

**处理建议**
1. 后端补 `username`（同 §3）。
2. 前端守卫按模式分叉：**编辑态只校验名字**（账号由后端保持原值），新增态才要求账号。
3. 禁用框要显示**真实账号**（有值且禁用），不要显示空占位"不存在时自动开通"（那句话只适用于新增态）。

## 8. 用户端：机构管理员登录后首页与「我的」数据重复

3. 「AI 会话」与「本月会话」**只保留一处**（建议留在组织卡，因为个人会话数对机构管理员无决策价值），并统一命名为"本月会话"。
4. 两张卡都已带范围徽标与数据源注脚（`scopeLabel` / `stat-src`），保留即可，无需新组件。

### S3 ⚠️ "随顶部选择器变化"的承诺只有 4 个页面兑现（与 #2 同源）

### S4 ✅ 统计期由**前端时钟**推导的页面不止一处（与 #1 同源）
