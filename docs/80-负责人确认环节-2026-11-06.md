# 80 · 去掉输入栏「指定负责人」，改为提交前的「负责人确认」环节（2026-11-06）

> 用户诉求（原话）：
> 「去掉输入框里固定指定负责人的入口和配置。审批流程调整为：用户填写完表单发起审批后，
> 再进入负责人确认环节，提供两种选择——默认负责人（沿用原本配置的流程）或指定负责人
> （支持选择多个），由用户自行决定。最终返回的数据中需包含数据流情况和处理人信息，
> 并保证结构清晰、字段完整。」
>
> 交付：入口已删、环节已立、契约已定。验收 `scripts/_verify_handler_confirm.py` **21 项 21 通过**。

## 1. 两处决策（已与用户确认）

| 问题 | 选择 |
|---|---|
| 指定多个负责人时怎么协作 | **依次审批**：按选择顺序 1→2 串行，前一人通过才轮到下一人 |
| 「负责人确认」覆盖哪些入口 | **所有审批类表单**：对话内表单卡片 + OA 独立请假表单 |

## 2. 入口：删掉「填表前先定人」的按钮

原先 `#oaAssignBtn`（输入栏常驻按钮）+ `#oaAssignBar`（已选 chip）+ 浮层选择器 + 澄清卡自动落定
（`window.oaAutoAnswerAssignee` 桥接），一共 4 段代码。

问题不在实现而在**顺序**：它要求用户**打开表单之前**就决定交给谁，且只能单选。
现在整段删除（连 CSS 的 `.assign-bar / .assign-pop` 一并清掉，`grep` 残留 0）。

## 3. 环节：填写 → 核对 → **确认负责人** → 提交 → 回执

```
表单填完 ─►「请核对以下信息」（原有）
        └►「确认提交」─► ★ 确认负责人（新增，底部弹层）
                          ├ 默认负责人：沿用 approval_flow_def 配置的节点（不传任何负责人字段）
                          └ 指定负责人（可多选）：挑 1..N 人，**顺序即审批顺序**
                        └► 真提交（带 assigneeUserIds）─► 回执（含处理人 + 数据流）
```

- 只有「一提交就走审批」的表单才弹这一步：`GET /v1/forms/launchable?policy=APPROVAL` 拉一次按 code 缓存，
  台账类（LEDGER）/ 续跑类（RESUME）表单不弹，不给用户多一步。
- 取消 = **不提交**：留在核对面板上，不用重填。
- 候选来自 `GET /v1/org/members`（与通讯录同源、排除本人），与后端「本机构在职成员」口径一致。

## 4. 后端：多选负责人怎么落节点

`ApprovalFlowService.SubmitReq` 增 `List<Long> assigneeUserIds`（保留 12/13 参兼容构造器，
其余 12 个调用点行为逐字不变）。`applyAssignees` 四条口径：

1. **自审拦截**：指定人含申请人 ⇒ 400（自己批自己无意义，且会占住节点）；
2. **顺序即审批顺序**：每人一条 `TYPE_SPECIFIC` + `MODE_SINGLE`，seq 1..N；
3. **无配置流 ⇒ 只剩指定人**（不追加企业管理员兜底，否则用户要等一个他没同意过的人）；
4. **有配置流 ⇒ 指定人插在最前**，原节点整体后移 N 位；原节点里与指定人**重复的整体剔除**，
   剔除后若一个不剩，则指定人处理完即终态。

校验统一收在 `ApprovalFlowService#validateAssignees`（本机构在职 + 非本人），
请假与表单两条链共用一处，报错文案一致。

## 5. 返回契约（用户要的「数据流 + 处理人」）

`POST /v1/leave/requests`、`POST /v1/forms/{code}/submit` 的 data 层新增两块：

```jsonc
"handlers": {                    // 谁在处理
  "mode": "SPECIFIED",           // DEFAULT | SPECIFIED
  "modeLabel": "指定负责人（依次审批）",
  "specified": [{"userId":3376,"name":"刘洋","seq":1},
                {"userId":3481,"name":"张大大","seq":2}],
  "specifiedCount": 2,
  "current": {"userId":3376,"name":"刘洋","seq":1,
              "approverType":"SPECIFIC","approverTypeLabel":"指定审批人"},
  "cc": [{"userId":3240,"name":"测试"}],
  "nodeCount": 3
},
"dataFlow": {                    // 单据怎么流
  "orderId": 40, "bizType": "NOTICE_PUBLISH", "title": "通知公告",
  "applicant": {"userId":3240,"name":"测试"},
  "submittedAt": "2026-11-06T18:20:11", "status": "PENDING", "statusLabel": "审批中",
  "nodeCount": 3, "currentSeq": 1, "currentTaskId": 1234,
  "steps": [{
    "seq": 1, "taskId": 1234,
    "approverType": "SPECIFIC", "approverTypeLabel": "指定审批人",
    "source": "SPECIFIED",       // SPECIFIED=用户指定 / FLOW=后台配置
    "approver": {"userId":3376,"name":"刘洋"},
    "nodeMode": "single", "status": "PENDING", "statusLabel": "待审批",
    "decidedAt": null, "note": null, "skipReason": null, "current": true
  }]
}
```

设计取舍：
- **中文标签与英文码双写**（`status` + `statusLabel`、`mode` + `modeLabel`、
  `approverType` + `approverTypeLabel`）：前端不必自己维护一份映射，也不会与后端文案漂移。
- **`source` 与 `current` 是派生字段**，只在回执里给：用户最关心「谁是我指定的」「现在卡在谁那儿」。
- **`timeline` 一行不改**：既有的待办 / 我的申请详情页读它，本次只新增不修改。

## 8. 四处自纠（都记在脚本注释里，避免下次再踩）

1. **接口路径想当然**：请假提交是 `POST /v1/leave/requests`，不是 `/v1/workflow/leave/requests`
   （`workflow` 只有 tasks/mine/defs/timeline）。首跑 10 条全红全是 404。
2. **日期落在周末**：假种单位是 WORKDAY，`today+1` 撞上周六 ⇒ 400「申请天数为 0（所选区间可能
   全部为休息日）」。判据改成「取下一个工作日」。
3. **假种吃掉额度导致二次假红**：首次跑选了占额度的 COMP（5 天），每跑一次就压 1 天在途，
   第二次跑直接「余额不足」。改为优先 `quotaDaysPerYear=0`（不占额度）的假种，
   并在清理段按剩余 PENDING 单重算 `pending_days`。
4. **弹层淡入动画截到半透明**：`opacity` 过渡 160ms，截图/判读赶在动画中间会看到「整层发灰、
   底下 tabbar 透出来」。开面板后固定等 500ms 再截图。
