## 二、修正清单（根因 → 修法 → 判据）

### 2.1 数据脚本工具：数据里有一个撇号就整条工具失败

- **场景**：`aios_ai/tools/sandbox.py::run_script` 把工具返回的数据（邮件正文、KB 片段）送进子进程。
  旧实现把 data 拼进源码：`DATA = json.loads(r'''<data>''')`，并先做 `replace("'", "\\'")`。
- **根因**：`'` 被改成 `\'`，而外层是 **raw 字符串** ⇒ 字面量里原样留下 `\'`
  ⇒ `json.loads` 抛 `Invalid \escape`。数据里只要有一个撇号（`don't` / `it's` / 英文正文常见）
  整条工具就废，报错还长得像「脚本语法错误」。
- **修法**：data 改走 **stdin**（`input=data_json`），源码里只剩常量，转义层彻底消失；
  同时显式 `encoding="utf-8"`（原来吃 locale，Windows 上是 cp936）。
- **判据**：`scripts/_check_sandbox_injection.py` **21/21**。C1 直接**实跑旧实现**复现
  `Invalid \escape`，另一条对照证明「纯反斜杠旧实现本来就能过」—— 结论不外扩。

### 2.2 企微 CLI 子进程：超时/取消后变孤儿、泄漏 fd

- **场景**：`mcp-hub/.../wecom_cli/runner.py`。企微 CLI 是长驻原生进程，每次调用都是一个子进程。
- **根因**三条：① `wait_for` 超时后只 `kill()`、**没 await `wait()`** ⇒ 管道传输层不关，漏 fd；
  ② 没接 `CancelledError`：客户端断开时 FastAPI 会 cancel 协程 ⇒ **子进程成孤儿继续跑**；
  ③ `auth.py` 三处 `proc.kill()` 同样没回收（容器里 uvicorn 是 PID 1，没人替你收尾）。
- **修法**：抽出 `_communicate()` / `_exec()` 统一收口 —— 超时、取消、任何异常都走
  `finally: kill → await shield(wait())`；`auth.py` 抽出 `_reap()` 替换所有裸 kill。
- **判据**：`scripts/_check_subprocess_reap.py` **26/26**。R2 是真的 cancel 一个真子进程后
  查 `/proc/<pid>` 不存在；C1 把 `finally` 拆掉后谓词必须转假（证明判据非恒真）。

### 2.3 秒数型环境变量写错：容器起不来且只给裸 traceback

- **根因**：`TIMEOUT = float(os.environ.get("AIOS_WECOM_CLI_TIMEOUT", "30"))` 在 **import 阶段**执行。
  `.env` 里写成 `30s` 或多打引号 ⇒ `ValueError: could not convert string to float` ⇒ 容器起不来，
  日志里只有一个跟业务毫无关系的栈。
- **修法**：`_env_seconds()` —— 仍 fail-fast（配置错就该拒绝启动），但异常里写明
  「哪个键、当前值、该写成什么样的数字」。
- **判据**：同上哨兵 R6（非数字 / 0 / 正常 / 未设置，四种都验）。

### 2.4 agent 漏声明两个「靠上游传递依赖活着」的包

- **根因**：`tools/client.py` 用 `langchain_core`、`speech/router.py` 用 `starlette`，
  两者都**没在 `pyproject.toml` 声明**，分别由 langchain-mcp-adapters / fastapi 间接带进来。
  这与历史上 langgraph 漏声明是同款事故：本地 `.venv` 手工装过所以能跑，镜像
  `pip install .` 只装清单 ⇒ 构建期不报错，**跑到那条路径才 ModuleNotFoundError**。
- **修法**：显式加 `langchain-core>=1.0,<2`、`starlette>=0.37`。
- **判据**：`scripts/_check_deps_consistency.py` R6（AST 全量扫 import，对照清单）。

### 2.5 本地 venv 自身是坏的（"我这能跑"这句话不成立）

- **实测**：`av` 的 `Version` 是 `None`（RECORD/METADATA 被中断的卸载流程清空，
  `pip install` 直接报 `uninstall-no-record-file`）；`pip check` 报
  `py-key-value-aio 0.4.6 要 beartype>=0.20.0，实际 0.19.0`；site-packages 里还有
  `~cp-2.3.0.dist-info` / `~ebsockets` 两个 pip 中断残留（`~` 前缀 ⇒ `pip` 每次都要告警）。
- **修法**：清残留 → `--ignore-installed --no-deps` 重装 `av==18.1.0` → 升 `beartype`。
  现在 `pip check` 干净、`av` 元数据可解析。
- **判据**：同上哨兵 R8/R9/R10/R11（版本元数据可解析、pip check 干净、无 `~` 残留、
  安装版本满足声明区间）。

### 2.8 企微「未读邮件」必失败：布尔开关被拼成带值

- **场景**：用户问「我企业微信里有什么未读消息」，助手回「调用企业微信邮箱搜索工具时
  出现了参数错误」，重试两次后放弃，并建议用户自己去后台看。
- **实测**（用真 CLI 跑出来的，不是推测）：
  ```
  wecom-cli mail search ... --only-unread true
  error: unexpected argument 'true' found
  ```
  `--only-unread` 在官方 CLI 里是**布尔开关（不带值）**，和 `--has-attachments`
  `--only-subject` `--has-star` 一样。而 `server.py` 里拼成了 `["--only-unread", "true"]`。
- **为什么难定位**：① 只在 `onlyUnread=true` 时触发 ⇒ 问「未读」必炸、问别的全好；
  ② help 文本写的是「true-仅未读 false-都返回」，看起来像要传值；③ 错误被包成工具错误
  交给模型，模型只能转述成「参数错误」⇒ 现象像是「模型不会用工具」。
- **修法**：把参数向量抽成纯函数 `mcp_hub/wecom_cli/argv.py`（零依赖、可离线测），
  `server.py` 一律调用它；顺带给工具失败加**日志**（原先 `_err()` 返回后什么都不记，
  生产上只能靠模型转述猜原因）。
- **判据**：`scripts/_check_wecom_cli_argv.py` **24/24** —— 拿真 CLI 的 `--help` 当事实源，
  逐个核对 4 个命令的「flag 拼没拼错 / 该带值的带没带 / 布尔开关有没有多塞值」，
  并用 `--dry-run` 做端到端。C1 把 `--only-unread` 改回带值 ⇒ 真 CLI 立刻回
  `unexpected argument`（判据非恒真）。
- **顺带核对**：`auth show --status`、`auth init --noninteractive --no-browser
  --output-qrcode <PATH>` 与 help 一致（人工核对，未纳入哨兵）。

## 三、保障生产可靠性的具体措施

1. **重试的边界写死**：只在「一个 delta 都还没吐给用户」时重试上游；已经推出去的正文不再重发，
   否则同一段话会出现两次。重试次数可配（`AIOS_MODEL_RETRY_ATTEMPTS`，默认 3，clamp 1~5）。
2. **两条错误通道分开**：上游失败 → `MODEL_UPSTREAM_ERROR` + 人话 `user_message`；
   本地异常 → `MODEL_STREAM_ERROR` + 异常类名。原始 JSON 只进 `detail`（截 200 字），
   不再直接怼到用户脸上。
3. **资源回收不依赖 GC**：子进程所有退出路径（正常/超时/取消/异常）都显式 kill + wait，
   `wait` 用 `shield` 包住以便取消态下也能等到。
4. **配置 fail-fast 且可诊断**：错就拒绝启动，但异常文本必须含「键名 + 当前值 + 正确写法」。
5. **每个判据都要有负向自检**：新哨兵一律带 `C1` 段，故意把被修的点改回去，证明会转红。
   本轮 5 个哨兵共 110 项，全部含负向段。
6. **验收不信文案**：连接器是否可用，以 DB `connector_connection.status` + `/manifest` 为准，
   不看模型自己说「已连接」（MiniMax 会零工具调用就声称已发送）。
7. **诊断要回显路径**：`/api/v1/wecom_cli/status` 增加 `cli` 字段（`probe()` 不抛异常），
   让「CLI 没装」与「还没扫码」在一条 curl 里就能区分。

## 五、落盘归位：所有项目文件都放仓库里（严禁 /opt）

### 5.1 为什么这是一条硬规矩（不是洁癖）

- `/opt` 是**系统保留目录**：属主、容量配额、备份与换机迁移都不受本项目控制；
- `/opt` 下由 root 建目录，而 `mcp-hub` 以 **uid 10001** 运行 ⇒ 写凭据直接
  `PermissionError: '/app/data'`（2026-10-31 生产实测，症状是连接器**全线**不可用）；
- 换机器/重装时只搬 git 仓库，仓库外的文件**一定漏搬**，现象是「扫码 404」「语音 503」，
  而代码和配置看起来全对；
- `git clean -xdf` / `rsync --delete` 会连带删掉它们，且没有备份。

### 5.2 仓库内 `/opt` 引用已清零

| 文件 | 改法 |
|---|---|
| `deploy/docker-compose.yml` | `AIOS_WECOM_CLI_BIN` 默认 `/data/wecom-cli-bin/wecom-cli`，宿主目录挂到 `/data/wecom-cli-bin`（容器内不再出现 `/opt`） |
| `mcp-hub/.../runner.py` | 报错文案同步改（原来教用户「挂到容器 /opt/wecom-cli」） |
| `deploy/.env.production` | CLI / 凭据 / ASR 三处示例路径改为**仓库内**：`<repo>/data/wecom-cli-bin`、`<repo>/data/wecom-cli`、`<repo>/agent/.models` |
| `deploy/k8s/20-agent.yaml` + `k8s/README.md` | `hostPath: /data/aioa/AIOA/agent/.models`（仓库内） |
| `deploy/ops/host-check.sh` / `offline-images.sh` / `set-secrets.py` | 示例路径改为 `$REPO` 口径；offline-images 新增 `TARGET_REPO`（可用 `AIOS_REPO_DIR` 覆盖） |
| `deploy/生产部署手册.md` | 统一用 `$REPO`，并置顶写明「一律放项目目录内，不要放 /opt」及原因 |
| `deploy/GITEE-两套环境配置指南.md` | `cd /data/aioa/AIOA/deploy` |

> `docs/33` 里那句 `/opt/aios/webroot` 是**历史计划的引述**，保留原文不改 ——
> 改它会篡改当初的决策记录。

### 5.3 生产机上还要你跑一次（脚本默认只读）

```bash
cd /data/aioa/AIOA
bash deploy/ops/move-into-repo.sh              # 只体检，打印迁移计划
bash deploy/ops/move-into-repo.sh --apply      # 真的搬（先自动备份 deploy/.env）
```

它只处理三类已知内容（企微 CLI、扫码凭据、ASR 模型），并遵守：
目标已存在且非空 ⇒ **不覆盖**，只报告；改 `.env` 用**按行重写**（不做模式替换，
因为口令里含 `&` 会被 sed 悄悄改坏，见 `set-secrets.py` 的教训）；
凭据目录搬完自动 `chown -R 10001:10001`；**不删源目录**（数据比整齐重要）。

搬完：

## 七、仍需人工完成 / 已知风险

1. **生产机跑 `move-into-repo.sh --apply`**（§5.3），否则 CLI 仍在仓库外。
2. **两把钥匙一动就解不开**：`AIOS_CONNECTOR_SECRET_KEY` 改动会让已存密文全部无法解密
   （`WECOM_CONNECTOR_KEY` 是 hub 侧、`aios.gitee.token-enc-key` 是 gitee 专用，三者独立）。
   改密钥 = 所有连接器重新扫码，务必先备份再改。
3. **`agent` 依赖仍是区间约束**（`>=`）。本轮没引入 lock/constraints 文件：镜像构建无法在
   开发机上验证，硬钉版本可能让生产 `docker compose build` 直接失败 —— 违反「不为整齐引入
   未验证改动」。当前用哨兵把「声明 vs 实际」的偏差**显性化**（R8/R11），是更稳的一步；
   要真正可复现构建，下一步应在**目标机**上 `pip freeze` 生成 constraints 再回填。
4. **GitHub CI 仍全红**，未定位（与本地哨兵无关，本地 110 项全绿）。
5. **两个 token 建议吊销**：Gitea PAT、ngrok authtoken（都曾出现在会话里）。
