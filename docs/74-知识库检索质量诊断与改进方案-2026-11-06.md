# 知识库「AI 总结不如网上公开资料」诊断与改进方案

> 现象：用户上传 5 个非遗名录 Excel（区级/市级/省级/国家级/联合国级），问「帮我统计下四川省的省级非遗项目有多少个?」，
> 数字人回答 **「知识库暂未收录 —— 已检索内部知识库，返回 0 条」**；而另一个工具对同一问题给出了
> 「1241 项、第六批 1132 项、第七批新增 68 项 + 扩展 39 项、国家级 153 项、传承人 1420 人」这类逐条可核的答案。
>
> 本文只回答三件事：**根因（带实测数字）→ 可执行方案（文件/参数级）→ 预期效果与验证方式**。
> 不用「模型不够强」搪塞 —— 实测证明，把同一份名录交给 GPT-4 级模型，在**当前切片+检索形态**下同样答不出来。

---

## 0. 结论先行

| # | 根因 | 实测/代码证据 | 影响 |
|---|---|---|---|
| 1 | **表格按行切片，列名与表名在数据块里丢失** | 500 行表切出 503 块，**含列名的块只有 1/503**（`KbFileParser.java:167,184` + `KbService.java:285,290`） | 模型看到 `\| 1 \| 川剧 \| 传统技艺 \| 四川省成都市 \|`，不知道哪列是"序号"、哪列是"批次" |
| 2 | **topK=5 面对「统计/计数」类问题结构上不可能答对** | `nodes.py:394` `top_k = es.get("topK") or 5`；实测 **top5 只覆盖 5/500 行 = 1.0%** | 让它数"共有多少条"，等于给 5 行明细问总数 |
| 3 | **混合检索退化为单路：向量腿 0 命中** | `EmbeddingProvider.java:68` local = FNV 哈希 char2gram；实测 **cos 最高 0.157、中位 0.080，过 0.5 阈值的切片 0/503** | `hybrid` 实际只有关键词一路在工作，向量库白建 |
| 4 | **关键词打分失去区分度，排序退化成"谁在前面"** | `KeywordScorer.java:52` 覆盖率 × `(1+ln(1+hit))`，类注释自承**无 IDF、无长度归一**；实测 **501/503 块同分 0.2209** | top5 永远 = 表格**前 5 行**，与问题无关 |
| 5 | **查询整句直查 + 提示词未告知"命中的是抽样"** | `retrieval.py:85` `{"keyword": question}`；`builder.py:158-176` 只拼 docName+content | 模型把"我只看过 5 行"误判成"库里没有"，于是答"暂未收录" |

**一句话**：不是模型不懂非遗，是**它根本没看到那张表** —— 只看到 5 行没有列名的碎行，且系统告诉它"这是知识库参考"、没说"这是全表的 1%"。

## 1. 逐项根因与方案

### 根因 1：表格被切成「一行一块」，列名只存在于一块里

**代码事实**

- `server/aios-resource/src/main/java/cn/aios/resource/service/KbFileParser.java:167` 先把 `### Sheet1` 写**单独一行**；
  `:184` 每个数据行写 `"| ... |\n"` —— **每行一个换行符**。
- `server/aios-resource/src/main/java/cn/aios/resource/service/KbService.java:285`
  `for (String para : content.split("\\r?\\n"))`；`:290` `if (p.length() <= size) out.add(p)` ——
  **单段 ≤500 字就直接成块**，不再合并。表格行普遍 30–60 字，于是**每一行 = 一个切片**。

**实测**（`.workbuddy/tmp/sim_kb_retrieval.py`，用线上同款算法复现）

```
表内 500 条数据行 -> 切出 503 个切片
第一块        : ### Sheet1                    ← 只有 sheet 名，无列名无表名含义
典型数据块    : | 1 | 川剧 | 传统技艺 | 四川省成都市 | 第六批 |
含列名的块数  : 1 / 503
```

`### Sheet1` 这种块**零信息量**却占一个切片位；而 500 个数据块**全部不带列名**。

**方案（P0，改 2 个文件）**

1. 新增 `server/aios-resource/src/main/java/cn/aios/resource/service/TableChunker.java`：
   - 输入：`docName` + sheet 名 + 表头行 + 数据行；
   - 输出：每块 = `《docName》/sheet 名｜列: 序号/项目名称/类别/申报地区或单位/批次｜` + **连续 N 行**（N 使块长 ≤ 480 字，通常 8–12 行）；
   - **表头 + 对齐行永不单独成块**（并入第一块）。
2. `KbService.split()` 增加前置分支：`if (p.startsWith("|"))` 走 `TableChunker`，其余仍走段落切分。
3. `KbFileParser.readSheet()` 不再逐行 `append('\n')`，改为返回结构化 `List<Row>` 交给 `TableChunker`
   （保持向后兼容：`parse()` 签名不变，内部拼装）。

**预期效果**：含列名块 1/503 → **100%**；向量腿 cos 上限 0.157 → **0.272**（实测，仅加列名，未换模型）；
模型可复述"这是名录表，列为序号/项目名称/类别/申报地区/批次"。

**验证**：`scripts/_check_kb_table_chunk.py` —— 断言 ①每个含 `|` 的切片前 200 字内含列名、②无「只含 sheet 名」的切片、
③块长 ≤500、④行不丢失（切片行数总和 = 表格行数）。

### 根因 2：topK=5 对「聚合类问题」是结构性不可能

**代码事实**：`agent/aios_ai/graph/nodes.py:394` `top_k = int(es.get("topK") or 5)`；
`MysqlKnowledgeStore.java:150-160` 按融合分降序**硬截断** topK。系统里**没有任何聚合/统计能力**。

**实测**

```
最终 top5（模型实际能看到的全部内容）
  | 1 | 川剧 | 传统技艺 | 四川省成都市 | 第六批 |
  | 2 | 蜀绣 | ...
  | 3 | 绵竹木版年画 | ...
  | 4 | 自贡灯会 | ...
  | 5 | 成都漆艺 | ...
top5 里含「合计/总数/共计」字样的切片：0 个
top5 覆盖数据行：5 / 500 行（1.0%）
```

即使检索**完美**（每块都带列名、都排对），5 块也答不出"共有多少条"。这是 RAG 对聚合类问题的固有失效，
不是调参能解决的 —— **必须换形态**。

**方案（P0，三件套）**

1. **入库时生成文档级统计切片**（新增 `StatsChunker`，与 TableChunker 同批产出）：
   ```
   《2026.2省级非遗项目名录》统计摘要｜数据行合计：1241 条｜
   按类别：传统技艺 412 条、民俗 233 条…｜按批次：第六批 1132 条、第七批 107 条…｜
   按申报地区：成都市 138 条…
   ```
   `kb_chunk` 加 `kind` 列（`TEXT/ROW/STATS`，V108 迁移）。
2. **聚合意图时强制注入统计切片**（不能只靠分数）：实测统计块与行块**同分**（0.01639 vs 0.01613），
   仅靠排序偶然拿 top1 —— 不可靠。改为：`nodes.py` 在 `pre_retrieve` 前做一次意图判定
   （`多少|几个|总数|合计|统计|汇总|排名|占比|各|分别`），命中则**额外**把命中文档的 `kind=STATS`
   切片直接塞进参考块（不占 topK 名额）。
3. **新增表格查询工具 `kb_table_query`**（第 19 个工具，`aios-chat` 下 `KbTableQueryToolHandler`）：
   入参 `{docName?, sheet?, groupBy?, where?, agg:"count|sum"}` → 走新的 `kb_row` 表做 SQL 聚合，返回 JSON。
   配套：`kb_document` 落 **结构化行**（`kb_row(doc_id, sheet, row_no, col_json)`），
   由 `KbFileParser` 解析 xlsx 时直出，不依赖原件（**注意**：`KbController.java:212-214` 现在只存解析文本、
   原件字节用完即弃，所以必须入库时抽行，事后无法补）。

**预期效果**：`1241 项 / 1132 项 / 107 项` 这类问题一次命中；`top5 覆盖率 1%` 不再是瓶颈（统计切片覆盖 100% 行）。

**验证**：`scripts/_verify_kb_aggregation.py` —— 造 500 行名录问"有多少个"，断言 ①回答含正确数字
②数字与 **pymysql 独立 `SELECT COUNT(*)`** 一致（不同源，铁律 7/12）③引用出现 `docName`
④**反向**：插一行再问，数字 +1（防硬编码/记忆化）。

### 根因 3：向量腿用的是「哈希词频」，与关键词腿同源，且被 0.5 阈值全部拦掉

**代码事实**

- `EmbeddingProvider.java:68-110` `LocalEmbeddingProvider`：FNV 哈希 char2gram 词频 → 256 维 L2 归一。
  类注释已写明：`bge-small-zh：预留扩展点。当前阶段不引入模型下载与推理依赖`。
  → **它本质是词袋，不是语义**；哈希碰撞还会引入噪声。
- `MysqlKnowledgeStore.java:119-122` `if (s >= threshold) vecScore.put(...)`；
  `retrieval.py:23` `DEFAULT_KB_THRESHOLD = 0.5`。
- `application.yml:136` `embedding-provider: ${AIOS_KB_EMBEDDING_PROVIDER:local}`（默认 local）。

**实测**

```
向量腿：cosine 最高 0.1569，中位 0.0795，过阈值 0.5 的切片 0/503
```

**0/503**。即 `mode=hybrid` 时向量一路**一条都没进**，RRF 的第二个列表是空的 —— 双路召回实际是单路。

**并且：降阈值不是解法**（实测反证）

```
threshold=0.0 -> 过阈 503/503，top1 变成「| 17 | 广安竹丝画帘 | ...」
                 （仍然与"有多少个"毫无关系，只是噪声换了个位置）
```

因为向量腿的排序信号与关键词腿**高度同源**，放开只会把噪声放大 —— 这也是为什么"调阈值"试了没效果。

**方案（P0）**

1. 接真语义向量：`aios.kb.embedding-provider=http`，指向已有 ollama/vLLM 的 `bge-m3` 或 `bge-small-zh-v1.5`
   （`application.yml:136-139` 已预留 `embedding.*` 与 `reembed-on-start`）。
2. **换 provider 后必须 `reembed-on-start=true` 跑一次全量重算** —— 否则旧 256 维向量与新 query 向量
   余弦恒为 0，表现为「检索不报错但永不命中」（配置注释里已警告，容易忽略）。
3. **阈值按新分布重标**：先用 `scripts/_check_kb_embedding_calibration.py` 跑 50 组 query×chunk 打印
   cosine 直方图，取**同分布 P90** 作阈值（bge 类模型相关文本通常 0.5–0.7，0.5 是合理的，但对 local 是灾难）。

**预期效果**：cos 中位 0.080 → **≥0.45**；过阈率 0/503 → **≥30%**；向量腿真正贡献语义召回
（同义改写能召回，例如"四川省级非遗有几项" ↔ "四川省省级非遗项目数量"）。

**验证**：`_check_kb_embedding_calibration.py` 断言 ①`kb_chunk.embedding_dims` 全部 = 新维度
②`embedding_provider` 无残留 local ③三组同义改写查询的 top5 **交集 ≥ 2**（语义召回应有的稳定性）。

### 根因 4：关键词打分无 IDF、无长度归一 ⇒ 同分塌陷 ⇒ 排序 = 切片顺序

**代码事实**：`KeywordScorer.java:52`
```java
out.put(c.getId(), (double) hit / qgrams.size() * (1.0 + Math.log1p(hit)));
```
无 IDF（"项目"这种到处都有的词与"非遗"同权）、无文档长度归一 ⇒ **同构的行分数完全相同**。

**实测**

```
关键词腿：命中 501/503，最高分 0.2209 —— 而且 501 个块几乎全在 0.22 附近
最终 top5 = 第 1..5 行（RRF 同分时按切片顺序，即 chunk_index 升序）
```

**方案（P1）**

1. `KeywordScorer` 换成真 BM25（`k1=1.2, b=0.75`）：加 IDF（用 `kb_chunk` 全量 DF 统计）与长度归一。
   改动面小：`score(chunks, query)` 内部先算 DF/avgLen，签名不变。
2. **每文档贡献配额**：`MysqlKnowledgeStore.search()` 在组装 topK 时限制单文档最多 `ceil(topK/2)` 块，
   防止一个 1241 行的大表把其它 4 份名录全部挤出 top5（当前实现必然发生）。

**预期效果**：不同数据行分差从 ~0 变为可区分；「同时问 5 张表」时每张表都能被看到；
单纯调阈值/调 topK 都做不到这一点。

**验证**：`_check_kb_bm25_ranking.py` —— 构造"1 张 500 行大表 + 4 份小文档"，断言 top5 至少含 3 份不同文档；
断言同一 query 换文档顺序后 top5 集合不变（**排序稳定性**：现在会因为插入顺序而变）。

### 根因 5：查询整句直查 + 提示词没告诉模型「你看到的是抽样」

**代码事实**

- `agent/aios_ai/knowledge/retrieval.py:85` `{"keyword": question}` —— 把
  「帮我统计下四川省的省级非遗项目有多少个?」**整句**当关键词，拆成 19 个 2-gram，
  其中 `帮我/我统/计下/有多/少个` 全是噪声，真正有区分度的只有 `非遗`。
- `agent/aios_ai/prompt/builder.py:175` `【知识库参考】《{name}》\n{text}\n【以上为知识库参考】`
  —— 只给 docName，**不给 chunk_index、不给"本节是第 X/Y 块"、不给"文档共 N 行"**。
- 系统提示里有"不要编造"（`builder.py:234`），但**没有**"命中片段是抽样，不代表全文没有"。

于是模型的推理链是：`看到 5 行残片 → 与问题不匹配 → 库里没有 → 回答「知识库暂未收录」`。
**它没有说谎，是我们没给它判断依据。**

**方案（P1）**

1. **查询改写**：`pre_retrieve` 前加一次轻量改写（可用当前模型，temperature=0，输出 JSON 数组）：
   `"帮我统计下四川省的省级非遗项目有多少个?" → ["四川省省级非遗项目名录", "省级非遗 项目 总数", "2026.2 省级 名录"]`
   —— 多查询并行召回、去重后合并（配 `mode=hybrid`）。成本：一次 ~200 token 调用。
2. **参考块补元信息**（`builder.py:175`）：
   ```
   【知识库参考 1/5】《2026.2省级非遗项目名录》（本文档共 1243 段，此为第 12 段）
   ```
3. **提示词加第 6 条纪律**（接在现有【系统内部事实】之后）：
   ```
   6. 知识库命中的片段是**抽样**：它只代表文档的一小部分，不出现某个词不等于文档里没有。
      遇到「多少 / 几个 / 总数 / 合计 / 排名 / 占比 / 分别」这类统计问题：
      a) 先找带「统计摘要」字样的片段，有就直接引用；
      b) 没有就调用 kb_table_query 对表格做聚合；
      c) 两者都没有，才说「未取得该口径数据」，并说明是"缺少统计口径"而不是"库里没有这份资料"。
      严禁在只看到几行明细时回答「知识库未收录」。
   ```

**预期效果**：不再出现"库里明明有 1241 行却说未收录"；明细类问题可引用到具体段落；
模型能主动区分"没检索到"与"没有这份资料"。

**验证**：`_check_kb_honesty.py` —— 断言 ①参考块含 `第 X/Y` ②聚合意图时 `kb_table_query` 被调用
③负向：故意给 3 行残片问总数，断言**不许**回复"未收录/没有该资料"，必须说明缺统计口径。

### 附带发现（运维级，会伪装成"检索 Bug"）

**「列表里有文档，但检索永远 0 条」** —— 本机库实测：

```
kb_document 存活 18 篇；其中 11 篇演示文档声明 chunk_count = 402 条
kb_chunk  实际存活 15 行；这 11 篇文档一条切片都没有
```

`kb_document.chunk_count` 是**声明的数字**，`kb_chunk` 里没有对应行 ⇒ 页面看着"已索引 402 段"，
检索命中 0。这类状态不会有任何报错。

**方案**：`KbService.index()` 结束前自检 `SELECT COUNT(*) FROM kb_chunk WHERE doc_id=? AND deleted_at IS NULL`
与 `chunk_count` 比对，不一致 → `state=FAILED`、`errorMsg="切片落库不完整（声明 N / 实际 M）"`。
再加一个对账接口 `GET /api/v1/kb/documents/{id}/integrity`（运维/验收用）。

## 2. 优先级、工作量与预期收益

| 优先级 | 改动 | 文件 | 预期收益（可量化） |
|---|---|---|---|
| **P0-1** | 表格感知切片（列名进块） | `KbFileParser` + `KbService.split` + 新增 `TableChunker` | 列名覆盖 1/503 → 100%；cos 上限 0.157 → 0.272 |
| **P0-2** | 统计切片 + 聚合意图强制注入 + `kb_table_query` | 新增 `StatsChunker`、`KbTableQueryToolHandler`、V108 迁移 `kb_row`/`kind` | 聚合类问答 0% → 100%；top5 覆盖率 1% 不再是瓶颈 |
| **P0-3** | 真语义向量 + 阈值重标 | `application.yml:136-139` + `_check_kb_embedding_calibration.py` | 过阈率 0/503 → ≥30%；同义改写召回稳定 |
| **P1-1** | BM25 + 单文档配额 | `KeywordScorer` + `MysqlKnowledgeStore.search` | 同分塌陷消失；5 表并查不再互相挤占 |
| **P1-2** | 查询改写 + 参考块元信息 + 提示词第 6 条 | `retrieval.py:85`、`builder.py:158-176, 234` | 消灭"库里有却说未收录" |
| **P2** | 入库自检 + 对账接口 | `KbService.index()`、`KbController` | 根除"有登记无切片"的静默失败 |

**整体预期**（对同一份 5 表 1241 行名录）：8 类问题（总数 / 按类别 / 按批次 / 某地区有哪些 / 传承人 / 联合国级 / 国家级 / 跨表对比）
**正确率从 0/8 提到 ≥7/8**，且每条答案都能落到 `docName + 行号`。延迟方面：当前每次检索把可见文档的**全部切片**
读进内存逐条算余弦（`MysqlKnowledgeStore.java:108`），1241×5 表 ≈ 6200 块，加列名与文档配额后需同步加
`doc_id` 预过滤与 `kind` 过滤，避免性能随文档量线性恶化。

`scripts/_verify_kb_nonheritage.py`（Python312 + pymysql，独立算真值，不复用被测代码）：

| # | 用例 | 断言 |
|---|---|---|
| 1 | 上传 5 个 xlsx | 每个 `chunk_count` = `SELECT COUNT(*) FROM kb_chunk`（不为 0、不为声明值） |
| 2 | 切片形态 | 含 `\|` 的切片 100% 前置列名；无「只含 sheet 名」的切片 |
| 3 | 「省级非遗有多少个」 | 回答含数字，且 = 独立 `SELECT COUNT(*)`；引用含 docName |
| 4 | 插 1 行后再问 | 数字 +1（证明不是记忆化答案） |
| 5 | 「按类别分别多少个」 | 各分类数字之和 = 总数 |
| 6 | 「成都市有哪些」 | 返回条目数 = 独立 `WHERE 地区='成都市'` 的 COUNT |
| 7 | 反向（负向） | 问库里没有的表（如"区级传承人"），必须说"未取得该口径数据"，**不许**编造数字 |
| 8 | 语义召回 | 「四川省级非遗有几项」与「四川省省级非遗项目数量」top5 交集 ≥2 |
| 9 | 诚实性 | 全流程 0 次出现「知识库暂未收录」+ 实际有数据的情形 |

## 4. 为什么要强调「不是模型能力问题」

对照截图可见：另一工具对同一问题的界面上写着 **「搜索 4 个关键词，参考 17 篇资料」** ——
它给模型的是 **17 篇带日期的公开资料 + 多关键词检索**；
本系统给模型的是 **5 行无列名的碎行、单关键词、单次检索、内部库 0 命中**。

差距在**喂给模型的上下文量级与检索策略**，不在模型本身：

- 上下文：17 篇 vs 5 个碎行（≈ 30 倍信息量差）；
- 检索：多关键词 + 联网 vs 单关键词 + 单库；
- 且本系统联网那一路（截图 1「已联网检索两次」）也退化成把整句长句丢给搜索引擎，返回的是政务门户首页。

所以本报告把 P0 全部压在**「让表格能被正确读懂与聚合」**和**「让向量腿真的有意义」**这两件事上 ——
这两件做对，同一模型、同一份名录，答案质量立刻收敛到可用；只调阈值、只加 topK、只换模型，都不会变。

## 5. 落地记录（2026-11-06 已实现）

### 5.0 先修了一个更靠上的根因：参考块恒为空

排查到 `agent/aios_ai/prompt/builder.py#build_kb_reference_block` 时发现：它只认
`content` / `text` 两个字段，而工具网关 `ToolGatewayService.searchKb()` 返回的字段叫 **`snippet`**
⇒ 每一条命中都被 `continue` 跳过，参考块**恒为空字符串**。

实测（改前）：

```
参考块长度 = 0
repr = ''
结论：命中片段**根本没有进入提示词**
```

也就是说：**即使检索完美命中，正文也从未进入上下文**，模型只看到「来源：xxx.xlsx」这个引用标签。
这条比本文第 1 节的五个根因都更靠上——它是「有资料却答不出」的直接原因，且完全静默。
已在同一次改动中修复（取值链加 `snippet` + 补「片段 #N」+ 补「这是抽样」使用说明），
回归用例 `agent/tests/test_kb_reference_block.py`（7 条，含「工具网关真实字段」固定判据）。

### 5.3 P0-3 现状：代码就绪，开关未合（缺 embedding 服务）

`HttpEmbeddingProvider` 本来就实现了（ollama / openai 两种协议），**不需要改代码**，
