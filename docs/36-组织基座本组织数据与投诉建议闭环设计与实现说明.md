## 1. 需求与本轮交付边界

用户原话拆成三条，逐条落到具体构件：

| # | 需求原文 | 落地为 | 证据 |
|---|---|---|---|
| ① | 机构、部门的管理员在**用户端首页可显示本组织的数据** | `OrgScopeStatsService.orgScope()` + `GET /api/v1/stats/org`，H5 首页新增 `cardOrg` 卡 | E2E D 组 8 项；H5 断言「普通成员首页不展示本组织数据卡」 |
| ② | 测试**新增企业 → 新增部门 → 新增员工**端到端流程，**有无 bug** | `scripts/e2e_v63_org_feedback.py` A/B/C 组（真调租户管理端与企业管理员端接口） | A/B/C 共 15 项断言；并借此**发现并修复 1 个真 bug**（见 §6） |
| ③ | 用户端「我的」页下**投诉与建议**，把用户输入**反馈给本部门的管理员** | `FeedbackService` + `org_feedback` 表 + `GET/POST /api/v1/feedback*`，H5「我的 → 投诉与建议」页 | E 组 11 项 + F 组 4 项（逐级上溯）+ G 组 7 项（负向） |

**边界与纪律**：
- 范围**由后端按登录身份裁决**，前端只渲染「后端说你能看什么」——前端传什么都能被伪造。
- 普通成员**不展示**该卡（`canSeeOrg=false`）。用户需求限定对象是「管理员」，**可见面按需求取最小**。
- 反馈送达是**不可逆动作**，绝不静默成功：找不到接收人时把 `NONE` 作为一等状态回给用户，而不是报错或假装成功。

## 2. 「本组织数据」范围裁决（唯一判定点）

范围只在一处判定：`OrgScopeStatsService.orgScope()`。判定顺序即优先级：

```
登录人 ─┬─ ROLE_ADMIN / ROLE_TENANT_ADMIN ─→ scope=TENANT      本租户全量
        ├─ ROLE_ORG_ADMIN（且 org_member 有 institutionId）─→ scope=INSTITUTION  本机构
        ├─ 是某个部门负责人（leader_user_id 命中）─→ scope=DEPARTMENT  本部门（我负责的）
        └─ 其余（普通成员 / 未纳管账号）─→ scope=NONE  不展示
```

各口径指标（**全部为实时计数，无 mock**）：

| scope | 指标 |
|---|---|
| TENANT | 在职员工 / 启用机构 / 启用部门 / 待我处理 / 本月会话 / 本月词元 |
| INSTITUTION | 机构成员 / 下属部门 / 待我处理 / 本月会话 / 本月词元 / 机构知识库 |
| DEPARTMENT | 部门成员 / 下级部门 / 待我处理 / 本月会话 / 本月词元 / 部门知识库 |

**口径同源原则**：机构口径与租户口径都对 `chat_conversation` 计数，差别只在 `user_id` 归属集合 —— 否则「机构数加起来 ≠ 租户数」，看板自身就自相矛盾（对应铁律「展示必须与事实同源」）。

**一人负责多部门怎么选**：优先选「本人主身份所在的那个」（同一份数据两处口径一致）；否则取 id 最小的，保证**同一账号每次得到同一结果**（可复现 > 随机挑）。其余负责的部门经 `ledDepartments` 一并返回，前端可切换。

> 前端 `#cardOrg` 在 `canSeeOrg=false` 时 `display:none`，并纳入「工作台空卡自动折叠」清单（`collapseHomeFallback`）—— 避免出现一张永远空的卡片。

## 3. 投诉与建议：接收人解析（逐级上溯）

用户只表达「我要反馈」，系统负责找到「谁来接」。解析按如下顺序，命中的层级与原因**都写进记录并回给用户**：

```
本部门负责人(org_department.leader_user_id)
   ↓ 未配置
本部门正职(org_member.duty_code='DEPT_PRINCIPAL')
   ↓ 未配置
本机构管理员(org_member.is_org_admin=1)
   ↓ 未配置
租户管理员(首个 ROLE_TENANT_ADMIN)
   ↓ 都没有
NONE（待人工指派，delivered=false 明确告知）
```

**为什么不直接找租户管理员**：部门管理员最了解本部门事务，质量最高；但现实里部门常没配负责人，若此时报错或假装成功，用户会以为反馈已送达 —— **这是最坏结果**。所以设计为逐级兜底，并把 `NONE` 也作为一等终态（对应铁律「每一步失败都要有终态」「不可逆动作绝不静默成功」）。

**部门负责人判定口径**（历史坑，勿回退）：只认 `leader_user_id` 或 `duty_code='DEPT_PRINCIPAL'`，**绝不**用 `job_title`（27/8/3 三口径分裂的历史 bug）。

**角色标签是中文口语，不是角色码**：接收层级对外显示为「本部门管理员 / 本机构管理员 / 租户管理员」，不下发 `DEPT`/`INSTITUTION` 这类内部码给用户端。

## 4. 闭环：提交 → 通知 → 回复 → 提交人可见

```
提交人                    系统                              接收人（本部门管理员…）
  │                        │                                      │
  │ POST /api/v1/feedback  │                                      │
  ├───────────────────────►│ ① 校验（内容非空 / ≤2000）            │
  │                        │ ② resolveAssignee 逐级上溯            │
  │                        │ ③ 落 org_feedback（含层级/原因）      │
  │                        │ ④ insertNotification(type=FEEDBACK)  │
  │                        ├─────────────────────────────────────►│ inbox 出现待处理
  │ ◄── delivered + note ──┤                                      │
  │                        │                                      │
  │                        │       POST /api/v1/feedback/{id}/reply│
  │                        │◄─────────────────────────────────────┤
  │                        │ ⑤ 校验回复人身份（接收人 / 同租户管理员 / 同机构企业管理员）
  │                        │ ⑥ 状态 → REPLIED，写 reply_content    │
  │                        │ ⑦ insertNotification 通知提交人       │
  │ ◄── 站内通知「已被回复」┤                                      │
  │ GET /api/v1/feedback/mine 看到答复（闭环最后一跳）             │
```

**接口清单**：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/feedback` | 提交；返回 `delivered` + `deliveryNote` + 解析到的层级 |
| GET | `/api/v1/feedback/mine` | 我提交的（含答复、状态） |
| GET | `/api/v1/feedback/inbox` | 派给我的（接收人视角，含匿名遮蔽） |
| POST | `/api/v1/feedback/{id}/reply` | 回复（仅接收人本人 / 同租户管理员 / 同机构企业管理员） |

**匿名只对上级生效**：提交人自己看自己的记录**始终是真名**；接收人视角按 `anonymous` 决定是否遮蔽。这是「匿名」的语义边界，不是 bug。

**通知落库 vs 调 NotificationService**：`aioa-org` 刻意不依赖 `aioa-resource`（模块边界，见 `OrgStatMapper` 注释），故走既有 `insertNotification` 原始 SQL 写入。用户端通知列表读的就是 `notification` 表，**站内送达成立**；代价是不走 `NotificationService` 的邮件/Webhook 通道分发（本阶段未启用该类通道，不构成缺口）。

**越权不泄露存在性**：非接收人回复他人反馈返回 **404**（不是 403）—— 403 等于告诉攻击者「这条记录存在」。

## 5. 关键工程约定（易错点）

1. **`GlobalExceptionHandler` 的 HTTP 状态口径**：只有 `401/403/404` 对应的 `BizException` 才映射成 HTTP 状态码；**其余（含 400 参数校验）一律返回 HTTP 200 + `body.code=400`**。因此**断言必须校验业务 `code` 字段，不能看 HTTP 状态码**（本套件的 `biz_reject()` 就是干这个）。
2. **登录返回字段是 `accessToken`**（不是 `token`）—— e2e 首个失败就栽在这。
3. **`AuthUser.nickname` 在请求期恒为 null**（发令牌处从未赋值），`AuditRecorder.displayName()` 会回落到登录用户名。组织域内**取姓名必须读 `org_member.name`**（`FeedbackService.displayNameOf()`）。
4. **数据用 `VARCHAR(2000)` 且校验前置**：超长在服务层拒绝，不留给数据库报错（错误信息更友好，也不占用事务）。
5. **e2e 收尾置机构为 `CLOSED` 而非删除**：删除会连带 `org_member` / `org_feedback` 历史，那正是下次排查的证据；置 CLOSED 保证套件**可重复运行**（否则「启用机构」会越堆越多）。

## 6. 本轮通过端到端**发现并修复的真实 bug**

> 这正是用户问的「有无 bug」的答案：**有，1 个，且只有端到端能抓到。**

**现象**：提交反馈后，记录里的 `submitterName` 显示的是登录用户名 `e2emem0170785`，而不是员工真实姓名「E2E成员」。

**根因**：`AuthUser.nickname` 在请求期恒为 null（发令牌的地方从不赋值），而 `AuditRecorder.displayName(actor)` 在 nickname 为空时回落到 username。结果是**用户看到的是内部登录 id**。

**修复**：组织域内改用 `displayNameOf(userId, actor)`，从 `org_member.name` 取名（组织域内的权威姓名源），`submit()` 与 `reply()` 两处同步替换。

**为什么只有 e2e 能抓到**：单元测试里 `AuthUser.nickname` 常被手工填好，接口测试若只看 `code==0` 也不会看姓名内容。**只有真走登录 → 真调接口 → 真读回显**，才会暴露这个「回填用户可见文案照抄了历史口径」的问题（对应铁律「展示必须与事实同源」「回填用户可见文案不准照抄历史原文」）。
