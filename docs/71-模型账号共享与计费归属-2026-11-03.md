# 模型账号共享与计费归属（账号管理）

> 2026-11-03。需求口径：用户可用**自行注册的账号**（如 DeepSeek）跑对话，供应商官方计费；
> 平台仍要统计词元，并在统计结果里**标注这笔用量是否由公司收费**；用户可**邀请同事共用**
> 自己的账号（供应商视角的「子账号」），被邀请人消耗的 token **由邀请者承担**；
> 参与共用的账号既可以是个人注册的，也可以是**公司默认提供**的。

## 0. 一句话结论

> **「谁在用」与「谁付费」拆成两个字段记在账本上，账号（凭证）本身带来源类型；
> 平台只做归属与统计，实际扣费仍由供应商按各自账号结算。**

原实现只有一个 `user_id`，它同时承担「使用者」和「扣额度的人」两个语义。
一旦允许 A 用 B 的账号，这两个语义必然分离 —— 所以本方案的核心不是加一张表，
而是**把账本上的一个 id 拆成 `bearer_user_id` + `charge_user_id`**，
再补一个 `company_charged` 标注供统计与对账使用。

## 1. 核心取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 复用 `model_config` 还是新建表 | **新建 `model_credential`** | `model_config` 是**全局单份**（无 `tenant_id`、无属主），是「平台级默认通道」；账号是「某个人的私产」，混在一张表里既做不了租户隔离，也无法表达「这行是谁的」 |
| 密钥存哪 | 库里存**密文**（`SecretCodec`，AES-256-GCM） | 与连接器凭据同口径；`model_config` 的 Key 只驻留 agent 内存，是因为它是**平台配置**，账号是**用户资产**，必须可跨重启读取 |
| 额度扣谁的行 | 扣 `charge_user_id` 的行，账本仍记 `bearer_user_id` | 只有拆开才能同时回答「谁用的」与「谁付的」；混在一起则邀请共享后无法追责 |
| 公司账号怎么判「公司收费」 | `owner_type=COMPANY` ⇒ `company_charged=1` | 由**凭证来源**推导，不接受前端传参（前端可传就能伪造账单口径） |
| 历史数据怎么标 | `company_charged` 可空 ⇒ NULL = **未标注** | 老账本不知道当时用的是谁的账号，补 0 等于谎报「个人自付」；统计里单列「未标注」 |
| 撤销共享后正在跑的会话 | **不打断**，下一轮拒绝 | 打断会毁掉已产生的输出；归属在 run 启动时快照，已启动的 run 记在撤销前的主体上 |

## 2. 账号来源类型

```
PERSONAL  用户自行在供应商注册的账号（如 DeepSeek 官网注册）
          · 计费发生在供应商侧，公司不收费 ⇒ company_charged = 0
          · 主账号持有人 = owner_user_id，也是共享时的承担人
COMPANY   公司统一采购/提供的账号
          · 走公司额度，公司收费 ⇒ company_charged = 1
          · charge_user_id 记 0（租户池），不挂到任何个人头上
```

`model_credential.provider_key` 与 agent 侧 provider 注册表 key 对齐（`deepseek` / `dashscope` / …），
这样「模型路由」（`model_ref`）与「用谁的凭证」可以各自独立选择：
同一个 `deepseek`，A 用自己注册的、B 用公司的，provider 相同而凭证不同。

## 3. 数据模型

### 3.1 `model_credential`（模型账号 / 凭证）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `tenant_id` | bigint | 个人账号也挂租户，保证统计与越权判断有边界 |
| `owner_type` | varchar(16) | `PERSONAL` / `COMPANY` |
| `owner_user_id` | bigint NULL | PERSONAL 必填（注册人 = 主账号持有人）；COMPANY 为 NULL |
| `provider_key` | varchar(64) | `deepseek` / `dashscope` / `vllm` / `ollama` / `minimax` |
| `provider_type` | varchar(32) | `openai_compatible` / `echo` |
| `name` | varchar(64) | 展示名，如「我的 DeepSeek」 |
| `base_url` | varchar(255) NULL | 空则回退 provider 注册表 |
| `model_name` | varchar(128) NULL | 空则回退注册表 |
| `api_key_cipher` | varchar(512) | `enc:` 前缀密文；**任何接口都不回传明文** |
| `key_hint` | varchar(64) | 掩码 `sk-****3f9a`，仅用于「是不是这把 Key」 |
| `share_enabled` | tinyint | 是否允许邀请同事共用（默认 0，需显式开启） |
| `status` | varchar(16) | `ENABLED` / `DISABLED` |
| `remark` | varchar(255) | |
| `created_at/by`、`updated_at/by`、`deleted_at` | | 软删 |

唯一键：`(tenant_id, owner_user_id, provider_key, name, deleted_at)` —— 同一个人可以为
同一个 provider 建多把 Key（如「个人」「团队报销」），但名字不能重。

### 3.2 `credential_share`（主账号 → 子账号授权）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `tenant_id` | bigint | |
| `credential_id` | bigint | 被共享的账号 |
| `owner_user_id` | bigint | 邀请者（冗余 `credential.owner_user_id`，便于按邀请者查） |
| `grantee_user_id` | bigint | 被邀请的同事 |
| `grantee_name` | varchar(64) | 冗余姓名，列表免 join |
| `status` | varchar(16) | `PENDING`（已邀未接受）/ `ACTIVE` / `REVOKED` / `EXPIRED` |
| `invite_code` | varchar(16) | 邀请码，便于口头/IM 传递 |
| `quota_tokens` | bigint | 该子账号的共享上限，`0` = 不限 |
| `used_tokens` | bigint | 已用量（用于上限判断；账本仍是唯一事实源，这里只是加速） |
| `expires_at` | datetime NULL | 到期自动失效（读时判定，不依赖定时任务） |
| `accepted_at` / `revoked_at` | datetime NULL | |
| `created_at/by`、`updated_at` | | |

唯一键：`(credential_id, grantee_user_id)`。撤销后再次邀请**复用同一行**（改状态、清 revoked_at），
否则唯一键会挡住「撤销后再邀请」这条最常见的操作。

### 3.3 `token_ledger` 扩列

| 新字段 | 语义 |
|---|---|
| `credential_id` | 本次用的哪个账号（NULL = 走平台默认通道） |
| `bearer_user_id` | **实际使用者**（发起对话的人） |
| `charge_user_id` | **平台侧承担者**（PERSONAL = 账号持有人；COMPANY = 0 表示公司池） |
| `charge_owner_type` | `PERSONAL` / `COMPANY`；NULL = 历史未标注 |
| `company_charged` | `1` 公司收费 / `0` 个人自付 / NULL 未标注 |
| `provider_key`、`model_name` | 便于按供应商/模型出账 |

索引：`idx_ledger_charge (tenant_id, charge_user_id, created_at)`、
`idx_ledger_credential (credential_id, created_at)`。

> `user_id` 列**保留不动**，语义冻结为「账本归属人」（= bearer），既有查询、导出、
> 前端账单页全部不回归。

## 4. 计费归属规则矩阵

| 场景 | credential.owner_type | bearer_user_id | charge_user_id | company_charged |
|---|---|---|---|---|
| 用自己注册的账号 | PERSONAL | 本人 | **本人** | 0 |
| 被邀请用同事的账号 | PERSONAL | 被邀请人 | **邀请者** | 0 |
| 用公司默认账号 | COMPANY | 使用者 | **0（公司池）** | 1 |
| 未绑定账号（平台默认通道） | NULL | 本人 | 本人 | NULL（未标注） |

两条硬规则（代码里 assert，不接受前端传参）：

1. `company_charged = (owner_type == COMPANY)`；
2. `charge_user_id = COMPANY ? 0 : credential.owner_user_id`。

## 5. 邀请同事时的权限与承担规则

**邀请方**：账号持有人本人（`owner_user_id`）；COMPANY 账号由**租户管理员**开启共享
（公司资产不能由某个员工私下分给同事）。

**被邀请方**：同租户、`sys_user.status = ENABLED` 的账号。

校验清单（每条都要有明确错误文案，不做静默失败）：

| # | 校验 | 不通过 |
|---|---|---|
| 1 | 凭证存在、未删除、属于当前租户 | 404 |
| 2 | 操作者是凭证持有人（COMPANY 时放宽为租户管理员） | 403 |
| 3 | 凭证 `status=ENABLED` | 400「账号已停用，无法共享」 |
| 4 | `share_enabled=1` | 400「该账号未开启共享」 |
| 5 | 被邀请人 ≠ 自己 | 400「不能邀请自己」 |
| 6 | 被邀请人同租户且 `ENABLED` | 400「只能邀请本单位在职同事」 |
| 7 | 未处于 ACTIVE | 409「该同事已在共享名单中」 |
| 8 | 共享人数上限（20） | 400「共享人数已达上限」 |
| 9 | 共享额度（若设了 `quota_tokens`） | 403「共享额度已用尽，请联系邀请人」 |

**token 承担**：被邀请人使用时 `charge_user_id = 邀请者`，
`bearer_user_id = 被邀请人`；额度准入查**邀请者**的额度行，
被邀请人自己的额度**一点不扣** —— 这就是「由邀请者承担」在数据上的唯一含义。

**撤销**：`status=REVOKED`。已经启动的 run 不打断（快照已落），下一次发起时
解析不到可用共享 ⇒ 按「未绑定账号」回落或直接 403（见 §6 顺序）。

## 6. 运行时：一轮对话用哪个账号

`RunService.start()` 按以下顺序解析（**只解析一次，结果落 context 快照**，
后续 `subscribe` 复用同一份，避免「首帧用一个账号、续跑换另一个」）：

1. 请求显式指定 `credential_id`，且**当前用户可用**（自己的 / 被 ACTIVE 共享的 / 公司账号）；
2. 否则取当前用户**自己的默认账号**（最近可用的一把 PERSONAL）；
3. 否则取**公司账号**（COMPANY，本租户内最近一把）；
4. 都没有 ⇒ `credential = null`，走平台默认通道（既有行为，逐字节不变）。

「当前用户可用」= 自己持有的 OR `credential_share` 里 `grantee=我` 且 `ACTIVE` 且未过期的。

选不到显式指定的账号时**不静默降级**：显式传了但不可用 ⇒ 403（明说无权限/已撤销），
只有「没传」才走 2→3→4 的自动顺序。这条与「不拿别人的 token 悄悄跑」是同一件事。

### 额度准入

| 凭证 | 查谁的额度行 | 用尽文案 |
|---|---|---|
| PERSONAL | `current(tenant, charge_user_id)` | 「该账号可用额度已用完，请联系账号持有人」 |
| COMPANY | `current(tenant, 0)` | 「公司词元额度已用完，请联系管理员」 |
| 无凭证 | `current(tenant, bearer)` | 既有文案（不回归） |

### 记账

`finish()` 里按 run 启动时快照的归属写 `token_ledger`，并对 `charge_user_id` 的行
`used_tokens += total`；`balance_after` 取**承担者**的余额（不是使用者的）。

## 7. 统计口径

三个正交维度，全部回账本聚合，页面不产生新数字：

| 维度 | 分组键 | 回答的问题 |
|---|---|---|
| 按账号 | `credential_id` | 每把 Key 花了多少、几个人在用 |
| 按使用者 | `bearer_user_id` | 谁在用（含借用别人账号的人） |
| 按付费人 | `charge_user_id` + `charge_owner_type` | 谁承担（个人 / 公司） |

固定汇总块（所有维度都带）：`companyChargedTokens` / `personalChargedTokens` /
`unmarkedTokens` + `byOwnerType`（PERSONAL / COMPANY / UNKNOWN 三档词元数）。

> **「是否公司收费」的标注只此一处**：`token_ledger.company_charged`。
> 前端展示的标签、导出的对账单、统计汇总全部读这一个字段，不允许页面按
> owner_type 二次推导（否则同一个数字在两个页面能对不上）。

## 8. 异常与边界

| 情况 | 行为 |
|---|---|
| 解密失败（换了密钥） | 500 且文案指明「密钥已变更，请重新录入」；**不返回空 Key 假装未配置** |
| 供应商侧 Key 失效 | 沿用 agent 既有的 `MODEL_UPSTREAM_ERROR`；账号页提供「测试连通性」 |
| 被邀请人离职/停用 | 共享行保留（审计），解析可用性时按 `sys_user.status` 过滤 |
| 共享到期 | 读时判定 `expires_at < now` ⇒ 视为 EXPIRED，并回写状态 |
| 同一 run 重复记账 | `run_id` 唯一 + 先查后插，与既有幂等一致 |
| 跨租户用凭证 | 404（不泄露存在性） |

### 10.3 踩到并已修正的坑

1. **跑 E2E 时 agent 是旧进程**：改动只在磁盘上，`resolve(credential=...)` 没生效，
   结果打到了真的 DeepSeek（词元 8298、回答是模型自己的拒答）。**Python 侧改动必须重启 agent。**
2. **校验失败 ≠ HTTP 400**：本项目是 200 + 信封 `code=400`（铁律 #29/30），
   断言一律看 `body.code`；只有 401/403/404 才映射 HTTP 状态。
3. **`/check` 是 GET**：控制器定义为 `@GetMapping`，脚本用 POST 打到 405。
4. **统计同一 key 可能多行**：历史未标注 + 本用例各一行，挑第一行会撞上历史数据造成假失败。
5. **`NOW()` 只到秒**：清理脚本用它做软删时间戳，同一秒内两行撞唯一键；要 `NOW(6)`。
   （应用侧走 MyBatis-Plus 逻辑删除，用的是 Java 侧微秒时间戳，不受影响。）

## 11. 已知边界

1. **共享额度上限只做「用尽即拒」**，不做周期重置；`used_tokens` 是加速字段，
   真正的事实源仍是 `token_ledger`（可按 `credential_id` 汇总校准）。
2. **撤销不打断已在跑的 run**：归属在 run 启动时快照，已启动的 run 记在撤销前的主体上。
3. **公司账号默认全租户可用**：没有按部门/岗位收窄（当前无此需求）；
   若要收窄，判定点应加在 `ModelCredentialService.loadForUser`。
4. **「未标注」是历史账本**：本次上线前的 `token_ledger` 没有归属列，
   统计里单列一档，不做回溯填充（填了就是编数据）。
5. **前端未做「对话里切换账号」的入口**：`credential_id` 已进 `CreateRunRequest`，
   H5/管理端可在发消息时带上；当前由账号页管理，会话按快照固定用同一个账号。
6. **`model_config`（平台默认通道）仍是全局单份**：本方案没有改它。
   「用谁的凭证」与「平台默认用哪个 provider」是两个正交维度，互不影响。
