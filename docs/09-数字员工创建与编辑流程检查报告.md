# 用户端「数字员工」创建与编辑流程检查报告

> 检查时间：2026-09-10
> 检查范围：用户端 H5（`user-client/index.html`）→ Java 后端（`WorkerController` / `AdminWorkerController` / `WorkerScheduleService`）→ Python agent（`/internal/v1/complete`）
> 检查方式：源码全链路追踪 + 线上接口实测 + 数据库落库字段核对

---

## 一、创建流程（入口 → 创建成功）

### 1.1 实际链路

| 步骤 | 位置 | 行为 |
|---|---|---|
| ① 入口 | 用户端「数字员工」页 | 按钮 `＋ 创建数字员工` → `createAgentFlow()` |
| ② 引导 | `createAgentFlow()` | 跳转会话页，注入「数字员工管家」欢迎语 + 3 个示例 chip |
| ③ 选择 | `agentDemo(q)` | 点示例（或自行作答）→ 渲染**任务确认卡**：名称 / 计划 / 动作 / 留痕 |
| ④ 确认 | `confirmAgent()` | 调 `POST /api/v1/workers` |
| ⑤ 落库 | `WorkerController.create()` | 写 `agent_worker` 表 |
| ⑥ 回显 | `state.workers.unshift(w)` + `renderAgents()` | 列表出现新员工，`toast('数字员工已创建并开始运行')` |

### 1.2 实测结果（`zhangsan` 登录）

请求：
```json
POST /api/v1/workers
{"name":"政策推送助手","icon":"bot",
 "description":"每天8点推送行业新政策",
 "scheduleText":"每天 8 点推送行业新政策"}
```

响应 `code:0`，返回 `id:14, status:"运行中", on:true`，前端展示正常。

**但数据库落库字段暴露了核心问题：**

```
id            = 14
name          = 政策推送助手
schedule_text = 每天 8 点推送行业新政策
schedule_time = None      ← 关键：定时执行时刻（调度器唯一匹配依据）
task_prompt   = None      ← 关键：任务内容（真实执行的输入）
enabled       = 1
status        = 运行中
```

## 二、❌ 核心缺陷：创建后**不具备真实执行能力**（空壳智能体）

### 2.1 问题定性

用户端创建的员工**只是一个展示记录**，无法被定时调度器执行，永远不会产出任何结果。

### 2.2 证据链

**证据 1 — 调度器扫描条件（`WorkerScheduleService.tick()`）**
```java
.eq(AgentWorker::getEnabled, 1)
.isNotNull(AgentWorker::getScheduleTime)     // ← 要求 schedule_time 非空
.eq(AgentWorker::getScheduleTime, nowStr)    // ← 要求精确等于当前 HH:mm
```
`schedule_time = NULL` 的记录**永远不会被扫到**。

**证据 2 — 执行前置校验（`WorkerScheduleService.runNow()`）**
```java
String prompt = worker.getTaskPrompt();
if (prompt == null || prompt.isBlank()) {
    errorMsg = "未配置任务内容（taskPrompt 为空）";   // ← 直接判失败
}
```
即使被手动触发，也因 `task_prompt = NULL` 直接失败。

**证据 3 — 生产数据实测（12 条有效员工）**

| id | 名称 | schedule_time | task_prompt | 可否执行 |
|---|---|---|---|---|
| 1–3 | 政策快讯员/请假助手/办文助手 | NULL | NULL | ❌ 无法执行 |
| 4 | 季度报表员 | NULL | NULL | ❌ 无法执行 |
| 5–7 | 用户端创建的一批 | NULL | NULL | ❌ 无法执行 |
| 8–11 | 晨报员（管理端创建） | 08:00 | 已配置 | ✅ 可执行 |
| 12–13 | 用户端创建 | NULL | NULL | ❌ 无法执行 |

> **结论：管理端创建的 4 条可正常执行；用户端创建的 8 条全部无法执行。** 这不是个例，是接口层的系统性缺失。

### 2.3 根因

`WorkerController.create()` 只映射了 `name / icon / description / scheduleText` 四个字段，
**没有接收、也没有解析** `scheduleTime`（HH:mm）与 `taskPrompt`：

```java
w.setStatus(AgentWorker.STATUS_RUNNING);
w.setLastOutput("尚未运行");
w.setScheduleText(...);   // 只存了人类可读描述
w.setEnabled(1);
// ← 缺失：w.setScheduleTime(...) / w.setTaskPrompt(...)
```

同时 user-client 的 `confirmAgent()` 也**没有传**这两个字段：
```js
const w = await API.createWorker({name:name, icon:'bot',
                                 description:plan, scheduleText:plan});
// ← 缺失：scheduleTime / taskPrompt
```

即：**用户表达的自然语言（「每天 8 点推送行业新政策」）从未被解析成可调度的结构化配置**，也没有交给模型转成任务提示词。

### 2.4 连锁影响

- 「运行中」状态是**虚假状态**：员工看起来在跑，实际永不触发
- 用户端「运行记录」按钮只弹一句 toast 文案，**无真实执行记录可看**（管理端才有 `/{id}/runs`）
- 用户端「已代办/最近产出」永远显示「尚未运行」

## 三、❌ 编辑流程问题

### 3.1 现状

| 项 | 实际情况 |
|---|---|
| 编辑入口 | 员工卡片「调整任务」按钮 → `editAgent(i)` |
| 实现 | `function editAgent(i){ createAgentFlow(state.workers[i]); }` |
| 「编辑」页表现 | 仅把原名称作为 chip 示例「按当前配置重新生成：XXX」，**表单里不带出任何原有配置**（时间、任务内容、名称都需重输） |
| 保存动作 | 走 `confirmAgent()` → `POST /api/v1/workers`（**新增**接口） |
| 后端更新接口 | `PUT /api/v1/workers/{id}` **不存在**（只有管理端 `PUT /api/v1/admin/workers/{id}`） |
| 用户端 API 层 | 只有 `workers / createWorker / toggleWorker`，**无 updateWorker** |

### 3.2 实测验证

对已存在的「政策推送助手」执行一次「调整任务」并确认：

```
编辑前员工数 = 14
编辑后员工数 = 15      ← 数量 +1
```

> **结论：「调整任务」实为「再建一条」，而非编辑。** 原记录纹丝未动，产生重复员工，且新记录同样缺少 `schedule_time` / `task_prompt`，依然不可执行。

### 3.3 用户问题的直接回答

> **已存在的数字员工如何编辑？**

**目前无法真正编辑。** 名义入口是员工卡片的「调整任务」，但它：
1. 不回填原有配置；
2. 调用的是新建接口，保存后**新增一条重复记录**，原记录不变；
3. 用户端没有 `PUT /api/v1/workers/{id}` 这类更新通道。

> **可修改字段范围？**

按设计应包含：`name`（名称）、`icon`（图标）、`description`（职责说明）、`scheduleTime`（执行时刻 HH:mm）、`taskPrompt`（任务内容）。**但当前一个都无法被编辑。**

> **保存后是否即时生效？**

- 若指「列表即时显示」：是，`state.workers.unshift()` + `renderAgents()` 立即刷新。
- 若指「新配置即时生效」：**否**。因为保存的是新记录，且仍缺 `schedule_time` / `task_prompt`，调度器依旧不会执行。

## 四、缺失与需修复清单（按优先级）

### P0 — 阻断性（不修则该功能形同虚设）

| # | 问题 | 修复点 |
|---|---|---|
| 1 | 用户端创建的员工无 `schedule_time` | `WorkerController.create()` 接收并按 `HH:mm` 校验/归一化 `scheduleTime`；`confirmAgent()` 一并提交 |
| 2 | 用户端创建的员工无 `task_prompt` | `create()` 落库 `taskPrompt`；缺省时用 `description` 兜底，禁止空值入「运行中」 |
| 3 | 自然语言「每天 8 点」无法转结构化时间 | 新增轻量解析（正则覆盖「每天/每周X HH:mm」「X 点」等）；或调 agent 先做一次**配置抽取**，把「什么时间 + 做什么」输出为 `{scheduleTime, taskPrompt}` 再确认 |
| 4 | 「调整任务」不更新而是新增 | 新增 `PUT /api/v1/workers/{id}`（用户端，租户内校验）；`editAgent()` 改为带 `id` 走更新；回填原配置到确认卡 |
| 5 | 编辑后不即时生效 | 更新成功后刷新 `state.workers`，并提示「已保存，下次执行时刻生效」 |

### P1 — 一致性与可用性

| # | 问题 | 修复点 |
|---|---|---|
| 6 | 状态虚假显示「运行中」 | 创建时若 `scheduleTime` 为空 → 状态置「待配置」而非「运行中」，并在卡片给出「去配置执行时间」引导 |
| 7 | 用户端无真实运行记录 | 新增 `GET /api/v1/workers/{id}/runs`（用户端只读，租户校验）；「运行记录」按钮改为打开记录列表 |
| 8 | 无法立即验证是否可用 | 新增 `POST /api/v1/workers/{id}/run`（用户端，可限频）；创建成功后提供「立即试跑一次」 |
| 9 | 无删除入口 | 用户端补 `DELETE /api/v1/workers/{id}`（逻辑删除，仅本人/租户内） |
| 10 | 名称自动截断生硬 | `q.slice(0,9)+'…助手'` 对长句产出「按当前配置重新生成…助手」这类无意义名称，应改为可编辑且给出更合理的默认命名 |
| 11 | 缺参数校验与失败提示 | 名称长度、`scheduleTime` 格式前后端双重校验；失败时提示可读原因（当前仅 `创建失败：xxx`） |

### P2 — 体验完善

| # | 问题 | 修复点 |
|---|---|---|
| 12 | 创建确认卡信息不足 | 补显「执行时刻」「任务内容」「下次执行时间」三项 |
| 13 | 无重复检测 | 同租户同名称+同时刻提示是否覆盖 |
| 14 | 用户端与管理端字段口径不一 | 用户端 `WorkerView` 未返回 `scheduleTime/taskPrompt`，应补齐以便编辑回填 |

## 五、修复建议方案（可直接落地）

### 5.1 后端 `WorkerController`

```java
// create：接收并解析调度配置
String scheduleTime = normalizeScheduleTime(body.getScheduleTime());  // HH:mm 校验
String taskPrompt   = trim(body.getTaskPrompt());
if (taskPrompt.isEmpty()) taskPrompt = trim(body.getDescription());   // 兜底
if (scheduleTime == null) {
    w.setStatus("待配置");            // 不再谎报「运行中」
} else {
    w.setStatus(AgentWorker.STATUS_RUNNING);
}
w.setScheduleTime(scheduleTime);
w.setTaskPrompt(taskPrompt);

// 新增：PUT /{id} —— 租户内原地更新（名称/图标/描述/scheduleTime/taskPrompt）
// 新增：GET /{id}/runs —— 用户端只读执行记录
// 新增：POST /{id}/run —— 立即试跑（复用 WorkerScheduleService.runNow）
// 新增：DELETE /{id} —— 逻辑删除
```

### 5.2 前端 user-client

```js
// 1) 确认创建时提交结构化字段
await API.createWorker({ name, icon:'bot', description:plan,
                         scheduleText:plan,
                         scheduleTime: parsedTime,   // 新增
                         taskPrompt: parsedTask });  // 新增

// 2) editAgent 区分新增/编辑，回填原配置
function editAgent(i){
  const w = state.workers[i];
  createAgentFlow(w);            // 确认卡带出 w.scheduleTime / w.taskPrompt
}
async function confirmAgent(btn, name, plan, workerId){
  const body = {name, icon:'bot', description:plan, scheduleText:plan,
                scheduleTime:..., taskPrompt:...};
  const w = workerId ? await API.updateWorker(workerId, body)
                     : await API.createWorker(body);
}

// 3) API 层补 updateWorker / workerRuns / runWorkerNow / deleteWorker
```

### 5.3 时间解析建议

在确认卡之前加一次**配置抽取**（可用 agent 或正则）：
- 输入：`每天 8 点推送行业新政策`
- 输出：`{ scheduleTime: "08:00", taskPrompt: "推送当日行业新政策要点摘要" }`
- 在确认卡上展示解析结果，允许用户手动修正后再提交 —— 这样既满足「一句话创建」，又保证落库字段完整。

## 六、检查结论

| 环节 | 结论 |
|---|---|
| 创建入口与交互 | ✅ 通顺，引导清晰 |
| 创建接口落库 | ⚠️ 成功但**字段不完整** |
| 创建后可用性 | ❌ **不可用**：缺 `schedule_time`+`task_prompt`，调度器永不触发 |
| 满足用户要求 | ❌ **不满足**：员工不会在指定时间执行用户描述的任务 |
| 编辑入口 | ⚠️ 有按钮，但语义错误 |
| 编辑保存 | ❌ **实为新增重复记录**，原记录不变 |
| 编辑即时生效 | ❌ 无更新通道，配置仍缺关键字段 |
| 运行记录 | ❌ 用户端无真实记录，仅 toast 文案 |

**整体判定：数字员工「一句话创建」目前是演示级空壳——列表能出现、状态显示「运行中」，但不具备真实定时执行能力，且「编辑」会制造重复数据。** 建议按第四节 P0 五项优先修复，其中 #1/#2/#3（补 `scheduleTime`/`taskPrompt` + 自然语言解析）是让功能真正可用的最小闭环，#4/#5（真正的更新通道）是编辑能力的前提。
