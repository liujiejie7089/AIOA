# 51 · 请假意图「自动判权 → 申请 / 跳转数字人」实施方案

> 需求原文（用户）：
> 「系统如果识别到我要请假，首先应该查看我是否有权限，没有就辅助帮我申请（用户可以取消），
> 如果有就自己跳转到对应的请假数字人」

本文件是本次改造的**唯一权威契约**。三层实现（agent / Java / H5）与验证都必须以本文件为准；
任何与本文件不一致的实现视为缺陷。

### 0.1 一个必须小心的命名陷阱

`applicable` 一词在两处含义**不同**，不要混用：

- `PermissionCatalog.applicable(code)` = 「该权限码**可申请**」（静态，与用户无关）
- `PermissionGrantService.catalog()` 里的 `applicable` = 「`!held && !pending`」＝**现在就可以申请**（与用户有关）

本方案新增字段一律命名为 **`held`**，不再复用 `applicable` 承载用户语义。

## 1. 冻结契约

### 1.1 请求（不变）

`POST /api/v1/workers/intent`，body `{"text": "..."}`。

### 1.2 响应 `data`（在既有字段基础上**新增 4 个**）

既有字段全部保留，新增：

| 字段 | 类型 | 语义 | 计算 |
|---|---|---|---|
| `held` | boolean | 当前用户**是否持有** `requiredPermission` | `PermissionCatalog.holds(user, permission)`；`permission` 为空时 `true`（无需权限） |
| `pending` | boolean | 当前用户对 `requiredPermission` 是否有**在途（PENDING）**申请 | `permission_grant` 中 `user_id` + `permission_code` + `status='PENDING'` 且未软删存在一行；`permission` 为空时 `false` |

> **为什么服务端不下发「要跳哪个数字员工」（设计取舍，勿擅改）**：
> 「跳转目标」由 H5 从**已经过服务端可见性过滤**的 `API.workers()` 列表里按
> `worker.workerType === intent.role` 取第一个匹配项。
> 这是**查表**（role → workerType 的通用映射），不是判权/判意图的**决策**；
> 而列表接口（`WorkerController.list()`）已经应用了可见性、`enabled`、内容审核三条过滤，
> 在其结果内取匹配项即**天然正确**，无需在后端跨模块复制一份可见性判定（复制即违反铁律 1）。
> `WorkerView` 已包含 `workerType` 字段，前端无需新接口。

### 1.3 新增动作（agent 侧）

`action` 新增取值 **`APPLY_LEAVE`**，`actionName = "请假"`。

判定词表（**窄口径**：必须表达「我要去办」，不得命中政策咨询）：

```
(要|想|打算|准备)\s*(请|休)          # 我要请假 / 我想休年假
帮我\s*(请|休)                       # 帮我请假 / 帮我休假（★ 2026-10-17 收窄，见下）
(申请|提交|发起)\s*(请假|休假|年假|调休|病假|事假|婚假|产假)
请(个|一天|两天|半天|三天)假          # 请个假
```

> ★ **2026-10-17 收窄（重要）**：原第 2 条是 `帮我\s*(请|休|申请|提交)`，会把
> **「申请权限」诉求**（`帮我申请…` / `帮我提交…`）也吞成 `APPLY_LEAVE`。这不是「漏」，是**语义混淆**：
> 「申请权限」走的是 V36「用户通过 AI 提交申请」（`apply_permission` 工具），不是「去办请假」。
> 混为一谈的后果（实测）：
> ① prompt 的 `APPLY_LEAVE` 分支写「不得调用申请权限类工具」，而全局硬规则写「用户显式要求提交/申请权限时照常调用」
> —— **同一份 system prompt 自相矛盾**，V36 正对照能否通过全凭模型仲裁，不可复现；
> ② 同一句还会让 H5 弹出「请假」卡片，与「AI 已提交申请」的事实冲突（违反铁律 1）。
> 收窄后 `帮我申请年假`（带**假种**）仍由第 3 条命中，不会漏。

**反例（必须不命中）**：
- 问政策类：`年假有几天`、`请假流程是什么`、`考勤制度怎么规定`、`我想知道年假怎么算`
  —— 没有「要去办」的意愿动词，应保持 `action=null`。
- **申请权限类（2026-10-17 新增）**：`请直接调用工具帮我提交 approval:leave 权限申请`、
  `帮我提交 approval:leave 权限申请`、`帮我申请一下请假权限` —— 应保持 `action=null`，
  以便走 V36 的 AI 提交路径、并且**不**触发 H5 的请假卡片。
  用例：`agent/tests/test_worker_intake.py::test_action_apply_leave_not_triggered_for_permission_apply`。

### 1.4 H5 分支（唯一判定在服务端）

在 `oaAfterOaAnswer()` 里、**不受项目上下文门控**地调用新函数
`oaMaybeLeaveAction(intent)`，仅当 `intent.action === 'APPLY_LEAVE'` 时进入：

| 条件 | 界面行为 |
|---|---|
| `held === false && pending === false` | 弹卡片：标题「办理请假需要「请假审批」权限」，正文说明该权限由租户管理员/系统管理员授权；两个按钮 **[帮我申请]** **[取消]** |
| `pending === true` | 卡片只提示「权限申请已提交，正在审批中」，无申请按钮（避免重复提交），保留 [取消] 关闭 |
| `held === true` 且 `state.workers` 里存在 `workerType === intent.role` 的可用员工 | 直接 `oaPickWorker(该员工)` 切到该数字人（按既有语义**新建会话**），并给出可见反馈 |
| `held === true` 且**不存在**匹配员工 | 先按 1.5 补齐目标，再跳转；反馈里说明「已为你创建并进入「请假助手」」 |

- **[帮我申请]** → `POST /api/v1/org/permissions/apply`，body：
  `{"permissionCode": intent.requiredPermission, "targetWorkerType": intent.role, "reason": "在对话中申请办理请假"}`
  - 成功 → 卡片冻结为「已提交，等待审批」，并提示后续可在「我的权限」查看进度
  - 失败 → 卡片内就地显示后端 `message`（**不要**吞掉，也不要弹通用 toast 顶替）
- **[取消]** → 关闭卡片，**不提交任何请求**。

> 「用户可以取消」的口径：**取消 = 放弃本次「帮你申请」的动作，不落库**。
> 已提交的 PENDING 申请**不在本次范围**内撤回（后端当前不支持，见 §0）。

### 1.5 目标数字员工缺失时的兜底

`held === true` 但在 `state.workers` 里找不到 `workerType === intent.role` 的可用员工（本演示环境即如此）时：

1. 调 `POST /api/v1/workers` 创建一名请假数字员工（`API.createWorker`，已存在）。
   —— 字段名以后端 `WorkerController` 创建接口（`WorkerController.java:381` 起）的实际 `@RequestBody` 为准，
   实现者**必须先读该 DTO**，不得照抄本文件的示例字段。
2. 创建成功后**重新拉取** `API.workers()`，再用返回的 id 跳转。
3. **幂等**：只有「找不到」才创建；同一用户重复触发不得产生第二个「请假助手」。
4. 创建**失败**（如缺 `worker:create`）时如实提示失败原因，不得静默吞掉、也不得假装已跳转。

### 1.6 收敛双判定点（铁律 1）

`oaIsLeaveRequest` / `oaLeaveCapable` / `oaMaybeLeaveForm` 这套**本地词表判定必须撤除**：

- `oaMaybeLeaveForm()` 要么删除，要么退化为**纯渲染器**（只负责把服务端已判定的结果画出来），
  **不得**再自行用本地词表判断「这是不是请假」。
- 收敛后「是不是请假」只有**一处**判定：agent 的 `intake.py`。

### 1.7 写操作闸门（**确定性**，不靠提示词自觉）

**背景（实测缺陷）**：只靠 §1.3 的 `action` 让 H5 弹卡片是不够的 —— 模型可能在用户**还没点按钮**时
就抢先调用 `apply_permission` 把申请落库，使「用户可以取消」形同虚设（卡片还在，申请已提交）。
写提示词只能**降低概率**，不能作为保证。**同一类缺陷已实测复现两次**：
`CREATE_WORKER`（记为 `D3`，见 `scripts/_verify_exec_intent_ui.py` 头部）与 `APPLY_LEAVE`（本轮）。

**机制**：`apply_permission` 是 `ExternalToolHandler` Bean，由 `ToolGatewayService.listTools()`
**无条件注入**模型工具表（该路径**绕过** `tool_definition` 表，故在库里 grep 不到它）——
这是 V36 需求①「用户通过 AI 提交申请」的入口，**不能删**。

**闸门（agent 侧，唯一判定点）**：`agent/aios_ai/graph/nodes.py::prepare()` 组装完工具表后调用纯函数
`filter_intent_write_tools(tools, detect_action(req.text))`：

| 本轮 `action` | 工具表 |
|---|---|
| 任意动作码（`APPLY_LEAVE` / `CREATE_WORKER` / `UPLOAD_FILE` / `REPORT_EXPENSE`） | **剔除** `apply_permission` ⇒ 模型即使「想」抢先落库也**无工具可调** |
| `null`（普通对话） | **原样返回**（零回归） |

**为什么按「有无动作意图」而不是按「是不是请假」**：`detect_action` 只可能返回 `_ACTION_RULES` 里的四个码，
而这四个动作的**确认入口都在界面**（H5 开窗口/卡片，用户点了才算数）⇒ 「本轮有动作意图」≡「界面拥有确认权」。
按动作枚举会漏（`CREATE_WORKER` 的同类缺陷 D3 就是这么漏下的），按这个谓词则一处覆盖全部。

**为什么只剔这一个工具**：这条链上外部工具只有两个 Bean（已核）——
`apply_permission`（**写**，V36 入口，不能删）与 `list_my_permission_grants`（**读**）。
读工具**必须保留**（模型要能回答「我申请到哪一步了」），故是白名单式剔一个，不是按前缀扫。

**为什么不会误伤 V36**：显式申请诉求（`帮我提交 approval:leave 权限申请`）按 §1.3 收窄后**不判任何动作**
（`action=null`）⇒ 闸门不触发、工具照常暴露。两侧判据都已被下列用例钉住：

- `agent/tests/test_aios_ai_graph.py::test_leave_intent_hides_permission_write_tool`（**判据回到事实源头**：
  直接观察模型实际收到的 `tools` 列表，而不是读提示词文本）
- `test_create_worker_intent_hides_permission_write_tool`、`test_upload_intent_hides_permission_write_tool`（泛化面）
- `test_explicit_permission_apply_keeps_write_tool`、`test_no_intent_keeps_write_tool`（负向对照）
- `test_filter_intent_write_tools_pure`（纯函数面，含扁平 schema 与 `is` 同一性）

**判别力已实测**：把 `prepare()` 里那次调用注释掉 → 上面 3 条正向断言**准确变红**，2 条负向对照仍绿；
还原后全绿（`grep -c MUTATION-TEMP` = 0）。

## 3. 验收判据（可复跑）

1. **接口层**：`POST /api/v1/workers/intent {"text":"我要请假"}`
   - zhangsan → `action=APPLY_LEAVE`、`held=false`、`pending=false`
   - admin → `action=APPLY_LEAVE`、`held=true`
2. **反例**：`{"text":"年假有几天"}` → `action` 必须为 `null`（不得触发申请卡）。
3. **申请落库**：**用 `fagai_liu`（tenant 2 普通成员，见 §0）**触发申请后，
   `GET /api/v1/org/permissions/catalog` 里 `approval:leave.pending` 变 `true`；再次 intent 应返回 `pending=true`。
   - ⚠️ 原文此处写 `zhangsan` 是**错的**：`zhangsan` 属 tenant 0 且无机构，首节点 `ORG_ADMIN` 解析不出审批人，
     `apply` 必返回 400（FR-B2）且 PENDING 插入回滚，`pending` 永远变不成 `true`（详见 §0 第三条）。
   - ⚠️ **收尾是硬要求**：PENDING 的申请**不可自助撤回**（`revoke` 明确拒绝），只能由**该机构管理员驳回**
     （`GET /api/v1/workflow/tasks?scope=todo` → `POST /api/v1/workflow/tasks/{id}/decide` body `{"decision":"REJECT"}`）。
     不收拾尾，本判据第二次跑必红（PENDING 残留 ⇒ 卡片不再给申请按钮）。
4. **跳转**：admin 触发后，H5 必须真的切到 `workerType=LEAVE_APPROVER` 的数字员工
   （新建会话且该会话绑定该 workerId），顶栏/气泡有可见反馈。
5. **负向对照（必备）**：把 H5 分支的条件反转（或把 agent 词表去掉）后，
   第 3/4 条必须**变红**；证明判据有判别力，不是恒真断言。

## 4. 已知边界（不粉饰）

- **演示环境原本没有任何请假数字员工**：§1.5 的兜底会在首次触发时**创建**一个。
  这是有意为之的产品行为（需求要求「自己跳转」），但属于**写操作**，需在反馈里明示。
- **`approval:leave` 不在任何 seed 授权里**：普通用户首次必然走申请分支，这是设计而非缺陷。
- **在途申请不可撤回**：用户若想撤回已提交的申请，需要后端新增能力（本次不做）。
- **额度**：`zhangsan` 今日免费额度已用完，真实对话会 `403`；但本需求走的是**关键词意图接口**，
  不消耗额度，故不受影响。
