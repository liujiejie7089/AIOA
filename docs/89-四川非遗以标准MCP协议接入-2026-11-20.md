| 项 | 结论 |

`McpBuiltinHandler` 在 aios-resource、工具服务在 aios-integration-scfy，两者无依赖关系，加 Handler 会引入跨模块耦合并重打包 fat jar；
hub 原生连接器是平台声明的标准扩展点（`connectors/registry.py`），零改基座。

## 3. 接入点（怎么被 agent 用到）

```
agent  ──mcp__scfy__<tool>──►  mcp-hub /mcp/scfy  ──GET /show/*──►  非遗服务 16060
          ▲ manifest                ▲ FastMCP 原生连接器
          │                         │
     server:8080 /api/v1/mcp/manifest（只列 trusted=1）
                                   ▲
                          POST /api/v1/mcp/servers/scfy/trust（信任闸门，写工具快照）
```

1. 部署后 hub 自动加载 `scfy`（日志 `scfy MCP 就绪：69 个只读工具`）。
2. **一次性信任**：管理员 `POST /api/v1/mcp/servers/scfy/trust`，探测 hub 通过后写工具快照、`trusted=1`。
   此后 `GET /api/v1/mcp/manifest` 才出现 scfy，agent 注入 `mcp__scfy__*`（与 qq_mail/wecom_cli 同流程）。
3. 用户提问由模型自行选工具，参数错配/缺参由 catalog description（含实测校正）引导，不猜参。

## 6. 数据访问边界与风险

- **只读**：55 工具全标 `read_only_hint=true`，无写路径；不接非遗后台 CRUD/需登录接口。
- **凭据**：`/show/*` 免登录，无凭据落盘；不引入新一轮密钥面。
- **静默失效**：area 用简称（甘孜州）、level 只有 country 生效等实测校正已写进工具 description；
  但模型仍可能传错，错误表现为空集而非报错 —— 属非遗系统侧缺陷，本模块只做如实提示，不改上游。
- **外部依赖**：生产默认指向西昌；若不可达，`tools/call` 返回 `ok=false` + 原因，不伪装成功。
- **验证用 hub**：本次为验证临时启动的 :8099 已停止；实际启用按用户自有终端 `start-all.sh` 或 compose。

## 8. 运行期故障复盘：14:38「省级非遗项目」无结果（2026-11-20）

用户在别的租户（tenant=56）只问「省级非遗项目」，页面回答「非遗项目查询服务调用失败，均未返回结果」。
**这不是 MCP 接入缺陷，也不是模型选工具的问题，而是非遗系统自身的数据库断了。**

**证据链**

| 层 | 实测 |
|---|---|
| 页面 | 数据来源标注 scfy 的 6 个工具（project_count/list/area_summary/type_data/batch_data/inheritor_count）全部 `ok:false` |
| 工具审计 | `run_20261120143837_892851`（SUCCEEDED）：6 个 scfy 工具 `output_digest` 均是 `{"ok":false,…,"errors":"调用非遗服务失败：…"}`；另 `kb_table_query` FAILED、知识库命中的是无关的成绩单 PDF |
| hub 日志 | `14:39:03 ~ 14:40:17 scfy call <tool> failed:`（server.py:91） |
| 直连上游 | `GET /show/project/getProjectCountByArea` 20s 后 `ReadTimeout`；加长到 45s 后返回 HTTP 200 但 body 是 `code=500`：`Could not open JDBC Connection for transaction; nested exception is com.alibaba.druid.pool.GetConnectionTimeoutException: wait millis 10000, active 0, maxActive 20, creating 1` |
| 线程栈 | `Druid-ConnectionPool-Create` 线程卡在 `com.kingbase8.core...ConnectionFactoryImpl.tryConnect → java.net.Socket.connect → waitForConnect`；业务线程卡在 `DruidDataSource.pollLast` 等连接 |
| 网络 | 非遗进程持有到 `192.168.0.205:54321`（人大金仓）的连接状态 `SynSent`；`Test-NetConnection 192.168.0.205 -Port 54321` → `TcpTestSucceeded=False, PingSucceeded=False` |
| 排除项 | 16060 端口 LISTEN、进程在、Redis 127.0.0.1:6379 与 MySQL 3306 均 LISTEN；模型、manifest、trust、hub 均正常 |

**根因**：非遗服务（Java 8 / war）依赖的 Kingbase8 数据库 `192.168.0.205:54321` 网络不可达，
Druid 建连卡在 TCP 握手 → 取连接 10s 超时 → 上游接口 20s+ 才回 500 → hub 侧 20s `httpx.Timeout` 先触发 `ReadTimeout` →
6 个工具全失败 → 模型据实回答「无法核验」。链路没有把失败伪装成空集，行为正确。

**恢复路径（不在 aios 侧）**：恢复本机到 `192.168.0.205:54321` 的网络（VPN/网段/数据库主机），
或修正非遗服务 `application.yml` 里的 `jdbc:kingbase8://192.168.0.205:54321/...` 指向可达实例后重启 16060。
恢复后 `test` 一次 MCP 工具即可，无需改 aios 代码、无需重新 trust。

**可改进项（未实施）**：hub 当前对上游超时统一回「调用非遗服务失败：timed out」，
模型只能笼统说「服务调用失败」。若后续要把「数据库不可达」这类原因透出给用户，需要在 scfy `server.py::_call`
里对 `httpx.TimeoutException` 单独给出人话提示（原错误仍只进日志），并同步更新工具 description。

## 9. 修复：MCP 工具连续失败熔断（2026-11-20 18:30）

**缺陷**：上游数据源整体不可用时，模型一轮内并发调 15 个同 server 工具，全部 20s 超时，
页面出现「部分接口失败…继续尝试其他接口」这类无法兑现的承诺（模型并没有真的继续，只是把失败结果写成计划）。

**改动**（agent 侧，4 个文件）：

| 文件 | 改动 |
|---|---|
| `agent/aios_ai/graph/nodes.py` | 新增 `MCP_MAX_CALLS_PER_SERVER=4`、`MCP_FAILURES_TO_TRIP=3`、`MCP_BREAKER_ERROR` 及三个纯函数 `_breaker_of_call` / `_plan_mcp_calls` / `_update_breakers`；`tools()` 节点按熔断态分流，短路调用不真实执行但**回注 ok=False**（协议要求），并更新跨轮熔断态 |
| `agent/aios_ai/graph/state.py` | `RunState` 声明 `mcp_breakers`（原始类型，checkpointer 可序列化） |
| `agent/tests/test_mcp_breaker.py` | 新增 8 条测试（单轮上限 / 已熔断全短路 / 连续失败置位 / 成功清零 / 隔离其他 server / 文案不外泄上游原文 / 图级 tool 消息完整 / 跨轮熔断） |

**两层保护**：

1. **单轮同 server 上限**：一轮内同一 server 最多真实执行 4 个调用，其余直接短路——15 个并发不再打满网关、不再各自等 20s。
2. **跨轮连续失败熔断**：同一 server 连续失败 3 次即置 `tripped`，本 run 后续该 server 的全部调用短路；任一成功即清零（真恢复优先）。

**关键纪律**：短路调用仍回注 `ok=False` 的 tool 消息（丢掉会让 `tool_call_id` 找不到结果，上游判协议错误）；
文案只说「数据源不可用、不要再试同数据源」，**不带上游错误原文**（铁律 7/12）。非 MCP 工具零影响。

**验证**：

## 13. 按租户接入改造（V115，2026-11-21）

> 本节只记接入模型的**形态变更**；完整实施、判据、API、双层闸门与验收见 `docs/93`。
