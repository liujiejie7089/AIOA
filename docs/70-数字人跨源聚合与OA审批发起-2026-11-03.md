# 数字人跨源数据聚合 与 OA 审批发起（2026-11-03）

> 两件事，一条主线：**让数字人真的能"替你汇总"和"替你办事"，并且每一步都可溯源、可流转。**
>
> - 能力一：用户说"总结本周工作"→ 代码主动拉齐已接入的三方数据 + 内部模块 + 内部知识库 → 统一汇总 → **逐条标注来源**。
> - 能力二：用户说"请个假，交给张三代批"→ 一次填完字段卡 → 指定处理人成为第 1 级 → 若后台配了审批流则**继续自动流转**。
>
> 本文回答三个被点名的问题：**数据源接入范围**（§2）、**审批流流转逻辑**（§4）、**异常处理方式**（§5）。

---

## 1. 核心取舍：语义给模型，扇出与流转给代码

两处都曾实测踩到同一个坑：**工具存在 ≠ 模型会用**。

| 场景 | 提示词已写明 | 模型实际行为 | 后果 |
|---|---|---|---|
| 模糊实体（2026-11-02） | "先查候选人再 ask_user" | 直接回"请提供姓名" | 多一轮往返 |
| 企微写操作 | "有写工具就调" | 写一段散文反问 | 用户以为功能没做 |
| **周报汇总（本轮）** | "多源都查一下" | 只查一两个源就开始写 | **半份周报，用户看不出来** |
| **请假发起（本轮）** | "问全再提交" | 逐项追问，假种码靠猜 | 五六轮往返，猜错被拒 |

结论写成纪律：**"该问哪几样 / 用什么控件"是语义判断，交给模型；"查哪些源 / 怎么流转"是确定逻辑，交给代码。** 代码侧不允许出现"模型大概率会…"这种假设。

## 2. 数据源接入范围

### 2.1 三类源，一张表

| 类别 | 来源 | 代码 | 本轮是否参与聚合 | 读取内容 |
|---|---|---|---|---|
| **三方连接器** | 企业微信 | `wecom_cli`（25 工具） | ✅ 会话 / 待办 / 日历 | `recent_group_sessions` `todo_list` `calendar_list` |
| | QQ 邮箱 | `qq_mail`（6 工具） | ✅ 收件箱 | `list_messages` |
| | 钉钉 | `dingtalk`（**未接入**） | ⭕ 预留 | 见 §2.4 |
| **内部模块** | 审批 | 网关工具 `list_my_approvals` | ✅ 我的审批单 | 单号 / 标题 / 状态 |
| | 请假 | `list_my_leaves` | ⭕ 规划中 | — |
| | 门户公告/会议/日程 | 无工具 | ❌ 未暴露 | 现有 REST 接口，见 §8 |
| **内部知识库** | 制度文档 | `search_kb_documents` | ✅ 语义检索 | 切片 + 文档名 |
| **外部网页** | 联网 | `web_search` | ❌ 不参与（周报不查外网） | — |

> **"接入"的定义**：工具进了 `/api/v1/tools` 白名单（网关）或 `/api/v1/mcp/manifest`（连接器），
> 且能被 `ToolClient` 调用。只有 REST 接口、没有对应工具的域**不算接入**——
> 模型看不见它，聚合也够不到它。

> **⚠️ 连接器是"一人一账号"**：`/api/v1/mcp/manifest` **按当前用户**返回（企微需本人扫码绑定）。
> 实测：未扫码的账号 manifest 返回 `[]`，聚合就只剩内部源，且**不会报错**（设计如此）。
> 所以「这个用户为什么没汇总到企微数据」的第一排查项永远是：他自己授权了吗。

### 2.2 每个源的口径（为什么选这些工具）

| 源 | 工具 | 参数 | 为什么是它 |
|---|---|---|---|
| 企微 · 最近会话 | `recent_group_sessions` | `days=7` | 官方上限就是 7 天，正好对应"这周" |
| 企微 · 待办 | `todo_list` | `limit=20` | "我欠了什么"是周报的必备一节 |
| 企微 · 日历 | `calendar_list` | 空（默认区间） | "我这周开了哪些会"交给日历比自己推更准 |
| 邮箱 · 收件箱 | `list_messages` | `limit=10` | 邮件是外部诉求的主要入口；10 封足够成文，不淹没重点 |
| 审批 · 我的单 | `list_my_approvals` | 空 | 请假/报销批到哪一步，属于"本周进展" |
| 知识库 | `search_kb_documents` | 用户原话 | 复用既有预检索，不另造一套 |

**刻意不查 `doc_search`（企微文档）**：企微文档库多是制度/资料，不属于"本周工作"，
拉进来会把周报写歪成资料汇编。用户真要引用文档会明说，走普通问答即可。

### 2.3 连接器可替换性

聚合计划里写的是**工具短名**（`todo_list`），不是 `mcp__wecom_cli__todo_list`。
运行时由 `resolve_plan()` 按后缀匹配本轮真实挂载的工具名，并**优先选与 `code` 同名的 server**。
这带来两个直接好处：

1. 换连接器（企微 → 钉钉）不改聚合代码，只要新 server 暴露同名工具；
2. 没装某个连接器的用户不会因为说了"周报"而报错——匹配不上就静默跳过该源。

### 2.4 新增一个数据源要改哪几处

| 步骤 | 位置 | 说明 |
|---|---|---|
| ① 暴露工具 | 连接器 catalog 或 `ToolGatewayService.REGISTRY` | 没工具一切免谈 |
| ② 登记来源名 | `agent/aios_ai/knowledge/sources.py` 的 `SOURCE_LABELS` / `SOURCE_KINDS` | 未登记会回退成 code 原文（不丢，但显示成英文） |
| ③ 接入聚合 | `agent/aios_ai/aggregate/plan.py` 的 `DEFAULT_PLAN` 加一条 `SourceCall` | 只有"周报该看它"时才加 |
| ④ 动作名 | `sources.py` 的 `MCP_TOOL_LABELS` / `GATEWAY_TOOL_LABELS` | 引用区显示"会话消息"而不是 `session_messages` |

## 3. 智能聚合与总结（能力一）

### 3.1 触发判据

```python
AGGREGATE_RE = 周报|日报|月报|季报|半月报|年报
             | (总结|汇总|归纳|整理).{0,6}(一下|这|本|近期|最近|本周|上周|本月|上月|工作|进展|情况)
             | (这|本|上周|本周|最近|近期).{0,4}(周|月).{0,4}(工作|情况|进展|总结|汇报)
             | 复盘|小结|汇报材料|工作汇报|述职
```

**反向闸**（命中即不触发）：`怎么写 / 如何写 / 模板 / 格式 / 范例 / 范文 / 要求是什么`
——问"周报怎么写"是要模板，不是要我们真去汇总。

为什么收窄：**触发即意味着多发 5 次工具调用**。误触发是实打实的延迟与配额。

| 输入 | 判定 | 理由 |
|---|---|---|
| 帮我总结一下这周的周报 | ✅ | 明确汇总诉求 |
| 汇总本周工作进展 | ✅ | 同上 |
| 复盘一下这个月 | ✅ | 同上 |
| 周报模板在哪里 / 周报怎么写 | ❌ | 要模板 |
| 我上周请了几天假 | ❌ | 单点查询 |
| 你好 | ❌ | 闲聊 |

### 3.2 扇出与并发

`aggregate/plan.py::gather()` 用 `asyncio.gather` 并发执行，**单源超时 12s**，
单源输出**截断 2200 字符**（不设上限会把上下文撑爆，也会让模型把最长那段当重点）。

### 3.3 来源标注：为什么"每条都能对上源"

引用条目形状在 2026-11-03 有意扩展：

```json
{"docId": "wecom_cli:m1", "title": "周报我周五发", "source": "wecom_cli",
 "label": "企业微信", "action": "会话消息"}
```

- 老键 `docId/title/source` 语义不变（既有调用方零改动）；
- 新键 `label`（中文源名）、`action`（动作名）供前端**分组展示**。

两级粒度：

| 粒度 | 何时用 | 例子 |
|---|---|---|
| **条目级** | 返回是列表且能挖到标题（`title/subject/name/content/…`） | 每封邮件、每份文档各一条 |
| **调用级** | 返回是单对象/纯文本/挖不到标题 | 「企业微信 · 最近会话（3 条）」 |

三条硬口径：

1. **单次调用最多 6 条**（`MAX_CITATIONS_PER_CALL`）——`list_messages` 回 200 封不该把 citations 撑成几百条；
2. **空结果不产引用**——"查了没查到"不是来源，标出来会误导用户以为有依据；
3. **交互工具不产引用**——`ask_user`/`request_form` 不是数据源，给它们挂"来源"会让引用区变成操作日志。

前端从"平铺一句 `来源：xxx`"改为**按来源分组**（`citeHtml()`）：
一个来源一行，行内最多 3 条具体条目，超出显示 `+N`。经典态与 OA 态各有一套配色。

### 3.4 失败口径（这条最关键）

单个源失败/超时/未授权**绝不打挂整条 run**，而是：

1. 记进 `SourceResult.error`；
2. 在注入块末尾**显式列出"本轮未能获取的源"**。

第 2 条是重点。静默跳过会让模型以为"已经查全了"，进而把半份数据写成完整周报——
**这不只是答错，是让用户无法察觉的答错**。把缺口告诉模型，它才会在回答里说"邮箱数据本次不可用"。

注入块还带五条硬要求（节选）：

> 3. 若某源本次未获取到（见上），必须在回答末尾**如实说明该源缺失**，不得用其它源的内容冒充它的覆盖范围。
> 4. 数据为空就直说"本周在 X 上没有记录"，不要编造。
> 5. 时间/数字必须来自素材，不要推算或补全。

### 3.5 与知识库预检索的分工

知识库**不**进 `DEFAULT_PLAN`：它走自己的语义检索（query 改写、阈值、切片拼装、`kb_on` 开关），
重复实现只会产生两套口径。但聚合块**必须把它的命中情况算进覆盖面**：

```
### 内部知识库 · 语义检索
已命中 3 个片段，原文见上文「参考片段」。
```

否则来源清单里只剩聊天记录与邮件，用户会以为 AI 没看公司文档。

### 3.6 聚合轮次必须收起表单工具（实测发现）

真机第一跑就翻车：用户说「总结一下我这周的工作，写个周报」，`intake` 把它判成**公文起草**意图，
模型随即调 `request_form` 弹了一张「工作报告」**空表** —— 5 个源的数据一条没用上，
界面只剩一张表。用户要的是「已经发生的事的汇总」，不是要填新表。

修法与 `filter_expert_tools` 同口径：聚合确实拿到数据后，**本轮不向模型暴露 `request_form`**
（`strip_form_for_aggregate`），而不是在提示词里写「不要弹表单」——后者是软约束，本项目已两次证明挡不住。

> 这条也解释了为什么"有没有聚合"不能看 `tool.call` 事件：扇出发生在 `prepare` 阶段
> （代码直连 `ToolClient`），**根本不进模型的 `tool_calls`**。可观测点是 citations 与正文的来源标注。

## 4. OA 审批发起与流转（能力二）

### 4.1 现状：引擎早就够用，缺的是"入口"

`ApprovalFlowService`（2250 行）已有：多级步骤展开、按类型找人（7 种策略）、条件路由、
会签/抢占、知会、加签、子流程、催办、超时扫描、模板版本 diff。

缺口只有两个，都在**入口层**：

1. AI 没有"发起请假"的工具（只有 5 个只读工具）；
2. 引擎的 `SPECIFIC` 策略只在 **step 自己声明 `approver_type=SPECIFIC`** 时才生效，
   而请假默认流是 `APPLICANT_SUPERIOR`——**用户选的人会被静默忽略**。
   表现正是"我选了张三，张三却没收到审批"。

### 4.2 指定处理人的语义（本轮核心）

`SubmitReq` 新增 `assigneeUserId`，在 `expandNodes` **兜底之前**先判定"后台到底有没有配流"：

```
提交
 ├─ assigneeUserId == null
 │    └─ 走原逻辑（完全不变）
 └─ assigneeUserId != null
      ├─ 自审拦截：assignee == 申请人 ⇒ 400
      ├─ 后台**没配**审批流 ⇒ 只有这一个节点，处理完直接终态
      └─ 后台**配了**审批流 ⇒ 插入为第 1 级（原节点 seq+1），此后按规则自动流转
```

三条硬口径：

| 情形 | 行为 | 理由 |
|---|---|---|
| 指定人 = 申请人 | **400 拒绝** | 自己批自己没有意义，且会占住唯一节点让流程永远等他自己 |
| 无配置流 | **单节点**，不追兜底节点 | 用户明确点名了人，不该让他再等一个他从没同意过的审批人 |
| 有配置流，首节点恰好是同一个人 | **不重复插入** | 否则同一个人要批两次 |

为什么不用 `specificApproverId`：它是"step 声明 SPECIFIC 时读的兜底值"，
绝大多数流程没有这个 step，塞进去会被静默忽略。这是**静默失败**，必须先消灭。

### 4.3 流转状态机（完整）

```
approval_order (PENDING)
  └─ expandNodes → N 条 approval_task（seq 升序；同 seq = 同一级的一组）
       └─ 当前节点 = seq 最小的 PENDING 组
            ├─ single    ：组内 1 人，他批完即推进
            ├─ parallel  ：会签，**全部通过**才推进
            ├─ grab      ：抢占，**任一人**处理即完成，同组其他置 SKIPPED
            ├─ 通过      → 推进下一 seq；末节点通过 ⇒ order=APPROVED + 回调
            └─ 驳回      → 其余 PENDING 全 SKIPPED ⇒ order=REJECTED + 回调
```

**"处理完成后直接返回处理结果"** 的落地：`submit` 的返回体已含
`currentApproverId / currentApproverName`，本轮再加 `assigneeUserId` 回显；
要查"批完了吗"用新工具 `get_approval_result(orderId)`，返回
`status / statusText / currentApprovers / currentStep / timeline`。

### 4.4 处理人候选的独立口径

`list_approval_handlers` 查的是**本机构 `org_member` 在职成员**，不是通讯录。

| 口径 | 能用吗 | 为什么 |
|---|---|---|
| 企微 `contact_search` | ❌ 不能 | 混着外部联系人 / 离职未清理的人，拿这些 id 建任务 = 永远没人处理的待办 |
| `org_member`（本机构在职） | ✅ | 审批引擎按 `user_id` 建任务，口径必须与组织一致 |

返回 `userId / name / jobTitle / dutyCode / departmentId`，**排除申请人本人**，上限 60。

### 4.5 一次填完：字段卡

`intent/leave_apply.py` 在 `prepare` 阶段用真实候选合成字段卡（复用 `ask_user.fields` 协议）：

| 字段 | 控件 | 候选来源 |
|---|---|---|
| 假种 | `select`（查不到目录时退化 `text`） | `list_leave_types`（只列启用中） |
| 开始 / 结束日期 | `date` | — |
| 事由 | `textarea` | — |
| **交给谁处理** | `select` + `searchable` | `list_approval_handlers` |

触发面**刻意收窄**到"请假类词 + 指派语义"：

| 输入 | 触发 | 走向 |
|---|---|---|
| 帮我请个假，交给张三代批 | ✅ | 字段卡（一次填完） |
| 我明天调休，让李四处理 | ✅ | 同上 |
| 帮我请假 | ❌ | 既有表单链路（零变化） |
| 请假流程是什么 | ❌ | 普通问答 |
| 我的请假记录查一下 | ❌ | 普通问答 |

命中后 **短路**：`rounds == 0` 直接把合成好的卡作为 tool_call 抛出，**不给模型写正文的机会**
（模型会用自己的话再问一遍，而且问不全、假种码靠猜）。

## 5. 异常处理

### 5.1 聚合侧

| 场景 | 行为 | 用户看到 |
|---|---|---|
| 某源超时（>12s） | 记 `error="超时"`，其余源继续 | 回答末尾"邮箱数据本次不可用" |
| 某源抛异常 | 同上，异常不外溢 | 同上 |
| 连接器未授权 | 记"调用失败"，**不算成功** | 同上 |
| 查询成功但为空 | **算成功**（`count=0`），渲染"（空）" | "本周在待办上没有记录" |
| 所有源都失败 | 仍注入"未能获取的源"块 | 模型如实说明，不编造 |
| 知识库未命中 | 写"已检索但未命中" | 不声称有制度依据 |
| 非汇总诉求 | `collect` 返回空串，链路完全不变 | 无感知 |

### 5.2 审批侧

| 场景 | 行为 | 用户看到 |
|---|---|---|
| 处理人不在本机构在职成员中 | `400`（服务端校验） | "指定的处理人不在本机构在职成员中，请重新选择" |
| 处理人 = 申请人 | `400` | "处理人不能是申请人本人" |
| 假种不存在 / 已停用 | `400` | "假种「X」已停用，不可申请" |
| 余额不足 | `400` | "可用 3 天，本次申请 5 天" |
| 需证明但未上传 | `400` | "「病假」必须上传证明材料" |
| 日期早于需提前天数 | `400` | "需提前 2 天申请，最早可申请 2026-11-05" |
| 节点全部被跳过 | `400` | "审批节点全部被跳过，请检查 threshold_days / when" |
| 并发决策同一任务 | `409`（`UPDATE … WHERE status='PENDING'` 判影响行数） | "该任务已被处理" |
| 查他人审批单 | `ok=false` | "无权查看该审批单" |
| 未绑定机构 | `ok=false`（不是空列表） | "当前账号未绑定机构，请先在组织管理中登记" |
| 假种/处理人候选查不到 | **不弹卡**（宁可退回模型问答，也不弹死控件） | 正常问答 |

> 校验一律复用 `LeaveService.submit` 的原链（`POST /api/v1/workflow/leave/requests` 同一条），
> **没有"AI 版宽松校验"** —— AI 只是另一个入口，不是旁路。

## 8. 已知边界

1. **聚合是"计划式"而非"自适应"**：`DEFAULT_PLAN` 固定 5 个源，不根据用户话里的线索动态增减
   （如"只看邮件"仍会扇出全部）。理由：自适应需要模型参与决策，而本轮的原则恰恰是不信任模型自觉。
2. **单源输出截断 2200 字符**：长会话会被截断，可能丢掉尾部信息。
3. **门户 / 项目 / Gitee 未接入**：只有 REST 接口、没有工具，聚合够不到。
4. **钉钉未接入**：`SOURCE_LABELS` 已留 `dingtalk` 词条，但无 server、无工具。
5. **请假表单入口仍存在**：不带指派语义的"帮我请假"走既有表单链路，与字段卡是两条路。
   长期应收敛成一条，但本轮为控回归面未动。
6. **`get_approval_result` 只认 `orderId`**：不能按"最近一单"查，用户需提供单号
   （模型可从 `submit_leave_request` 的返回值里拿）。
7. **审批流的条件表达式仍只支持单字段比较**（`when: {field, op, value}`），
   没有金额/天数之外的复合表达式。
8. **聚合覆盖范围取决于"本人授权"**：连接器按用户隔离，未扫码的账号自然没有该源，
   且不报错（§2.1 的警示）。想验证多源聚合，请用已授权的账号。
9. **聚合扇出不产生 `tool.call` 事件**：它发生在 `prepare` 阶段。以此判断"有没有聚合"会误判为没有，
   请看 citations 与正文的来源标注。
