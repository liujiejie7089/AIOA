## 0. 共同前提

### 0.1 ★ 必须先纠正的一个前提：后端 ASR 解决不了「录不到音」

用户选「后端 ASR」，直觉是「这样内网 HTTP 也能用」。**这个推论只对一半，且错的那一半是致命的。**

麦克风相关的浏览器 API（`navigator.mediaDevices.getUserMedia`）与 Web Speech API 一样，**都要求安全上下文**（`https://` 或 `http://localhost` / `127.0.0.1`）。**在 `http://10.0.0.3` 这类局域网 HTTP 地址下，`navigator.mediaDevices` 直接是 `undefined`** —— 浏览器连录音能力都不提供。

⇒ **「录音」与「识别」是两段，后端 ASR 只换掉了「识别」那一段，「录音」这一段仍然被安全上下文卡住。**

| 访问方式 | 能否录音（getUserMedia） | 后端 ASR 有用吗 |
|---|---|---|
| `https://mall.egooaicloud.com/aioa/h5/`（公网 HTTPS） | ✅ 可以 | ✅ 有用 |
| `http://localhost` / `127.0.0.1:8080` / `:5181`（本地） | ✅ 可以 | ✅ 有用 |
| `http://10.0.0.3/...`（生产内网 HTTP） | ❌ **不可以** | ❌ **无用**（没有音频可上传） |

**因此语音方案必须同时选「录音怎么来」，见 §2.2 的三条路。** 这也意味着：**若坚持内网 HTTP 直连交付语音，则要么给内网配 HTTPS，要么只能退化为「选/传音频文件→转写」，不存在第三条路。**

### 0.2 三条已核实的事实（勿再按直觉假设）

1. **「供 AI 参考」的链路上游已经通了。** 知识库上传 → 解析 → 切片 → 向量化 → 工具回调检索 → 回答带 `citations` 出处，**全链路已实现并有验收**（`_e2e_kb_doc.py`、`e2e_v62_milvus_kb.py`）。本次**不需要**新造检索机制。
2. **`i-mic` 图标已在产物里但没有控件用它**（`user-client/_build_oa.py:45` 的 `ADD_SYMBOLS` 注入 `i-mic`）；全仓 `agent/**`、`server/**`、`web/**` 搜 `asr|tts|audio|speech|voice|whisper` **零命中**，`agent` 依赖里**没有任何音频库** ⇒ 后端 ASR 是**从零新增**。
3. **项目文档库与知识库是两套存储，前者不进检索面。** 项目文档走 `FileController` 落本地盘（`aioa.upload.dir`）；知识库**不存原文件**，只存解析正文 + 切片 + 向量（`KbController.java:133-135` 注释「原文件不落盘」）⇒ **「传到项目文档里」本身不构成「供 AI 参考」**，见 §1.3 关键决策 ①。

### 0.3 三层同源纪律（本次触发的第 1 处）

「支持的格式」与「大小上限」这两件事，**后端 / 用户端 / 文案**必须同值：

- 现状**已经脱钩**：格式白名单常量写死在 `KbFileParser.java:41`（`SUPPORTED = "pdf、docx、doc、xlsx、xls、txt、md、csv"`），**漏列了 json/log**（`KbFileParser.java:31` 的注释与 `:53-69` 的实际分派都包含 json/log）⇒ 用户按提示以为不支持 json/log，实际支持；反过来 400 文案也就这样错了。
- 大小上限**三处硬编码**：常量 `KbFileParser.java:39` `MAX_BYTES = 50L*1024*1024`、控制器文案 `KbController.java:210`「文件超过 **50MB** 上限」（数字写死在字符串里）、配置 `application.yml:88` `aioa.file.max-size-mb: ${AIOA_FILE_MAX_SIZE_MB:50}`。
- 判据（铁律 1「展示必须与事实同源」）：**这四处（含前端 `accept`/文案）必须由一个出口派生**，改一处全局一致。

### 0.4 现状总览（一句话）

**「AI 参考文档」能力齐全但缺对话内入口；「文档落点分场景」与「格式/大小单一出口」是本次真正要新建/收敛的部分；「语音」从零新增且被安全上下文卡住录音。**

## 1. 需求一 · 对话内上传文档供 AI 参考

### 1.1 目标

用户在**对话坞**（`#oaDock`）里直接上传一份文档，随后向 AI 提问时，**AI 能检索到该文档内容并据此回答，且在回答中标出出处**。

### 1.2 范围

**做**：对话坞新增附件入口；按会话上下文决定落点；上传后把内容送进可检索面；上传结果在对话里可见；格式/大小约束收敛为单一出口；后端 400 文案纠错。

**不做**（明确排除，避免范围蔓延）：不新建第二套检索机制；不引入对象存储；不改知识库的解析/切片算法；不做「文档在线预览/编辑」；不做「会话级附件生命周期」（§5-Q5 已定本轮不做）。

### 1.3 关键设计决策

**① 落点分场景，且「项目内」必须额外入检索面**（核心）

用户口径：项目内→项目文档库；普通对话→知识库。但见 §0.2-3：**只落项目文档库 = 用户能在项目里看到，AI 却看不到**，直接违背本需求的目标。故：

- **普通对话（无项目上下文）**：直接 `POST /api/v1/kb/documents/upload`（`scope=PERSONAL`）⇒ 天然进检索面（会话检索默认覆盖本人可见资料）。
- **项目上下文（`oaState.currentProject` 非空）**：**双写**——
  - ① 落**项目文档库**（沿用现有链路 `POST /v1/files/upload` + `POST /v1/pm/projects/{id}/docs/documents`，用户可在项目详情「文档」页签看到，行为与今天一致）；
  - ② **同时**把同一份文件的解析正文登记进**知识库**，并**打上项目归属标记**，使其可被检索命中。
  - 检索范围：会话已在项目上下文时，由 agent 传 `kbScope` = **该项目已入库文档的 doc id 集合**。现有 `kbScope` 本就是「文档 ID 集合」（`KbController.java:330-347`）⇒ **不需要新增作用域枚举**，只需在项目会话的上下文里带上这个集合。

  ⚠️ 双写必须**原子语义**：②失败 ⇒ ①必须回滚或明确告知「已存项目文档但未被 AI 索引」，**不允许静默成功**（铁律 2）。是否采「先②后①」由实现定，但**终态必须回写主对象**。

**② 落点必须对用户可见地说明**（否则用户不知道该去哪找、也不知道 AI 到底看没看到）

上传成功后：在对话坞插一条气泡（复用 `_oa_app.js:1383 oaPushBub()`），文案明确「已上传《X》到**项目文档 / 我的知识库**，本次提问可引用」。落点不可猜。

**③ 格式与大小：一个出口，四处派生**（见 §0.3）

**④ 出处在回答里已有展示，不新造**：`_oa_app.js:1590` 已渲染「来源：…」引用块，`citations` 由 agent 回写（`ToolGatewayService.java:196-220` 返回 `docId/docName/snippet/chunkIndex/score/source`）。本次只保证**新上传的文档能进检索面**，呈现沿用。

### 1.4 格式与大小限制（口径）

| 项 | 值 | 唯一出口 |
|---|---|---|
| 支持格式 | `pdf / docx / doc / xlsx / xls / txt / md / csv / json / log` | 后端常量（修正后的 `SUPPORTED`） |
| 大小上限 | **50 MB**（沿用现值） | `aioa.file.max-size-mb`（读 `AIOA_FILE_MAX_SIZE_MB`，默认 50）⇒ 常量由它派生 |
| 详情查看截断 | 20000 字符（`VIEW_MAX_CHARS`），超长置 `truncated=true` | `KbController.java:85`（**保留现值，不在本轮改动**） |

**必须一并修掉的两处失真**：
1. `KbFileParser.java:41` 的 `SUPPORTED` **补上 `json`、`log`**；
2. `KbController.java:210` 文案里的硬编码「50MB」改为**由上限派生**（改配置后文案跟着变）。

**前端不得自造第四份**：H5 的文件选择器 `accept` 与超限前置校验文案，必须与后端同值；因 H5 是**构建产物**（`index.html` 不可手改，须改 `_oa_app.js` 后 `python user-client/_build_oa.py` 重建），需**用哨兵断言前后端同值**（见 §1.9 V3）。

### 1.5 AI 如何引用文档内容（机制说明，本轮不改）

1. 用户在对话里提问；
2. agent 判定需要外部资料 ⇒ 经业务工具网关回调 `ToolGatewayService.searchKb()`（`ToolGatewayService.java:196-220`），参数 `topK / threshold / mode / kbScope` 由 agent 透传；
3. 检索：`embeddingProvider.embed` → `store.search(mode ∈ {vector, bm25, hybrid})`；
4. 命中片段（`docName / snippet / chunkIndex / score / source="knowledge_base"`）进入模型上下文；
5. 回答落地时 agent 回写 `message.completed.citations` ⇒ 用户端渲染「来源：…」（`_oa_app.js:1590`）。

⚠️ **已知短板（列为依赖，不是本轮必做）**：默认 `aioa.kb.embedding-provider=local` 是 **256 维 char 2-gram 哈希、确定性但无语义**（`EmbeddingConfig.java:15-19`）。真语义检索需切 `http` + `store=milvus`（`docs/32`）。**本需求「AI 引用得准不准」主要由它决定**，建议单独立项。

### 1.7 角色权限

- 上传到**知识库（普通对话）**：与今天 `kbUploadFile` 同权——**已登录用户可上传，作用域 `PERSONAL`**；不得因本次改动放宽到跨用户可见。
- 上传到**项目文档库（项目内）**：沿用项目文档既有权限（非项目成员不得写）。
- **负向要求**：新入口**不得**成为绕过项目权限的后门（例如从普通对话把文件塞进某项目）。

### 1.8 预期输出

1. 对话坞出现附件入口，点击后走与上下文匹配的落点；
2. 上传成功在对话里有明确回执（含落点）；
3. 普通对话上传后提问，回答能命中该文档并标注来源；
4. 项目内上传后提问，回答能命中该文档并标注来源，且该文档同时出现在项目「文档」页签；
5. 超限/不支持格式给出**与后端同源**的提示文案。

### 1.10 风险

- **R1｜检索质量**：默认无语义 embedding 会让「引用得准」打折（见 §1.5）⇒ 先按现状交付并显式告知用户，切 Milvus 单独立项。
- **R2｜双写的失败窗口**：②失败而①成功会造成「看得见、AI 看不到」的静默不一致 ⇒ 由 V8 兜住。
- **R3｜权限后门**：新入口若允许在普通对话里指定 `projectId`，即成越权写入 ⇒ 由 §1.7 负向要求 + 权限套件兜住。
- **R4｜同一文件两份存储**：项目内双写会产生「项目文档库一份 + 知识库解析正文一份」，存储与删除语义需明确 ⇒ **§5-Q4 已定：删除项目文档时同时撤出检索面**。

## 2. 需求二 · 语音输入（后端 ASR）

### 2.1 目标与范围

**目标**：用户在对话坞点一下麦克风、说一句话，**文字落进输入框**，用户可编辑后再发送。

**做**：坞内麦克风入口；录音；上传；后端 ASR 转写；文本回填输入框；全链路失败态显式化。

**不做**：不做 TTS 朗读（用户已定「仅输入」）；不做语音唤醒；不做实时流式转写（先按「录完再转」交付）。

### 2.2 关键设计决策

**① ★ 录音来源（受 §0.1 约束的三条路，必须选一条）**

| 案 | 做法 | 内网 HTTP 直连可用？ | 代价 |
|---|---|---|---|
| A | `getUserMedia` + `MediaRecorder` 录音 → 上传 | ❌ 不可用 | 最自然；**要求 HTTPS 或 localhost** |
| B | `input[type=file][accept=audio/*][capture]` → 上传已有/现场录的音频 | ✅ 可用（移动端可唤起系统录音；桌面端一般只能选文件） | 体验退化，但**不受安全上下文限制** |
| C | A + B 并存（A 可用则用 A，否则退到 B） | ✅ 可用 | 体验最好、工作量最大 |

> **已定案 C（A 优先 + B 兜底）**，依据见 §5-Q1。两案都必须：不可用时**显式提示原因**（不得静默失败）。

**② 按钮必须由用户直接点击触发**（`pitfalls #121`）
`getUserMedia` / `MediaRecorder.start()` **只能**在用户手势的同步调用栈里发起；**绝不允许**从 `oaAfterOaAnswer()` 之类的异步续段唤起——那正是 2026-10-11「上传窗口打不开」的成因（手势瞬时激活失效、调用被静默忽略）。

**③ 转写结果的处理**：**填入 `#oaInput` 供编辑**，**不自动发送**。理由：ASR 有误识别，自动发送会把错字直接送进对话与模型上下文。

**④ 隐私与留存（已定）**：音频**不留存** —— 转写完成即删、不落持久盘、不跨用户可见（依据见 §5-Q2）；界面明示「上传的音频仅用于本次转写」。

**⑤ 失败态必须显式**（铁律 2）：未授权 / 无麦克风 / 安全上下文不支持 / 超时 / 转写为空 / 后端 5xx —— **每一种都要有可见文案**，禁止「点了没反应」。

### 2.3 交互方式与使用场景

**交互**（默认案 C/A）：
1. 点击坞内麦克风按钮（用户手势）→ 按钮进入「录音中」态（**必须有可见的录音指示与时长**，否则用户不知道在不在录）；
2. 再点一下（或松手）结束 → 按钮进入「转写中」态；
3. 转写完成 → 文本填入 `#oaInput`，**焦点落到输入框**，用户可改再发；
4. 任一步失败 → 按钮回原位 + 明确提示。

**使用场景**（写出场景是为了校准取舍）：
- 移动端/手持设备上不方便打字时口述一段话；
- 长文本口述（如「把这周的三件事总结一下」）；
- **明确不适用**：嘈杂环境、需要精确术语/编号的场景（ASR 易错）—— 因此**必须有「先填入可编辑」这一步**。

| `server/**` 或 `agent/**` | **新增转写端点**（建议 `POST /api/v1/voice/transcribe`，multipart 音频）+ **新增 ASR 模型/依赖** |

⚠️ **后端 ASR 是本需求最大的新增面**：当前 `agent` 零音频依赖、模型网关只有 LLM/embedding（`agent/app/model_gateway/gateway.py`）。**已定：用离线模型**（依据见 §5-Q3）；实现期需确认具体模型、许可与资源占用。

### 2.5 角色权限

已登录用户可用；音频与转写文本**不得**跨用户可见；转写端点必须鉴权（未登录 401），且**不得**接受任意 URL/路径参数（防 SSRF）。

### 2.6 验收判据（含负向对照，连跑两次）

| # | 正向 | 负向对照 |
|---|---|---|
| S1 | 点击麦克风 → 出现录音态（有可见指示） | 未点击时**不得**出现录音态（证明 S1 非恒真） |

| S6 | 未登录调转写端点 → 401 | —— |
| S7 | **手势约束**：录音只能由按钮点击触发 | 断言从异步续段调用会失败/被拦（对齐 G9b 的写法：钉住「由谁触发」） |

### 2.7 风险

- **R5｜录音可用性取决于访问方式**（§0.1）——**这是本需求最大的交付风险**，必须在 §5 先定。
- **R6｜ASR 模型引入成本**：离线模型（体积/内存/CPU）与云端 API（合规/外网）各有代价。
- **R7｜自动化测试测不出手势缺陷**（同类于既有结论）：Playwright/CDP **不校验**瞬时时手势激活，`filechooser`/麦克风照样能被脚本触发 ⇒ **S7 只能钉「由谁触发」，最终仍需真机验证**。

## 3. 两者在对话流程中的整合

```
用户在对话坞
  ├─ 点【附件】 ──► 判定上下文
  │                 ├─ 有项目 ⇒ 项目文档库(①) + 知识库登记(②)  （双写，②失败必回写）
  │                 └─ 无项目 ⇒ 知识库(PERSONAL)
  │               ⇒ oaPushBub 回执（含落点）
  │               ⇒ 提问时 AI 检索命中 ⇒ 回答带「来源：…」
  │
  └─ 点【麦克风】(用户手势) ──► 录音 → 上传 → 后端 ASR 转写
                             ⇒ 文本填入 #oaInput（不自动发送）
                             ⇒ 用户编辑后走原有 oaSend()
```

**共性纪律（两条需求共用）**：
1. **入口都在对话坞，且都必须有可见的三态**（进行中 / 成功 / 失败）——「点了没反应」是本项目反复出现的缺陷类型。
2. **依赖用户手势的浏览器能力，只能由用户直接点击触发**（`pitfalls #121`），不得从异步续段唤起。
