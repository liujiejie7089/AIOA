# 审批先调后台自定义表单，后续环节再动态生成（2026-11-06）

> 用户诉求（原话）：
> 「审批时，要先调用后台对应 oa 模块的自定义表单，然后再根据后面还有什么业务，
> 比如选择负责人（提供下拉选择让用户选择）动态生成，不要所有的请求都挤在一张表单里面。」

## 1. 改动前到底发生了什么（截图实证）

截图里那张卡：假种（radio）×6、开始/结束日期、请假事由、**审批负责人文本框（"王启铭"）**，
全部挤在同一张卡片里，底部还有一条已提交回执。

排查后确认了三件独立的事，任何一件都足以造成这个观感：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 这张卡**不是**后端表单，是 agent 自造的 `ask_user` 字段卡 | 页面 `.leave-form` 数量 = 0、`.clar-fields` > 0 |
| 2 | 它是**模型**造的，不是代码造的 | `leave_apply.build_card` 的处理人字段是 `type=select`（下拉），截图里却是文本框 |
| 3 | 短路没命中，所以模型有了自由发挥的机会 | `ASSIGN_RE` 只认「交给张三代批」，不认「**审批人王启铭**」 |

字段还漂移了：`form_template` 里请假是 6 个字段（含 `days`、`proof`），自造卡只有 5 个，
`days` 丢失、`proof` 没有 —— 用户填完仍可能被后端以「缺必填」拒一次。

## 2. 正确链路本来就有，只是请假没走

```
用户说「帮我请假，审批人王启铭」
   ↓  agent/intent/leave_apply.py：只挑表单码（不造字段）
   ↓  request_form{form_code:"leave_request"}   ← 只三个键：form_code / reason / prefill
   ↓  clarify 节点 interrupt()
   ↓  Java RunService.buildNeedFormPayload
        resolveForRender(tenantId, code)  ← 字段/必填/选项从 form_template.schema_json 补全
   ↓  H5 renderFormHtml：按 x-type 渲染（select/date/number/textarea/file…）
   ↓  用户填完 → 点提交
   ↓  H5 askHandlers：**单独一步**问负责人（默认 / 指定）
   ↓  POST /v1/forms/leave_request/submit（指定时带 assigneeUserIds）
   ↓  回执（handlers + dataFlow）
```

关键分工（与 `tools/request_form.py` 既定约束一致）：

- **agent 不生成 fields**：字段定义在 DB，agent 拿不到也不该猜；
- **Java 是唯一事实源**：`available_forms` 下发可用表单码，`resolveForRender` 补全字段；
- **负责人不属于业务表单**：它在提交时由前端选择器问，不写进 schema。

## 3. 改了什么

### agent（2 文件）

`aios_ai/intent/leave_apply.py` —— 整体重写：

| 旧 | 新 |
|---|---|
| `prefetch()` 查假种 + 可审批人（2 次工具调用） | 删除（不再需要） |
| `build_card()` 拼 5 个字段（含 handler） | `build_request()` 只产出 `request_form{form_code}` |
| `build_block()` 列 userId 候选 | `build_block()` 明确「负责人不在表单里，不要再追问审批人」 |
| `ASSIGN_RE` 只认「交给张三代批」 | 补「审批人王启铭 / 负责人：张大大 / 审批人=李四」 |
| 兜底：查不到人就退化为文本输入 | `pick_leave_form()` 挑不到码就返回 None（**绝不猜 code**） |

表单码来源（优先级）：`biz_type=LEAVE` → `module_code=leave` → `code` 含 `leave`。
全部来自 Java 下发的 `available_forms`，因此**不会硬编码 `leave_request`**（租户改了 code 也不会错）。

`aios_ai/graph/nodes.py` + `state.py` —— `leave_card` → `leave_form`（改名即改语义：
从"合成好的询问卡"变成"要开哪张表"）。准备阶段不再 `await` 两次工具调用。

### Java（1 文件）

`FormTemplateService.resolveForRender` 之前按 `properties` 的**键顺序**输出 fields，
而 MySQL 的 `JSON` 列会重排对象键（见 §5），于是 39/43 张平台表单渲染成乱序。
新增 `orderFieldEntries(props, requiredOrder)`：**required 数组顺序在前，非必填在后**。
抽成包级静态方法以便脱离 DB 单测（`FormFieldOrderTest`，5 例）。

### H5（1 文件）

- 字段卡/表单的等待提示分类型：表单「请填写表单…」、确认「等待你的确认…」、澄清「等待你的选择…」
  （原来三者共用「等待你的选择…」，表单场景下用户会以为要在字段里"选"一项）；
  清理判据从「文本相等」改为 `data-wait` 属性 —— 否则改文案就删不掉占位。
- `renderFormHtml` / `askHandlers` **未改**：既有实现已满足"渲染 schema + 独立选择器"。

## 4. 返回契约（request_form 只这三个键）

```json
{
  "kind": "form",
  "form_code": "leave_request",
  "reason": "请假申请",
  "prefill": {}
}
```

`prefill` 刻意留空：把原话（"帮我请个假交给张三代批"）塞进 `reason` 字段会得到一句垃圾值，
比空着更糟。`fields` 一律由 Java 补全。

## 5. 字段顺序：不能靠 JSON 对象键顺序

MySQL 的 `JSON` 列会**重排对象键**。实测 `archive_borrow` 的键顺序是
`title(5) → archive_no(10) → borrow_use(10) → attachments(11) → return_date(11) → archive_type(12)`
—— 正是 key 长度升序、同长再字典序。

所以 `_gen_oa_form_seed.py` 的 `build_schema()` 虽然按业务顺序写 properties，
**落库后这个顺序就没了**。43 张平台表单里 39 张受影响。

修法：`required` 是**数组**，不受重排影响，而种子里的 required 顺序恰好就是业务顺序。
契约写明在 `orderFieldEntries` 的 javadoc 里：**schema 的 required 顺序 = 开发者写下的业务顺序**。

请假表修复前后：

| | 顺序 |
|---|---|
| 修复前 | 请假天数 → 证明材料 → 请假事由 → 结束日期 → 假种 → 开始日期 |
| 修复后 | 假种 → 开始日期 → 结束日期 → 请假天数 → 请假事由 → 证明材料 |

> 长期更稳的做法是给每个字段加显式 `x-order`（不依赖 required 的隐式约定），
> 需要同时改种子生成器 + 迁移 + 渲染三处，本轮未做，已记入待办。

## 8. 三处自纠（都踩实了）

1. **打包假成功**：`bash mvnw ... | tail -15; echo "EXIT=$?"` 拿的是 `tail` 的退出码，
   而真实结果是 `[ERROR] Failed to clean project: Failed to delete aios-gitee\target`。
   根因是 VSCode 的 Java 语言服务（15:53 启动）锁着该目录 ⇒ `clean` 删不掉。
   改为**不带 `clean`** 的 `package`（只重编变化源文件），并用 `> log 2>&1` + `echo $?` 取真实码。
2. **断言自证循环**：V2d 初版写成
   `order_labels == [l for l in api_labels if l in order_labels]` —— 拿接口自己筛自己，恒真。
   改为「DB 的 required 顺序 → label」与「接口前 N 个 label」直接比。
3. **顺序断言用了 sorted**：V2c 最初把两边都 `sorted()` 后比较，等于把要验的东西比掉了。
   改成有序比较。
