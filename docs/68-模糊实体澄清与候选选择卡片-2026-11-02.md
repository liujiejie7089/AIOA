# 68 · 模糊实体澄清与候选选择卡片（2026-11-02）

> 需求来源：用户在 2026-11-02 给出的口径 —— 「查我同事考勤」这类话没有唯一标识时，
> 不能猜人、也不能只反问一句，而要**把通讯录候选渲染成按钮让用户点**，点完再执行。
> 本文记录需求逐条落到哪一处代码、为什么这么落，以及实测与未做。

## 1 需求口径（原文要点）

触发：查询涉及「同事」等模糊实体，且未提供唯一标识（工号/完整姓名）。已能唯一定位则跳过。

1. 调企业微信通讯录接口，按关键词（姓名片段/部门）过滤，返回 userid / name / department / position，候选 ≤10。
2. 用动态选择按钮渲染候选，文案 `{姓名}（{部门}/{职位}）`，payload 传 userid。
3. 本轮只澄清、不执行业务查询；用户选择后，用回传 userid 执行原查询。

边界：无结果 → 提示未找到、建议按部门/工号搜；>10 → 不列按钮、先补条件；
重名 → 按钮带部门/职位区分，仍分不清追加部门选择；接口失败/无权限 → 报错并降级手输；
用户取消 → 终止。

约束：未确认前不默认猜测；不泄露未选中同事的信息。

## 3 三个关键决策

### 3.1 上限 10 为什么要有「三处相等」的哨兵

候选上限原本散在三处、各写一份，历史上是 `server` 10 / `ask_user` 6 / H5 `slice(0,6)`。
后果是**第 7~10 个候选人被两级静默丢弃**，而模型以为已经列全了 —— 用户选不到人，
且没有任何报错可循。所以哨兵 `_check_entity_clarify_flow.py` 判的不是「各自等于 10」，
而是 **hub / agent / H5 三者相等且为 10**（E1）；E7 做负向自检：把 `MAX_OPTIONS` 改回 6 必须转红。
只改一处、忘了另外两处，这一条就会红。

### 3.2 「本轮只澄清」必须是确定性闸，不能只写提示词

模型很容易在同一轮里既问「是哪位同事」、又先把考勤按猜出来的人查了一遍。
等用户点完按钮，那份错误结果已经躺在上下文里 —— 答案会「错得看起来很像对的」，
比直接报错更难发现。`clarify` 节点现在按链别分流：

- `ask_user`（澄清）：`leftovers` 全部丢弃，`pending_calls = []`，用户选择后回到 agent 重新决策；
- `request_form` / `request_confirm`：**保持原行为**（这些轮的余量调用是有意的），避免回归。

⚠️ 丢弃时**必须补 tool 消息**：`assistant.tool_calls` 有几个 id，`messages` 里就得有几条
`role=tool` 回包，否则下一次请求会被严格实现直接判 400。补的内容是
`{"ok": false, "error": "SKIPPED_PENDING_CLARIFICATION", "message": "本轮只向用户澄清，该调用未执行…"}`，
让模型知道「不是查了没数据，而是根本没查」。同时写一条 `status=SKIPPED` 进 `tool_calls_log`，
审计里不能「凭空少一次调用」。

### 3.3 为什么 contact_search 必须传 `searchMode=list`

官方 CLI 的 `contact users search` 有两种模式：默认模式 **热度 top3 截断**，`list` 才枚举列表。
2026-11-02 实测同一租户下关键词「刘」：两种模式都只回 1 人（该租户共 3 人），
但默认模式的截断阈值在人数多的企业里会直接吃掉同名同事。故提示词与工具描述都要求
**枚举候选时传 `searchMode=list`**，并在 `total/hasMore` 上让模型判断「够不够列按钮」。

## 4 界面改动（H5）

- `clarCardHtml`：`slice(0,6)` → `slice(0, CLAR_MAX_OPTS)`（10）；
- `.clar-opts` 加 `max-height:320px; overflow-y:auto`，10 个候选内部滚动；
- 挂载后量 `scrollHeight > clientHeight`，溢出才打 `.clar-card.many`：
  底部 16px 渐隐（暗示还有内容）+ 确认按钮 10px 间距。
  **不溢出时样式一字未变**，2~6 个选项的常规卡片零回归。

浏览器实测（Playwright + msedge，`file://`，无后端）：

| 候选数 | 渲染按钮 | `.many` | 确认按钮间距 |
|---|---|---|---|
| 3 | 3 | false | 0 |
| 6 | 6 | false | 0 |
| 10 | 10 | true | 10px |

10 个候选时选第 10 个并确认 ⇒ 卡片显示「已选择：张三10（研发部/工程师）」，回传 `value=uid9`。

## 5 已知边界

1. **按部门名搜不到人**：`contact users search` 的 `keywords` 只匹配姓名/别名/拼音，
   实测关键词「成都易构」返回 0 人。所以需求里的「按部门过滤」目前只能靠用户给姓名片段；
   真要按部门筛，得先拿到部门 id 再查成员（CLI 有 `contact departments`，本轮未接）。
2. **`total` 不是全公司命中数**：上游 `users_count` 就是「这次返回了几个人」，
   默认模式下它本身已被截到 top3。所以 `hasMore` 只能反映「这次回包是否被我们截断」，
   不能反推「公司里共有几个张伟」。
3. **真实 HITL 端到端已跑通**（见 §7）：`prepare` 预取 → 顺序截胡（不调模型）→
   `need_clarification` 帧 → resume 带 userid 续跑。曾经的「只写了提示词、模型只反问」
   已经不再是问题，取而代之的是两个**新**的边界（§7.4）。

## 7 连接器无关化 + 真机验证（2026-11-02 第二轮）

### 7.1 用户的要求与它暴露的真实问题

> 「你用截图测试的方式给我测试，这个功能应该对所有连接器都适用，不只是企业微信，
> 修改完后再测试一下QQ邮箱」

第一轮只做到「写了提示词 + 定了上限」，**模型仍然只反问不查**。根因有两条：

1. `contact users search` 的 `keywords` 是必填 —— 用户只说「同事」时**没有任何关键词可搜**，
   模型据此认定「没法查」，于是把找人的活推回给用户；
2. 「提示词写了」≠「模型会做」。同一条链路上，软约束已经失效过一次（form_hint 当时也是）。

所以这一轮把它做成**代码级确定性路径**，并且**按工具名发现人源**，不认连接器 code。

### 7.2 设计：一处判定，两条连接器走同一条路

新增 `agent/aios_ai/tools/entity_clarify.py`（连接器无关）：

```
工具清单 ──► find_people_source()
              ├─ 短名命中 contact_search / search_contacts / user_search …
              │     ⇒ kind=contact（通讯录，value = userid）      ← 企业微信走这里
              └─ 短名命中 list_messages / list_mails / list_emails
                    ⇒ kind=mail（最近邮件往来，value = 邮箱）      ← QQ 邮箱走这里
              （只有 search_messages 不算：它的 query 必填，而这里恰恰不知道该搜什么）
```

判定与执行分三层，**逐层收紧**：

| 层 | 位置 | 判据 | 作用 |
|---|---|---|---|
| ① 触发 | `needs_entity_clarify` | 人称指代（同事/某人）**且** 动作或渠道词（发给/消息/邮件/日程…） | 「同事的报销流程是什么」不该弹卡 |
| ② 预取 | `prepare` 节点 | ①成立 + HITL 开 + 人源存在 | 真查一次，候选进 `state.entity_candidates`，并往 system 注入**可照抄的 options JSON** |
| ③ 出卡 | `agent` 节点 | 候选非空 + 未澄清过 + 用户没点名 + 非群发 ⇒ **第一轮直接短路**（不调模型）；否则模型若「零工具调用且确实在反问人名」⇒ 补一张卡 | 保证按钮一定出现，且不掺废话 |

三条护栏（都是为了不打扰）：

- `names_in_text`：用户已经点名了某个候选（「给同事**刘洋**发条消息」）⇒ 不弹卡；
- `BROADCAST_RE`：群发语义（群发/所有同事/每位同事/群里…）⇒ 不收敛成「选一个人」；
- 候选为空 ⇒ 一律不弹（宁可退回文字追问，也不弹空卡）。

### 7.3 QQ 邮箱这条链路：为什么不能只看收件箱

`qq_mail.list_messages` 的收件箱里是 **GitHub CI 通知 / 系统邮件**，只聚合发件人时
候选池是 `notifications@github.com` 这种——技术上「能用」，实际上毫无价值。
「给同事发邮件」真正该给的候选是**我最近写过的人**，所以邮件这条路取两段再合并：

1. `list_folders` 找到「已发送」文件夹（**按名字判**：`Sent Messages` / `[Gmail]/Sent Mail` /
   `Sent Items` / 已发送 —— 不写死 QQ 的常量）→ `list_messages` 取 20 封的 `to` 收件人；
2. 收件箱 30 封的 `from` 发件人；按邮箱去重，收件人优先。

实测（真实邮箱 3260791262@qq.com）产出 10 位真实往来人：
`CareYou_CQ、羽生.、345953339、卿港、刘洋、zghsr、1640547496、cxcysuse、liujiejie7089、QQ音乐项目组`。

### 7.4 按钮文案：只在需要区分时才带括号

候选文案的规则从「`姓名（部门/职位）` 一律带」改成**按需**：

- 名字唯一 ⇒ 只显示姓名（10 个不重名的人各带一串邮箱，等于把按钮变成地址簿，每行还被挤成两行）；
- 有重名 ⇒ 重名的那几个都带上区分项（部门/职位 → 邮箱 → 来源群）；
- 只有一个候选 ⇒ 保留区分项（这时它是信息，不是噪音）。

### 7.6 真机端到端（Java :8080 + agent :8000 + hub :8099 + 真实模型）

用户原话「帮我给同事发条消息说下午三点开会」，事件序列：

```
第一轮（修复前）: run.started → tool.call(contact_search) → tool.result
                 → message.delta（正文列了编号名单，还带 [阿修bot.](wobVco…) 链接）
                 → need_clarification → run.completed
第一轮（修复后）: run.started → need_clarification → （零正文、零 tool.call）
                 options = 3 位真实同事，value = userid
resume(选刘洋)  : 续跑 → 模型继续 → 进入二次确认（未直接发出，避免打扰真人）
```

**真机暴露的两个退化（都已修，且都有断言盯着）**：

1. **只给姓名、不给 value** ⇒ 模型不知道怎么调 `ask_user`，退回「正文编号列表」，
   还把 userid 渲染成 Markdown 链接。修法：注入块直接给出可逐字照抄的 `options` JSON，
   并明令「不要把名单写进正文、不要把 value 给用户看」；
2. **正文已经流出去就收不回来** ⇒ 即便补了卡，用户还是先看到那段带机器值的废话。
   修法：候选就绪且用户没点名时，`agent` 第一轮**直接短路**（`rounds == 0` 才截胡），
   连模型都不调 —— 更快、更干净，也不再消耗 token。
   （`rounds > 0` 时仍保留「兜底补卡」，覆盖「模型自己先查了一轮、下一轮又改成正文列名单」的走向。）

### 7.7 真机验证不得不做的两件事（记录在案，已复原）

- **借凭据复现「已授权」态**：QQ 邮箱唯一一条 `CONNECTED` 记录属于一个已被 e2e 清理掉的用户
  （tenant 56 / user 3240）。为了拿到真实邮件，把该行凭据临时挂到 `admin`（id=2）上，
  验证完**已还原**为 `NEED_AUTH` + 空凭据 + 原 `connected_at`。
- **不要真发消息**：resume 后模型进入二次确认即停，没有真的把「下午三点开会」发出去。

### 7.8 已知边界（本轮新增）

1. `:has()` 依赖：卡片最小宽度挂在 `.bubble:has(.clar-card)` 上。老 WebView 不支持 `:has()`
   时会退回「卡片跟着气泡收缩」，长邮箱可能折行 —— 可用但不好看，不阻断。
2. 邮件这条链路最多 3 次工具调用（folders + 已发送 + 收件箱），首次出卡会比企微慢几百毫秒；
   只在「同事 + 动作词」命中的轮次触发，不是每条消息都跑。

## 8. 一次交互交齐（选完不终止 + 动态文本框 + 单次提交，2026-11-02 第三轮）

### 8.1 现场症状

用户截图：点「小亮」→ 卡片落款「已选择：小亮」→ **气泡再无下文**。
任务就此终止，用户还得再打一句「下午三点开会」才能继续。

这不是渲染问题（卡片渲染得好好的），也不是模型偷懒 —— **是回填把上下文切断了**。

### 8.2 根因：回填只给了一个标量

`interrupt()` 恢复后的 tool 消息是**模型唯一的输入**。改造前它长这样：

```json
{"ok": true, "data": {"answer": "wobVcoRgAA…"}}     // 只有一个 userid
```

模型拿到的信息只有「用户选了一串机器值」。它既不知道这串值是谁，
更不知道「要发什么内容」——**唯一能做的就是把问题再问一遍**。
于是：选人（第 1 轮）→ 内容（第 2 轮）→ 执行（第 3 轮），
中间任何一步用户走开，上下文就断在那儿。

判据：**一次暂停必须能把「这一步缺的全部信息」收齐**，
否则澄清链就必然退化成多轮往返。

### 8.3 三处契约（缺一处就不成立）

| 位置 | 承担什么 | 具体形状 |
|---|---|---|
| `tools/ask_user.py` | 声明「这一项还缺内容」 | 选项级 `needs_text` / `text_label` / `text_placeholder`；卡级 `text_input{label,placeholder,required}` |
| `graph/nodes.py` | 把回填归一成模型读得懂的上下文 | tool 消息 `{value,label,text}` + `next` 指令 |
| `user-client/index.html` | 触发、渲染、提交 | `needs_text` ⇒ 选中即展开输入框并变必填；`clarAnswerPayload()` 统一载荷 |

**为什么选项级而不是卡级**：`needs_text` 挂在**选项**上，语义是「选了这一项才需要补充」。
同一张卡里若混着「选人（要内容）」和「只看通讯录（不要内容）」，
卡级字段会把后者也逼成必填。卡级 `text_input` 保留给另一种场景：
**这一问本身就要一段文字**（例如「请描述一下你的需求」），与选项无关。

### 8.4 一次交互的状态机（触发 → 渲染 → 提交）

```
候选就绪 & 用户没点名（can_short_circuit）
   └─ build_clarify_call(members, text)
        └─ content_hint(text) 命中「发消息/邮件/日程/待办」⇒ with_content_hint()
             ⇒ options[i].needs_text = true, text_label = "要发送的内容"

H5 clarCardHtml(p)
   ├─ hasNeeds = opts.some(o => o.needs_text === true)
   ├─ 有 ⇒ 渲染 .clar-text-wrap[hidden]（**默认隐藏**，不无端撑高气泡）
   └─ 卡级 text_input ⇒ 渲染时就展开

mountClarCard 三件套
   ├─ textGate():  need = 选中项.needs_text || 有卡级输入
   │               required = 选中项.needs_text || 卡级.required
   ├─ syncText() : 展开/收起 + 换 label/placeholder + **收起即清空**
   └─ syncOk()   : 选了人 **且**（必填的已填）才解禁「确认」

提交（一次）
   settle(value,label,text) → 落款「已选择：X；已填写：Y」
      → resolve({value,label,text})
         → API.resumeStream(runId, clarAnswerPayload(pick))   ← 两形态共用
```

**关键约束**（都有断言盯着，见 §8.7）：

- `needs_text` 一经选中即**必填** —— 既然这一步就是缺内容，就不该允许空着交上去；
- 切到不需要内容的选项时**清空**输入框，否则会把上一项的内容带到下一项；
- 输入框里普通 Enter 换行、**Ctrl/Cmd+Enter** 提交（内容常常是多行的）；
- 载荷**始终**是 `{value,label,text}`（`text` 为空也带），形状统一，agent 侧不用猜。

### 8.5 循环为什么能连续

三层保障，缺一层就会「看起来又断了」：

1. **H5 侧 `while(clar || form || cfm)`**：一次 resume 之后若又来暂停帧，
   回到循环顶部接着渲染 —— 不是「处理一次就收工」。两形态（`send` / `oaSend`）各有一份，
   同口径。
2. **agent 侧 tool 消息带 `next` 指令**：
   「信息已齐备，请**直接执行**用户最初的请求，不要再向用户重复确认同一件事。」
   不给这句话，模型会礼貌地再确认一次（用户视角＝又一轮往返）。
3. **`clarifications` 一旦非空，短路与兜底合成都停手**（`not state.get("clarifications")`）：
   否则续跑后又合成一张同样的卡 —— 无限弹卡。

**顺序修正**：`.tx`（正文容器）是气泡第一个子节点，卡片是追加在末尾的兄弟节点，
于是续跑产生的回答会被写进 `.tx`、**视觉上飘在问句上方**（先读到「已发给刘洋…」
再读到「要发给哪一位同事？」）。`liftTextBelowCard(bubble)` 在卡片落定后把**空的**
`.tx` 挪到卡片之后 —— 读起来才是「选完 → 于是有了这个结果」。
有前导正文（模型先说一段再提问）时不挪：那段话本来就该在上面。

### 8.6 通用性：不只连接器

这套机制**与连接器无关**，也不只服务「模糊实体」这一条链：

- 代码合成路径（`entity_clarify.build_clarify_call`）与模型自调路径（`ask_user` 工具 schema）
  共用 `with_content_hint()`，两条路给出的 options **同一份形状**；
- `build_block()` 把带 `needs_text` 的 options JSON 直接给模型照抄，
  并在注入块里补一句「不要再追问内容」—— 否则模型自己调工具时不标这个字段，
  用户选完人仍被追问，等于绕过了整套改造；
- `text_input`（卡级）对任意 `ask_user` 调用可用，与连接器毫无关系。

一句话：**任何「这一步缺不止一个信息」的场景，都能压成一次交互。**

### 8.8 踩到的坑（有一个是真正的 bug）

1. **`_clarify_answer` 不能无差别套在三条链上**（本轮**真 bug**，被测试当场抓住）。
   三条链共用 `interrupt()` 的位置，但回填形状完全不同：
   clarify 是标量/`{value,label,text}`，form 是回执对象，confirm 是 `{decision: true}`。
   一开始在 resume 之后统一 `payload = _clarify_answer(answer)`，
   结果 confirm 的 `{"decision": true}` 被压成 `{"value": null}` —— **决策被吃掉**，
   模型看不见「用户点了确认」，写工具永不执行（`test_request_confirm` 两条用例直接红）。
   修法：按 `chain` 分工，只有 clarify 归一。
   **教训：多链共用的位置，任何「统一归一」都要先问「三条链的形状真的一样吗」。**
2. **`content_hint` 按「最先出现的动作词」判定，不是按表里顺序**。
   「发条消息说下午三点开会」同时命中「消息」与「开会」：固定顺序会让它被判成「约会议」，
   要一个「时间与主题」—— 而用户要的明明是「要发送的内容」。改为取最早匹配位置。
3. **`content_hint` 的会议类正则太窄**：`日程|会议|约个|约一下|安排` 接不住
   「帮我约同事开个会」（是「约同事开个会」，中间夹了字）。补 `开会`、`约.{0,6}(会|时间|见面)`、
   `碰头`、`排期`。
4. **测试里 `page.route` 装完就卸 ⇒ resume 必然失败**。`send()` 是在用户点「确认」之后
   才发 resume 的，脚本若在卡片挂载后就 `unroute`，那一刻请求会打到假域、气泡里出现 fetch 报错，
   「回填后有没有继续」就永远验不到（表现是 `resume_body` 恒为 None）。
   拦截必须覆盖到 run 收口（`start_session` / `finish_session` 分开）。
5. **agent 用 `&` 起会被回收**（铁律 26 的又一例）。中途出现「Java 报 Connection refused:
   127.0.0.1:8000」，而 curl 又是通的 —— 其实是进程被回收后 curl 也 000，
   只是两次检查相隔太久没看出来。用后台任务起，并在跑 E2E 前先探活。
6. **起 agent 必须带 `AIOS_MCP_HUB=true`**。`start-all.sh` 里是 `export` 的，
   手工起容易漏；漏了的现象**不是报错**，而是 `capabilities degraded=[('mcp','UNRESOLVED')]`
   + `模糊实体预取 0 个候选` + 模型自己弹一张**空选项**的卡
   （「要发给哪位同事？请输入姓名或工号」）—— 看起来像「澄清链坏了」，实际是工具没注入。
