# 10 · 数字员工职责边界与权限规则

> 版本：V22（2026-09-11）　适用范围：用户端「专家与员工 → 数字员工」下的「对话 / 调整任务」会话，以及请假申请等按职责划分的数字员工场景。
> 本文是该能力的**规格源**：职责边界、权限规则、交互流程、触发节点与判定逻辑的唯一口径。代码实现必须回到本文，不得散写字符串。
>
> **V22 变更**：按角色区分「使用」与「管理」两条通道——**使用**数字员工（对话、提交请假申请、查看运行记录）对所有成员开放；**管理**数字员工（创建/修改/启停/立即执行/删除）收敛为仅租户管理员。会话绑定不再要求权限码（原 V21 的 R3/T2 权限校验取消）。

---

## 1. 目标

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 数字员工会话内 AI **只回答与其职责相关的问题** | 会话绑定数字员工后，越界提问得到「礼貌拒答 + 说明职责范围」，不正面回答无关问题 |
| G2 | 请假类数字人具备**请假审批权限**，其他数字人按各自职责授予权限 | 类型 → 所需权限的映射在 `WorkerRole` 中唯一定义，且可被接口读出 |
| G3 | **不具备权限就不能创建或承担该类型角色**（管理类操作仅限租户管理员） | 创建/改类型/启停/立即执行/删除五类管理操作均前置校验，不通过即 403，且不落库 |
| G4 | 会话中可**保存与查看历史对话** | 「会话记录」可列历史会话、展开查看完整对话内容、并可载入继续提问 |
| G5 | **所有成员都能提交请假申请**，不受管理员限制 | 普通成员可与会话绑定请假数字人、拿到《请假申请》表单并提交审批单（`POST /approvals` 200） |

非目标（本期不做）：细粒度字段级权限、跨租户共享数字员工、数字员工的并行多 Agent 编排。

## 2. 术语与角色定义

**数字员工角色类型（WorkerRole）** —— 职责边界与所需权限的唯一定义源。类型决定「能答什么」与「谁有资格做」。

| 类型码 | 名称 | 职责边界（会话可回答范围） | 所需权限码 | 可创建/承担该类型角色的角色 |
|---|---|---|---|---|
| `GENERAL` | 通用办公助手 | 通用办公问答、文案撰写与信息整理 | `chat:basic` | 普通成员、租户管理员 |
| `LEAVE_APPROVER` | 请假审批数字人 | 受理请假申请、校验请假类型与证明材料、按请假制度给出送审与答复意见 | `approval:leave` | 仅租户管理员 |
| `KB_ASSISTANT` | 知识库问答数字人 | 基于企业知识库检索企业制度与资料，据实作答并标注引用来源 | `kb:read` | 普通成员、租户管理员 |
| `DOC_DRAFTER` | 公文起草数字人 | 起草通知、请示、报告、函等公文，遵循公文格式规范 | `doc:draft` | 普通成员、租户管理员 |

> 右列语义为「**谁可以创建/承担该类型角色**」，**不等于**「谁能与它对话」。对话（使用）对所有成员开放，见 §3 权限矩阵。

**权限模型三段链**：

```
WorkerRole（类型） --requiredPermission--> PermissionCatalog（权限码） --GRANTS--> 允许的角色集合
```

- 权限判定以**角色**为依据（与平台既有审批口径一致：`ApprovalController` 的待办与审批动作均要求 `ROLE_ADMIN`），避免两套互相矛盾的权限语义。
- 「是否是管理员」统一由 `PermissionCatalog.isAdmin(user)` 判定，与审批动作同一口径，不另立标准。
- `AuthUser.permissions` 若将来接入 `sys_permission`，只需在 `PermissionCatalog.holds()` 中优先判断细粒度权限，调用方无需改动。
- 未知权限码默认**拒绝**（`rolesOf` 返回空集合）。

**职责边界的两级取值**：数字员工实例的 `description`（自定义职责）优先；未填写时回落到角色的预设职责（`WorkerRole.duty()`）。

## 3. 权限规则

按「**使用**」与「**管理**」两条通道划分，所有判定的唯一依据是登录用户的角色（`ROLE_ADMIN` / `ROLE_USER`）。

### 3.1 操作范围权限矩阵

| 操作 | 接口 / 判定点 | 普通成员 | 租户管理员 | 说明 |
|---|---|---|---|---|
| 查看数字员工列表 | `GET /api/v1/workers` | ✅ | ✅ | 只读，限本租户 |
| 查看类型目录 | `GET /api/v1/workers/role-types` | ✅ | ✅ | 只读，`granted` 表示「可否创建该类型」 |
| 查看运行记录 | `GET /api/v1/workers/{id}/runs` | ✅ | ✅ | 只读留痕，限本租户 |
| **与数字员工对话（使用它）** | `POST /api/v1/conversations`（带 `workerId`） | ✅ | ✅ | 绑定后受职责范围约束（越界拒答） |
| **提交请假申请** | `POST /api/v1/approvals` | ✅ | ✅ | 业务操作，不受管理员限制 |
| 查看我的申请 | `GET /api/v1/approvals?scope=mine` | ✅ | ✅ | 仅本人 |
| **创建**数字员工 | `POST /api/v1/workers` | ❌ 403 | ✅ | 敏感管理操作 |
| **修改**数字员工（含改类型/任务内容/执行时刻） | `PUT /api/v1/workers/{id}` | ❌ 403 | ✅ | 敏感管理操作 |
| **启停**数字员工 | `POST /api/v1/workers/{id}/toggle` | ❌ 403 | ✅ | 敏感管理操作 |
| **立即执行**数字员工 | `POST /api/v1/workers/{id}/run` | ❌ 403 | ✅ | 敏感管理操作（触发真实运行并计费） |
| **删除**数字员工 | `DELETE /api/v1/workers/{id}` | ❌ 403 | ✅ | 敏感管理操作 |
| 查看待我审批 | `GET /api/v1/approvals?scope=todo` | ❌ 403 | ✅ | 既有审批口径 |
| 通过 / 驳回审批 | `POST /api/v1/approvals/{id}/decision` | ❌ 403 | ✅ | 既有审批口径 |

> 一句话口径：**能否用** = 同租户 + 员工未停用（所有成员）；**能做什么** = 该员工的职责范围（越界拒答）；**能否改** = 仅租户管理员。

### 3.2 规则表

| 规则 | 内容 | 违反结果 |
|---|---|---|
| R1 | **管理类操作**（创建/修改/启停/立即执行/删除数字员工）仅租户管理员可执行 | 403，前置拒绝：不落库、不改状态、不产生半成品 |
| R2 | 创建数字员工时，除管理员身份外还须持有该类型所需权限码（类型 → `requiredPermission`） | 403，不落库 |
| R3 | 将既有数字员工改为新类型 = 承担新角色，须重新通过 R2 校验 | 403，类型不变更 |
| R4 | **使用类操作**（建立绑定会话/提交请假申请/查看运行记录）对所有本租户成员开放 | —（不做角色限制） |
| R5 | 绑定会话仅校验：① 员工存在且租户一致 ② 员工未停用 | ① 404；② 400 |
| R6 | 类型未显式指定时按名称/职责关键词推断（请假/休假/考勤 → `LEAVE_APPROVER`；知识库/检索 → `KB_ASSISTANT`；公文/通知/请示/报告 → `DOC_DRAFTER`；否则 `GENERAL`） | 推断结果同样走 R2 |
| R7 | 审批动作（待办查看 / 通过 / 驳回）仍沿用既有口径，仅租户管理员 | 403 |

> R1/R2/R3 管住「谁能建、谁能改」，R4/R5 保证「谁都能用」——**提交请假申请对所有成员开放，创建/删除等敏感操作仅限管理员**，两者互不影响（管理收敛不影响使用）。

**越权拦截口径**：后端统一抛 `BizException.forbidden(...)` → 全局映射为 **HTTP 403** + 中文 message（明确写出「谁可执行」「当前账号是什么」「哪些操作不受限制」）；前端以「操作受限」弹窗呈现该 message，并给出「联系管理员」出口。前端同时按角色显隐管理入口（普通成员不渲染创建按钮、启停开关、「立即执行」「调整任务」），做到**入口不可见 + 后端不可绕过**双层防护。

## 4. 完整会话交互流程

进入会话有**两个入口**，按角色显隐：

| 入口 | 谁可见 | 用途 | 是否出现配置卡片 |
|---|---|---|---|
| **「对话」**（V22 新增） | 所有成员 | 使用该数字员工：提交请假申请、业务提问 | 否（纯业务问答） |
| **「调整任务」** | 仅租户管理员 | 修改该员工的执行时刻与任务内容 | 是（「确认创建 / 保存修改」） |

```
用户                用户端(H5)                     后端(Spring)                  Agent(Python)
 │                     │                              │                            │
 │ 点「对话」            │                              │                            │
 ├────────────────────>│ useAgent(i)                  │                            │
 │                     │  setChatWorker(worker)       │                            │
 │                     │  显示「职责限定：<角色名>」徽标  │                            │
 │  ── 或（仅管理员）── │                              │                            │
 │ 点「调整任务」        │ createAgentFlow(worker)      │                            │
 │                     │  setChatWorker(worker)       │                            │
 │                     │  显示「职责限定：<角色名>」徽标  │                            │
 │                     │                              │                            │
 │ 输入问题并发送        │                              │                            │
 ├────────────────────>│ send()                       │                            │
 │                     │                              │                            │
 │                     │ ① ensureConversation         │                            │
 │                     │   POST /conversations        │                            │
 │                     │   {title, appCode, workerId} │                            │
 │                     ├─────────────────────────────>│ ② 绑定校验(见 §5 T2)        │
 │                     │<─────────────────────────────┤   agent_code=worker:<id>   │
 │                     │                              │   worker_id=<id>           │
 │                     │ ③ POST /conversations/{id}/runs                            │
 │                     ├─────────────────────────────>│ 额度准入 → 内容审核 → 落 user 消息
 │                     │<───────────── runId ─────────┤                            │
 │                     │ ④ GET /runs/{runId}/events (SSE)                           │
 │                     ├─────────────────────────────>│ ⑤ 组请求：模型 + 多轮历史     │
 │                     │                              │   + scope(见 §5 T3)         │
 │                     │                              ├───────────────────────────>│ ⑥ 系统提示注入职责边界
 │                     │                              │                            │    + 越界拒答规则
 │                     │<════ message.delta × N ══════┤<═══════════════════════════┤ ⑦ 生成

 │                     │<════ run.completed ═══════════┤     + 计费                  │
 │                     │ ⑨ 命中请假请求且绑定的是请假类员工 → 追加《请假申请》表单       │
 │                     │                              │                            │
 │ 点「会话记录」        │                              │                            │
 ├────────────────────>│ openHistory()                │                            │
 │                     │ GET /conversations ─────────>│ ⑩ 本人历史会话列表           │
```

> 管理类动作（「立即执行」「调整任务」「启停」「创建」「删除」）在用户端**仅对租户管理员渲染**；后端 `requireAdmin` 对同一批接口做前置 403 兜底，前端隐藏不是唯一防线。

**关键约定**

- 会话与数字员工的绑定关系**只落在后端**（`chat_conversation.worker_id`），前端仅传 `workerId`，不传职责文本——职责边界由后端从 `agent_worker` 读取并下发，避免前端伪造 scope 越权。
- 会话一旦绑定，**整个会话生命周期都受该职责边界约束**；多轮历史同样在该边界内（系统提示随每轮下发）。
- SSE 事件契约不变（`message.delta` / `message.completed` / `run.completed`），职责限定对前端透明。

## 5. 触发节点与判定逻辑

| 节点 | 位置 | 触发时机 | 判定逻辑 | 不通过 |
|---|---|---|---|---|
| **T0 管理类准入（新增 V22）** | `WorkerController.requireAdmin` | 创建/修改/启停/立即执行/删除 | `PermissionCatalog.isAdmin(user)`（角色含 `ROLE_ADMIN`） | 403 `「<动作>」仅租户管理员可执行；如需变更数字员工配置，请联系租户管理员。提交请假申请等业务操作不受此限制。` |
| **T1 创建准入** | `WorkerController.create` | 创建数字员工 | 先 T0；再 `role = resolveRole(显式类型 ‖ 名称/职责推断)`；`PermissionCatalog.holds(user, role.requiredPermission())` | 403 `该数字人属「X」，需持有权限码 …；当前账号无权创建或承担该类型角色` |
| **T1' 改类型准入** | `WorkerController.update` | 更新时传了 `workerType` | 先 T0；再同上 | 403，类型保持原值 |
| **T2 会话绑定准入（V22 放宽）** | `ConversationService.bindWorker` | 创建会话时带 `workerId` | ① 员工存在且租户一致；② 未停用；**不再要求权限码**（使用对所有成员开放） | ① 404；② 400 |
| **T3 职责范围下发** | `RunService.buildScope` | 每轮 run 组装请求时 | 若 `conversation.workerId != null` → 读员工，拼 `scope{worker_id,name,role,role_name,duty,permission}` 下发 Agent | 读不到员工则 `scope=null`（降级为通用助手，不阻断） |
| **T4 职责限定生效** | `agent_runtime._build_messages` | Agent 构造 messages 时 | 有 `scope` → **整体替换**身份提示为「你是数字员工「X」（角色：Y）。职责边界：Z」，并追加 4 条硬规则：① 只答职责内 ② 越界礼貌拒答并说明范围 ③ 不编造、查不到如实说 ④ 不声称职责外权限 | 无 `scope` → 走原通用助手提示 |
| **T5 职责内细化** | 同上 | `scope.role == LEAVE_APPROVER` | 追加请假场景专条：受理申请、校验类型与证明材料、依制度给送审与答复意见；与请假无关的审批一律不处理 | — |

**判定优先级**：T0/T1/T1'/T2 是**确定性前置校验**（纯角色比对，不依赖模型，可单测）；T4/T5 是**模型侧软约束**（提示词约束，用于开放域问答的边界把控）。T0 管住「谁能改」，T2 保证「谁都能用」，T4/T5 保证「用的时候不越界乱答」——三者互补，不可互相替代。

## 6. 会话记录（保存与查看）

**保存**：无需新增存储——会话与消息在对话流程中已落库：
- `chat_conversation`：会话元信息（标题、`worker_id`、消息数、最后消息时间）；
- `chat_message`：逐条消息（`role`、`content`、`citations`、`tool_calls`、`seq`）。

**查看**：用户端会话页顶部「会话记录」入口
1. `GET /api/v1/conversations` → 本人历史会话列表（倒序，标题 + 数字员工标记 + 时间 + 消息数）；
2. 展开某条 → `GET /api/v1/conversations/{id}/messages` → 完整对话内容（只读回放，懒加载）；
3. 「继续此会话」→ 载入消息到会话页并复用原 `conversationId`，后续提问自动续接上下文（后端按 `seq` 取近 10 轮历史）。

**权限**：会话列表与消息接口本就按 `user_id` 归属过滤（`getOwned` / `ownedWrapper`），跨用户访问返回 403，记录天然隔离。

## 8. 风险与边界

- **提示词约束的强度**：T4/T5 依赖模型遵循系统提示，属软约束；对**强对抗性**的越界尝试（诱导、角色扮演绕开）不保证 100% 拦截。若要硬约束，需在 Agent 侧增加「职责相关性判定」二次调用或关键词规则，成本更高，本期不做。
- **权限口径来源**：本期以角色为准（与既有审批口径一致）。若引入细粒度权限表，`PermissionCatalog.holds()` 与 `isAdmin()` 是唯一改动点。
- **历史数据**：V21 迁移按名称/职责关键词回填 `worker_type`，仅命中「请假/休假/考勤」等明确关键词者升级为专用类型，其余保守留在 `GENERAL`，避免误判扩大权限面。
- **V22 的取舍**：会话准入放宽后，普通成员可与请假数字人对话并拿到《请假申请》表单；**审批动作本身仍仅限租户管理员**（`POST /approvals/{id}/decision`），故「能提交」不等于「能批准」。数字员工自身不会执行审批动作，其职责是受理、校验与给出送审意见。
- **前端隐藏 ≠ 安全边界**：用户端对普通成员不渲染管理入口，但这只是体验优化；真正的边界在 `requireAdmin` 的前置 403。任何绕过前端的直接调用同样被拦。
