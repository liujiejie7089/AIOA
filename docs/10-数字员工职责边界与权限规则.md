# 10 · 数字员工职责边界与权限规则

> 版本：V21（2026-09-11）　适用范围：用户端「数字员工 → 调整任务」进入的会话，以及请假审批等按职责划分的数字员工场景。
> 本文是该能力的**规格源**：职责边界、权限规则、交互流程、触发节点与判定逻辑的唯一口径。代码实现必须回到本文，不得散写字符串。

---

## 1. 目标

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 数字员工会话内 AI **只回答与其职责相关的问题** | 会话绑定数字员工后，越界提问得到「礼貌拒答 + 说明职责范围」，不正面回答无关问题 |
| G2 | 请假类数字人具备**请假审批权限**，其他数字人按各自职责授予权限 | 类型 → 所需权限的映射在 `WorkerRole` 中唯一定义，且可被接口读出 |
| G3 | **不具备权限就不能创建或承担该类型角色** | 创建/改类型/建绑定会话三处均前置校验，不通过即 403，且不落库 |
| G4 | 会话中可**保存与查看历史对话** | 「会话记录」可列历史会话、展开查看完整对话内容、并可载入继续提问 |

非目标（本期不做）：细粒度字段级权限、跨租户共享数字员工、数字员工的并行多 Agent 编排。

---

## 2. 术语与角色定义

**数字员工角色类型（WorkerRole）** —— 职责边界与所需权限的唯一定义源。类型决定「能答什么」与「谁有资格做」。

| 类型码 | 名称 | 职责边界（会话可回答范围） | 所需权限码 | 允许角色 |
|---|---|---|---|---|
| `GENERAL` | 通用办公助手 | 通用办公问答、文案撰写与信息整理 | `chat:basic` | 普通成员、租户管理员 |
| `LEAVE_APPROVER` | 请假审批数字人 | 受理请假申请、校验请假类型与证明材料、按请假制度给出送审与答复意见 | `approval:leave` | 仅租户管理员 |
| `KB_ASSISTANT` | 知识库问答数字人 | 基于企业知识库检索企业制度与资料，据实作答并标注引用来源 | `kb:read` | 普通成员、租户管理员 |
| `DOC_DRAFTER` | 公文起草数字人 | 起草通知、请示、报告、函等公文，遵循公文格式规范 | `doc:draft` | 普通成员、租户管理员 |

**权限模型三段链**：

```
WorkerRole（类型） --requiredPermission--> PermissionCatalog（权限码） --GRANTS--> 允许的角色集合
```

- 权限判定以**角色**为依据（与平台既有审批口径一致：`ApprovalController` 的待办与审批动作均要求 `ROLE_ADMIN`），避免两套互相矛盾的权限语义。
- `AuthUser.permissions` 若将来接入 `sys_permission`，只需在 `PermissionCatalog.holds()` 中优先判断细粒度权限，调用方无需改动。
- 未知权限码默认**拒绝**（`rolesOf` 返回空集合）。

**职责边界的两级取值**：数字员工实例的 `description`（自定义职责）优先；未填写时回落到角色的预设职责（`WorkerRole.duty()`）。

## 3. 权限规则

| 规则 | 内容 | 违反结果 |
|---|---|---|
| R1 | 创建数字员工时，操作者必须持有该类型所需权限 | 403，不落库 |
| R2 | 将既有数字员工改为新类型 = 承担新角色，需重新通过权限校验 | 403，类型不变更 |
| R3 | 建立「绑定该数字员工」的会话时，操作者必须持有该类型所需权限 | 403，会话不创建 |
| R4 | 类型未显式指定时按名称/职责关键词推断（请假/休假/考勤 → `LEAVE_APPROVER`；知识库/检索 → `KB_ASSISTANT`；公文/通知/请示/报告 → `DOC_DRAFTER`；否则 `GENERAL`） | 推断结果同样走 R1 |
| R5 | 已停用的数字员工不可建立绑定会话 | 400 |

> R1–R3 构成「不能创建、不能承担」的完整闭环：**创建**被 R1 拦、**改类型**被 R2 拦、**以其身份对话**被 R3 拦。

## 4. 完整会话交互流程

```
用户                用户端(H5)                     后端(Spring)                  Agent(Python)
 │                     │                              │                            │
 │ 点「调整任务」        │                              │                            │
 ├────────────────────>│ createAgentFlow(worker)      │                            │
 │                     │  setChatWorker(worker)       │                            │
 │                     │  显示「职责限定：<角色名>」徽标  │                            │
 │                     │                              │                            │
 │ 输入问题并发送        │                              │                            │
 ├────────────────────>│ send()                       │                            │
 │                     │                              │                            │
 │                     │ ① ensureConversation         │                            │
 │                     │   POST /conversations        │                            │
 │                     │   {title, appCode, workerId} │                            │
 │                     ├─────────────────────────────>│ ② 绑定校验(见 §5 T2)        │
 │                     │<─────────────────────────────┤   agent_code=worker:<id>   │
 │                     │                              │   worker_id=<id>           │
 │                     │ ③ POST /conversations/{id}/runs                            │
 │                     ├─────────────────────────────>│ 额度准入 → 内容审核 → 落 user 消息
 │                     │<───────────── runId ─────────┤                            │
 │                     │ ④ GET /runs/{runId}/events (SSE)                           │
 │                     ├─────────────────────────────>│ ⑤ 组请求：模型 + 多轮历史     │
 │                     │                              │   + scope(见 §5 T3)         │
 │                     │                              ├───────────────────────────>│ ⑥ 系统提示注入职责边界
 │                     │                              │                            │    + 越界拒答规则
 │                     │<════ message.delta × N ══════┤<═══════════════════════════┤ ⑦ 生成
 │                     │  流式渲染                     │                            │
 │                     │<════ message.completed ══════┤ ⑧ 输出审核 → 落 assistant 消息
 │                     │<════ run.completed ═══════════┤     + 计费                  │
 │                     │                              │                            │
 │ 点「会话记录」        │                              │                            │
 ├────────────────────>│ openHistory()                │                            │
 │                     │ GET /conversations ─────────>│ ⑨ 本人历史会话列表           │
 │ 点某条会话            │ GET /conversations/{id}/messages ──────────────────────>│ ⑩ 完整对话内容(只读)
 │ 点「继续此会话」      │ 载入 msgs + conversationId    │                            │
```

**关键约定**

- 会话与数字员工的绑定关系**只落在后端**（`chat_conversation.worker_id`），前端仅传 `workerId`，不传职责文本——职责边界由后端从 `agent_worker` 读取并下发，避免前端伪造 scope 越权。
- 会话一旦绑定，**整个会话生命周期都受该职责边界约束**；多轮历史同样在该边界内（系统提示随每轮下发）。
- SSE 事件契约不变（`message.delta` / `message.completed` / `run.completed`），职责限定对前端透明。

## 5. 触发节点与判定逻辑

| 节点 | 位置 | 触发时机 | 判定逻辑 | 不通过 |
|---|---|---|---|---|
| **T1 创建准入** | `WorkerController.create` | 创建数字员工 | `role = resolveRole(显式类型 ‖ 名称/职责推断)`；`PermissionCatalog.holds(user, role.requiredPermission())` | 403 `该数字人属「X」，需持有权限码 …；当前账号无权创建或承担该类型角色` |
| **T1' 改类型准入** | `WorkerController.update` | 更新时传了 `workerType` | 同上 | 403，类型保持原值 |
| **T2 会话绑定准入** | `ConversationService.bindWorker` | 创建会话时带 `workerId` | ① 员工存在且租户一致；② 未停用；③ `holds(user, role.requiredPermission())` | ① 404；② 400；③ 403 `无权与该「X」会话…` |
| **T3 职责范围下发** | `RunService.buildScope` | 每轮 run 组装请求时 | 若 `conversation.workerId != null` → 读员工，拼 `scope{worker_id,name,role,role_name,duty,permission}` 下发 Agent | 读不到员工则 `scope=null`（降级为通用助手，不阻断） |
| **T4 职责限定生效** | `agent_runtime._build_messages` | Agent 构造 messages 时 | 有 `scope` → **整体替换**身份提示为「你是数字员工「X」（角色：Y）。职责边界：Z」，并追加 4 条硬规则：① 只答职责内 ② 越界礼貌拒答并说明范围 ③ 不编造、查不到如实说 ④ 不声称职责外权限 | 无 `scope` → 走原通用助手提示 |
| **T5 职责内细化** | 同上 | `scope.role == LEAVE_APPROVER` | 追加请假场景专条：受理申请、校验类型与证明材料、依制度给送审与答复意见；与请假无关的审批一律不处理 | — |

**判定优先级**：T1/T1'/T2 是**确定性前置校验**（纯角色比对，不依赖模型，可单测）；T4/T5 是**模型侧软约束**（提示词约束，用于开放域问答的边界把控）。前者保证「无权限者拿不到该角色」，后者保证「拿到角色后不越界乱答」——两者互补，不可互相替代。

## 6. 会话记录（保存与查看）

**保存**：无需新增存储——会话与消息在对话流程中已落库：
- `chat_conversation`：会话元信息（标题、`worker_id`、消息数、最后消息时间）；
- `chat_message`：逐条消息（`role`、`content`、`citations`、`tool_calls`、`seq`）。

**查看**：用户端会话页顶部「会话记录」入口
1. `GET /api/v1/conversations` → 本人历史会话列表（倒序，标题 + 数字员工标记 + 时间 + 消息数）；
2. 展开某条 → `GET /api/v1/conversations/{id}/messages` → 完整对话内容（只读回放，懒加载）；
3. 「继续此会话」→ 载入消息到会话页并复用原 `conversationId`，后续提问自动续接上下文（后端按 `seq` 取近 10 轮历史）。

**权限**：会话列表与消息接口本就按 `user_id` 归属过滤（`getOwned` / `ownedWrapper`），跨用户访问返回 403，记录天然隔离。

## 8. 风险与边界

- **提示词约束的强度**：T4/T5 依赖模型遵循系统提示，属软约束；对**强对抗性**的越界尝试（诱导、角色扮演绕开）不保证 100% 拦截。若要硬约束，需在 Agent 侧增加「职责相关性判定」二次调用或关键词规则，成本更高，本期不做。
- **权限口径来源**：本期以角色为准（与既有审批口径一致）。若引入细粒度权限表，`PermissionCatalog.holds()` 已是唯一改动点。
- **历史数据**：V21 迁移按名称/职责关键词回填 `worker_type`，仅命中「请假/休假/考勤」等明确关键词者升级为专用类型，其余保守留在 `GENERAL`，避免误判扩大权限面。
