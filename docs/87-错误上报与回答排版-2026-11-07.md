# 87 · 错误上报与回答排版（2026-11-07）

> 三张用户截图驱动的一轮 debug：`debug`（用户端三条红色报错）、
> 「管理端也不能启用 minmax」、「返回给用户的内容整理格式」。
> 三条看似无关，落在同一条链上：**失败原因在链路里被泛化、编号被丢掉、
> 成功产出的正文又没走到渲染器**。

---

## 1. 现场与取证

| # | 截图现象 | 回源证据 |
|---|---|---|
| ① | 用户端三条相同红字：`生成失败：生成过程中断，内容可能不完整　建议：重试一次；仍失败请把错误编号发给管理员`，**一个编号都没有** | 文案逐字命中 `agent/aios_ai/errors.py` 的 `MODEL_STREAM_ERROR`；`facade.py` 用 `getattr(exc, "trace_id", None)` 取编号，普通异常恒为 `None`，`error_payload` 的 `if error_id` 又把字段整个丢掉 |
| ② | 管理端启用 MiniMax 失败，toast 里整段上游 JSON：`{"type":"error","error":{"type":"insufficient_balance","message":"The model 'MiniMax-M1' is no longer available. (2013)","http_code":"404"},"request_id":"…"}` | `app/main.py:_describe_upstream()` 把 `resp.text` 前 160 字直接拼进 message；响应体里 `insufficient_balance` 与 `no longer available` 同时出现 |
| ③ | 「写一份周报」正文里 `##` / `\|` / `**` 全以裸符号挤成一段，旁边挂着「工作周报」表单卡 | 库里 `chat_message.content` **有真实换行**（`LF=18` / `LF=5`），换行没丢；是 `need_form` 暂停帧让 SSE 提前 `return`，两个形态都只在**最终收口**才调 `formatAnswer()`，等待填表期间正文停在流式 `tx.textContent` |

排查中的两个客观事实（避免误判方向）：

- 库里 `agent_run` / `chat_message` 在 2026-11-07 12:00 之后**没有** 21:08 的 run（DB `NOW()` = 21:20，最新 run 停在 00:27）。同期 Java 日志有
  `HikariPool - Thread starvation or clock leap detected (housekeeper delta=18h36m7s)` ⇒ 机器休眠约 18h36m 后唤醒，截图大概率是浏览器休眠前残留的 DOM。
  因此不把「复现 21:08 原现场」当作完成标准，改为**复现同一条代码路径**并修掉确定缺陷。
- 真机 `/internal/v1/models/check` 对 `minimax / deepseek / dashscope` **三通道都返回 `ok=true`**；
  库里 `model_config` 的 MiniMax 行是 `model_name=MiniMax-M3.1-Flash`、`enabled=1`。
  截图里的 `MiniMax-M1` 是**已下线**的模型名（用户当时填的那个），不是当前配置。
  ⇒ 「MiniMax 通道不可用」在当前配置下不成立；真正的产品缺陷是失败提示把原始 JSON 抖给用户、
  且把「模型下线」和「余额不足」混为一谈。

## 2. 根因与修复

### 2.1 错误载荷：承诺编号却不带编号 + 一切异常都说成「生成过程中断」

`agent/aios_ai/errors.py`

- `CATALOG["MODEL_STREAM_ERROR"]` 的默认 suggestion 不再提「错误编号」；
  新增 `stream_payload(run_id, trace_id)` 动态拼编号，且 `suggestion` 里的值与 `errorId` **同一个值**。
- 新增 `MODEL_BALANCE_INSUFFICIENT`（402 / `Insufficient Balance` ⇒ 「模型账号余额不足」+ 充值或换模型），
  不再泛化成「模型服务本次没有返回结果」。
- `upstream_payload()` 的**分类顺序**调整：`MODEL_NOT_FOUND`（404 / `no longer available`）先于余额判断。
  MiniMax 那个 404 响应体同时带 `insufficient_balance`，先判余额会把「换个有效模型名」误报成「去充值」。
- 新增 `exception_payload(exc, run_id, trace_id)`：按异常类名分 `MODEL_TIMEOUT` /
  `MODEL_UPSTREAM_ERROR` / `INTERNAL_ERROR`，**每条都带编号**；代码 bug 不再伪装成模型流中断。
- `INTERNAL_ERROR` 默认 suggestion 同样去掉空口承诺（`internal_payload()` 仍会拼上真实编号）。

`agent/aios_ai/graph/facade.py`

```python
emitted = seq > seq_start
logger.exception("graph run %s failed (error_id=%s, emitted=%s, exc=%s)",
                 run_id, run_id, emitted, type(exc).__name__)
payload = (errors.stream_payload(run_id) if emitted
           else errors.exception_payload(exc, run_id))
```

只有**已经吐过正文**的断流才配说「内容可能不完整」；日志里带上编号本身，
用户报「错误编号 run_xxx」时运维能直接 grep 到这次 run 的堆栈。

### 2.2 `resume` 端点返回空 200（HITL 卡片提交/取消全挂）

`agent/app/main.py` 的 `resume_run(run_id, body, request)` 里，
`event_stream()` 第一行写的是 `trace_id = req.user_context.trace_id` ——
**`req` 在本函数里根本不存在**（参数名是 `body`，模块也没有全局 `req`），
而这一行在 `try` **之前**，NameError 直接冒泡；`except` 分支里的
`internal_payload(trace_id)` 又引用未赋值的局部变量 ⇒ 二次异常。
真机实测：`POST /internal/v1/runs/.../resume` 返回 **HTTP 200 + 空 body**，
Java 收不到任何帧，界面表现为「生成过程中断 / AI 不再回话」。

修复：`trace_id = request.headers.get("X-Trace-Id") or run_id`；
三个端点的 `GuardError` 分支同时补 `error_id=trace_id`。
修复后同一探针返回带 `errorId` 的 `INTERNAL_ERROR` + `run.failed` 两帧。

### 2.3 管理端连通性校验外发上游原文

`_describe_upstream()` 原先把 `resp.text` 前 160 字拼进 message（`request_id`、
供应商内部措辞全上屏）。改为统一走 `errors.upstream_payload()`，
原始 body 只进日志（`mask_secrets`），对外只给「一句人话 + 下一步」：

```
配置的模型「MiniMax-M1」已下线或不存在（HTTP 404）：请管理员在「模型配置」里
把模型名「MiniMax-M1」换成供应商当前提供的名称（在供应商控制台的模型列表里能看到），
无需改代码即可生效
```

`check_model` 把 `provider.model` 传进去，文案能点名到底是哪个模型失效；
`except` 分支也不再 `f"连接失败：{exc}"` 外发异常原文。

### 2.4 H5：错误码兜底与 Java 兜底帧

`user-client/index.html`

- `ERR_FALLBACK` 补 `MODEL_STREAM_ERROR` / `MODEL_BALANCE_INSUFFICIENT` / `AGENT_STREAM_ERROR`。
- `sseError()` 对 `AGENT_STREAM_ERROR`（Java `errorJson()` 把 `error.getMessage()` 直接外发的帧）
  丢弃原始 message，只用兜底人话，避免 URL / 类名泄漏到界面。

### 2.5 H5：暂停帧让 Markdown 渲染器来不及跑

`formatAnswer()` 本来就支持标题 / 表格 / 列表 / 加粗 / 引用（CSS `.ans-table-wrap` 也在），
但经典形态 `send()`（≈7469 行）与 OA dock（≈13860 行）**只在最终收口**调用它。
`API._sse` 遇到 `need_form / need_clarification / need_confirm` 直接 `return`，
随后 `mountFormCard()` 等用户填表 —— 这期间正文仍是 `onDelta` 的
`tx.textContent = text`，`white-space:normal` 把换行折叠成空格，`##`、`|` 全裸露。

修复：两个形态各加一个 `renderAnsNow()` / `oaRenderAnsNow()`，
在 `onClarification / onForm / onConfirm` 三个回调里立刻把已有正文排版一次：

```js
function renderAnsNow(){
  if(!text) return;
  bubble.classList.add('ans');
  tx.innerHTML = formatAnswer(text);
}
```

流式阶段仍用 `textContent`（逐字重排 HTML 会卡），暂停与最终收口都走渲染器；
OA 块保留 `typeof formatAnswer === 'function'` 守卫，与既有收口写法一致。
两个 script 块 `node --check` 语法均通过。

## 4. 新坑（111–116，全文见 `topics/pitfalls.md`）

- **111**：文案里写「请把错误编号发给管理员」就必须真有 `errorId`；`getattr(exc,"trace_id")` 恒 None 是隐形丢字段。
- **112**：同一响应体可同时含 `insufficient_balance` 与 `no longer available` ⇒ 模型下线必须优先于余额判断。
- **113**：`try` 之前抛异常 + `except` 里引用未赋值局部变量 = HTTP 200 空 body，比 500 更难查。
- **114**：连通性校验的 `resp.text` 属于上游原文，只进日志；管理端 toast 不是日志查看器。
- **115**：暂停帧提前 return ⇒ 收口渲染器不跑；「库里有换行、界面挤成一段」先查显示层，别查传输层。
- **116**：浏览器休眠残留 DOM 会让「截图时间」与「库里 run 时间」对不上（Hikari clock leap 是旁证）。
