## 2. 缺口优先级

- **P0（本轮做）**：⑥ 租户域名、⑩ 子租户、③ 平台调整租户资源上限 —— 这三条是「平台/租户两层管理能力」的主干，用户第一条就在讲这个。
  **2026-09-28 更新：⑩ 子租户已按用户决定移除，不再做；⑥ 与 ③ 保留**（见 §5.5）。
- **P1（下一轮）**：⑫ 机构类型补 2 类、⑲ 部门管理员有限改人、⑳ 用户↔员工多对多。
- **P2（最后做，风险最高）**：⑦ 全局租户隔离拦截器（`TenantLineInnerInterceptor`）。**必须放在最后**：它会一次性改变所有表的查询口径，既有 60+ 套件与 50 条已修坑都建立在「显式 tenant_id 条件」之上。

## 3. 默认假设（先按此实施；与你的意图不符时以本节为清单逐条纠正）

> **2026-09-28 作废声明**：下列假设 **1、2、3、5** 对应的是**子租户**能力，该能力已按用户决定移除（见 §5.5）。
> 它们已不是「待你拍板的假设」，而是**已作废的历史口径** —— 保留原文只为可追溯当初凭什么这么设计。
> 仍然有效的是：**假设 4**（域名只做格式/唯一性校验、不绑 DNS）与 **假设 6**（虚拟管理员账号判据）。

1. **租户层级只允许一层**：平台 → 顶层租户（`level=1`）→ 子租户（`level=2`）。**子租户不能再建子租户。**
   理由：规格只说「在本租户下建子租户」；无限层级会让权限、隔离、账单三套口径同时发散。
   拒绝时给出明确文案，不做静默降级。
2. **子租户的父租户由服务端推导**（= 调用者本租户），**不接受请求体传 `parentId`**。理由：让 body 决定归属 = 越权入口（同类缺陷本项目已经犯过一次，见 `pitfalls.md`）。
3. **子租户有独立域名与独立资源池**（它是「租户」，不是「机构」）；其资源由父租户**分配**：
   新建子租户时指定的词元上限 **不得超过父租户的剩余可用额度**
   （剩余 = 父租户 `token_total` − 已分配给本租户各机构的 `org_quota.quota_tokens` − 已分配给已有子租户的额度）。超限时报错并说明差额。
4. **域名只做格式与唯一性校验**（`^[a-z0-9]([a-z0-9-]*[a-z0-9])?(\.[a-z0-9-]+)+$`，转小写、去空格），
   **不做 DNS/证书绑定**（本项目是本地单端口部署，真域名解析不在代码范围内）。字段允许为空（历史租户不强制补）。
5. **平台管理员也能建子租户**（它是最高管理身份），其父租户取 `?tenantId=` 或默认租户，口径复用 `OrgGuard.resolveRequestTenant`。
6. **「虚拟管理员账号」不新增列**：继续以「无 `org_member` 行」为判据，但在人员接口里**显式回吐 `virtual: true/false`**，让前端能标注，避免再靠约定口头传达。

### 5.3 批次 C 的落地清单与证据（2026-09-27）

**规格原话**：「理论上，用户和员工存在多对多的关系。每个员工都有一个用户帐号，有些管理员用户帐号是虚拟的，
没有对应的员工，一个员工也可以有多个用户帐号。」

**根因**：`org_member.user_id` 是**单值**外键 ⇒ 一员工多账号只能靠「多建一行员工」近似，
那会把「一个人」拆成「多个人」，连带把部门人数、审批人、统计口径全带偏。

**迁移**：`V67__org_member_account.sql` —— 建中间表 `org_member_account(id, tenant_id, member_id, user_id, is_primary,
created_at, created_by, updated_at, deleted_at, alive)`，
`alive` 为 `IF(deleted_at IS NULL, id, 0)` 生成列 + `UNIQUE KEY uk_member_account(member_id, user_id, alive)`；
**回填既有 53 名员工**各一行 `is_primary=1`。实测 Flyway `now at version v67`，回填 53 行。

**后端**：
- `OrgMemberAccount.java` / `OrgMemberAccountMapper.java`（新建）—— 中间表实体与 Mapper。
- `service/MemberAccountService.java`（新建）—— 中间表的**唯一写入口**：
  - `syncPrimary(member, actorId)` —— `is_primary=1` 的**唯一**产生处（把该员工其它主标记降级、把目标账号置为主）；
    建档（新建/批量导入）后调用，保证「有员工就有主账号行」。
  - `attach`（追加绑定，先校验账号租户 == 员工租户，跨租户 403）、`detach`（**主账号不可解绑**，给明确文案，
    不做静默降级）、`dropAll`（删员工时清绑定，避免孤儿行）、`byMembers`（批量取，避免 N+1）、
    `candidates`（本租户账号清单，`virtual = boundMemberName == null`）、`virtualUserIds`。
  - 解绑 = 软删；因唯一键含 `alive`，解绑后**重新绑定同一账号不撞键、也无需复活旧行**（复活会被 `@TableLogic`
    自动附加的 `deleted_at IS NULL` 挡住，是易踩的坑）。
- `service/OrgTreeService.java` —— `createMember`/`importMembers` 调 `syncPrimary`；`deleteMember` 调 `dropAll`；
  列表 `memberViews` 批量取 `accounts`（形状恒定）、单员工 `view` 取真值。
- `controller/OrgAdminController.java` —— `GET /org/accounts`（候选，`requireOrgUser`）、
  `POST /org/members/{id}/accounts`、`DELETE /org/members/{id}/accounts/{userId}`（均 `requireOrgWriter`）。

不会产生「失去层级标识的孤儿租户」。层级列无数据要搬迁，`DROP` 不需要先备份。

selectTenantByCode / countTenantByDomain / selectTenantAdmin / countUsersOfTenant / updateTenantUsersStatus /

#### 实施中必须分清的一条边界（本批最大的坑）

`api/subTenant.ts` 里**同时装着**「子租户 CRUD」与「平台调额度 `updateTenantQuota`」。

#### 顺带修掉的既有缺陷（都在**被保留**的能力上，属本轮核查中发现）

1. **「清空登录域名」是假成功**。`TenantController.update` 用 `updateById(entity)`，而 MyBatis-Plus 默认
   `FieldStrategy.NOT_NULL` **不会把 `null` 字段写进 `SET`** ⇒ 接口回 `200 + domain:null`，库里纹丝不动。
   用户在界面上把域名清空点保存，看到「已保存」，域名其实还在。
   → 改 `LambdaUpdateWrapper.set(...)` 显式写 NULL，并回吐**重读**后的实体（展示与事实同源）。
   实测证据：`e2e_tenant_domain_quota.py` 的 A6/A7 —— 修前 A6 回 200，但 A7「库里应为 NULL」报红。
2. **「调整资源」弹窗一点保存就把席位清零**。`TenantAdminView.openQuota` 把 `expertSeats/skillSeats`
   **硬写 0**，而 `QuotaService.upsertPool` 对席位**没有**「不得低于已用」的兜底 ⇒
   打开弹窗看到 0、保存即把真实席位（如 12/18）写成 0，且无任何提示、无校验拦截。
   而后端 `list` **早就**回吐了 `expertSeats/skillSeats/expertUsed/skillUsed`，注释写明
   「弹窗要能预填当前值，否则用户看不到自己正在改什么」—— 前端从未接上。
   → 改为从行数据预填。守卫 **K7** 钉死「预填」；e2e **B8/B9/B10** 钉死后端契约
   （只提交词元则席位不动 / 显式提交才改 / 真落库）。
