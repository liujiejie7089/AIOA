## 1. 需求一 · 用户端项目功能

> **用户原话**：「项目列表支持点击查看，每个项目作为独立上下文且互不影响；处理项目时在首页进行，顶部显示当前项目名称；后端分配的数字人仅在所属项目内可用，其他项目不可使用；处理项目过程中支持上传文档，并在后端统一展示与查看；支持上报账单及花费信息。」

### 1.1 目标

把用户端（H5，单文件 `user-client/index.html`）的「项目」从**只读清单**升级为**第一等上下文**：
进入某项目后，首页顶部显示项目名；该上下文内的对话/数字人/文档/账单**都以该项目为作用域**，
且与其它项目、与「无项目」的普通对话**互不串扰**。

### 1.2 范围

**做**：① 列表可点击进入；② 项目上下文（顶栏 + 状态）；③ 首页对话坞按项目隔离；④ 数字人按项目过滤与硬校验；
⑤ 项目内上传文档（用户端发起点）并复用管理端已建的「文档」页签做统一展示；⑥ 项目内上报账单/花费（发起 `pm_expense`）。

**不做（明确排除）**：新建独立项目模块；用户端做项目的全量管理（立项/成员/任务/合同）；
把管理端的经费/合同/里程碑界面搬进用户端；改 `user-client` 的构建方式（仍走 `_build_oa.py` 单文件产物）。

### 1.3 关键设计决策

**① 形态：仍是「同文件双形态」**（`docs/39 §2.2` 的既有决策，无改动）。
`user-client/` 的文件铁律照旧：**只改 `_oa_app.js` / `_oa_extra.css` 等源，改完跑 `_build_oa.py` 生成 `index.html`**；
`index.html` 是产物，不得手改（项目记忆「唯一构建入口」）。

**② 项目上下文 = 一个显式状态 + 一处判定点。**
新增 `S.currentProject`（`{id, name, projectType, status, myRole}`），并新增**唯一进入/退出函数**
`enterProject(p)` / `exitProject()`；所有「当前项目」的读取只允许经 `currentProjectId()`。
**禁止**各处散读 `S.projects` 自行推断当前项目（否则必然出现「A 处显示项目名、B 处仍用无项目会话」的两套口径）。

**③ 会话隔离：项目会话与普通会话分账，且服务端可校验。**
现状：`state.conversationId`（经典形态）与 `state.oaConvId`（OA 对话坞）已分账，但**都与项目无关**。
方案：新增 `S.projectConvId[projectId]`，使「每个项目一条独立会话」；并且——
**这是与需求④的接口**：会话必须携带 `project_id` 到后端，否则数字人隔离无从校验（见 1.3-④）。
⇒ 需要后端 `chat_conversation` 增加 `project_id`（可空）列，`createConversation` 接受并落库。

**④ 数字人按项目隔离：三层过滤，缺一不可。**

| 层 | 位置 | 作用 |
|---|---|---|
| 可选集过滤 | 用户端「选择数字员工」卡 | 有当前项目时，只列 `GET /pm/projects/{id}/workers` 的已分配员工；无当前项目时不展示项目专属员工 |
| 会话绑定校验 | 后端创建会话/发起运行 | 会话若带 `project_id`，则 `worker_id` 必须在该项目的 `pm_project_worker` 且 `enabled=1`，否则 403 |
| 上下文下发 | `RunService.buildScope` | 组装 Agent 请求时按项目取 `effectiveScope`（这是 `docs/43 §5.3` 有意缓做的**唯一一处跨域接线**） |

> **现状证据（已核实）**：`grep -rn "pm_project_worker\|PmProjectWorker" server/ --include=*.java | grep -v aioa-project`
> **结果为空** ⇒ 分配表从未被聊天链路消费；`RunService.java:224` 只 `buildScope(conversation.getWorkerId())`，
> `:469-483` 仅读 `agent_worker` + `WorkerRole`，**不含任何项目维度**。故「数字人只在所属项目可用」目前**完全不成立**。

**⑤ 文档：用户端只做「发起上传」，展示一律复用管理端。**
用户端上传走**与前端同一对接口**（不新增后端）：`POST /v1/files/upload` → `POST /v1/pm/projects/{id}/docs/documents`（`source=UPLOAD`）。
「后端统一展示与查看」= 管理端 `PmProjectDetailView` 的**文档**页签（已实装），**不另建一套查看器**。
> ⚠️ **依赖 §3 的修复**：该端点当前 100% 500，用户端接入**必须先修 §3**，否则新功能一上线即坏。

**⑥ 账单/花费：只复用 `pm_expense` 的「追加式账目」语义，不在用户端开编辑口。**
`pm_expense` 的契约是**无 update、只能红冲**（`docs/43 §4` K4）：用户端只提供「上报」表单（新增一条），
修正入口统一走红冲（可由项目负责人/机构管理员在管理端做），避免用户端出现「改了就查不到」的账。

### 1.6 预期输出

1. 用户端项目卡片可点击 → 进入项目上下文，**首页正文显示项目名**（顶栏恒为「工作助手」，见 §7 的 2026-10-10 复核），有明确的「退出项目」；
2. 无项目时与有项目时是**两套会话**，互不影响（切换项目不串历史消息）；
3. 项目内点数字人 → **只出现该项目已分配且 `enabled=1` 的数字员工**；用未分配的员工 id 直连接口 → **403**；
4. 项目内可上传文档 → **管理端同一项目的「文档」页签可见并可按名/来源检索**（不新建查看器）；
5. 项目内可上报花费 → 管理端「经费」页签出现对应流水（`direction/category/amount/occurred_at`）。

### 1.7 验收判据（每条都要能「连跑两次」且判据回到事实源头）

- **A1** 首页**正文**里的项目名 = `GET /v1/pm/projects/{id}` 的 `name`（**不得**读界面自己的缓存副本）。
  > ⚠️ 2026-10-10 变更：本条原写「**顶栏**显示项目名」，后经用户指令改为「项目名以 chip 落在首页正文（`#oaProjSlot`）、
  > 顶栏恒为『工作助手』」。**不要把顶栏改回显示项目名** —— 那会与用户口径相反（详见 §7）。
- **A2** 切换项目后，`listMessages` 返回的会话 id **必须**与切换前不同（证明会话分账）；
- **A3** **负向对照（必须有，否则判据无效）**：把 `pm_project_worker` 里某员工置 `enabled=0` → 该员工**不得**出现在选择卡，且直连接口 403 变红；
- **A4** 有项目时选择卡的候选集 = `GET /pm/projects/{id}/workers` 的已分配集（集合相等，不是「包含」）；
- **A5** 用户端上传后，管理端 `GET /pm/projects/{id}/docs/tree` 能查到该文档（跨端同源）；
- **A6** 上报一条花费后，`GET /pm/projects/{id}/expenses` 条数 +1，且金额/时间与提交一致。

## 2. 需求二 · 管理端菜单权限

> **用户原话**：「机构管理员登录管理端后菜单分配过少，需支持机构管理员为本机构配置参数；重新整合菜单并分别分配给企业、机构管理员，且不涉及对方权限的功能不得分配。」

### 2.1 现状（已核实，`MainLayout.vue` 的可见性矩阵）

菜单门禁**只有一档** `showTenantMenu = TENANT_SCOPE_ROLES = [ROLE_ADMIN, ROLE_TENANT_ADMIN]`，
机构管理员（`ROLE_ORG_ADMIN`）被它整体挡在门外：

| 菜单组 | 门禁（`MainLayout.vue`） | `ADMIN` | `TENANT_ADMIN`(企业) | `ORG_ADMIN`(机构) | `DEPT_LEADER` | `MEMBER` |
|---|---|---|---|---|---|---|
| 首页 / 审批 / 知识库 / 通知 | 无（:92,:110,:134,:143） | ✅ | ✅ | ✅ | ✅ | ✅ |
| 智能服务 · 数字员工 `/workers` | `WORKER_MANAGER_ROLES` (:173,:471) | ✅ | ✅ | ✅ | ✅ | ❌ |

| 智能服务 · 业务工具 / 业务系统 | `showTenantMenu` (:176,:177) | ✅ | ✅ | **❌** | ❌ | ❌ |
| 成果与项目 · 成果沉淀 `/results` | `showTenantMenu` (:186) | ✅ | ✅ | **❌** | ❌ | ❌ |
| 成果与项目 · 项目管理 `/pm/projects` | `PM_VIEW_ROLES` (:201,:478) | ✅ | ✅ | ✅ | ✅ | ✅ |
| 运营管理 `/kpi` `/quotas` | `showTenantMenu` (:205) | ✅ | ✅ | **❌** | ❌ | ❌ |
| 租户与机构 | `showTenantMenu` (:215) | ✅ | ✅ | **❌** | ❌ | ❌ |
| 组织与员工 `/org-structure` | `ORG_VIEW_ROLES` (:258,:461) | ✅ | ✅ | ✅ | ✅ | ✅ |
| 权限与安全（角色/审批流/审计/审核记录） | `showTenantMenu \|\| showReviewRecordMenu` (:272) | ✅ | ✅ | **❌** | ❌ | ❌ |
| **系统配置（系统参数 / 仓库配置 / 功能管理 / 模型管理）** | `showTenantMenu` (:306) | ✅ | ✅ | **❌** | ❌ | ❌ |
| 平台管理（内容审核） | `isPlatformAdmin` (:330,:451) | ✅ | ❌ | ❌ | ❌ | ❌ |

**⇒ 「菜单过少」的实质**：机构管理员确实拿不到「系统配置」整组 —— 而其中**「系统参数」是机构管理员唯一真正需要的
「为本机构配置参数」入口**。「运营管理 / 租户与机构 / 平台管理 / 权限与安全（角色、审批流、审计）」**本就不该给它**
（那是平台或租户的职责），不属「分配过少」，属**正确的最小权限**。

### 2.2 目标

1. 让机构管理员**能为本机构配置参数**；
2. 把菜单按「平台 / 企业(租户) / 机构」三档重新整理，**每档只保留本档职责**，不越界；
3. 顺带消掉「同一能力两套口径」的隐患（如 `/settings` 既是平台配置又是租户配置）。

### 2.3 范围

**做**：① 新增**机构作用域**的参数配置能力（含菜单项、路由、接口、常量三处同源）；
② 菜单可见性从「一档 `showTenantMenu`」细化为**每档一个具名常量**（禁止再散写 `hasAnyRole(..., TENANT_SCOPE_ROLES)`）；
③ 按 §2.4 的矩阵落地方案；
④（可选，低优先）租户管理员的「成果沉淀 / 运营管理」归位复核。

**不做**：把平台专属菜单（内容审核、租户管理、角色与权限、功能管理、模型管理）下放给机构；
给机构管理员开「费用分摊 / 资源授权 / 入驻进度」（这三项是租户对机构的管理动作，反向即越权）。

## 3. 需求三 · 管理端项目管理「文档上传失败」

> **用户原话**：「管理端项目管理的文档上传失败问题，需定位原因并给出解决方案。」

### 3.1 结论先行：**已复现、已定位、根因唯一且确定**

**症状**：管理端 → 项目管理 → 项目详情 → **文档**页签 → 「上传文档」→ 前端弹「服务内部错误」，文档不出现。

**根因**：`PmDocService.java:355` 的三元表达式**把包装类型 `Long` 拆箱成 `long`**，
而「上传」路径下 `sizeBytes` **必然为 null** ⇒ **NPE ⇒ 500**：

```java
// server/aioa-project/.../service/PmDocService.java:355
d.setSizeBytes(contentText.isEmpty() ? asLong(body.get("sizeBytes")) : (long) contentText.getBytes().length);
//              ↑ 上传路径 contentText 为空，走这一支          ↑ 这一支是 long（基本类型）
//   三元表达式做「数值提升」⇒ Long 被拆箱为 long；而 asLong(null) 返回 null ⇒ NullPointerException
```

而前端**根本不发 `sizeBytes`**：
`PmProjectDetailView.vue:1303-1308` 的 `pmCreateDocument(projectId, {folderId, name, source:'UPLOAD', fileId})`
**没有 `sizeBytes`**；`api/pm.ts:339-342` 的请求类型里也**没有**这个字段。
⇒ 这是「两端对同一字段的口径不一致」类缺陷，**100% 必现**，与角色、项目类型、文件大小均无关。

### 3.2 证据链（本轮实跑，可复跑）

**① 直接复现（本地 8080，项目 id=78，`canManage=true`）**

```
POST /api/v1/pm/projects/78/docs/documents   {"folderId":23,"name":"x","source":"UPLOAD","fileId":9}
→ {"code":500,"message":"服务内部错误"}
```
> 注意：`GET /docs/tree` 的 `canManage=true` ⇒ **排除「权限不足」**（子代理初判的 #1 原因已被实证推翻）。

**② 后端日志拿到确切位置**

```
ERROR c.a.c.web.GlobalExceptionHandler - Unhandled exception on POST /api/v1/pm/projects/78/docs/documents
java.lang.NullPointerException: Cannot invoke "java.lang.Long.longValue()" because
    the return value of "cn.aioa.project.service.PmDocService.asLong(Object)" is null
    at cn.aioa.project.service.PmDocService.createDocument(PmDocService.java:355)
    at cn.aioa.project.controller.PmDocController.createDocument(PmDocController.java:81)
```
（`logs/backend-8080.log`）

**③ A/B 对照（决定性证据 —— 唯一变量是 `sizeBytes`）**

| 用例 | 请求体 | 结果 |
|---|---|---|
| A | `{folderId:23, name:"probe_no_size.txt", source:"UPLOAD", fileId:10}` | **`code:500`** |
| B | 同 A **+ `"sizeBytes":13`** | **`code:0`**，返回 `{"id":3,...,"sizeBytes":13,"version":1}` |

⇒ 唯一变量即根因，无其它解释。（探针数据已清理：文档 id=3 已删，`docs/tree` 文档数回到 0。）

**④ 为什么「AI 创建」不报错**：AI 路径传了 `contentText` → 三元走 `(long) contentText.getBytes().length` 一支，
**永不触碰 `asLong`** ⇒ 只有「上传」路径坏。这与用户「上传失败」的表述完全吻合。

### 3.3 解决方案

**修复（后端，必做）** —— 消除拆箱 + 让 `sizeBytes` 回到唯一事实源：

```java
// 目标写法（示意）
Long sizeBytes = null;
if (PmDocument.SOURCE_AI.equals(source) && !contentText.isEmpty()) {
    sizeBytes = (long) contentText.getBytes(StandardCharsets.UTF_8).length;
} else {
    sizeBytes = asLong(body.get("sizeBytes"));
    if (sizeBytes == null && fileId != null) {
        sizeBytes = fileRefMapper.sizeOf(fileId);   // ← 从 sys_file 取，单一事实源
    }
}
d.setSizeBytes(sizeBytes);   // 允许为 null（列可空），不再拆箱
```

> **为什么优先取 `sys_file.size` 而不是让前端补字段**：字节的真实大小只有 `sys_file` 知道；
> 让前端传等于「同一事实两处来源」，一旦前端不传/传错就静默写错。**后端能查到就自己查**
> （符合铁律 1「展示必须与事实同源」）。
> 若担心 `sys_file` 查询开销，可在 `PmAiRefMapper` 这类**只读窄接口**里加 `sizeOf`，与既有做法一致。

**配套（前端，建议做）** —— 让请求体带上 `sizeBytes: f.size`，并在 `api/pm.ts` 的请求类型里补上该字段。
即使后端已修，补上它也让两端口径一致、便于排障。

**同类隐患（本轮顺带发现，建议同批修）**

| # | 隐患 | 依据 | 处置 |
|---|---|---|---|
| 1 | 同名文档**无重名限制**，只会 `version+1`（`nextVersion`） | `PmDocService.java:364-371` | 明确为「同名自动升版」并在 UI 提示版本号（**不是** bug，但需定口径） |
| 2 | `pm_document.name` 为 `VARCHAR(256)`，超长名会**在 insert 时炸 500**（非 400） | `V72__pm_document.sql` | 入口做长度校验，超长回 400 并给明确文案 |
| 3 | `createDocument` **未拦只读终态**（`CLOSED/ARCHIVED` 项目仍可写文档） | `PmDocService.createDocument` 只过 `requireVisible` + `requireWrite` | 按 `PM_PROJECT_READONLY_STATUS` 补拦截（与其它 PM 写操作对齐） |
| 4 | 全部文档接口**无自动化覆盖** | `_smoke_pm.py` / `_check_pm_guards.py` 的 `PM_PERMS` 只到 `pm:project|task|member`，**不含 `pm:doc:*`**；仓库无 `_verify_pm_doc*` | 新增 `scripts/_verify_pm_doc_upload.py`（见 3.4） |
| 5 | 「上传体积」存在**双重限制**：Spring `max-file-size: 50MB`（`application.yml:37-38`）与 `FileController` 的 50MB 硬编码（`FileController.java:74`） | — | 两处收敛到同一个可配键，避免将来只改一处 |

### 3.4 预期输出 / 验收判据

**输出**：管理端「上传文档」在正常路径下**必然成功**；错误路径（超长名、只读项目、非本项目文件夹）一律回 **4xx + 可读文案**，不再出现裸 500。

- **C1** `POST .../docs/documents`（`source=UPLOAD`，**不带** `sizeBytes`）→ `code:0`，且落库 `size_bytes` = `sys_file.size`（与事实上传字节数一致）；
- **C2** **负向对照**：把修复回退（`asLong(...)` 直接拆箱）→ 新套件**必须变红**（否则等于没测）；
- **C3** 只读项目（`CLOSED`）写文档 → 4xx 且文案指明「项目已结项」；
- **C4** 超长文档名 → 4xx（**不是** 500）；
- **C5** 端到端：管理端上传 → `docs/tree` 可见 → 用户端（§1）同一接口上传 → 管理端同样可见（跨端同源）；
- **C6** 该套件纳入既有回归面，与 `_smoke_pm.py` / `_e2e_pm_ui.py` **连跑两次**。

## 4. 需求四 · 「本地系统参数齐全，生产只剩少数几项」

> **用户原话**：「本地项目系统参数齐全，但代码部署到生产环境后仅剩少数几项，需排查配置差异并说明原因与修复方式。」

### 4.1 结论先行：**已取证、已定位；这是「数据播种缺陷 + 兜底永不触发」的双缺陷叠加**

**症状取证（生产只读，`admin/Admin@123` 登录）**

```
GET https://mall.egoaicloud.com/aioa/api/v1/admin/configs
→ code=0, data.total = 3
   分组 CONVERSATION: ['chat.default_expert_key']
        QUOTA:        ['billing.package.scenes']
   （合计 3 条；本地同接口为 14 条 + 后续迁移追加的若干条）
```

### 4.2 根因（三层叠加，逐层给证据）

**第 1 层 —— 种子只播了「租户 1」，从没播「平台模板」**
`V18__sys_config.sql` 的 14 条 INSERT **全部是 `tenant_id = 1`**：
```
grep -cE "^\s*\(1, '"  V18__sys_config.sql   → 14
grep -cE "^\s*\(0, '"  V18__sys_config.sql   → 0    ← 平台模板(tenant_id=0)一条都没播
```

**第 2 层 —— 后续迁移只往「平台模板」里塞了零星几条**
`V33__billing_package_scenes.sql` 播 `billing.package.scenes`（tenant_id=0）、
`V34__tenant_content_approval.sql` 播 `approval.tenant.content`（tenant_id=0）、
`V62__default_expert_config.sql` 播 `chat.default_expert_key`（tenant_id=0）。
⇒ **`tenant_id=0` 成了「非空但只有 3 条」的畸形模板**。

**第 3 层 —— 首次克隆的兜底条件被永久打死（关键）**
`AdminConfigController.loadTenantConfigs()`（:272-288）：
```java
List<SysConfig> rows = mapper.selectList(... tenant_id = <调用者租户> ...);
if (!rows.isEmpty()) return rows;                    // ← ① 有任意行就直接返回，绝不补齐
List<SysConfig> templates = mapper.selectList(... tenant_id = 0 ...);
if (templates.isEmpty()) templates = BUILTIN_DEFAULTS;  // ← ② 只有「平台模板为空」才用代码兜底
// 克隆 templates → 本租户
```
- ① 使「租户已有几行但缺了 14 条基座」**永远不会被补齐**；
- ② 使代码里的 `BUILTIN_DEFAULTS`（14 条完整基座，`AdminConfigController.java:326-361`）**永远用不到** ——
  因为 `tenant_id=0` 已被第 2 层写成「非空」。

**⇒ 合起来**：任何 `tenant_id ≠ 1` 的租户，首次克隆拿到的是**只有 3 条的平台模板**，
且此后**永远停在 3 条**。本地「齐全」只是因为本地演示租户恰好是 **1**。

> **同一缺陷类已在 `docs/28 §2.8(D-8)` 记录过一次**（「新租户入驻只播种 `approval_flow_def` 与 `org_duty`，
> 未播种 `leave_type`」）—— 本次是 **`sys_config` 上的第二例**，说明「新租户/新租户配置播种不全」是**系统性**问题，
> 建议按**通用播种器**一次性治理，而不是逐个表打补丁。

### 4.3 解决方案（数据 + 代码 + 播种器，三者缺一不可）

**① 数据修复（Flyway 追加迁移，只追加不改已应用文件）**
- 把**完整基座**（V18 的 14 条 + 后续各次追加的键）以 `ON DUPLICATE KEY UPDATE` 播进 `tenant_id = 0`
  （作为**唯一权威模板**）；
- 再把模板键 **backfill 到所有已存在的租户**：`INSERT ... SELECT FROM sys_config WHERE tenant_id=0`
  ＋ `ON DUPLICATE KEY UPDATE config_key=config_key`（幂等，**只补缺失键，不覆盖用户已改的值**）。

**② 代码修复（`loadTenantConfigs` 改为「并集自愈」）**

```java
// 目标语义（示意）：
List<SysConfig> mine     = selectByTenant(tenantId);          // 本租户已有
List<SysConfig> template = selectByTenant(0L);                 // 平台模板
if (template.isEmpty()) template = BUILTIN_DEFAULTS;           // 模板真为空才兜底
// 键级并集：本租户缺哪个键就补哪个（补的是模板的 default，不动已有值）
return unionByKey(mine, template, /*fillMissingOnly=*/true);
```
⇒ 把「有没有行」的判断改为「**键是否齐**」的判断。这样即使将来又有新迁移往模板加键，
**所有租户下一次读取即自动补齐**，不再需要每次补一条 backfill 迁移。

**③ 播种器修复（治本，防第 3 次复发）**
把「新租户入驻需要哪些表/哪些键」抽成**一处清单**（`Provisioner` 列表），
在①的迁移里以同样方式 backfill 旧数据、在入驻流程里以同样方式播新数据 —— **同一份清单，两个入口**。
`docs/28 §2.8(D-8)` 的 `leave_type` 一并纳入。

### 4.4 改动模块

| 层 | 文件 | 改什么 |
|---|---|---|
| 迁移 | 新增 `V78+__sys_config_template_backfill.sql` | 补全 `tenant_id=0` 模板 + 幂等 backfill 到所有租户 |
| 后端 | `aioa-resource`：`AdminConfigController.loadTenantConfigs` | 「有行即返回」→「键级并集自愈」 |

| 文档 | 本文件 + `docs/28 §2.8` | 记录「template 为空才兜底」这个反模式 |

### 4.5 预期输出 / 验收判据

**输出**：任意租户（含新建）读 `GET /admin/configs` 都拿到**完整参数集**；已改过的值不被覆盖；新迁移加键后**自动补齐**。

- **D2** `tenant_id=0` 的模板键集 ⊇ 全仓所有 `sys_config` 插入键的并集（静态可校验）；
- **D3** **负向对照**：人为删掉某租户的一条参数 → 再次读取 → **自动补回**（证明自愈生效）；再删 `tenant_id=0` 的一条 → 读取**不得**因模板缺键而报错；
- **D4** 幂等：backfill 迁移**连跑两次**结果一致，且**不覆盖**已修改的值（用一条被改过的参数作对照）；
- **D5** 新租户入驻后，`sys_config` / `leave_type` / `approval_flow_def` / `org_duty` **同时齐备**（一条断言覆盖整张播种清单）。

**为何不改**：全仓「机构管理员」的 254 处里绝大多数是**注释/文档叙述**，用户可见文案只有上述 4 处；
**只改这 4 处会造成「代码注释说机构、界面说企业」的新一层不一致**，而全量改属跨模块文案批次且会改动用户已熟悉的界面用语。
按「改动面大于收益 ⇒ 记录不改」处理。**跟进建议**：先由产品定权威称谓（建议「机构管理员」，与 `docs/38` 六层模型对齐），再一次性改「文案 + 注释」，并同步 `docs/38`。
