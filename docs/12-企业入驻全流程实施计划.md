# 企业入驻全流程实施计划

> 依据：《AIOA 管理端需求规格说明书（租户管理员端 + 企业管理员端）》V2.0（FR-A ~ FR-K，共 32 条，M 级 25 条）
> 目标：以「企业入驻」视角补齐多租户组织基座，并全面升级机构内部的审批流程与请假流程
> 数据库：多租户架构一期采用 **MySQL**（行级隔离 + 机构硬边界）
> 编制：2026-09-11

---

## 一、总体判断

规格书的核心不是「加几个页面」，而是把系统从 **单租户演示态** 升级为 **四级主体链驱动的多租户态**：

```
平台运营端（另行成文）
   └── 租户（tenant）        计费与资源分配主体 · 租户管理员
         └── 机构（institution）  法人组织实体 · 企业管理员
               └── 部门 / 团队     机构内行政条线（≤5 层）
                     └── 个人       最小身份主体（个人端使用）
```

两端职责一句话划界：**租户管资源与规则，企业管组织与执行**；
范围纪律（规格书第七章，不可突破）：租户管理员端**不提供**机构内部组织管理功能，企业管理员端**不提供**跨机构数据与配额调整能力。

## 二、现状差距分析

### 2.1 已有基座（可复用）

| 层 | 现状 | 复用方式 |
|---|---|---|
| 租户 | `sys_tenant(id,name,code,status)`；全表已带 `tenant_id` | 直接扩展，无需改表 |
| 身份 | `sys_user` + `sys_role(role_code,data_scope)` + `sys_permission` + `sys_user_role` | 新增角色 `ROLE_TENANT_ADMIN` / `ROLE_ORG_ADMIN`，`data_scope` 承载行级隔离 |
| 额度 | `tenant_quota(tenant_id,user_id,quota,used,free)` + `token_ledger` | 作为「个人/共享」层额度，新增机构层与部门层额度 |
| 审批 | `approval_order`（单级：`approver` 字符串 + `status`） | **保留兼容**，新增多级审批任务表与其并行 |
| 知识库 | `kb_document`（含 scope 字段） | 增加机构/部门可见范围 |
| 审计 | `client_activity_log` + `AdminAuditController` | 统一收敛到新的 `audit_log`（两级：租户级/机构级） |
| 账单 | `token_ledger` + `payment_order` | 分摊账单与账本逐笔对齐 |

### 2.2 缺口（规格书要求但当前完全没有）

| FR | 功能 | 现状 | 缺口 |
|---|---|---|---|
| FR-B | 机构生命周期（新建/编辑/停用/恢复/注销） | 无 | **实体与全流程均缺失** |
| FR-G | 部门树（≤5 层）+ 员工管理 + 批量导入 | 无 | **组织域完全缺失** |
| FR-D | 分摊规则（固定比例/用量实摊/成本中心）+ 账单 + 试算 | 无 | **完全缺失** |
| FR-C2 | 机构配额分配 + 调整实时生效 | 仅 `tenant_quota` 单层 | 缺机构层与分配流水 |
| FR-H1 | 机构内额度二次分配（部门/员工） | 无 | 缺部门层额度 |
| FR-E1/E2 | 专家/技能/模型**按机构**授权 | 仅全局可见范围 | 缺机构维度授权 |
| FR-F2/FR-K2 | 两级审计（租户级/机构级） | 仅单级操作日志 | 缺 `institution_id` 维度与前后值留痕 |
| FR-A3 | 敏感操作二次确认并留痕（原值/新值） | 前端有确认框 | 缺后端 `audit_log` 原值/新值 |
| FR-H3/FR-J2 | 扩容申请 / 资源开通申请（演示链路） | 无 | 缺申请单与审批串联 |

### 2.3 已有但与规格口径不一致

- `approval_order.status` 当前为单级流转；规格要求「部门负责人 → 企业管理员」多级。
- 请假目前硬编码在前端表单（`bizType='LEAVE'` + `formData` JSON），无假种、无余额、无工作日计算。

## 三、功能范围（一期）

### 3.1 覆盖矩阵

一期实现 **全部 25 条 M 级**；O 级中仅实现与「入驻闭环」强耦合的两条演示链路（FR-H3 扩容申请、FR-J2 资源开通申请），其余 O 级（机构建档模板、分摊试算、共享知识库、风控策略、团队）按二期排期。

### 3.2 本次交付的能力边界

1. **企业入驻 8 步闭环编排**（主交付）：每一步落库、可查进度、可校验。
2. **四级额度链路**：租户资源池 → 机构配额 → 部门额度 → 个人额度，任一层调整即时贯通（成员端可见延迟 ≤ 1 分钟）。
3. **多级审批流**：审批流定义（按业务类型配置节点）+ 审批任务逐级流转 + 全量留痕。
4. **请假流程升级**：假种配置、假期余额、工作日/自然日计算、提交前校验、审批通过后扣减。
5. **两级审计 + 机构硬隔离**：企业管理员跨机构访问必须 0 成功（作为 E2E 验收项）。
6. **分摊出账**：三类分摊规则 + 试算 + 账单生成（含序时流水号与规则版本号）。

## 四、数据模型设计（MySQL）

### 4.1 隔离策略

| 层 | 隔离键 | 规则 |
|---|---|---|
| 租户 | `tenant_id` | 所有表必备；租户间行级隔离 |
| 机构 | `institution_id` | **硬边界**：企业管理员的所有查询强制注入本机构条件 |
| 部门 | `department_id` | 机构内可见范围 |
| 个人 | `user_id` | 个人额度与个人申请 |

统一约定（与既有表一致）：`id BIGINT AUTO_INCREMENT`、`created_at/updated_at/created_by`、**逻辑删除用 `deleted_at`**（MyBatis-Plus `logic-delete-field`），唯一键用「业务键 + 存活列」避免逻辑删除冲突。

### 4.2 新增表（16 张）

#### A. 组织域（FR-B / FR-G）

**`org_institution` 机构**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| tenant_id | BIGINT | 所属租户 |
| name / code | VARCHAR | 机构名称 / 机构编码（租户内唯一） |
| org_type | VARCHAR(32) | GOVERNMENT 政务机关 / ENTERPRISE 企业 / ASSOCIATION 社团 |
| credit_code | VARCHAR(64) | 统一社会信用代码 |
| legal_person | VARCHAR(64) | 法定代表人 / 负责人 |
| contact_mobile / contact_email | VARCHAR | 联系方式 |
| admin_user_id | BIGINT | 企业管理员（唯一，FR-B2） |
| status | VARCHAR(16) | ACTIVE 正常 / SUSPENDED 停用 / CLOSED 已注销 |
| established_at | DATE | 成立日期 |
| onboard_step | INT | 入驻进度（0~8），见流程设计 |
| remark | VARCHAR(512) | |
| deleted_at | DATETIME | 逻辑删除 |

唯一键：`uk_org_inst_code(tenant_id, code, alive)`。

**`org_department` 部门**
`id, tenant_id, institution_id, parent_id, name, code, level(1~5), path(物化路径 /1/3/7/), leader_user_id, sort, status, deleted_at`
约束：`level ≤ 5` 由服务端强校验；调整 `parent_id` 时同步迁移子树 `path` 与成员 `department_id`（FR-G1）。

**`org_member` 员工成员关系**（user ↔ 机构/部门）
`id, tenant_id, institution_id, department_id, user_id, name, mobile, email, employee_no, job_title, is_org_admin, status(ACTIVE/DISABLED), joined_at, deleted_at`
唯一键：`uk_org_member(tenant_id, institution_id, user_id, alive)`。
> 设计取舍：**不改 `sys_user` 表**，成员关系独立成表 —— 既满足「租户管理员可兼任某机构普通成员但不自动获得管理权」（FR-A2），也避免侵入既有鉴权链路。

#### B. 资源池与配额（FR-C / FR-H）

**`tenant_resource_pool` 租户资源池**
`id, tenant_id, period(YYYY-MM), token_total, token_used, expert_seats, expert_used, skill_seats, skill_used, warn_threshold(默认20), expire_at, status, deleted_at`

**`org_quota` 机构配额**
`id, tenant_id, institution_id, period, quota_tokens, used_tokens, free_tokens, warn_threshold, effective_from, effective_to, frozen(0/1), status, deleted_at`
唯一键：`uk_org_quota(tenant_id, institution_id, period, alive)`。
校验：`Σ 机构 quota_tokens ≤ 资源池 token_total`（FR-C2）；`frozen=1` 时消耗性操作直接拒绝（FR-C3）。

**`dept_quota` 部门额度**
`id, tenant_id, institution_id, department_id, period, quota_tokens, used_tokens, warn_threshold, deleted_at`
校验：`Σ 部门 quota_tokens ≤ 机构 quota_tokens`（FR-H1）。

**`quota_alloc_log` 配额分配流水**（对齐「配额分配与预警页」与审计）
`id, tenant_id, scope_type(TENANT/ORG/DEPT/USER), scope_id, period, action(ALLOCATE/ADJUST/FREEZE/UNFREEZE/CONSUME), before_tokens, delta, after_tokens, reason, operator_id, operator_role, created_at`

#### C. 费用分摊（FR-D）

**`cost_alloc_rule` 分摊规则**
`id, tenant_id, name, rule_type(FIXED_RATIO/USAGE/COST_CENTER), period_type(MONTH/QUARTER), config_json(比例表/成本中心映射), version(自增), effective_from, status(DRAFT/ACTIVE/RETIRED), deleted_at`
> 变更次期生效并留痕：改规则 = 生成新 `version`，旧版置 `RETIRED`。

**`cost_alloc_bill` 分摊账单**
`id, tenant_id, rule_id, rule_version, institution_id, period, usage_tokens, unit_price, amount, serial_no(序时流水号), ledger_checked(与账本核对标记), generated_at, deleted_at`
唯一键：`uk_cost_bill(tenant_id, institution_id, period, rule_version, alive)`。

#### D. 资源授权（FR-E）

**`resource_grant` 资源授权**
`id, tenant_id, institution_id, res_type(EXPERT/SKILL/MODEL/KB), res_id, res_name, enabled, granted_by, granted_at, deleted_at`
唯一键：`uk_resource_grant(tenant_id, institution_id, res_type, res_id, alive)`。
生效规则：未授权的机构，其成员端**不可见**该资源（FR-E1）；模型清单按机构差异化并携带计费倍率（FR-E2）。

#### E. 审计（FR-F2 / FR-K2 / FR-A3）

**`audit_log` 两级审计日志**
`id, tenant_id, institution_id, actor_id, actor_name, actor_role, action, target_type, target_id, before_json, after_json, ip, created_at`
不可篡改：**只写不提供更新/删除接口**；租户级查询不过滤 `institution_id`，机构级强制过滤。

#### F. 审批与请假（FR-H3 / FR-J2 演示链路 + 流程升级）

**`approval_flow_def` 审批流定义**
`id, tenant_id, institution_id, biz_type(LEAVE/QUOTA_EXPAND/RESOURCE_OPEN/...), name, steps_json([{seq, approver_type(DEPT_LEADER/ORG_ADMIN/SPECIFIC), approver_id, threshold_days}]), status, deleted_at`

**`approval_task` 审批任务**（多级节点）
`id, tenant_id, institution_id, order_id(→approval_order.id), seq, approver_type, approver_id, approver_name, status(PENDING/APPROVED/REJECTED/SKIPPED), note, decided_at, created_at, deleted_at`
> 与既有 `approval_order` 并行：`approval_order` 仍是单据主表，`approval_task` 承载多级流转，既有单级接口保持不变（保证既有 180 项 E2E 零回归）。

**`leave_type` 假种配置**
`id, tenant_id, code(ANNUAL/SICK/CASUAL/MARRIAGE/MATERNITY/COMP), name, unit(DAY/HOUR), quota_days_per_year, need_proof(0/1), advance_days, max_consecutive_days, paid(0/1), status, deleted_at`

**`leave_balance` 假期余额**
`id, tenant_id, institution_id, user_id, leave_type_code, year, total_days, used_days, pending_days, deleted_at`
唯一键：`uk_leave_balance(tenant_id, user_id, leave_type_code, year, alive)`。

**`leave_request` 请假单**
`id, tenant_id, institution_id, department_id, user_id, order_id(→approval_order.id), leave_type_code, start_date, end_date, days, reason, proof_file_id, status(DRAFT/PENDING/APPROVED/REJECTED/CANCELED), deleted_at`

1. 16 张新表 + 索引 + 唯一键；

## 五、流程设计

### 5.1 企业入驻 8 步闭环（主交付）

规格书第三章主链路，前 4 步租户端、5~7 步企业端、第 8 步回租户层：

| 步 | 环节 | 操作端 | 动作 | 落库实体 | 校验门禁 |
|---|---|---|---|---|---|
| 1 | 租户开通 | 平台运营端 | 创建租户、交付资源池套餐与管理员账号 | `sys_tenant` / `tenant_resource_pool` / `sys_user` + `sys_user_role` | 资源池 `token_total > 0` |
| 2 | 建立机构 | 租户管理员端 | 创建机构、指定企业管理员 | `org_institution`(status=ACTIVE) / `sys_user_role`(ROLE_ORG_ADMIN) | 机构编码租户内唯一；管理员唯一；同租户 `code` 不重复 |
| 3 | 资源授权 | 租户管理员端 | 分配词元配额上限、授权专家/技能/模型 | `org_quota` / `resource_grant` / `quota_alloc_log` | `Σ机构配额 ≤ 资源池总量` |
| 4 | 分摊规则 | 租户管理员端 | 配置机构间分摊规则 | `cost_alloc_rule`(version=1, ACTIVE) | 固定比例合计 = 100% |
| 5 | 组织搭建 | 企业管理员端 | 建部门树、导入员工、二次分配额度到部门 | `org_department` / `org_member` / `dept_quota` | 部门层级 ≤5；`Σ部门额度 ≤ 机构配额` |
| 6 | 能力启用 | 企业管理员端 | 建设机构知识库、确认授权资源可用 | `kb_document`(scope 扩机构/部门) / `resource_grant` 引用可见 | 存在 ≥1 已授权资源 |
| 7 | 成员使用 | 个人端 | 成员使用专家/技能/知识库；发起请假 | `token_ledger`(计量到机构) / `leave_request` / `approval_order` / `approval_task` | 机构未冻结；额度充足 |
| 8 | 结算对账 | 租户管理员端 | 查看分摊账单、处理预警、在线续费 | `cost_alloc_bill` / `payment_order` | 账单与账本逐笔一致 |

**进度模型**：`org_institution.onboard_step` 由各步完成后推进；`GET /api/v1/tenant/onboarding/{institutionId}/progress` 返回 8 步完成态与阻塞原因。

**降级预案**（规格书第七章）：若排期紧张可先「租户与机构一对一」，但**数据模型与权限模型按两级建设**，二期放开多机构无结构性改造 —— 本次按两级完整实现，故无需降级。

### 5.2 配额链路与即时贯通

```
分配：租户资源池 ──分配──> 机构配额 ──二次分配──> 部门额度 ──> 个人（tenant_quota）
调整：任一层写入 quota_alloc_log（before/delta/after + reason + operator）→ 通知链路
消耗：会话结束 → token_ledger 记账 → 同步 +org_quota.used_tokens / dept_quota.used_tokens
预警：used/(quota+free) ≥ (1 - warn_threshold) → 生成预警（机构级 / 租户级）
冻结：机构配额耗尽 → org_quota.frozen=1 → 该机构所有消耗性操作返回 403 并引导申请扩容
```
**一致性口径**：剩余 = `quota_tokens + free_tokens - used_tokens`（沿用既有 `BillingService` 口径，两级账目实时一致）。

### 5.3 审批流模型（多级）

```
提交单据（approval_order, status=PENDING）
   └─ 按 biz_type 匹配 approval_flow_def → 展开 steps_json 为 N 条 approval_task(seq 升序, PENDING)
        └─ 取 seq 最小的 PENDING 任务为当前节点
             ├─ 通过 → status=APPROVED，推进下一节点；末节点通过 → 单据 APPROVED + 触发后置动作
             ├─ 驳回 → 单据 REJECTED，其余任务 SKIPPED
             └─ 阈值跳级：天数 ≤ threshold_days 时跳过 ORG_ADMIN 节点（SKIPPED 留痕）
```
节点类型：`DEPT_LEADER`（按 `org_department.leader_user_id` 解析）/ `ORG_ADMIN`（按 `org_institution.admin_user_id` 解析）/ `SPECIFIC`（指定人）。
兜底：解析不到审批人时**不静默通过**，落 `ORG_ADMIN` 并在单据备注写明原因。

### 5.4 请假流程（升级后）

```
1. 员工选假种 → GET leave_type（含是否需证明/提前天数/最长连续天数）+ 查 leave_balance 余额
2. 填起止 → 服务端算 days（工作日/自然日按假种 unit 与 calendar 规则）
3. 提交校验（任一不过即拒绝，返回具体原因）：
   · 机构未冻结、额度/科目正常
   · leave_type.status=ENABLED
   · days ≤ max_consecutive_days
   · 提前天数 ≥ advance_days（当日紧急假由 ORG_ADMIN 特批节点兜底）
   · need_proof=1 时必须有 proof_file_id
   · available = total - used - pending ≥ days
4. 落库：leave_request(PENDING) + approval_order(bizType=LEAVE, formData 携带结构化字段)
   + 展开 approval_task（默认「部门负责人 → 企业管理员」）+ leave_balance.pending_days += days
5. 审批：逐级通过；驳回 → 释放 pending_days，单据 REJECTED
6. 终审通过：used_days += days，pending_days -= days，回写 approval_order.status=APPROVED，
   写入 audit_log，通知申请人
```

### 5.5 权限与隔离规则（可测试的硬边界）

| 角色 | data_scope | 可见 | 不可见/不可做 |
|---|---|---|---|
| ROLE_TENANT_ADMIN | TENANT | 本租户全部机构数据 | 机构内部组织管理（部门/员工增删改） |
| ROLE_ORG_ADMIN | ORG | 本机构全部数据 | 其他机构任何数据；跨机构配额调整 |
| ROLE_DEPT_LEADER | DEPT | 本部门及下级 | 其他部门 |
| ROLE_MEMBER | SELF | 本人数据 | 管理类操作 |

实现方式：`AuthUserContext` 取当前用户 → 解析 `org_member` 得 `institution_id` → 服务层统一注入 `tenant_id + institution_id` 条件；越权访问统一返回 **404**（不泄露存在性）或 **403**，与既有约定一致（`BizException.forbidden` / `notFound`）。

## 九、实施顺序与风险

**顺序**（每步完成即验证，避免大爆炸式提交）：
1. V24 迁移 → 起服务验表 → 2. aioa-org 模块骨架 → 3. 租户端服务/接口 → 4. 企业端服务/接口 → 5. 入驻编排 → 6. 审批/请假升级 → 7. 前端页面 → 8. E2E 全流程 → 9. 收口提交

**风险与对策**
| 风险 | 影响 | 对策 |
|---|---|---|
| 新表与既有 `approval_order` 语义重叠 | 既有 180 项 E2E 回归 | 新表并行不替换，既有接口零改动 |
| `Σ配额 ≤ 资源池` 并发超额 | 账目不一致 | 服务层加行锁 + 分配流水，写前校验 |
| 机构隔离靠应用层 | 越权泄露 | 服务层统一注入硬边界 + E2E 渗透断言 |
| Flyway 版本冲突 | 后端起不来 | 新建迁移前先 `ls db/migration` 取最大版本（历史踩过） |
| 沙箱子进程被回收 | 长驻后端被杀 | 长驻服务用常驻后台任务启动（历史踩过） |
