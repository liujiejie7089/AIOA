## 3. 逐项详评

### 项 1 · 四端权限与多租户 —— **≈85%，基本达标**

**四端如何落地（重要事实）**：不是四个物理端，而是**同一个管理端 shell + 按角色分层菜单**，加一个独立 H5。

| 端 | 实现 | 判别依据 |
|---|---|---|
| 平台运营端 | `web/apps/shell` + `minTier:'platform'` | `/admin` `/tenants` `/content-reviews` `/tools` |
| 租户管理端 | 同 shell + `TENANT_SCOPE_ROLES` | `/institutions` `/onboarding` `/resource-grants` `/cost-alloc` `/quotas` `/approval-flow-defs` |
| 企业管理端 | 同 shell + `ORG_VIEW_ROLES` | `/org-structure` `/org/members` `/org/dept-quotas` `/org/kb` `/org/leave` |
| 普通用户端 | `user-client/index.html`（3722 行，12 页） | `page-home/chat/todo/perm/result/bill/buy/me/agent/log` |

**数据可见范围**：`data_scope` 六档角色（ROLE_ADMIN/TENANT_ADMIN/ORG_ADMIN/DEPT_LEADER/MEMBER/USER）
＋ `OrgGuard.resolveRequestTenant()` 租户作用域硬绑 ＋ `visible_scope`(SELF/DEPT/ORG/TENANT) 资源级可见性。

**全链路闭环（申请→审批→授权→使用→计费→审计→回收）**：✅ **真实成立**
- 申请/审批/授权/回收：`permission_grant` + `/org/permissions/{apply,revoke,pending,catalog,holdings,mine}`（V36–V38 刚收口，E2E 63/63）
- 使用：`PermissionCatalog.holds()` 先查 `AuthUser.permissions` 再查角色
- 计费：`token_ledger` 按 run 记账
- 审计：`audit_log` 283 行 + 哈希链（`prev_hash/hash/hash_algo`，V25）+ 三端查询入口

**应用超市**：`app_registry` + `/api/v1/apps` + `permission_code` + `visible_scope`(V12) + `AppHost.vue` 子应用宿主。**但仅 2 个应用。**

**缺口**：
1. 四端无独立登录入口/品牌，租户端与企业端靠菜单隐藏区分 → 演示时「四端」观感不足（功能上成立）。
2. 应用超市**无上架/下架审批**，无应用级计费项（与项 7 耦合）。
3. 审计**只覆盖管理配置类动作**（创建/修改/权限变更），**业务数据读取（谁查了哪些经营数据）未留痕** —— 对「税务风险数据」这类高敏感场景是硬伤。
4. 权限回收后在途 JWT 内的 `permissions` 刷新机制未验证（回收即时性存疑）。

## 4. 横向专题（架构与实现要求）

### 4.1 「AI 与 Agent 相关业务必须在 Python 模块中实现」

**结论：基本合规，有 1 处外溢。**

- ✅ 合规面：`agent/app/core/{intent_router,agent_runtime,echo_runtime,runtime,guards}.py` +
  `model_gateway/` + `tools/{gateway_client,sandbox}.py`。Java 侧通过 `agentBaseUrl + /internal/v1/{runs,complete,models/apply}` 调用，**不做 LLM 直连**。
- ⚠️ **外溢点**：`server/aioa-resource/.../KpiInsightService.java` 在 **Java 侧持有 `SYSTEM_PROMPT` 并拼装业务提示词**
  （`buildPrompt()` 组装指标+趋势文本），再转发给 Python `/internal/v1/complete`。
  模型调用在 Python（可接受），但**提示工程与 AI 业务逻辑在 Java**，违反「AI 相关业务在 Python」的边界。
  建议下沉：Python 侧新增 `/internal/v1/insight`，Java 只传结构化指标 JSON。

### 4.2 专家职责边界

- ✅ 有据可依：`docs/10-数字员工职责边界与权限规则.md` + `docs/15-数字员工权限矩阵.md`；
  代码侧 `WorkerRole`(GENERAL/LEAVE_APPROVER/KB_ASSISTANT/DOC_DRAFTER) → `requiredPermission` → `PermissionCatalog`。
- ⚠️ 运行时**未见「不得处理无关任务」的强制守卫**：`intent_router.route(text, enabled_tools)` 只是
  **按开关关闭工具**（`expert_config.tools`），若某专家被关了 `sql_query` 会回落到 `chat` 兜底，
  **不会明确拒绝并说明边界**。边界表达缺失（对应项 6 的「能力边界」结构要求）。

### 4.3 AI 生成表单的展示 / 编辑 / 保存 / 校验 / 提交

**结论：❌ 无通用机制。** 现状是 `user-client` 中 `openSkill()` **硬编码**一张参数卡
（文种 select / 主题 textarea / 字数 input）＋ `genDocInChat()` 把参数拼成一句话发给后端。
- 展示：写死 HTML，非「按模板渲染」
- 编辑：可改但无字段级校验（无必填/长度/正则）
- 保存：无草稿保存
- 提交：仅拼字符串，无结构化提交与回执
截图 `数据分析·办文助手` 与 `调整数字员工任务确认` 两张卡**均为前端硬编码模板**，非 AI 生成。

## 5. 补齐计划

排序原则：**先补「挡住其他项」的公共能力**（前置检查、表单设计器、应收账单），再补独立业务域。

### 阶段一 · P0-a：数字员工标准流程收口（项 6）—— 不新增业务表

| # | 交付物 | 落点 | 验收判据 |
|---|---|---|---|
| 1 | `POST /api/v1/workers/precheck` 前置检查（六项：权限/能力/审批人/表单/审批流/计费），返回 `{ok, blocked[], hints[], script}` | `aioa-resource` | 六项各造一个缺失场景，`blocked` 精确命中且带管理员话术 |
