## 一、为什么不是二选一

| 事实 | 结论 |
|---|---|
| `snsapi_privateinfo` + `auth/getuserdetail` 返回的 `biz_mail` 只是**邮箱地址字符串** | OAuth **换不来** IMAP/SMTP 收发能力；企微企业邮不向第三方开放邮箱 OAuth |
| `send_text_message` / `contact_search` 是**应用级 API**（access_token = corpId+secret） | 与「哪个用户授权」无强绑定；A 模式的真实价值是**身份与审计**（userid/biz_mail） |
| `snsapi_privateinfo` 只能在企微内置浏览器弹授权框 | PC/外浏览器只能走 `qrConnect` 兜底（仅 userid，无 user_ticket/biz_mail） |

⇒ **A 为主（身份+消息+通讯录）+ B 为必备（邮件收发）+ 可叠加（A+B）**。
用户在 H5 眼里只有一个「企业微信」，连接态分 `A` / `B` / `AB` 三种。

## 二、架构

```
H5（MCP Client，SSE 长连接）
   │  tools/call：connect / get_my_profile / mail_* …
   ▼
mcp-hub :8099  /mcp/wechat_work（原生 FastMCP，非代理）
   ├─ wecom/catalog.py    双模式目录（唯一事实源：13 工具 + 两组 schema + credential_fields）
   ├─ wecom/gate.py       模式闸门：连接态 → 工具白名单（A 组 / B 组 / lifecycle）
   ├─ wecom/graph.py      LangGraph 工作流（gate → execute），SqliteSaver 检查点
   ├─ wecom/store.py      SQLite：tenant_config / connection / oauth_state（凭据全 enc: 密文）
   ├─ wecom/crypto.py     AES-256-GCM，enc: 格式与 Java SecretCodec 同口径
   ├─ wecom/oauth.py      authorize / qrConnect URL 构造、UA 分流、state 一次性 10min、token 缓存
   ├─ wecom/wecom_api.py  方案A 后端（Mock + qyapi 实装）
   ├─ wecom/mail.py       方案B 后端（Mock + P2 实装 imaplib/smtplib）
   ├─ wecom/identity.py   身份解析：Java `/api/v1/auth/me`（mock 模式走测试头）
   └─ wecom/admin_api.py  REST 面：/api/v1/wecom/*
                              ├─ GET/PUT  tenant-config   租户配置（掩码/upsert，仅管理员）
                              ├─ GET      connections     我的连接态（脱敏）
                              ├─ GET      oauth/authorize-url  授权链接（URL 模板）
                              └─ GET      oauth/callback  授权回调 → 换身份 → 落库 → 302
   ▼
企微开放 API（gettoken / getuserinfo / getuserdetail / message/send / user/list）
IMAP·SMTP（腾讯企业邮 imap.exmail.qq.com:993 / smtp.exmail.qq.com:465）
```

对齐 Octop 的映射：`catalog.json` → `catalog.py`；`auth_kind` ∈
{`oauth2_privateinfo`, `imap_app_password`} → 同一连接器下的两种授权形态；
`allowed_tools` → 模式闸门；`credential_fields` → B 模式声明式表单。

`connection_status`。

**A 组（模式 A / AB）**：

| 工具 | required | 说明 |

## 四、授权链路

### 方案A（企微 App 内 OAuth）

1. `connect(mode=A)` → 取租户配置（corpId/agentId/redirectUri）→ `issue_state`（一次性，10 分钟 TTL）。
2. UA 分流：含 `wxwork`/`MicroMessenger` → 网页授权；否则 → `qrConnect`（兜底，仅 userid）。
3. **URL elicitation**（`session.elicit_url`，敏感交互不走 LLM 上下文）下发授权页；
   客户端不支持时降级：把 `authorizeUrl` 放进工具结果，H5 渲染按钮。
4. 用户在企微内授权 → 企微 302 到 `/api/v1/wecom/oauth/callback?code&state`。
5. 回调 `consume_state`（一次性）→ `getuserinfo` 换 userid+user_ticket →
   `getuserdetail` 换姓名/biz_mail → 合并进连接态（A）→ 302 回结果页。
6. `connect` 轮询等待连接态落地（默认 30s，超时返回 pending 由 H5 轮询）。

### 方案B（企业邮箱客户端专用密码）

1. `connect(mode=B)` → **表单 elicitation**（email + client_password，声明式字段来自 catalog）。
2. 后端 `probe`（IMAP 探活；P2 实装 imaplib）→ 失败分类（未开 IMAP / 授权码错 / 网络）。
3. 凭据加密落库（`b_credential`），连接态合并为 B（或 AB）。

## 五、URL 模板与 Scheme（交付物②）

```
网页授权（企微内置浏览器）：
https://open.weixin.qq.com/connect/oauth2/authorize
  ?appid={corpId}&redirect_uri={urlencode(redirectUri)}&response_type=code
  &scope=snsapi_privateinfo&agentid={agentId}&state={state}#wechat_redirect

PC 扫码兜底：
https://open.work.weixin.qq.com/wwopen/sso/qrConnect
  ?appid={corpId}&agentid={agentId}&redirect_uri={urlencode(redirectUri)}&state={state}
```

- `redirectUri` 必须注册进企微管理端「网页授权及 JS-SDK 可信域名」，且协议/域名/端口完全一致
  （`127.0.0.1` 不是可信域名——实测踩过：授权框根本不出现，回调零命中）。
- 企微未开放「任意 URL 的公开 scheme」。进入授权页的途径：① 管理后台/连接器面板
  「复制授权链接」；② 在企微 App 内打开 H5（文件传输助手/收藏/自建应用工作台主页）。
  不做 `weixin://` 硬跳（无文档保证，且会被企微拦截）。
- 回调结果页：`WECOM_OAUTH_RESULT_URL?wecom=ok|fail&reason=...`（H5 路由 `/connectors`）。

## 六、配置项（交付物①，管理端动态管理）

| 配置 | 位置 | 说明 |
|---|---|---|
| corpId / corpSecret / agentId | 管理端 → 运营管理 → 连接器配置（PUT /api/v1/wecom/tenant-config） | 密文存储；GET 只回掩码。Java 侧 `connector_tenant_config` 保留原口径，Python 侧为运行态副本（P4 补同步） |
| redirectUri | 同上；缺省按 `WECOM_PUBLIC_BASE_URL` + `/api/v1/wecom/oauth/callback` 推导 | 必须与企微可信域名一致 |
| IMAP/SMTP 开关 + 客户端专用密码 | 成员本人在邮箱设置中操作 | 路径随企业邮版本略有差异，文档按版本截图维护 |
| `WECOM_CONNECTOR_KEY` | 部署 env（base64 32 字节） | `WECOM_MOCK=0` 时缺失即启动失败；`openssl rand -base64 32` 生成 |
| `WECOM_MOCK` | 部署 env | **默认 0**；1 = 虚拟企业+虚拟邮箱（联调/哨兵） |

## 七、错误排查清单（交付物⑦，与 wecom_api.ERRCODE_REASONS 同源）

| 现象 | 原因 | 处置 |
|---|---|---|
| 授权框不出现 / 回调零命中 | redirect_uri 非可信域名；`agentid` 填成占位串（实测踩过 `wecom`） | 管理端按第五节核对三件套 |
| `40003` | 可信域名不含回调地址 | 企微管理端加域名 |
| `301025` / `40001` | corpSecret 错 | 重新保存配置 |
| `40029` | code 一次性且 5 分钟内有效，重复使用/超时 | 重新发起授权 |
| `45009` | access_token 每次现取 | token 缓存已内置（剩余 5 分钟刷新） |
| `81013` / `81014` | user_ticket 过期 / 非本企业成员 | 重新授权 |
| `60011` | 应用无该接口权限或通讯录可见范围不足 | 管理端开权限 |
| `MAIL_NOT_ENABLED` | 成员未开启 IMAP/SMTP | 邮箱设置中开启 |
| `MAIL_AUTH_FAILED` | 客户端专用密码错（≠登录密码） | 重新生成授权码 |
| 模式闸门拒绝 | 工具与连接态模式不符（如 A 模式调邮件工具） | 按拒绝文案 `connect` 补绑另一模式 |

## 八、权限隔离（交付物⑦⑧）

- **租户配置**：仅 `ROLE_ADMIN` / `ROLE_TENANT_ADMIN` 可写（经 Java `/auth/me` 判定）；
  读只回掩码。任何响应不含凭据明文/密文。
- **用户凭据**：按 `(tenant_id, user_id)` 隔离；`get_my_profile` 只回本人身份；
  审计记录 userid 与动作，**永不回传 user_ticket**（一次性使用后即弃）。
- **模式闸门**：工具调用前校验连接态模式；越权调用返回可读拒绝（引导补绑），不静默失败。
- **存储**：SQLite 单文件，凭据列全 `enc:` 密文（哨兵 S17 扫库文件字节断言无明文）；
  `data/` 不进 git。
- **日志**：只记 server/tool/ok/duration 与租户/用户 ID；Authorization、收件人、正文、
  授权码、密码一律不落日志。

## 十、已知限制

- 真机验证硬限制：`snsapi_privateinfo` 必须真机 + 企微管理端可信域名，本机只能 mock；
  P1 需用户配合排一次真机冒烟。
- 企业邮箱若并非腾讯企业邮（自建 Exchange 等），B 的授权码路径不同，第一节配置文档需覆盖。
- `qrConnect` 分支只拿 userid（企微协议限制），拿不到 biz_mail——H5 需明示「在企微 App 内打开可获得完整身份」。
- Java 侧 V97/V99 种子（check_connection / send_text_message / get_my_profile）保持不变，
  与 hub 原生目录同名同 schema；Java 的 WeComMcpHandler 不再被 hub 调用（hub 原生实现），
  Java 侧注册表数据仍供 OA 面板展示。

## 十一、附录：企微管理端配置操作手册（交付物①完善，2026-10-28）

### A. 方案A：企微管理端五步（超管/管理员，一次性）

登录 `work.weixin.qq.com`（超管扫码）：

1. **建自建应用**：「应用管理」→ 自建 →「创建应用」→ logo/名称/**可见范围**（全员或目标部门）
   → 应用详情记下 **AgentId**（如 1000002）。
2. **取三件套**：corpId 在「我的企业」页最底部（`ww` 开头）；**corpSecret** 在应用详情「Secret」
   →「查看」（可能要管理员验证），可重置，重置后旧的立即失效。
3. **配可信域名**：应用详情 →「网页授权及 JS-SDK」→ 填「**可作为应用 OAuth2.0 网页授权功能的
   回调域名**」（只能 1 个；JS-SDK 域名是另一个框，可 10 个，别填错）。
   硬性要求：**不带协议头、不支持 IP/内网域名/泛域名、需备案**（建议备案满 72h 再绑）；
   需下载 `WW_verify_*.txt` 校验文件放到域名根目录且**之后不能删**。
4. **配可信 IP**：应用详情 →「可信 IP」→ 加 mcp-hub 服务器的**公网出口 IP**（漏配报 `60020`；
   家宽动态 IP 每次都得改，真机联调建议固定 IP 服务器）。
5. **开 API 权限**：应用详情 →「API 权限」——`contact_search` 需通讯录读取权限且可见范围覆盖
   目标成员；`send_text_message` 用应用消息推送（自建默认具备）；`get_my_profile` 不额外要权限。

### B. 方案B：企业邮箱双重开关（管理员 1 步 + 每成员 3 步）

腾讯企业邮 IMAP/SMTP 是双重开关，少一步都连不上：

- **管理员**：管理端 →「协作」→「邮件」→「安全管理」→「**客户端访问权限**」→ 修改 IMAP/SMTP
  服务范围，勾选要用邮箱的成员（没勾的成员自己开不了）。
- **成员**（网页登录 `exmail.qq.com`，建议企微扫码）：
  ①「设置」→「收发信设置」→ 开启 IMAP/SMTP 服务；
  ②「设置」→「邮箱绑定」→ 开启「安全登录」（开了就必须用专用密码，登录密码无效）；
  ③ 同页生成**客户端专用密码**（授权码），绑定 B 模式时填它，不是登录密码。
- 服务器参数无需成员填写，系统内置默认值（与腾讯官方文档一致）：
  `imap.exmail.qq.com:993` SSL 收信 / `smtp.exmail.qq.com:465` SSL 发信。
