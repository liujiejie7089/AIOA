# 22 · 管理端登录口径与演示口令归一化（V40）

> 缘起：用户报障「输入机构，管理员账号，User@123 很多都登不上去，你测试一下并修复」。
> 实测归因后为**两个互相独立的根因**；修复涉及 1 处后端语义、1 个迁移、1 处前端文案，
> 另在回归中暴露并修掉 1 个产品缺陷 + 2 个脚本缺陷。记录时间 2026-09-15。

---

## 1. 现象与归因

### 1.1 主因：租户名「逐字相等」把机构名称挡在门外（1004）

管理端登录表单的字段标签是「租户名称」，但机构 / 企业管理员按直觉填的是**自己所辖机构名称**
—— 例如把「某某智能科技有限公司研发中心」填进租户名称。

`AuthService.assertTenantName` 原实现要求入参与 `sys_tenant.name` **逐字相等**，于是：

| 账号 | 密码 | 填「某某智能科技有限公司研发中心」 | 填「某某智能科技有限公司」 |
|---|---|---|---|
| `znkjyf_admin`（tenant 9 机构管理员） | `User@123` | **1004 租户名称与账号不匹配** | 0 成功 |

同一账号、同一密码，只因租户名填写口径不同而结果相反 —— 这正是「**很多**都登不上去」的来源：
**凡机构管理员按机构名称填，必失败**。

### 1.2 次因：单个账号的口令孤例（1001）

全库 125 个启用账号的口令分布：

| 口令 | 账号数 | 说明 |
|---|---|---|
| `User@123` | 123 | 租户侧统一口令 |
| `Admin@123` | 1 | 平台管理员 `admin` |
| `123456` | **1** | **`dsj_admin`（tenant 2 租户管理员，id=3）** |

`dsj_admin` 是唯一的租户侧例外。判定其为**遗留不一致而非有意设计**，依据三条独立证据：

1. 其余全部租户侧账号（含 tenant 3–9 的租户管理员与机构管理员）一律 `User@123`；
2. `scripts/verify_config_effect.py` 早已写死 `DEFAULT_PWD = "User@123"` 并调用 `login("dsj_admin")`
   —— 该脚本因这个孤例**一直是坏的**（`r.json()["data"]["accessToken"]` 抛 `KeyError`）；
3. `scripts/seed_worker_templates.py` 同样 `PWD = 'User@123'`，并把 `dsj_admin` 列在 `TENANT_ADMINS` 里。

即：仓库内已有两处代码**按 `User@123` 调用它**，说明约定本来就是 `User@123`。

## 2. 修复

### 2.1 后端：租户名多形态匹配（`AuthService`）

`assertTenantName` 改为调用 `tenantNameMatches`，接受四种形态（先归一化：去全部空白 + 转小写）：

1. 租户名称**全称**；
2. 租户**编码**（如 `MYQY-DEMO`，短、好敲）；
3. 该租户名下**任一机构名称**（用户视角里「机构」就是他所属的那个组织，最易填对）；
4. 上述任一名称与入参**互为包含**，且两侧长度均 ≥ 3（容忍「某某市某某区大数据管理局」写成「大数据管理局」）。

**安全边界不变**：`accepted` 集合只由「该账号自身所属租户」的名称 / 编码 / 机构名构成，
不存在跨租户误配的可能；跨租户填写仍返回 1004。校验顺序也不变 —— **密码错（1001）优先于租户名判定**，
避免通过错误码差异探测账号归属。

失败文案由「租户名称与账号不匹配」升级为回显所属租户名并列出可填项：

> 租户名称与账号不匹配。该账号属于租户「某某智能科技有限公司」，填该租户名称、租户编码或其下属机构名称均可

（密码已校验通过，向持证人回显其自身所属租户名不构成越权泄露，且「该填什么」正是原提示缺失的部分。）

### 2.2 数据：`V40__normalize_dsj_admin_password.sql`

把 `dsj_admin.password_hash` 归一化为 `User@123` 的 BCrypt 哈希（**取自本库中已用 `User@123` 的既有账号**，
不引入明文）。**追加迁移而不修改 V24** —— 已应用迁移的 checksum 不可变。

影响：仅 1 行 `sys_user.password_hash`；昵称 / 租户 / 角色均不动。平台账号 `admin`（`Admin@123`）不动。

### 2.3 前端：`LoginView.vue`

- 字段标签「租户名称」→「**租户 / 机构名称**」；
- placeholder 与 tip 说明**租户全称 / 租户编码 / 机构名称三种填法均可**、可省略「某某市某某区」等前缀；
- 演示账号提示同步更新。

### 2.4 测试基线同步

- `e2e_full_system.py`（8 处 `('dsj_admin', '123456')`）、`e2e_v32_org_scope.py` → `User@123`。

## 3. 回归中暴露并修掉的缺陷

### 3.1 产品缺陷：重建同名账号撞唯一键 → 500

`verify_v39_provisioner.py` 报：`POST /api/v1/tenant/institutions` →
`DuplicateKeyException: Duplicate entry 'v39probe_admin' for key 'sys_user.username'`。

根因：`sys_user.username` 上的唯一键**覆盖已软删行**，而 `AccountProvisioner.resolveOrCreate`
只查 `deleted_at IS NULL`，查不到便直接 INSERT → 撞唯一键。这**不是单纯的数据漂移**：
只要「机构注销 → 再用同名管理员重建机构」就会 500，是真代码路径上的缺陷。

修复：新增 `OrgStatMapper.selectDeletedUserByUsername` + `reviveUser`，`resolveOrCreate` 在插入前
先查同名软删行，命中则**复活**（清 `deleted_at` + 复位归属 / 昵称 / 联系方式 / 演示口令 / 启用态）并返回。

实测：`verify_v39_provisioner` **连跑两次 11/11**，新建机构返回 `adminUserId=3156`（即被复活的旧行 id），
证明走的是复活分支而非插入。

数据侧另补回 tenant 9 缺失的 `RESOURCE_OPEN` 租户级默认流（上一次被中断的探针删掉后未补回）——
补回内容与 `ApprovalFlowProvisioner` 的播种定义逐字一致。

### 3.2 脚本缺陷：占位符选择器与未定义变量

- `repro_logout_401.py` 使用了未定义的 `TENANT` → `NameError`，此前根本跑不起来。补 `TENANT = "默认租户"`。
- 登录页文案改动打挂两处 **placeholder 选择器**（`input[placeholder='某某智能科技有限公司']`）：
  `e2e_admin_personnel_scope.py` 4 处、`repro_logout_401.py` 1 处 → 统一改用稳定选择器
  `input[autocomplete="organization"]`。

**纪律**：E2E 选择器不要绑 placeholder 等展示文案，应绑 `autocomplete` / `type` 等语义稳定属性。

## 5. 影响面与既有约定

- **口令约定**：租户侧全部 `User@123`（V40 起 `dsj_admin` 亦同），平台 `admin/Admin@123`。
  `docs/14-入驻租户账号清单.md` 的「统一密码 User@123」表述**现已无条件成立**。
- 引用 `dsj_admin` 口令的脚本已全部对齐；任何把 `123456` 当作 `dsj_admin` 口令的脚本 / 文档均已失效，需改 `User@123`。
- 登录表单稳定选择器：`input[autocomplete="organization"]`（租户名）/ `input[autocomplete="username"]` / `input[autocomplete="current-password"]`。
