## 一、功能修复与完善

### 1. 管理端「机构」「入驻进度」显示无数据

**现象**：管理端「机构管理」与「入驻进度」页面空白，而「组织与员工」「数字员工」正常。

**根因（不是权限问题，是数据作用域问题）**
`/api/v1/tenant/*` 下所有接口（institutions / org-quotas / grants / cost-rules / onboarding / overview）
都以 **调用者自身的 `tenantId`** 作为过滤条件，且写法为 `u.getTenantId() == null ? 0L : u.getTenantId()`。
系统管理员的 `tenant_id = 0`，于是永远查 `tenant_id = 0` 这个"默认租户"——
而业务数据都在 2~7 号租户下，自然一条也查不到。
"组织""员工"能显示，是因为它们走的是 `/api/v1/org/*`（V32 已做过作用域改造）。

**改动点**
| 文件 | 改动 |
|---|---|
| `aioa-org/.../support/OrgGuard.java` | 新增 `resolveScopeTenant()`（租户管理员硬绑本租户、平台管理员按 `?tenantId` 或默认租户）、`selectableTenants()`、`defaultTenantId()`（取机构数最多的租户，避开 id=1 的 0 机构默认租户）、`resolveRequestTenant()` |
| `aioa-org/.../controller/TenantAdminController.java` | `tenantId(u)` 改走 `guard.resolveRequestTenant(u)`；新增 `GET /api/v1/tenant/scope` 返回可切换租户清单 |
| `aioa-org/.../controller/OnboardingController.java` | 4 处 `tenantId` 解析统一改走 `guard.resolveRequestTenant(u)` |
| `web/apps/shell/src/api/tenantScope.ts`（新增） | 全局租户作用域状态；拦截器自动给 `/tenant/` 前缀请求带上 `?tenantId=` |
| `web/apps/shell/src/layouts/MainLayout.vue` | 头部新增租户切换器（仅平台管理员可见）；切换后以 `path@tenantId` 作为 key 强制重挂载路由页 |

**顺带修复**：入驻进度页面此前**连真实租户也查不到**——`OnboardingController` 有同一处 `tenantId=0` 写法，
这也是同一个根因，一并修掉。

**验证**：平台管理员 `/tenant/institutions` 由 `n=0` → `n=5`（默认租户）；租户管理员 `jyj_admin`
不带参数得本租户 3 家机构、带 `?tenantId=2` 返回 404（跨租户被正确拦截）。

### 2. 租户管理员（企业管理员）无法自行创建数字人与专家

**根因**：`AdminWorkerController` 与 `ExpertConfigController` 各写了一套"仅 ADMIN / TENANT_ADMIN"的判定，
与 `PermissionCatalog` 的权限码体系（`worker:create` / `worker:manage`）不一致——
企业管理员（`ROLE_ORG_ADMIN`）在权限目录里有创建权，在管理端却被 403。

**改动点**
- `PermissionCatalog` 新增权限码 `expert:manage`（角色：ADMIN / TENANT_ADMIN / ORG_ADMIN）。
- `AdminWorkerController`：`requireAdmin()` → `requireManager(permission, action)`，按权限码判定；
  新增机构/部门维度的 `listScoped()` / `requireOwned()` / `applyScopeOnCreate()`（企业管理员创建的归属本机构；
  部门负责人创建的强制锁定 `DEPT` + 本部门）。
- `ExpertConfigController`：`isAdmin` → `PermissionCatalog.holds(user, EXPERT_MANAGE)`。
- 前端 `constants/permissions.ts`（新增）+ `router/index.ts` + `MainLayout.vue`：
  「数字员工」「专家配置」菜单与路由改为按角色集合判定，与后端权限码一一对应。

> 设计要点：前端菜单、路由层级、后端权限点三处必须同源。历史上正是三处各写一套，
> 才出现"菜单能进但接口 403""接口放开了但菜单藏起来"两类互为镜像的缺陷。

### 3. 开放普通用户端数字员工的配置修改能力

**改动点**
- `worker:create` 权限下放至**全体登录用户**（依据见下）；新增 `worker:edit:self`（创建者可改自己的）。
- `visible_scope` 新增取值 `SELF`：**非管理者**创建的数字员工一律强制锁定为 `SELF`，
  在源头就不接收前端传入的 scope —— 即使改包塞 `visibleScope=TENANT` 也无法把个人助理提升为全员可见。
- `WorkerController`：`update` / `toggle` 改走 `requireManageOrOwner()`（管理者改全部、创建者改自己）；
  `list()` 过滤 `SELF` 他人数据；`requireOwned()` 增加"创建者恒可访问"优先分支。
- `WorkerView` 新增 `createdBy` / `mine` / `editable` / `auditStatus` 字段，前端据此渲染入口。
- H5 `renderAgents()`：由"整页 canManage"改为**逐卡 `canEdit`**；自建卡片标注「仅我可见」徽标。

**为什么放开创建权而不是"只放开修改"**：数字员工本质是"个人 AI 助理"，人人都找管理员代建既不现实、
也放大审批负担。真正的风险点不是"能不能建"，而是"建出来谁能看见"——因此用可见范围兜底，
而不是剥夺创建权。**删除仍只认管理权限**（`worker:manage`），避免"能建就能删"把治理权彻底下放。

**验证**：`zhangsan`（ROLE_USER）自建成功，`visibleScope=SELF`；同伴账号看不到该助理；
本人可改可启停；改他人创建的返回 403；删除返回 403。

### 测试中发现并修复的两个真实缺陷

#### 缺陷 1：任意不存在的接口路径返回 500，掩盖"接口不存在"

- **现象**：访问 `/api/v1/workflow/leave/types`（实际路径为 `/api/v1/leave/types`）返回 HTTP 500「服务内部错误」。
- **根因**：Spring Boot 3.2 起，未匹配的请求在静态资源处理阶段抛 `NoResourceFoundException`，
  它落到 `GlobalExceptionHandler` 的 `@ExceptionHandler(Exception.class)` 兜底，被包装成 500。
- **危害**：拼错路径会被误判成"后端崩了"，排查方向完全跑偏。
- **修复**：`GlobalExceptionHandler` 补 `NoResourceFoundException` 显式处理 → 404，并给出
  `接口不存在：<path>` 提示。
- **验证**：同一路径现返回 `http=404 {"code":404,"message":"接口不存在：/api/v1/workflow/leave/types"}`。

#### 缺陷 2：「租户管理员创建内容需上一级审核」此前完全没有实现

- **现象**：租户管理员创建数字员工/专家后**立即生效**，平台管理员无任何待办，也不存在审核入口。
- **修复（V34）**：
  - `agent_worker` / `ai_expert` 增加 `audit_status` / `audit_note` / `reviewed_by` / `reviewed_at`；
  - 存量数据一律置 `APPROVED`（新约束不应让历史数据瞬间变成"未过审"）；
  - 新增 `ContentReviewService`：开关（`sys_config.approval.tenant.content`，**默认开启**）× 角色
    （仅"租户管理员且非平台管理员"需送审）两层判定；
  - 新增审核台：`GET /api/v1/admin/content-reviews?status=`、`POST /api/v1/admin/content-reviews/{type}/{id}/review`
    （**驳回强制填意见**，意见回显给创建者）；
  - 管理端新增「内容审核」菜单与页面（仅平台管理员可见，路由守卫同步）；
  - H5 对待审内容显示「待上级审核」/「已驳回 + 驳回理由」徽标。
- **关键设计取舍**：
  - 审核态用**独立列**而非复用运行态 `status`——后者是"配好了没有"，前者是"让不让它生效"，二者正交；
    混用会让调度器把待审内容当故障处理。
  - **待审内容对普通成员不可见、不参与调度**，但创建者本人与管理员始终可见——
    否则会出现"提交了却消失"的困惑。
  - 「从模板创建」同口径补上审核态，避免它成为绕开审核的**旁路**。
- **验证**：见 E 组 6 项全部通过；审核台页面无头渲染 8/8 通过。
