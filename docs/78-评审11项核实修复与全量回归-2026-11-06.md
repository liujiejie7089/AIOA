## 2. 逐项核实与修复

### A1［高］MCP 工具失败仍被报成成功

**判断依据（取证）**

1. `client.py` 构造 `MultiServerMCPClient({...})` 时**没有** `handle_tool_errors` 参数 ⇒ 取库默认 `True`。
2. langchain-mcp-adapters 0.3.2 的语义：`handle_tool_errors=True` 时把 `CallToolResult(isError=True)`
   **包成 `ToolMessage(status="error")` 正常返回**，不抛异常；因此原代码走到 `return ok=True`。
3. 原代码里的 `if c.get("isError")` 只在「返回 content blocks」这一形态下才可能命中，
   而该形态在本路径上拿不到 ⇒ 实际是兜底分支，不是唯一判据（清单说「纯死代码」略过头，方向对）。

**修改**（`agent/aios_ai/tools/client.py`）

- 构造时显式 `handle_tool_errors=False` ⇒ 工具级错误以 `ToolException` 形式抛出，由既有 `except` 捕获为 `ok=False`。
- `invoke()` 里补 `ToolMessage` 兜底：`getattr(resp, "status", None) == "error"` 直接判失败并回传 `content`。
- 保留 content blocks 分支（含 `isError` / `error:` 前缀）作为第三种形态的兜底。

**影响范围**：所有走 `mcp__` 前缀的工具调用（内置 QQ邮箱、企微 CLI、外部 MCP 服务器）。
行为变化只有一条：**原本被吞掉的失败现在会如实报错**。不改变成功路径的返回值形态。
`transport/session` 级失败原本就抛，不受影响。

**验证**：`agent/tests/test_mcp_tool_errors.py` 8 条（含 ToolException、ToolMessage(status=error)、
`error:` 前缀 block、显式 `isError`、纯字符串/文本块仍判成功、未知工具仍报错）。

### A2［中］syncTools 的逻辑删除恢复是空操作

**判断依据（取证）**

- `McpServerTool.deletedAt` 带 `@TableLogic`；`updateById` 走 NOT_NULL 字段策略 ⇒ `setDeletedAt(null)` 不进 UPDATE。
- 表上有 `uk_mcp_tool(server_id, name)` 唯一键，**不区分删除态** ⇒ 软删行仍占键。
- 因此真实后果是两层：① 恢复不了；② 后续按 `(server_id, tool_code)` 插入会 `DuplicateKeyException`
  —— 清单只写了 ①，实际 ② 更致命（一次探活抖动可能让整个 sync 整批回滚）。
- 补充：**用 `LambdaUpdateWrapper` 也修不好** —— `@TableLogic` 会给 select/update 自动追加
  `deleted_at IS NULL`，wrapper 照样够不到软删行。只能裸 SQL。

**修改**

- `McpServerToolMapper#restoreDeleted(serverId, name)`：裸 SQL
  `UPDATE mcp_server_tool SET deleted_at = NULL, updated_at = NOW(6) WHERE server_id=? AND name=? AND deleted_at IS NOT NULL`。
- `McpRegistryService#syncTools` 开头先逐工具复活，**再** selectList（顺序是判据：先查后复活等于没复活）；
  删掉原先无效的 `row.setDeletedAt(null)`。

**影响范围**：MCP 工具目录同步（trust / probe / 内置连接器自动信任）。
幂等（`deleted_at IS NOT NULL` 条件），对没有软删行的服务器只多 N 条空 UPDATE。
真实库实证：`wecom_cli` 从 5 个工具同步到 **25 个**（20 行 insert 未撞唯一键），随后 untrust 复原，工具目录保留 25 行。

**验证**：`McpRegistrySyncToolsTest` 4 条（复活早于 select 的 `InOrder`、复活后走 update 不走 insert、
新增行不带 deletedAt、消失的工具仍被软删）。

### A3［低］哨兵脚本在 GBK 控制台崩溃

**判断依据（取证）**

- `PYTHONIOENCODING=cp936 python -c "print('\u2705')"` 实测
  `UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'`；默认环境 `stdout.encoding = utf-8` 不崩。
- 实际受影响面比清单大：`scripts/*.py` 中含 emoji 的有 **97 个**（243 个 py 文件的 40%），
  原本只有 2 个有防护。
- `scripts/sitecustomize.py` **不会被自动加载**（Python 只从 `sys.path` 找 sitecustomize，脚本目录不自动进 sys.path）⇒
  必须逐文件加，或者靠统一 launcher（本项目没有）。

**修改**：批量在 243 个脚本的 `docstring` / `from __future__` **之后**插入幂等防护

```python
try:  # A3：GBK 控制台打印 ✅ 会 UnicodeEncodeError；统一按 utf-8 输出（Windows 控制台/伪终端都正确）
    sys.stdout.reconfigure(encoding="utf-8"); sys.stderr.reconfigure(encoding="utf-8")
except Exception:
    pass
```

用 `ast` 定位插入点（不能插在 `from __future__` 之前）、插入后再 `ast.parse` 复核，
插入后 `compileall` 全量编译 **ok=True**。

**影响范围**：仅输出编码。`reconfigure(encoding="utf-8")` 在 Windows 控制台走 `_WindowsConsoleIO`（UTF-16 API），
中文与 emoji 都正确；在 git-bash/管道下按 utf-8 输出。**不改变任何断言与退出码**。

**验证**：`PYTHONIOENCODING=cp936` 下实测 `✅ ❌ ⚠ 中文正常`，退出码 0。

### B1［中］MAX_SCAN_ROWS 守卫对「带过滤」查询失效

**判断依据（取证）**：守卫 `if (idx + 1 > MAX_SCAN_ROWS)` 在过滤 `continue` **之前**，
但 `idx++` 在 `continue` **之后** ⇒ `idx` 计的是「命中行数」。过滤条件命中率低时，扫描 20 万行 `idx` 也可能只有个位数。

**修改**：拆两个计数器 —— `idx` 只做分页序号（命中行），`scanned` 做守卫（物理行）。
守卫阈值提为实例字段 `scanRowGuard`，配 package-private `scanRowGuardForTest(int)`（200 000 行造不出来，只能调小测）。

**影响范围**：只影响超大表的拦截时机。正常表格（几千行）行为完全不变。

**验证**：`KbTableQueryPagingTest#scanGuardCountsScannedRowsNotHits` —— 62 行表 + 守卫 10 + 只命中 1 行的过滤条件，
必须被拦下（老实现在这里返回 ok）。

### B2［中］totalRows 跨 sheet 求和与 sheet 选择语义矛盾

**判断依据（取证）**：`total += s.table().rows().size()` 把**所有** sheet 行数累加后放进 `totalRows`，
而 `matchedRows` 只算选中那张表 ⇒ 成绩单场景下 `sheet=成绩明细, matchedRows=62, totalRows=76`，
模型会据此判断「还有 14 行没取」，正是 docs/76 要消灭的「数字对不上」。

**修改**：`totalRows` 改为**所选表**的物理行数；全资料各表行数仍逐表给在 `docs[]` 里（信息不丢）。
同步把 `KbTableQueryPagingTest` 的断言从 `ROWS + 3` 改成 `ROWS`，并**新增**断言
「`docs` 里仍能看到成绩汇总 3 行」—— 按纪律（不为转绿放宽断言），这里是把断言改得更严，同时补一条防丢失的断言。

**影响范围**：`kb_table_query` 工具回的 `totalRows` 字段语义收窄。唯一消费方是测试断言与模型提示词；
`docs[]` / `matchedRows` / `hasMore` / `nextOffset` 语义不变。

**验证**：`KbTableQueryPagingTest` 11/11（含多表默认选最大表、切 sheet、按汇总表列过滤选中汇总表）。

### B3［低］注释与实现不符（统计摘要「不占配额」）

**判断依据（取证）**：注释写「不占普通配额」，但主循环 `if (hits.size() >= max) break;` 把已注入的摘要一起计入
`max`；摘要最多 `MAX_STATS_HITS = 2` 条，因此实际只给数据行留 `max-2`。

**修改**：只改注释（如实写明「占 max、最多 2 条、不做额外追加是为了守住 token 预算」）。
**不改实现的理由**：`hits` 就是回给模型的最终列表，追加会让总量突破 `max`，等于悄悄放大每次问答的上下文成本。

**影响范围**：无行为变化。

### B4［低］`_ASK_PREFIX` 交替顺序导致只剥短词

**判断依据（取证）**：`(?:请|麻烦|帮我|帮忙|给我|替我|替我看看|...)+` —— Python 交替最左优先，
`替我` 先于 `替我看看`、`麻烦` 先于 `麻烦你`，且 `+` 只会拿**同一批分支**反复匹配，补不回被漏掉的长词。
实测 `替我看看四川省非遗项目有多少个` 清洗后是 `看看四川省非遗项目`，`麻烦你统计一下…` 清洗后以「你」开头。

**修改**：长词前置，并补 `请帮我 / 麻烦你 / 替我看看 / 替我瞧瞧 / 帮我看看 / 帮我看下 / 告诉我`、`看看 / 瞧瞧 / 查一下 / 看一下`。

**影响范围**：只影响检索变体 2（清洗句）。变体 1（原句）与引号变体不变；变体上限仍 3 条。

**验证**：`test_kb_query_variants.py` 9/9，新增两条专测（「看看」被一起剥掉且以「四川省」开头；
「麻烦你…」不留下孤立的「你」）。

### B5［低］KeywordScorer.occurrences 注释不成立

**判断依据（取证）**：实现每命中一次就把游标推到匹配串之后 ⇒ 非重叠计数。`"aa"` 在 `"aaa"` 里得 1，

### B6［低］GradeSheetExtractor.summary 两处边界

**判断依据（取证）**

1. `off < -labels.size()` —— `off = values.size() - labels.size()`，且此时已保证 `values` 非空 ⇒
   `off ≥ 1 - labels.size() > -labels.size()`，**恒假**，是死检查。
2. `off > 0`（数值多于标签）时 `vi = j + off` 会跳过前 `off` 个数值 —— 同一套右对齐规则，若多余值其实在末尾则整体偏一位。

**修改**：删死检查；注释写明「以右端为基准」的两面（数值少 ⇒ 正确右对齐，避免「毕业设计(论文)题目」错配 80.26；
数值多 ⇒ 会跳过前 off 个，属已知风险），并说明**不猜**的理由（没有可靠信号判断多余值在头还是在尾）。

**影响范围**：无行为变化（死检查删掉后逻辑等价）。风险以注释形式登记，供后续有真实样本时再定。

**验证**：`GradeSheetExtractorTest` 6/6；成绩单全链路 `_verify_kb_grade_sheet.py` 31/31。

### B7［低］AsrController.callAgent 非 JSON 响应会 500

**判断依据（取证）**：`objectMapper.readTree(raw)` 在 `resp.statusCode() != 200` 判断**之前**且无 try
⇒ agent 被网关/反代挡回 HTML 时抛 `JsonParseException`，用户拿 500，与类注释声明的「失败一律 503」相反。

**修改**：抽出 `parseJsonOrNull(raw, status)`（内部 try + WARN 日志，只记状态码与长度，不记 body 内容），
调用方按三种情况分流：

- 非 200 且能解析 ⇒ 透传上游状态码 + `message`（保留原有语义，不吃掉错误信息）；
- 非 200 且不能解析 ⇒ `BizException(503, "语音识别服务不可用，请稍后重试")`；
- 200 但不能解析 ⇒ 同样 503（避免下游 `root.has()` NPE）。

**影响范围**：`/api/v1/asr/transcribe` 与 `/api/v1/asr/status` 的失败表达。成功路径不变。

**验证**：`AsrControllerTest` 5 条。用 JDK 自带 `HttpServer` 起假 agent 分别回 HTML 502 / 纯文本 200 / 空 body /
JSON 502 / 正常 JSON。**注意口径**：`BizException(503)` 会被 `ErrorCode.ofCode` 归一成
`MODEL_UPSTREAM_ERROR`（code=502，HTTP 层仍是 200 + 信封），这是错误码体系的既有约定，
所以断言写成 `ErrorCode.MODEL_UPSTREAM_ERROR.code()` 而不是字面 503 —— 关键判据是「抛业务异常 + 人话，而不是解析异常」。

**① `_verify_project_isolation` G4 失败 —— 套件指向已废弃的源文件（桶 C）**

**② `e2e_worker_schedule_exec` 1 项失败 —— 前置探针自身失效**

  原因是 agent 的 `/internal/v1/*` 已强制服务令牌，探针没带票。

- **建议**：探针补服务令牌。本次**不**改它 —— 这条探针的设计初衷就是「宁可报红」，放宽等于自毁防线。
