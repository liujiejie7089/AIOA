# 69 · 动态交互控件协议（菜单 / 候选框 / 文本框）

> 2026-11-02。承接 `docs/68`（模糊实体澄清卡）：那张卡只有「单选 + 一段补充文字」，
> 这一轮把它扩成**按语义动态生成控件**的通用协议 —— 一条消息里缺几样就问几样，
> 控件之间可以有依赖，用户在一次交互里交齐，交完流程自己往下走。
>
> 一句话分工：**语义判断交给模型（决定问什么），合法性与状态交给代码（保证问得对）**。

---

## 1. 触发条件与判断依据

要回答的是两个不同的问题，别混在一起：

| 问题 | 由谁决定 | 判断依据 |
|---|---|---|
| **要不要弹卡？** | 代码（确定性闸）+ 模型 | ① 确实缺完成请求所必需的参数，或意图模糊到无法确定动作；② 代码侧另有两条硬闸（见下） |
| **弹哪些控件？** | 模型（按语义） | 用户这句话里缺几样、每样是哪类信息（§1.2 判据表） |

### 1.1 「要不要弹」的五道闸

1. **模型自判**：`ask_user` 的 description 明写「仅在确实无法继续时使用；不要追问次要细节，
   更不要凭猜测编造默认值继续执行」。这是软闸。
2. **确定性短路**（`entity_clarify.can_short_circuit`）：候选已就绪 + 用户没点名 + 非群发
   ⇒ **第一轮不调模型**，直接合成一张卡。软闸挡不住「模型把名单写进正文」，
   所以这一条是硬的（见 docs/68 §7）。
3. **泛动作确定性闸**（`entity_clarify.needs_action_clarify`）：**人称 + 泛动作
   （说个事 / 联系 / 沟通 / 商量 / 跟进…）+ 没说具体渠道** ⇒ 直接合成字段卡（§1.5）。
   加这条的原因是模型这条路**实测没走通**（§1.3）。
4. **`clarifications` 非空则不再合成**：续跑后不许再弹同一张卡，否则无限弹。
5. **HITL 关闭（`agent_hitl=False`）时整条链不生效**：没有 checkpointer，`interrupt()`
   会直接抛错。

### 1.2 「弹哪些控件」的判据表

模型看到的是这张表（写在工具 description 里，它会照着选）：

| 用户这句话缺的东西 | 语义线索 | 控件 | `type` |
|---|---|---|---|
| 有限、互斥的几项里挑一个 | 动作类型、优先级、时间范围 | 菜单（按钮组） | `select` |
| 候选很多 / 要按关键词找 | 人名、部门、单据号、客户 | 候选框（输入即过滤） | `select` + `searchable: true` |
| 可以选多个 | 参与人、标签、通知方式 | 多选 | `multi` |
| 一句话 | 姓名、标题、编号 | 单行文本 | `text` |
| 一段话 | 消息内容、事由、说明 | 多行文本 | `textarea` |
| 时间 | 日期、截止时间 | 日期 / 日期时间 | `date` / `datetime` |
| 数量 | 金额、人数、时长 | 数字 | `number` |

**三条「不要」**（同样是判据的一部分）：

- 能枚举的**不要**给人一个空文本框（用户得猜格式）；
- 时间**不要**让人手打「明天下午三点」这种自由文本（没法校验、没法直接用）；
- 只有一样东西缺、且选完就够时，**不要**用 `fields`，用更轻的 `options`（§1.4）。

### 1.3 实测：模型这条路**没走通**，所以又加了一道闸

工具 schema 已经把 `fields` 摆在模型面前（`capabilities/providers.py` 每次都注入），
描述里也写了「缺几样就问几样、用什么控件」。真机（DeepSeek，zhangsan / 企微）实测
「帮我和同事说个事」：

```
frames: run.started → message.delta ×3 → message.completed → run.completed
正文: 「请告诉我您要传达的具体内容，以及您想发给哪位同事。为了确保信息准确传达，我需要知道同事的姓名或工号。」
```

**它一次工具都没调**，写了一段散文反问 —— 与 docs/68 §7.5 是同一类失效
（提示词写「先查再问」⇒ 它直接反问；写「用 fields」⇒ 它写散文）。
用户要的「一次交互交齐」在这条路上等于零。

于是补第三道闸：`needs_action_clarify(text)` = 人称 + 泛动作 + **没有**具体渠道词。
命中后 `build_action_fields_call()` 直接合成字段卡，**不调模型**。
同一句话修复后：

```
frames: run.started → need_clarification      ← 零正文、零 tool.call
question: 要我帮你做哪件事、对谁做？
· [select]  action  想做什么（发消息 / 约会议 / 建待办 / 其它）
· [select]  person  对象（真实通讯录 3 人，可输入过滤）
· [textarea] content 要发送的内容        ← 依赖 action=message
· [datetime] when    会议时间            ← 依赖 action=meeting
· [text]     title   待办标题            ← 依赖 action=todo
· [textarea] other   具体要做什么        ← 依赖 action=other（逃生通道）
```

判据写得很窄（`_CONCRETE_ACTION_RE` 一命中就退出），所以「帮我给同事发条消息」仍然走
原来的单选卡（选人 + needs_text），零回归 —— 有 E12 用例与真机回归双盯。

**结论（值得记住的一条）**：模型能给的是**语义假设**，不能给**交互保证**。
要保证的交互必须有代码闸；模型只负责它真正擅长的部分 —— 这张卡里哪些字段、取什么候选，
代码猜不出来，但"什么时候必须问"可以。

### 1.4 为什么「语义判断」交给模型，而不是代码

代码能做的是**模式匹配**（`content_hint`：「发消息/邮件/日程/待办」缺内容），
它只覆盖得了已知动作。而「帮我和同事说一下」这种话缺的是**动作本身**，
代码猜不出来 —— 硬编码一张动作清单，是在用代码替用户想象需求。

所以边界划在这里：

```
模型：这句话缺什么 → 生成 fields（含类型、候选、依赖）
代码：schema 是否合法 → 剪枝叶 / 降级 → 渲染 → 求值 → 校验 → 提交
```

代码**不判断语义，但绝不信任模型的 schema**（§3.4 的收敛规则）。

### 1.5 三代卡型的优先级

前端按这个顺序判，只走第一条命中的分支：

```
p.fields 非空                      ⇒ 字段卡（本节协议）
else p.options / p.text_input      ⇒ 单选卡（docs/68）
else                               ⇒ 自由输入 .clar-free
```

服务端已经保证「有 fields 就没有 options / text_input」（`build_clarification` 直接丢弃），
所以不存在「一张卡两套控件、两套必填规则」的歧义。

## 2. 支持的输入类型

`FIELD_TYPES` 是**封闭枚举**（`ask_user.py`），前端同此一套，不认识的类型在服务端就降级了。

| `type` | 渲染成 | 值形状 | 适用 |
|---|---|---|---|
| `select` | `.clar-opts > .clar-opt`（按钮组，单选） | `string` | ≤10 个互斥候选 |
| `select` + `searchable` | `.clar-search` + `.clar-cands > .clar-cand` | `string` | 候选多（上限 50），要按关键词找 |
| `multi` | `.clar-opts.multi > .clar-opt.multi`（方形勾选标记） | `string[]` | 可多值 |
| `text` | `<input class="clar-inp" type="text">` | `string` | 姓名、标题 |
| `textarea` | `<textarea class="clar-text">` | `string` | 消息内容、说明 |
| `date` | `<input type="date">` | `"YYYY-MM-DD"` | 日期 |
| `datetime` | `<input type="datetime-local">` | `"YYYY-MM-DDTHH:mm"` | 日期时间 |
| `number` | `<input type="number" step="any">` | `string`（保留原始输入，校验时转数） | 金额、数量 |

字段级可选属性：`required` / `placeholder` / `hint` / `default` / `max_len` /
`min`·`max`（number 专用）/ `options` / `searchable` / `visible_when`。

## 3. 控件之间的依赖与状态变化

### 3.1 依赖的声明

```json
{"id": "action", "label": "想做什么", "type": "select", "required": true,
 "options": [{"value":"message","label":"发消息"},
             {"value":"meeting","label":"约会议"},
             {"value":"todo","label":"建待办"}]}

{"id": "content", "label": "消息内容", "type": "textarea", "required": true,
 "visible_when": {"field": "action", "op": "eq", "value": "message"}}

{"id": "when", "label": "会议时间", "type": "datetime", "required": true,
 "visible_when": {"field": "action", "op": "eq", "value": "meeting"}}
```

`op` 只有五种（多一个都不认）：

| op | 含义 | 例子 |
|---|---|---|
| `eq`（缺省） | 等于 | `action == "meeting"` |
| `neq` | 不等于 | `priority != "low"` |
| `in` | 属于集合 | `action in ["message","mail"]` |
| `empty` | 该字段为空 | 选了「其它」才出现的自定义说明 |
| `truthy` | 该字段有值 | 填了收件人才出现的「抄送」 |

### 3.2 两条状态规则

1. **隐藏 ⇒ 清空 + 不校验 + 不提交**。
   「选消息填了内容 → 改选会议」时，内容框收起并**清空**：
   既不能把上一支的内容带进下一次提交，也不能让它拦住本次提交（用户看不见的问题不算问题）。
2. **显示 ⇒ 应用 `default`（只一次）**。
   默认值不能覆盖用户已经填过的值 —— 用户切走再切回，填的东西要还在。

### 3.3 求值顺序：迭代到不动点

「可见性由当前值决定，而当前值只统计**可见**字段」——这是个循环依赖。
所以求值**不是一遍过**，而是反复刷新直到不再变化：

```js
for(var pass = 0; pass <= fields.length + 1; pass++){
  var vals = values();          // 只统计可见字段
  ...翻转需要变的字段...
  if(!changed) break;           // 不动点
}
```

步数上限 = 字段数 + 2，足以覆盖任何**链形**依赖（a→b→c）。**环形**依赖不能靠迭代兜底，
必须在服务端剪掉（§3.4）。

### 3.4 坏 schema 的三道收敛（服务端 `_as_fields`）

模型给的 schema 不可信，一律先收敛再渲染：

| 异常 | 处理 | 为什么这么降级 |
|---|---|---|
| 未知 `type` | 降级 `text` | 宁可让人打字，也不要前端拿到未知 type 渲染成空白块 |
| `select`/`multi` 没有候选 | 降级 `text` | 没有选项的菜单是**死控件**，点不动也交不了 |
| `id` 重复 | 保留第一个 | 回填按 id 取值，重复必然互相覆盖 |
| 缺 `id` / `label` | 丢弃该字段 | 没法回填，用户也看不懂 |
| 字段 > 6 个 | 截断 | 再多就该拆成两问，而不是做成问卷 |
| 依赖指向不存在的字段 / 指向自己 | **剪掉条件，保留字段** | 条件坏了最坏是「多问一项」；按坏条件隐藏会导致「必填项看不到、提交又通不过」 |
| 依赖成环 | 剪掉闭环那条边 | 环会让可见性在「都不显示」和「都显示」之间来回跳 → 控件闪烁、确认按钮乱变 |
| `op` 不认识 | 按 `eq` | 少一个操作符不至于整卡作废 |
| `in` 的 value 不是数组 | 剪掉条件 | 不做「猜你意思」的比较 |

前端还有一层兜底：`type` 落到 `else` 分支时一律渲染成 `text`，永不白屏。

### 3.5 用户可见的状态变化

```
挂载          → 依赖字段全部隐藏；**不预先亮红**（没碰过的字段不报错）
选/填任一字段  → 重算全部可见性 → 隐藏的清空、显示的取默认值 → 逐字段校验 → 落款？
点「确认」     → 全部可见字段通过校验？ 否 ⇒ 点亮问题字段 + 焦点送到第一个错的，不提交
                                        是 ⇒ 冻结卡片 + 落款「已提交：…」+ resolve
```

**「确认」不置灰**（与单选卡不同）：多字段卡里按钮灰掉只会让用户对着表单猜漏了哪一项；
让它可点、点了就地指出问题，才是能自解释的交互。

## 4. 输入后如何流转到下一环节

```
用户点「确认」
  └─ mountClarFields.collect()
       {value, label, text, values}
         · values  —— 每个**可见**字段一项，键就是 schema 的 id
         · value/label —— 第一个「选了值」的选择型字段（兼容旧的单选语义）
         · text    —— 第一个非空的文本型字段（兼容旧的「补充内容」语义）
  └─ clarAnswerPayload(pick)  → {value, label, text, values?}   ← 两形态（send/oaSend）共用
  └─ POST /api/v1/runs/{id}/resume  {"answer": {...}}
  └─ Java RunController.resume **原样转发**给 agent /internal/v1/runs/{id}/resume
  └─ LangGraph interrupt() 返回这个对象
  └─ nodes.clarify：只对 clarify 链做 _clarify_answer 归一
       → tool 消息 {"ok":true,"data":{"answer":{value,label,text,values}},
                    "next":"信息已齐备，请直接执行…不要再重复确认"}
  └─ agent 下一轮拿到这条 tool 消息 ⇒ 执行原任务（调工具 / 出结果）
  └─ 若又暂停（还缺别的信息）⇒ H5 的 while(clar||form||cfm) 回到顶部再弹一张卡
```

**为什么 value/label/text 三件套还留着**：老客户端、老回放脚本、老断言都按这三个键读，
`values` 是**增量**。没有字段卡时载荷里不会出现 `values` 键 —— 形状逐字节不变。

**为什么 `values` 的键就是 id**：模型生成 schema 时已经知道语义（`action` / `when`），
tool 消息里用同样的键回填，它读起来零翻译成本（不用把 `wobVco…` 反推成「这是谁」）。

**转发的形状不用改 Java**：`resume` 的 body 一直是「透传一个 JSON」，对象/标量都能穿透
（docs/68 §8.3）。这一轮只在对象里多了一个 `values`。

## 5. 异常与无效输入的处理

### 5.1 客户端：能就地判断的，就地判断

| 情形 | 判定 | 用户可见 | 是否提交 |
|---|---|---|---|
| 必填为空 | `required && isEmpty` | 字段红框 + 「必填」 | 否（点确认也不交） |
| 超长 | `len > max_len` | 「最多 N 字（当前 M）」 | 否 |
| 非数字 | `Number(x)` 非有限 | 「请填数字」 | 否 |
| 越界 | `min` / `max` | 「不能小于 1 / 不能大于 1000」 | 否 |
| 日期格式 | 正则 `YYYY-MM-DD[THH:mm]` | 「请选择日期」 | 否 |
| 多选为空 | — | 只校验「必填」，不校验个数 | `[]` 或按必填拦 |

两条体验约束（都有断言盯着）：

- **不预先亮红**：红框与红字只在「碰过这个字段」之后出现 —— 一进卡片全是红框等于噪音，
  用户还没开始填就先被指责一遍；
- **点确认要说话**：校验不通过时**不提交**，但必须点亮所有问题字段并把焦点送到第一个错的，
  否则用户以为按钮坏了。

### 5.2 服务端：模型给的 schema 坏了也不崩

见 §3.4 的九条收敛。原则统一：**降级到「还能用」，而不是报错到「用不了」**。

### 5.3 用户放弃 / 停止生成

`cancelClarCard()` 把未决卡以 `null` 收掉 → `mountClarCard` resolve(null) →
`send()` 的 `if(!pick) break` 就地收口，不发 resume、不污染上下文。

### 5.4 回填形状异常

`_clarify_answer` 认四种形状（标量 / 三键对象 / 带 values 的对象 / 只剩 text 的对象），
所以老客户端、脚本回放、手工 curl 都不会把 answer 丢成空。

### 5.5 已知边界（这轮没做，写在这里而不是藏着）

1. **resume 失败时卡片已冻结**，用户不能原地重试，只能重新说一遍。
   要改需把 settle 的冻结时机挪到 resume 成功之后（涉及 `send()` 的收口流程），
   这轮没动 —— 现状至少不会「假装成功」。
2. **候选框是纯前端过滤**（候选已在卡里），不做远程搜索。候选 > 50 时只取前 50，
   需要「边输边查」得再引入一次工具调用，不在本轮范围。
3. **依赖只支持单层条件**（`visible_when` 一个条件），不支持 `and/or` 组合。
   实际场景里两个条件同时成立才算数的很少；真要支持，得把 `visible_when` 换成数组语义。
4. **`default` 只在字段首次显示时应用一次**，不跟随依赖变化重算（否则会覆盖用户输入）。

`_shots_clar_fields.py` 的关键判据（图为 `docs/assets/clar-fields/clar-fields-*.png`，
卡片由生产代码 `entity_clarify.build_action_fields_call` 生成，不是手写 JSON）：

- 初始：三个依赖字段全隐藏，**不预先亮红**
- 选「发消息」⇒ 只有「消息内容」展开，其余依赖字段仍隐藏
- 改选「约会议」⇒ 消息内容**收起且清空**，会议时间展开
- 候选框输入「刘」⇒ 8 个候选里只剩 1 个（就地过滤）
- 空表点确认 ⇒ **一次 resume 都没发**，必填字段亮红说明「必填」
- 一次提交的载荷（脚本直读浏览器发出的 POST body）：

```json
{"answer": {
  "value": "meeting", "label": "约会议", "text": "",
  "values": {"action": "meeting", "person": "wob1",
             "when": "2026-11-03T15:00"}
}}
```

- 隐藏字段（`content` / `title`）**没有**出现在 `values` 里 —— 这是「隐藏即不提交」的证据
- 落款逐字段列出：`已提交：想做什么：约会议；对象：刘洋；会议时间：2026-11-03T15:00`
- 提交后助手在同一气泡里继续说话（循环没断）
- 数字卡：`5000` ⇒ 「不能大于 1000」且不提交；改 `128` 后可提交

## 8. 一句话回顾

- **问什么**由语义决定（模型），**问得对不对**由协议决定（代码）；
- 依赖不是提示词里的约定，是 `visible_when` 这样的**可求值声明**；
- 隐藏即清空、不校验、不提交 —— 让「用户看不见的东西」永远不参与判断；
- 一次提交只发一次 resume，载荷带全 `values`，回填形状向后兼容；
- 无效输入一律**就地说明 + 不提交**，绝不静默吞掉。
