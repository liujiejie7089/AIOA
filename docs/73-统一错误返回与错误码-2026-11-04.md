# 统一错误返回与错误码（2026-11-04）

> 一句话目标：**任何一次失败，用户看到的都是「一句人话 + 一句建议 + 一个错误编号」，
> 而工程师在日志里能拿到完整的原始信息（含堆栈、上游原文、SQL）。**
>
> 起因是两次真实现场：`生成失败：{"code":"MODEL_UPSTREAM_ERROR","message":"…","detail":"status=404 {\"type\":\"error\"…"}`、
> `Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'`。
> 前者把上游 JSON 甩给了用户，后者把 Spring 内部类型名当成了「给用户看的解释」。

---

## 1. 错误分类（category）

分类是**稳定契约**：前端/网关按分类决定动作（重试 / 跳登录 / 提示联系管理员），
不需要枚举具体码。具体码（`errorCode`）允许随业务增加，分类不轻易变。

| category | 含义 | 前端典型动作 | 日志级别 |
|---|---|---|---|
| `VALIDATION` | 参数/表单不合法 | 标红字段、提示改哪里 | WARN（含原始 message） |
| `AUTHENTICATION` | 未登录 / 令牌失效 | 跳登录页、清本地令牌 | WARN |
| `PERMISSION` | 已登录但无权限 | 提示找管理员开通 | WARN |
| `NOT_FOUND` | 资源或接口不存在 | 提示刷新/核对地址 | WARN |
| `CONFLICT` | 状态冲突、重复提交、唯一键冲突 | 提示刷新后重试 | WARN |
| `RATE_LIMIT` | 触发限流/配额 | 提示等待或提额 | WARN |
| `UPSTREAM` | 外部依赖失败（模型、连接器、托管方） | 可重试；附「去哪检查配置」 | WARN/ERROR |
| `INTERNAL` | 服务内部错误 | **不解释细节**，只给错误编号 | ERROR（含堆栈） |

**归类原则**：错误的归属看「谁能让它不再发生」，不看它在哪一层抛出。
路径写错（`NoResourceFoundException`）归 `NOT_FOUND` 而不是 `INTERNAL` ——
否则排查方向会被带偏到「后端崩了」。

## 2. 统一返回字段

后端所有 HTTP 响应都走 `cn.aios.common.resp.ApiResponse`。

### 2.1 成功

```json
{ "code": 0, "message": "ok", "data": { }, "traceId": "1ffc126d99b14ac6" }
```

### 2.2 失败

```json
{
  "code": 403,
  "errorCode": "PERMISSION_DENIED",
  "category": "PERMISSION",
  "message": "当前账号没有这个操作的权限",
  "suggestion": "换用有权限的账号，或让管理员在「角色权限」里为你开通",
  "details": [ { "field": "apiKey", "message": "不能为空" } ],
  "traceId": "1ffc126d99b14ac6",
  "data": null
}
```

| 字段 | 何时出现 | 约定 |
|---|---|---|
| `code` | 总是 | 数字码，**向后兼容**（既有 400/401/403/404/405/406/500/501 不变；新增 409/422/429/502/504） |
| `message` | 总是 | 给人看的一句话；**不得**含类名、SQL、路径、堆栈、上游原文 |
| `errorCode` | 失败时 | UPPER_SNAKE 机器码。前端按它分支，**不匹配中文文案** |
| `category` | 失败时 | 见 §1 |
| `suggestion` | 失败时 | 可操作建议：去哪个页面、改哪个字段、等多久、找谁 |
| `details` | 仅校验类 | `[{field, message}]`，前端据此标红输入框 |
| `traceId` | 总是 | 错误编号；与日志同号，用户报障时凭它 `grep` |

成功响应**不输出** `errorCode/category/suggestion/details`（`@JsonInclude(NON_NULL)`），
旧解析代码完全不受影响。

## 3. 错误码表（`cn.aios.common.error.ErrorCode`）

| errorCode | code | category | HTTP | 默认文案（节选） |
|---|---|---|---|---|
| `VALIDATION_FAILED` | 400 | VALIDATION | **200** | 提交的内容有误，请按提示修改后重试 |
| `PARAM_INVALID` | 400 | VALIDATION | 400 | 请求参数不合法 |
| `PARAM_MISSING` | 400 | VALIDATION | 400 | 缺少必填参数 |
| `BODY_UNREADABLE` | 400 | VALIDATION | 400 | 请求内容不是合法的 JSON |
| `METHOD_NOT_ALLOWED` | 405 | VALIDATION | 405 | 该接口不支持这种请求方式 |
| `NOT_ACCEPTABLE` | 406 | VALIDATION | 406 | 该接口不提供你要求的响应格式 |
| `UNAUTHENTICATED` / `TOKEN_INVALID` | 401 | AUTHENTICATION | 401 | 登录状态已失效，请重新登录 |
| `PERMISSION_DENIED` | 403 | PERMISSION | 403 | 当前账号没有这个操作的权限 |
| `TENANT_FORBIDDEN` | 403 | PERMISSION | 403 | 该数据不属于你所在单位，无法访问 |
| `RESOURCE_NOT_FOUND` | 404 | NOT_FOUND | 404 | 要找的内容不存在或已被删除 |
| `API_NOT_FOUND` | 404 | NOT_FOUND | 404 | 接口地址不存在 |
| `STATE_CONFLICT` | 409 | CONFLICT | 409 | 数据状态已变化，本次操作没有生效 |
| `RATE_LIMITED` | 429 | RATE_LIMIT | 429 | 操作太频繁，已被限流 |
| `MODEL_UPSTREAM_ERROR` | 502 | UPSTREAM | 200 | 模型服务本次没有返回结果 |
| `MODEL_NOT_FOUND` | 502 | UPSTREAM | 200 | 配置的模型已下线或不存在 |
| `MODEL_AUTH_FAILED` | 502 | UPSTREAM | 200 | 模型密钥无效或没有调用权限 |
| `MODEL_RATE_LIMITED` | 502 | UPSTREAM | 200 | 模型调用过于频繁 |
| `MODEL_TIMEOUT` | 502 | UPSTREAM | 200 | 模型响应超时 |
| `CONNECTOR_ERROR` | 502 | UPSTREAM | 200 | 连接的外部应用调用失败 |
| `INTERNAL_ERROR` | 500 | INTERNAL | 500 | 服务内部出错了，本次操作没有完成 |
| `NOT_IMPLEMENTED` | 501 | INTERNAL | 200 | 该功能尚未开放 |

### 3.1 为什么有的失败是 HTTP 200

沿用既有铁律（`iron-rules #29`）：**表单/业务校验失败 = HTTP 200 + `code=400`**。
H5 与部分 e2e 只看 `body.code` 判成败，改成真实 4xx 会让既有链路误判为「网络故障」。
鉴权/权限/资源不存在则用真实 4xx（浏览器与网关需要它）。

模型类错误（`MODEL_*`）也走 200：一次对话失败不该让浏览器把整页判成 HTTP 错误。

### 3.2 保留的特殊契约（不许「统一」掉）

| 契约 | 位置 | 为什么不能动 |
|---|---|---|
| `code=40090` + `data.rule_violation` | `FormRuleExceptionHandler` | H5 靠它渲染「规则未通过 + 可选项」卡片；本次只在同一响应里**追加** `errorCode/category/suggestion`，码值不变 |
| `code=424 / 429 / 503` | `GiteeExceptionAdvice` | 「托管方授权失效」必须与「平台登录失效」区分，否则前端会误判为掉线并强制登出 |
| `event: error` 走 HTTP 200（SSE） | `GlobalExceptionHandler#respond` | EventSource 对非 2xx 只报笼统连接失败且不断重连 |

## 4. 各层职责

### 4.1 Java 后端

| 位置 | 职责 |
|---|---|
| `common/error/ErrorCode` | 唯一码表：码 → HTTP → 文案 → 建议 |
| `common/error/ErrorText` | 清洗（去类名/包名/栈/SQL/路径）+ 脱敏（密钥）+ 字段消息中文化 |
| `common/resp/ApiResponse` | 统一信封；`fail(ErrorCode, …)` 系列工厂 |
| `common/exception/BizException` | 抛错入口：`badRequest/forbidden/notFound/conflict/upstream/of(...)`，`.withSuggestion(...)` |
| `common/web/GlobalExceptionHandler` | **唯一出口**：归类 → 清洗 → 留痕 → 按 SSE/JSON 分别回写 |
| `security/SecurityConfig` | 401/403 的 entryPoint / accessDeniedHandler，同一套 `ErrorCode` |
| 各业务 Controller/Service | **只抛 `BizException` + 一句人话**，禁止 `throw new RuntimeException("SQL 报错…")` |

抛错写法（推荐）：

```java
throw BizException.badRequest("模型名不能为空");

throw BizException.of(ErrorCode.MODEL_NOT_FOUND, "模型「" + name + "」已下线")
        .withSuggestion("在「模型配置」里改用当前可用的模型名（可用其 /models 列表确认）");
```

### 4.2 agent（Python）

- `aios_ai/errors.py`：与 Java **同一套码与字段**（`code/category/message/suggestion/retryable/errorId`）。
- `llm/upstream.py#UpstreamError.payload`：把 HTTP 状态映射到 `MODEL_AUTH_FAILED / MODEL_RATE_LIMITED /
  MODEL_TIMEOUT / MODEL_NOT_FOUND / MODEL_UPSTREAM_ERROR`，并从上游 body 里抽 `request_id` 作为 `errorId`。
- `graph/facade.py`、`app/main.py`：SSE `event: error` 帧与 HTTP 异常处理器**一律**用 `errors.*` 构造载荷，
  **不再外发** `str(exc)` / `exc.errors()` / 上游原始 JSON。

### 4.3 前端

| 端 | 入口 | 行为 |
|---|---|---|
| 管理端 | `api/index.ts`（拦截器 + `unwrap`） → `ApiError`；`utils/error.ts#describeError` | `message` 已并入「（建议：…）」；`describeError` 用于需要带错误编号的场合 |
| 用户端 H5 | `req()` 透传信封字段；`errText()/sseError()`（脚本块 1，挂 `window.AIOS_ERR`） | SSE 错误帧解析成对象后拼文案，**不再**把 JSON 字符串塞进 `Error.message` |

> ⚠️ H5 的两个 `<script>` 各自作用域，`errText` 实现只在块 1，块 2（OA 形态）在 IIFE 内**取引用**；
> 别在块 2 再复制一份实现，也别把 `var` 插到 `'use strict'` 前面（会静默关掉严格模式）。

## 5. 日志约定

| 场景 | 级别 | 记录内容 |
|---|---|---|
| 业务异常（4xx） | WARN | `[traceId] METHOD URI -> ERROR_CODE message \| 原始: <脱敏后的原始 message>`，有 `cause` 再补一条 |
| 校验失败 | WARN | 字段列表 + 原始 `BindException` 消息 |
| 数据冲突 | WARN | 根因 message（脱敏，含表名/约束名 —— **只进日志**） |
| 5xx 兜底 | ERROR | 完整堆栈（`log.error(..., e)`） |
| 客户端断开 | DEBUG | 不算故障（499），不写堆栈，避免刷屏 |
| 上游模型失败 | WARN | `status / model / body（前 500 字符）` |
| agent 未捕获异常 | ERROR | `logger.exception`（完整 traceback） |

**脱敏**：`sk-…`、`Bearer …`、`password=/api_key=/token=` 形态在落盘前统一打码
（`ErrorText.maskSecrets` / `errors.mask_secrets`）。日志可以留结构，但不该留密钥。

## 6. 禁止出现在对外文案里的内容

- Java/Python 全限定类名、堆栈行、`Exception:` 前缀
- SQL 语句、表名、列名、约束名（`Duplicate entry 'x' for key 'uk_y'`）
- 绝对路径（`C:\aios\...`、`/opt/...`）、jar/文件行号
- 上游原始响应体、`request_id` 以外的供应商内部字段
- 密钥、令牌、密码的任何片段（掩码也不给）
- 框架措辞（`Failed to convert value of type ...`、`JSON parse error: ...`）

`ErrorText.sanitize` 覆盖上述规则；**清洗只是兜底，抛错方本就该直接给人话**。

## 7. 兼容与迁移

1. `ApiResponse.fail(int, String)` 仍可用（老代码遍布各模块）：`errorCode/category` 由 `ErrorCode.ofCode(int)` 反查补齐，
   因此**老调用点自动获得新字段**，不需要一次性全改。
2. `BizException(int, String)`、`getCode()` 行为不变；新代码优先用 `BizException.of(ErrorCode, msg)`。
3. `GlobalExceptionHandler` 的历史修正全部保留：类型不匹配→400、路径不存在→404、
   Accept 不对→406、客户端断开→499、SSE 异常→`event: error` 帧。
4. 文案有变化的两处（**已同步改断言**）：`参数类型不正确：「id」应为整数`（保留「类型」二字）、
   `接口不存在：/path`（保留「接口不存在」）。
