## 1. 产品目标

| 期 | 用户诉求（原话口径） | 产品能力（一句话） |
|---|---|---|
| **二期（P3）** | 「有些事是整个部门干的，不该挂着某个人的名字上报」 | **以部门名义发起审批单：单据主体是部门，审批链起点锚定「部门所属机构」而非提交人的个人层级。** |
| **三期（P4 完整版）** | 「知会要能覆盖所有审批业务；我读过的知会别再算未读，但还得能回查」 | **知会通用化（任一业务可配）+ 待阅已读/未读态（读过的降噪、可回查）。** |

**二期要解决的三件事**：① 部门不能作为申请主体（`approval_order` 无主体字段）；② 无「仅部门负责人可代表部门发起」的权限闸门；③ 部门申请与个人申请在单据上无法区分。

**三期要解决的三件事**：① 知会只对 `PERMISSION_GRANT` 默认流生效，其他业务配了也不通用；② 待阅没有已读/未读，机构管理员每单都被反复提示；③ 知会的通知口径、去重口径、可见性口径未成文。

## 2. 用户故事（按角色，每条带验收要点）

### 2.1 部门负责人

| # | 故事 | 验收要点 |
|---|---|---|
| D-1 | 作为**部门负责人**，我想「以 XX 部门名义」提交权限申请，这样单据记录的是部门的事、而不是我个人 | 提交后 `applicant_type='DEPARTMENT'`、`applicant_department_id=本部门`、`user_id=我`；首节点 = 机构管理员 |
| D-2 | 作为部门负责人，我不想自己审自己提交的部门申请 | 审批链**不出现** `DEPT_LEADER` 我本人作为首个审批人；若我同时是机构管理员，则自审防护跳过该级并顺延到租户管理员，`skipReason` 写明原因 |
| D-3 | 作为部门负责人，我想在申请页只对**我负责的部门**看到「以部门名义申请」开关 | 非负责人角色（普通成员 / 其他部门负责人）看不到可用开关；强行调用接口返回业务错误且不落库 |
| D-4 | 作为部门负责人，我想看到部门申请单与个人申请单的明显区分 | 单据卡片带「部门申请」徽标 + 部门名；详情展示主体与提交人 |

### 2.2 普通成员

| # | 故事 | 验收要点 |
|---|---|---|
| M-1 | 作为普通成员，我**不能**以部门名义申请，但我不应看到会误导的入口 | 开关不可用（隐藏或置灰 + 提示「仅部门负责人可代表部门申请」）；接口层拦截（同机构越权 403 / 跨机构跨租户 404） |
| M-2 | 作为普通成员，我申请权限的行为**完全不变** | 不带 `applyAsDepartment` 时，`applicant_type='USER'`、`applicant_department_id=NULL`，与一期逐字一致（缺省兼容） |

### 2.3 机构管理员

| # | 故事 | 验收要点 |
|---|---|---|
| A-1 | 作为机构管理员，部门申请应指向我来审（部门之上的一级） | 部门申请首节点 = 机构管理员；`timeline` 恰 1 个有效节点（`levels=1` 时一级即终审） |
| A-2 | 作为机构管理员，我收到的知会不再反复提示「未读」 | 已读知会不再计入 `ccUnread`、前端不再显示未读标记；但仍能在「抄送我的」回查（带 `readAt`） |
| A-3 | 作为机构管理员，我能看到知会单的完整流转路径以便督办 | 知会行含 `bizType / title / 申请人 / 当前节点 / timeline`；知会进入所有已配 `cc` 的业务类型 |

### 2.4 租户管理员

| # | 故事 | 验收要点 |
|---|---|---|
| T-1 | 作为租户管理员，我想在流程配置页为**任一业务**的节点配置知会对象 | 管理端流程配置页每节点可多选知会对象；保存后 `steps_json.cc` 落库；无需改代码即可生效 |
| T-2 | 作为租户管理员，我配的知会不能影响审批流转 | 配 `cc` 后 `scope=todo` 不含知会条目；单据终态不因知会停留；知会不可 `decide` |

### 2.5 平台管理员

| # | 故事 | 验收要点 |
|---|---|---|
| P-1 | 作为平台管理员，我能在审批中心区分「个人申请 / 部门申请」 | 管理端审批中心列表与详情展示 `applicant_type` 徽标与部门名 |
| P-2 | 作为平台管理员，我不能代表任何部门发起申请（平台账号不属于机构） | 平台账号调部门申请 → 业务错误（不落库） |

## 3. 需求池（P0 / P1 / P2）

> 优先级：**P0 = 必须**（二期/三期可独立验收的底线）；**P1 = 应该**；**P2 = 可选**。
> 所有新增请求体字段一律「**缺省 = 旧行为**」（不传 / `null` / `false` 时与一期逐字等价）。

### 3.1 二期 · P3「部门作为申请主体」

| 编号 | 需求 | 角色 | 验收标准 | 优先级 |
|---|---|---|---|---|
| **E-01** | `approval_order` 增 `applicant_type VARCHAR(16) NOT NULL DEFAULT 'USER'`（`USER`\|`DEPARTMENT`）与 `applicant_department_id BIGINT NULL` | 架构/开发 | 旧行迁移后全部为 `'USER'` / `NULL`，存量单据读取行为不变 | **P0** |
| **E-02** | 权限申请入口 `PermissionGrantService.ApplyReq` 增 `applyAsDepartment`（`Boolean`，缺省 `false`）与 `departmentId`（`Long`，可空）；`applyAsDepartment` 为空/`false` 时**完全走一期路径** | 部门负责人 | 不传该字段 → `applicant_type='USER'`、`applicant_department_id=NULL`、审批链与一期一致 | **P0** |
| **E-03** | 新增 `OrgGuard.requireDeptLeader(departmentId)`：**判定口径 = `org_member.duty_code='DEPT_PRINCIPAL'`（同部门任一正职即可）**，回落 `org_department.leader_user_id`；**不得使用 `job_title`** | 部门负责人 | 正职可发起；非正职（含 `job_title` 含「负责人」但 `duty_code` 非正职）不可发起 | **P0** |
| **E-04** | 部门申请的**审批链起点 = 该部门所属机构**：`superiorLadder` 检测 `applicant_type='DEPARTMENT'` 时从 `ORG_ADMIN` 梯级起算（跳过 `DEPT_LEADER`，因提交人即部门负责人）；**仍适用自审防护** | 部门负责人 / 机构管理员 | 首节点 = 机构管理员；提交人若同时是机构管理员则顺延租户管理员并在 `skipReason` 写明 | **P0** |
| **E-05** | 部门申请的**租户/机构边界**：`departmentId` 必须属于提交人所属机构；跨机构/跨租户一律 **404**（不泄露存在性），同机构非本部门负责人 **403** | 普通成员 / 平台管理员 | 越权调用返回业务错误（HTTP 200 + `code!=0`）且**不落库**（`approval_order` / `permission_grant` 均无新行） | **P0** |
| **E-06** | **单据主体可区分**：部门申请单在用户端「我的申请」、待办详情与管理端审批中心均展示「部门申请」徽标 + 部门名；申请主体 = 部门，提交人单独展示 | 全部角色 | 列表与详情均能区分 `USER` / `DEPARTMENT`；`timeline` 有效节点数**不含** CC | **P0** |
| **E-07** | 用户端 H5「权限申请」页增「**以部门名义申请**」开关 + 部门选择；仅 `duty_code='DEPT_PRINCIPAL'`（含 `leader_user_id` 回落）的部门可选 | 部门负责人 / 普通成员 | 负责人：开关可用、只能勾选本人负责的部门；非负责人：开关不可用并给提示；提交后单据落库字段正确 | **P0** |
| **E-08** | 部门申请**幂等键与个人申请分账**：部门申请按 `(departmentId, permissionCode)` 判重（同部门同权限仅一条在途/生效），个人申请按 `(userId, permissionCode)` 判重，两者互不冲突 | 部门负责人 | 同一部门重复提交 → 业务错误「已有待审申请」；负责人的个人申请不因部门申请而被拦 | **P1** |
| **E-09** | 部门申请扩展至其他业务类型（`QUOTA_EXPAND` / `RESOURCE_OPEN`），引擎侧 `applicant_type` 通用化，入口按业务需要开启 | 机构管理员 | 引擎对任一 bizType 均支持 `DEPARTMENT` 主体；未开启入口的业务保持旧行为 | **P1** |
| **E-10** | 部门内成员可查看本部门的部门申请记录（只读） | 普通成员 | 本部门成员可见本部门历史部门申请；跨部门不可见 | **P2** |

> **口径澄清（关键取舍，务必执行）**：本阶段「以部门名义」**只改变「单据主体 + 审批链起点 + 发起权限闸门」**，**不改变授权发放对象** —— 审批通过后 `permission_grant` 的授权对象仍为**提交人本人**（保持一期授权链路 `DbPermissionResolver` 不变）。「部门共享权限 / 授权给部门全体成员」属新话题，见 §7 Out of Scope。

### 3.2 三期 · P4 完整版「知会 / 待阅通用化 + 已读态」

| 编号 | 需求 | 角色 | 验收标准 | 优先级 |
|---|---|---|---|---|
| **C-01** | **知会配置通用化**：任一业务类型（`PERMISSION_GRANT` / `LEAVE` / `QUOTA_EXPAND` / `RESOURCE_OPEN`）的 `steps_json.cc` 均生效，**与业务类型无关** | 租户管理员 | 任一 bizType 配 `cc` 后均生成 `CC` 任务；不配则无 CC 任务、行为与一期一致 | **P0** |
| **C-02** | **管理端流程配置页可视化配 `cc`**：每节点增「知会对象」多选（企业管理员 / 部门负责人 / 租户管理员 / 平台管理员），保存写入 `steps_json.cc` | 租户管理员 | 页面保存后 `steps_json` 含正确 `cc` 数组；无需改代码即生效 | **P0** |
| **C-03** | **待阅已读/未读态（数据落点）**：`approval_task` 增 `cc_read_at DATETIME(6) NULL`（`NULL` = 未读） | 架构/开发 | 新增列缺省 `NULL`；旧 CC 行为未读；不影响 `task_role='APPROVE'` 行 | **P0** |
| **C-04** | **待阅已读接口**：`POST /api/v1/workflow/cc/{taskId}/read` 置本人 CC 任务 `cc_read_at`；**幂等**（重复调用不报错、时间不倒退）；非本人任务 404（不泄露存在性）；`APPROVE` 任务调用返回业务错误 | 机构管理员 | 标记后 `read=true`、`readAt` 有值；重复标记成功且 `readAt` 不变；他人/审批任务被拒 | **P0** |
| **C-05** | **`scope=cc` 每行带已读信息**：返回 `read`(bool) 与 `readAt`；**已读条目仍可回查**（不再是「读过就消失」） | 全部角色 | 已读后该条目仍在 `scope=cc` 列表中，仅 `read=true` | **P0** |
| **C-06** | **计数口径**：`summary` **保留 `cc` = 抄送我的总条数**（一期语义不变），**新增 `ccUnread`** = 未读知会数 | 全部角色 | `cc` 不因已读而减少；`ccUnread` 随标记已读正确减少；`todo` 不含 CC（不阻塞） | **P0** |
| **C-07** | **前端未读表现**：H5「抄送我的」Tab 展示未读数；未读条目加「未读」圆点/高亮；**点开详情自动置已读**；已读条目显示「已阅」 | 机构管理员 | 渲染级可验：未读有标记、点开后标记消失、计数减 1 | **P0** |
| **C-08** | **知会去重与排除**：① 同一单据同一人**只生成一条** CC（跨节点/跨类型去重）；② **不抄送申请人本人**；③ **已是审批人的人不再抄送**；④ 解析不到人时跳过（不生成空 CC） | 架构/开发 | 多节点重复配同一知会对象 → 仍只一条；申请人自己收不到自己的 CC；审批人不同时是 CC | **P0** |
| **C-09** | **通知口径**：知会生成时推送站内通知（`type=APPROVAL`）；**点开知会详情后联动置该通知已读**；`ccUnread` 与前端未读标记同一数据源 | 机构管理员 | 知会到达即有一条通知；点开后通知置已读；页面未读数与实际一致 | **P0** |
| **C-10** | **各业务默认知会模板**（播种器 `ApprovalFlowProvisioner.DEFAULTS` + 回填迁移，**只补空值、不覆盖已配**） | 租户管理员 | 新租户自动拿到；老租户仅补齐无 `cc` 的默认流；已显式配置的流程不动 | **P1** |
| **C-11** | `cc` 支持 **`SPECIFIC` 指定人**（`cc` 项含指定用户 id），用于「抄送某位领导」 | 租户管理员 | `cc:["SPECIFIC"]` + `cc_user_ids` 生效；指定人进「抄送我的」 | **P1** |
| **C-12** | 「抄送我的」支持**全部标记已读**（批量） | 机构管理员 | 批量后 `ccUnread=0`，列表条目仍可回查 | **P2** |

### 3.3 知会在各类业务上的可见性 / 通知口径（成文规格）

| 业务类型 | 默认审批链（一期已落地） | 建议默认知会对象 | 知会可见性 | 通知口径 |
|---|---|---|---|---|
| `PERMISSION_GRANT` | `APPLICANT_SUPERIOR levels=1` | `["ORG_ADMIN"]`（已落地） | 机构管理员可见单据摘要 + 完整 `timeline`，可督办 | 生成即推通知；点开置已读 |
| `LEAVE` | `DEPT_LEADER → ORG_ADMIN`（≤3 天跳级） | `["ORG_ADMIN"]`（跳级时上级仍知情） | 同上 | 同上 |
| `QUOTA_EXPAND` | `ORG_ADMIN → TENANT_ADMIN` | `["TENANT_ADMIN"]` 或空 | 同上 | 同上 |
| `RESOURCE_OPEN` | `ORG_ADMIN → TENANT_ADMIN` | `["TENANT_ADMIN"]` 或空 | 同上 | 同上 |
| 对外发文 / 成果类（`ApprovalService` 单级） | 单级 `ORG_ADMIN` | `["ORG_ADMIN"]` | 同上 | 同上 |

> 表格中的「建议默认」由 C-10 的播种器/回填落地；**是否配置仍由租户管理员显式决定**，回填**只补空、不覆盖**。

## 6. 待确认问题（仅列**真正需要业务决策**项，均给出默认建议）

| # | 问题 | 默认建议（我方倾向） | 影响面 |
|---|---|---|---|
| **Q-1** | 一个部门有**多个 `DEPT_PRINCIPAL`** 时，以谁为部门申请的**提交人**？ | **任一正职均可发起**，`user_id` = 实际点击提交者（不强制固定某一人）。理由：多正职（正/副职/分管）是合法配置，强行指定会制造新的单点；单据主体是**部门**，提交人只作留痕。 | E-03 / E-04 / 单据展示 |
