### P0-1 通知网关 `HttpGatewayChannel` 未钉 HTTP/1.1（EMAIL/SMS/PUSH 全丢）

- **位置**：[server/aioa-resource/src/main/java/cn/aioa/resource/service/notify/HttpGatewayChannel.java:57-60](server/aioa-resource/src/main/java/cn/aioa/resource/service/notify/HttpGatewayChannel.java#L57-L60)
- **现状**：
  ```java
  private final HttpClient http = HttpClient.newBuilder()
          .proxy(NO_PROXY)
          .followRedirects(HttpClient.Redirect.NEVER)
  ```

- **风险**：JDK HttpClient 默认 HTTP/2 优先 → 对明文 `http://` 内网通知网关发 **h2c upgrade** → 对方不支持 → body 推迟到升级成功 → 5s 超时后全空。**所有 EMAIL / SMS / PUSH 通知静默丢失**。
- **与历史关系**：与 pitfalls.md #55 / #16 **同源**（`AgentHttpClient` 已修 / 通知通道未修），是目前少有的「同款缺陷第二处」实例。
- **修复**：
  ```java
  import static java.net.http.HttpClient.Version.HTTP_1_1;
  private final HttpClient http = HttpClient.newBuilder()
          .version(HTTP_1_1)
          .proxy(NO_PROXY)
          .followRedirects(HttpClient.Redirect.NEVER)
          .build();
  ```
  或直接 `cn.aioa.common.http.AgentHttpClient.agentBuilder()`（[WorkerScheduleService.java:63](server/aioa-resource/src/main/java/c/nioa/resource/service/WorkerScheduleService.java#L63) 用的就是它）。
- **静态守卫扩展**：把 `scripts/_check_agent_httpclient.py` 的检查面从「`HttpClient.newBuilder` 出现就告警」扩展到「**任何** `HttpClient.newBuilder` 缺 `.version(HTTP_1_1)` 即报错」—— 现版本只挡 `ToolDispatcher`，对 `HttpGatewayChannel` / `HttpEmbeddingProvider` 不命中。

### P0-2 Agent 端模块级可变状态无锁（`_replay` 缓存）

- **位置**：[agent/aioa_ai/runtimes/multi_task.py:55](agent/aioa_ai/runtimes/multi_task.py#L55)
  ```python
  _replay: "OrderedDict[str, tuple[float, list[SseEvent]]]" = OrderedDict()
  ```
- **调用栈**：
  - `_replay_get`（line 58-68）做 `move_to_end` + `pop`
  - `_replay_put`（line 71-75）做 `popitem(last=False)`
  - `_replay_put` 在 `_execute` **yield 完成后**调用（line 119）
- **风险**：
  1. CPython 官方**未承诺** `OrderedDict` 跨协程安全（GIL 只保单条字节码，`move_to_end` / `popitem` 涉及内部链表重排，GIL 切换可能切断链表）。
  2. SSE 断线重连是**客户端行为**——同一个 `run_id` 的第二个请求可能在第一个 run 的尾帧还在写 `_replay[id]` 时 `_replay_get` 同一 key，**拿到旧帧序列**。
  3. 缓存值 `list[SseEvent]` 包含**用户对话数据**（question、模型回答、工具调用 payload），5 分钟 TTL 内可被相同 run_id 复用触发「拿到别人对话内容」**信息泄露**。
- **修复**：
  1. `_replay_get` / `_replay_put` 用 `asyncio.Lock` 包一层（FastAPI 是 asyncio）。
  2. **优先级更高**：缓存里 payload 加 `tenant_id` + `user_id`，重放时校验调用方 token 与缓存项是否同主体，不匹配直接丢弃。
  3. 或改用 Redis（与 HITL 复用的基础设施），跨进程也能安全回放。

### P1-3 `RunService.nextSeq` 竞态 → 同一会话两条消息同 seq

- **位置**：[server/aioa-chat/src/main/java/cn/aioa/chat/service/RunService.java:1396-1402](server/aioa-chat/src/main/java/cn/aioa/chat/service/RunService.java#L1396-L1402)
  ```java
  private long nextSeq(Long conversationId) {
      ChatMessage last = messageMapper.selectOne(new LambdaQueryWrapper<ChatMessage>()
              .eq(ChatMessage::getConversationId, conversationId)
              .orderByDesc(ChatMessage::getSeq)
  ```

#### D1 · KbService.normalizeScope() 静默改写 DEPT/ORG 为 PERSONAL

- **位置**: `server/aioa-resource/src/main/java/cn/aioa/resource/service/KbService.java:300-304`
- **缺陷类型**: 数据一致 / 权限失效
- **现象**:
  ```java
  private static String normalizeScope(String scope) {
      return SCOPE_TENANT.equalsIgnoreCase(scope) ? SCOPE_TENANT : SCOPE_PERSONAL;
  }
  ```
  - 任何非 TENANT 值（含 DEPT/ORG）会被强制改写为 PERSONAL
  - 部门级/机构级 KB 被错误降级为个人 KB → 跨用户共享丢失
  - OrgKbService 把 KB 挂到机构时设了 `scope="DEPT"`，但只要走过 update 路径就被回退
  - 没有日志/告警，DB 落地后才发现（无法回滚）
- **修复建议**:
  ```java
  private static String normalizeScope(String scope) {
      if (scope == null) return SCOPE_PERSONAL;
      String up = scope.toUpperCase();
      if ("TENANT".equals(up) || "DEPT".equals(up)
          || "ORG".equals(up) || "PERSONAL".equals(up)) {
          return up;
      }
      return SCOPE_PERSONAL;
  }
  ```
  并在 KbController.update() 入参校验 scope 合法性；单测钉住「DEPT/ORG 不会被改写为 PERSONAL」

#### D2 · OrgStatMapper.selectKbOfInstitution 缺 tenant_id 过滤（跨租户数据泄漏）

- **位置**: `server/aioa-org/src/main/java/cn/aioa/org/mapper/OrgStatMapper.java:185-190`

- **现象**:

  ```java
  @Select("SELECT ... FROM kb_document WHERE deleted_at IS NULL "
  ```

#### P0-2（= §二十五新增 P0-S）Milvus 写入失败 warn-only，但 KBService 仍把 doc 标为 OK

- **位置**: `KbService.java:139-163`（`index`）+ `MilvusKnowledgeStore.java:162-170`（`saveEmbedding`）+ `:230-252`（`indexChunk`）
- **缺陷类型**: data consistency
- **现象**: `embedAll`（`:166-177`）逐切片 try/catch 静默吞掉异常；`MilvusKnowledgeStore.saveEmbedding` 把 Milvus upsert 包在 try/catch 里只 log warn；`indexChunk` 维度不一致也只 warn 跳过。结果：**MySQL 落库 + state 置 OK + progress=100，但 Milvus 一条都没有**，向量召回永远空，前端无任何提示
- **证据**:
  ```java
  // KbService.java:145-152
  int count = store.replaceChunks(doc, chunks);
  embedAll(doc.getId(), doc.getTenantId(), chunks);
  doc.setState(KbDocument.STATE_OK);  // ← 后续向量失败无感知
  doc.setChunkCount(count);
  doc.setErrorMsg(null);
  ```
  ```java
  // MilvusKnowledgeStore.java:165-170
  try { indexChunk(chunkId, content, vector); }
  catch (Exception e) { log.warn("Milvus 索引写入失败（已落 MySQL，可由回填重建）..."); }
  ```
- **修复建议**:
  1. Milvus 路径上 count「实际写入 Milvus 的切片数」并在 `state=OK` 前 assert 与 `chunkCount` 相等
  2. 或在 KbDocument 增加 `vector_synced_at / vector_synced_count` 字段
  3. 任何向量化缺失 → state=PARTIAL 或 vector_state=DEGRADED，前端红点提示
- **优先级**: **P0**（**新发现**，未在 §十七/§二十一 列出）
- **与启动期 `assertDimsAgree` 的精神相反** —— D6 fail-fast 是预防，这里是事后静默

#### P1-9（独立）KB 文档没有任何写入/容量配额

- **位置**: `KbService.java:99-121`（`register`）+ `KbController.java:175-186`
