# ADR-002：工具权限 = 用户权限，Agent 不做二次授权

- 状态：已落地
- 日期：2026-09

## 背景

Agent 以「谁」的身份调业务接口？可选：

1. 给 Agent 一个高权限服务账号，自己在代码里判断能不能调；
2. 透传发起方用户的令牌，以该用户身份调；
3. 两边都做：先查用户权限，再查工具白名单。

方案 1 的问题是「模型说什么就调什么」，权限边界形同虚设；方案 3 看似稳妥，但会出现
两套真相：工具注册表里配了、Agent 侧没配，于是调用莫名失败，且没人说得清该改哪边。

## 决策

**透传用户 accessToken**：Java 侧工具网关以「当前登录用户」执行，Agent 侧只负责转发
模型输出的 `tool_calls`，不做二次授权判断。越权数据在 SQL 层就查不到。

## 取舍

- 代价：Agent 拿不到用户令牌时工具全不可用（定时任务、后台批处理场景）。
  这类场景走 `/internal/v1/complete`（不进工具循环），或显式传入一个受限的服务身份，
  不靠放宽这条规则来绕过。
- 收益：新增工具不需要在 Agent 侧同步配一遍权限；权限的真相只有一份（后端）。

## 后果

- 工具清单也由后端下发（`GET /api/v1/tools`），模型能看到的工具 = 该用户能用的工具，
  从源头减少「模型调用了注定失败的工具」。
