# ADR-004：计划执行按 run_id 幂等回放（重连不重跑）

- 状态：已落地（批次 4，`agent/app/core/multi_task.py`）
- 日期：2026-09

## 背景

ADR-003 定下「编排器不做重试」——重复触发会让有副作用的工具被执行两次。但 SSE 的
**断线重连是客户端行为**，服务端拦不住：本平台 Spring `SseEmitter` 在流结束时
**不发送终止 chunk**（`/api/v1/runs/{id}/events` 与新加的计划执行端点都一样，已实测确认），
浏览器与严格 HTTP 客户端都会认为连接中断并重连。

对「对话 run」重连是可接受的：后端有终结态回放，不会重复推理。但对**计划执行**
没有这层兜底 —— 重连会把整份计划再跑一遍，副作用翻倍，正好踩中 ADR-003 要避免的事。

## 决策

按 `run_id` 缓存一次执行产出的全部事件帧（TTL 5 分钟，最多 64 份，LRU）：同一个
`run_id` 再来，直接回放缓存帧，**一个工具都不执行**。

`run_id` 由调用方给定则沿用（Java 侧透传）；未给定才由服务端生成。这样浏览器用同一份
body 重发时能命中回放。

## 取舍

- 缓存放内存、单实例：多副本部署时重连打到另一个副本会重跑。当前是单实例部署；
  真上多副本时应把帧缓存换成共享存储（Redis），规则不变。
- 只缓存「跑完」的流：客户端中途断开的不缓存（没跑完的计划没有可回放的结论）。
- 不做「执行中的去重锁」：两个并发的同 run_id 请求仍可能各跑一次。调用方用同一个
  run_id 并发请求本身就是误用。

## 后果

- 有副作用的计划才敢交给前端长连接用；
- 端到端断言为「同一 runId 两次请求的帧序列完全一致（含各任务 durationMs）」——
  若发生重跑，durationMs 必然不同，断言会红。
