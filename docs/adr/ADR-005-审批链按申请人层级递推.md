# ADR-005：审批链按申请人层级递推，而不是展开固定模板

- 状态：已落地（V39，`aioa-org` `ApprovalFlowService.expandNodes`）
- 日期：2026-09

## 背景

审批流定义里有一种节点类型「申请人的上级」（`APPLICANT_SUPERIOR`）。最初按固定
`steps_json` 展开：链上写几级就批几级。组织一调整就出问题——

- 申请人换了部门，审批人还指向旧部门负责人；
- 链上写三级但申请人已经是一级主管，于是出现「自己批自己」或批到不相干的人；
- 修复方式只能是人工改流程定义，改完历史单据的口径又不一致。

## 决策

遇到 `APPLICANT_SUPERIOR` **不展开固定 steps**，改为从「申请人所在层级 + 1」起
逐级向上递推（`superiorLadder`），并跳过三类人：空位、申请人本人（自审防护）、
重复出现的人。

「谁是部门负责人」的唯一权威口径是 `org_duty`（职务字典）+ `org_member.duty_code`
（V41/V42 收敛，原先存在三套口径）。

## 取舍

- 代价：审批链不再能「一眼从定义上看全」，要看组织树才知道实际会批几级。
  补偿是把解析结果落到 `approval_task` 行上，事后可查。
- `levels` 参数（V42）限定最多批几级，避免长链条把单据拖死。
- 知会（CC）节点生成 `task_role='CC'` 的任务：**不阻塞**流程、不进待办、不可决策。

## 后果

- 组织调整后审批链自动跟着变，不需要人工改流程定义；
- 兜底分支必须把 `effectiveType` 写成**实际生效的类型**（不是声明类型），
  否则排查时会误以为是模板没配。
