# ADR-003：多任务协同执行「显式计划」，不做 LLM 自动拆解

- 状态：已落地（批次 4，`agent/app/core/orchestrator.py`）
- 日期：2026-09

## 背景

架构文档写的是「主 agent 编排式（Planner → 业务域子 agent → 汇总）」。落地时有一个
必须回答的问题：**计划谁来做**。

让 LLM 现场拆解目标，看起来最智能，但拆解结果不可复现 —— 同样的诉求每次拆出的步骤
和顺序都可能不同，于是：

1. 无法断言（测试只能「大致对」）；
2. 出问题无法归因（是模型拆错了，还是某个步骤执行错了）；
3. 同一个请求重放一次结果就变了，审计讲不清楚。

## 决策

编排器只负责**忠实地执行一份给定的计划**：调用方把子任务、依赖（`dependsOn`）和入参
引用（`$taskId.field`）写清楚，编排器做依赖分层 → 同层并发 → 汇总。拆解（Planner）
留给上层，不在本模块。

- 同层并发有上限（默认 4）：并发的目的是省等待时间，不是放大下游压力。
- 依赖失败 → 下游**跳过并写明原因**，不是「照跑然后拿到空数据」。
  用一个失败任务的结果当入参继续跑，只会得到看似成功、实则建立在错误前提上的答案。

## 取舍

- 牺牲了「用户一句话就自动拆解」的体验。这是有意的：先把可复现、可断言的执行侧
  做扎实，Planner 作为上层能力后补。
- 不做重试。重试属工具网关与治理层；编排器重复触发会让有副作用的工具被执行两次。

## 后果

- 计划本身成了可枚举、可测试、可审计的对象：执行前先发 `tasks.planned`（含分层信息），
  事后 `tasks.completed` 给出 ok/failed/skipped 计数与每个任务的耗时。
