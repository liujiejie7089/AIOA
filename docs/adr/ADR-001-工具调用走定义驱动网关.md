# ADR-001：工具调用走「定义驱动网关」，不在代码里硬编码分发

- 状态：已落地（V59，`aioa-bridge`）
- 日期：2026-09

## 背景

Agent 要调用业务系统能力。最初的实现是「注册表 + switch 分发」：工具写在代码里，
新增一个工具要改 Java 代码、重新打包、重启。这带来两个后果：

1. 业务系统接入成本高，与「接入 = 注册一个工具」的目标不符；
2. 治理能力（权限、幂等、审批、审计）只能逐个工具手写，漏一个就是一个洞。

## 决策

工具的行为由**一条定义**（`tool_definition` 表行）描述：端点、HTTP 方法、参数映射
（headers/query/body）、结果抽取（JMESPath）、是否需审批、是否需幂等键、权限规则。
调用时按固定顺序过五道闸门：解析 → 权限 → 幂等 → 审批（HITL）→ 分发。

新增工具的途径有三条，互不排斥：SQL 定义、`@AioaTool` 注解自动注册（SDK 扫描 →
`ToolDefinitionSink` 落库）、以及 DB 里查不到时回落到 SDK 的本地声明。

## 取舍

- **多了一层间接**：排查问题要先看定义再看代码。用调用日志（`tool_invocation_log`
  记录入参脱敏值、结果体、耗时、状态）把这个成本补回来。
- **不做「定义热更新 + 缓存失效通知」**：定义改了要重新发布或等下一次解析。
  当前工具数量是几十级，不是几千级，缓存一致性的复杂度不值。
- **参数映射只支持三种位置**：不做通用模板引擎。模板引擎会让「这个参数是拼到 URL
  还是 body」变成运行时才暴露的问题。

## 后果

- 权限/幂等/HITL 成为**所有工具默认具备**的能力，新增工具自动继承；
- 幂等重放返回与首次调用**同形状**的结果（重放时同样走一次结果抽取），
  否则调用方要为「首次成功」和「重放成功」写两套解析。
