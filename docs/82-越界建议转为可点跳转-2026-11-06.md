# 数字人干不了的时候，把「一句话」变成「可点的跳转」（2026-11-06）

> 用户诉求（原话）：
> 「如果当前数字人无法处理，那就提示跳到合适的数字人处理」

## 1. 截图现场：一句话，没有任何入口

请假助手读了《策划书.docx》，回：

> 知识库里确实有《策划书.docx》（自贡彩灯数字文旅方向）。**这属于策划书内容解读，
> 超出我的请假办理职责范围；请改问文档解读数字员工或项目负责人。**

用户的下一个动作应该是「去找那位」；界面上却**没有任何可点的地方** —— 只能自己退回列表里翻。

排查确认了两件事，它们叠加才造成这个结果：

| # | 事实 | 为什么 |
|---|---|---|
| 1 | `worker.handoff` 这条链路是**完整**的 | run 开始前按**用户原话**与数字人任务名做 Tier A/B 文本匹配（`matchHandoff` 纯函数） |
| 2 | 但用户原话是「策划书里面说了什么」 | 不含任何数字人任务名 ⇒ Tier A（整词/码命中）与 Tier B（核心词最长公共子串）**全部落空** |
| 3 | 前端 `oaSuggestList()` 做的是**关键词打分** | 同样召回 0 ⇒ 连兜底卡都不出现 |

**根因不是"缺个按钮"，而是判定位置错了**：越界不是用户说出来的，是模型读完知识库、
发现答非本职责之后才承认的。**判定只能从回答正文里取**，而既有链路只看用户原话。

## 2. 两条链路，语义必须分开

新增一个 SSE 帧 `suggest.worker`，与既有 `worker.handoff` **并列但不重叠**：

| | `worker.handoff` | `suggest.worker`（本轮新增） |
|---|---|---|
| 时机 | run **开始前** | run **结束时**（读完整回答） |
| 输入 | 用户原话 + 任务名 | **回答正文** |
| 效果 | **已经**改绑 `conversation.worker_id`，本轮回答由新数字人产出 | **只是建议**，不改任何状态 |
| 用户动作 | 无（自动），前端落一条「已转交、不用重说」气泡 | 用户点了才跳 |

分开的理由很硬：run 前能判的（用户明说「找报销」）就该**直接转**，别让用户再点一次；
run 后才知道的（答完才发现不归我管）**不能**替用户决定 —— 万一它判断错了，用户已经被改绑走了。

## 3. 判定：`RunService.suggestWorker(...)` 纯函数

`static` 方法，11 例单测直接跑，不进 Spring。规则（按短路顺序）：

1. 回答空 / 候选空 / `currentWorkerId == null` ⇒ `null`。
   **最后这条与 `matchHandoff` 是同一道硬闸**：会话没绑数字人（用户直接选了专家 AI 或走通用助手），
   就无所谓「转给谁」，给跳转等于把会话**劫持**给某个数字人。
2. 正文没有**越界话术** ⇒ `null`。正常回答里也可能顺嘴提到别的数字人，不能一提就给按钮。
   正则只认「明确拒绝 + 指向别处」：
   `(超出|不属于|不在)…(职责|范围|权限)` / `不负责…(这|该|此)` / `(请|建议|可以)(改问|咨询|联系|找)…` /
   `职责范围之外` / `不在我的职责`。
3. 正文点名了某个数字人（`workerName` 或 `taskName` 完整出现）⇒ 取**名字最长**的那个。
   越具体越可能是它：同一句里既有「文档」又有「文档解读数字员工」，后者才是真目标。
4. 一个都没点名 ⇒ `null`。**宁可不给按钮，也不要把用户送错人。**

`candidatesOf(tenantId)` 从原来的 `resolveHandoff` 里抽出来共用 —— 候选口径必须一致，
否则会出现「能自动转过去的」和「建议你转过去的」是**两批人**这种更坏的情况。

## 4. 真机核对时发现的一件事：截图里那个人在库里不存在

写单测时顺手查了库：

```sql
SELECT id,name FROM agent_worker WHERE tenant_id=56 AND (name LIKE '%文档%' OR name LIKE '%解读%');
-- 1314  文档管理数字人        （能力：文档上传 doc_upload）
-- 全租户都没有「文档解读数字员工」
```

也就是说 **「文档解读数字员工」是模型自己编的名字**。按第 3 节的规则 4，这时应该"不给按钮"——
但那样截图场景在真实数据下**依然是一句话、依然无入口**，等于白做。

于是补了第二张卡（`kind:'pick'`）：**越界但点不到具体人时，给「去挑一位能办的数字人」**。

- 不猜人：编出来的名字硬映射到「文档管理数字人」，等于把用户送到一个**也不做这件事**的地方
  （它的职责是上传/归档，不是解读），比不给按钮更挫败；
- 但不留死路：卡上「去看看」直接进数字员工清单页（`#v-workers`，全量清单；
  首页宫格只列 `OA*` 模块，越界的目标未必在其中）；
- 顺手把原问句存进 `setPendingTaskText()`，选完人**自动填回输入框**，不用重打。

## 5. 一次点击做三件事

点卡片上的「换他重答」时：

```
POST /v1/conversations/{id}/handoff  {workerId}
   ↓ conversationService.rebindWorker（同租户 / 未停用 / 项目可分配 三重校验在 bindWorker 里）
   ↓ 只改 worker_id，**不新建会话**（换会话会丢历史，新数字人接不住同一句原话）
   ↓ S.worker 更新 + oaBanner() 顶部变「与「文档管理数字人」对话中」
   ↓ 原问题原样重发（oaSend）—— 仍在同一条会话里
```

`handoff` 失败时降级为既有的 `oaPickWorker`（换会话），绝不让按钮点不动。

**为什么不复用 `oaPickWorker` 直接换会话**：换了会话，新数字人看到的是一个空上下文，
用户还得把「策划书」再指一遍。同会话改绑则保留了刚才那轮的附件、引用与历史。

## 7. 踩到的坑

- **`time.sleep` 堵死 Playwright 的事件分发**（已记 `pitfalls` 97）。
  第一版 `wait_until` 用 `time.sleep(0.15)` 轮询，`pg.route` 的桩回调与 `page.on("request")`
  全都排不上队 ⇒ 「原问题没被重发」报红。而**紧接着**一次 `pg.evaluate()` 之后同一变量就变成了 2 条。
  现象极像产品缺陷（浏览器明明发了请求、记录却没有），实际是测试自己把队列堵住了。
- **`S` 不在 `window` 上**：`index.html` 是 IIFE，`var S` 是闭包内变量；
  只有 `window.oaState = S`、`oaGo`、`oaSend` 等显式挂出去的才可见。
  会话 id 最终取自**真实请求 URL**（`/v1/conversations/(\d+)/runs`），比读状态对象更硬。
- **B 段拿到的是上一轮的旧卡**：`.guide` 是追加型容器，新场景必须先点「新对话」清空，
  否则断言与点击都作用在老卡上（A 段的卡仍在页面上）。已加 B0 专门钉这一条。
- 单测里我把「库里不存在的人」写成了候选集里**确实存在**的名字，断言自相矛盾当场报红 ——
  改成按真实库形状造候选（有「文档管理数字人/文档上传」，没有「文档解读」）。

## 8. 没做的（诚实记账）

- **真实 agent 端到端没跑**：建议帧的**发出**由单测 + 代码路径覆盖，
  e2e 验的是**帧到界面之后**的契约。理由是真跑一轮要模型在线、回答不确定（模型未必说越界话术），
  断言会变成「看运气」。这与 `_verify_form_autocall_live.py` 那类「真 LLM」套件的取舍不同，
  故在此明写，不当成已验证。
- **候选只认完整名字命中**：模型说「文档解读助手」而库里是「文档管理数字人」时不匹配
  （落到挑人卡）。按「送错人比不送更糟」的取舍，暂不做模糊匹配；
  若以后要做，应做成「候选列表里给出 2~3 个近似项让用户选」，而不是替用户挑一个。
- **挑人卡不带方向感**：现在只跳到全量清单，没有按越界话术预筛（比如提到「文档」就排在前面）。
  要做的话判据仍在后端（它才看得到正文），前端只负责渲染顺序 —— 这一轮没做。
