## 一、P0：后端按 `start-backend.bat` 无法启动

**现象**：`start-backend.bat` 原样执行必失败；当前 8080 之所以活着，是因为有人手工加了
JVM 参数绕过校验。

**证据**（进程命令行，`Get-CimInstance Win32_Process -Filter "ProcessId=15040"`）：

```
C:\Users\刘尖尖\.jdks\ms-21.0.8\bin\java.exe -Dspring.flyway.validate-on-migrate=false
  -jar server/aioa-boot/target/aioa-boot-0.1.0-SNAPSHOT.jar …
START=10/02/2026 16:50:38
```

而 `start-backend.bat` 里**没有**这个 `-D`。去掉它复跑即得：

```
FlywayValidateException: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 68
-> Applied to database : 2036569566
-> Resolved locally    : -1046176694
```

**根因**：`V68__remove_sub_tenant.sql` 在**被应用 20 分钟后**（文件 mtime `09-28 12:03:17`，
`flyway_schema_history.installed_on = 09-28 11:43:14`）被改过，改动内容进了
`a259445` 这个提交；`application.yml` 又开着 `validate-on-migrate: true`。
讽刺的是 V68 文件自己第 15–17 行就写着「改动其内容会让校验和对不上，下次启动直接
MigrationChecksumMismatchException」。

**定性为「非语义改动」的证据**（这一步不能省，否则 repair 会掩盖真实的 schema 漂移）：

```
DESC sys_tenant            -> id tenant_id code name status created_at updated_at created_by deleted_at domain
SHOW INDEX FROM sys_tenant -> PRIMARY, code, uk_tenant_domain
```
`parent_id` / `level` 两列与 `idx_tenant_parent` 索引**都已不存在**，`domain` 与
`uk_tenant_domain` **保留** —— 与 V68 文件的 DDL 语义逐条一致，差异只可能在注释/空白。

**处置：已修且已验证。** 按 Flyway 官方口径做一次 repair（把历史行校验和更新为当前文件的值），
不动任何业务数据：

```sql
UPDATE flyway_schema_history SET checksum=-1046176694 WHERE version='68' AND checksum=2036569566;
```

验证（端口 18081 起一个临时实例，**不带** `-Dspring.flyway.validate-on-migrate=false`）：

```
Schema `aioa` is up to date. No migration necessary.
Started AioaBootApplication in 23.401 seconds
```

**遗留**：其他环境（生产 10.0.0.3）历史行同样记录着旧校验和，升级时需做一次同样的
repair，否则启动即失败 —— 建议写进部署手册的升级步骤。**迁移文件不可再改**（V68 之后再改还会复发）。

## 二、管理端「AI 助手不能用」——实为两个前端缺陷 + 一个服务端协议缺陷

复现：管理端登录 → 顶栏「AI 助手」→ 发送消息。修复前界面表现：回答气泡**长时间空白**，
随后**整段一次性弹出**，气泡被标红，下方出现红色 `network error` 横幅（截图
`logs/proof/ai-assistant/02-after-send.png`）。

### D-A（前端，已修且已验证）增量不实时渲染

`web/apps/shell/src/stores/assistant.ts`：消息入列时 `this.messages.push(aiMessage)`，
随后在 SSE 回调里改的是**局部变量 `aiMessage`**（push 进去的原始对象），
而不是响应式数组取回的代理对象。Vue 3 的依赖收集挂在代理上，直接改原始对象**不触发通知**，
于是流式期间气泡恒空，直到 `finally { streaming = false }` 才顺带渲染一次 —— 用户看到的就是
「卡住 2 秒后突然蹦出整段」。

判据：复现脚本第 D6 项「流式期间气泡有内容的轮询次数」。修复前 = 0；修复后 **≥1**
（本轮两次复跑分别观测到 1 和 2 —— 该计数取决于流式分片与轮询的相对时机，会波动，
故判据只认 `>0`，不锚定具体数值；锚死 2 会得到一个会随机变红的假红灯）。

### D-B（前端，已修且已验证）把「已按协议结束」当网络错误

`web/apps/shell/src/api/runs.ts` 的 `onerror` 对任何读流异常都调 `handlers.onError()`。
本服务端 SSE 响应**不发分块终止块**（见 D-C），浏览器读流必然抛
`net::ERR_INCOMPLETE_CHUNKED_ENCODING`，于是**回答明明已完整到达**，界面仍标红并弹
「network error」。

run 的终态在协议上由 `message.completed` / `run.completed` 定义，不由 TCP 关闭定义，
因此终态帧之后的关闭是**预期收尾**。修复：收到终态帧后置 `terminal=true`，此时
`onerror` 抛内部哨兵 `StreamEndedAfterCompletion` 并在 `streamRun` 内吞掉它
（不能只是 `return`：`fetch-event-source` 的 `onerror` 返回 `undefined` 会按默认 1s
**无限重连**，见其 `fetch.js`）。

判据：修复后 `_repro_admin_assistant_ui.py` 12/12 通过（含无错误横幅、无 pageerror）。

### D-C（服务端，未修 —— 给方案）SSE 响应缺分块终止块

**现象**：`GET /api/v1/runs/{id}/events` 的所有帧都送达，但 `Transfer-Encoding: chunked`
响应结尾**没有 `0\r\n\r\n` 终止块**，客户端一律报错。

**证据**（`--raw` 看原始分块帧，末 40 字节）：

```
… } \r\n 2 \r\n \n \n \r\n      ← 最后一个数据块之后什么都没有
curl: (18) transfer closed with outstanding read data remaining
```

两条路径（`/api/v1/runs/{id}/events` 与单端口 `/aioa/api/v1/runs/{id}/events`）**同样报 18**
⇒ 与 `AioaPathPrefixFilter` 无关。已 SUCCEEDED 的 run 走 `replay` 分支（发几帧后立刻
`emitter.complete()`）**同样报 18** ⇒ 与长连接/心跳无关，是 `SseEmitter` 收尾方式本身。

**定性**：这不是本项目独有的代码错误，与 Spring/Tomcat 的已知问题同形
（SPR-14444 / spring-framework#19014「SSE: Terminating chunk not sent using tomcat」，
服务端同形异常 `IllegalStateException: Can't set AsyncWebRequest with concurrent handling in progress`）。
本项目此前**已经知道并容忍**了它 —— `scripts/e2e_v63_single_port.py` 的 D6b 就专门为它开了白名单，
理由是「回答已完整送达」。H5 用户端因为一收到 `run.completed` 就 `return`、不再读下一块，
所以**实际不受影响**；受影响的只有管理端（走 `fetch-event-source`，把关闭当错误上报）。

**处置：未修。** 前端按协议终态容忍（D-B）已让功能可用；服务端建议单独排期：
在 `RunService` 的收尾路径确认 `emitter.complete()` 是否被容器正确处理（改为先 flush、
或换用 `ResponseBodyEmitter` + 显式 `response.flushBuffer()`），判据直接用
`scripts/_check_sse_termination.py` 的 **curl 退出码必须为 0**（现在是 18，
即该脚本会打 `[STATUS] DEFECT-PRESENT`）——该脚本已从 gitignore 的 `_diag_*` 转为
入库的 `_check_*` 报告型哨兵，专门用来看住这条缺陷是否被修掉。

## 三、项目管理：立项时「自动建仓」必然 500，且把整条立项回滚

**现象**：`POST /pm/projects` 带 `{projectType:"DEV", createRepo:true}` 返回
`{"code":500,"message":"服务内部错误"}`，并且**项目行、成员行全部没有落库**。
而复现脚本里 B1 每次都是这个结果。

**证据**：
```
POST /pm/projects {projectType:DEV, createRepo:true} -> code=500 服务内部错误
SELECT … FROM pm_project  -> 只有同批次的 BUSINESS 项目，DEV 项目一条都没有
```

**根因（两处叠加）**：

1. `PmProjectService.create` 未传 `departmentId` 时把它默认成 `0`，并原样塞给建仓：
   ```java
   cb.put("departmentId", departmentId);   // departmentId 可能是 0L
   ```
   而 `GiteeProjectService.create` 对部门是**必填且必须真实存在**：
   ```java
   OrgDepartment dept = requireDepartment(tenantId, departmentId);
   // selectById(0) → null → 抛 BizException("归属部门不存在或不属于当前租户")
   ```
2. 抛出的异常虽然被 `catch (Exception e)` 吞掉（只记 `repoWarning`），但
   `GiteeProjectService.create` 标了 `@Transactional`，与外层**共用同一个事务**；
   内层异常已把该事务标记为 rollback-only，于是外层方法返回时提交失败，
   Spring 抛 `UnexpectedRollbackException` → 500，**整条立项连项目行一起被回滚**。

   这与代码自己的注释直接矛盾 —— 第 166–167 行写着「自动建仓是尽力而为……立项本身仍应成功」。

**影响**：用户按界面提示选了「自动建仓」，得到的是一次 500 和「白填一遍表单」体验；
`repoWarning` 这条设计好的兜底路径**在这条分支上永远走不到**。

**处置：已修（源码，编译通过）——待重启后端验证。** 两处一起改（缺任一处都还留着一个坑）：

1. **`GiteeProjectService.create` 改为独立事务**（`server/aioa-gitee/.../GiteeProjectService.java`）：
   ```java
   @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRES_NEW)
   ```
   这样它的失败**不可能**污染调用方事务，调用方那段 `try/catch` 才真正生效（此前是
   「catch 住了，但事务已被标记 rollback-only」，所以异常吞不掉、提交才炸）。
   ⚠️ 这一步是**通用兜底**：不只为「部门为 0」这一种触发条件，而是任何建仓失败都不再回滚立项。
2. **把内部哨兵值挡在边界外**（`server/aioa-project/.../PmProjectService.java`）：
   立项时 `departmentId` 缺省会补 `0L`（表示机构直属、未挂具体部门），而建仓要求真实部门。
   现在在建仓前先判 `departmentId == null || departmentId <= 0`，命中则**不发那次调用**，
   直接回一条可执行的中文警告（提示补归属部门 / 或去「项目与仓库」建好再绑定），
   省掉一次注定失败的跨模块校验。

验证：`cd server && bash mvnw -DskipTests -q compile -pl aioa-project,aioa-gitee -am` → 通过（exit 0）。
**接口行为尚未回归** —— 生效需要一个编译了本次改动的新 jar，而那必须先停掉正在跑的 :8080，
见文末「为什么本次不重启后端」。

## 四、项目仓库：每小时一次的成员同步失败风暴（已持续 16 天，仍在继续）

**现象**：`/gitee/tasks/stats` 显示 `FAILED 1475 / DONE 1871`，看起来像一次大面积故障。

**证据**：
```
按类型：SYNC_MEMBER  FAILED=1468  DONE=59      ← 96% 失败率
last_error 分布： "Not Found Project" ×1264
biz_id 分布：    项目 14/25/33/37/52/76 各 244 条，其余为个位数
时间跨度：      首次 2026-09-16 17:32:57 → 最近 2026-10-02 22:17:15（本次会话期间仍在产生）
```
这 6 个项目的 `gitee_owner` 全是 `aioa-tenant2-*`、`html_url` 指向**本机桩**
`http://127.0.0.1:8090`，即早前用桩做的 E2E 遗留行，**状态却仍是 ACTIVE**。

**根因**：`GiteeSyncScheduler.calibrateAll` 按 `status = ACTIVE` 取项目并对每个成员入队
`SYNC_MEMBER`（注释里写着「只对 ACTIVE 项目做，FAILED 的会白跑一轮外部调用」）。
托管方后来从桩切到了真实 gitee.com，而这 6 行既没被清理、也没有任何字段记录它属于哪个托管方 ——
`gitee_project` 表**没有 provider 列**。于是每小时对着一批不存在的组织校准协作者，
必然 `Not Found Project`；失败虽是终态，但**下一小时照旧重新入队**，没有熔断也没有告警。

**影响**：① 运维统计被污染 —— 真正的失败信号被 1264 条噪声淹没（这就是「1475 FAILED」的真相）；
② 每小时固定产生一批无谓的外部调用尝试。

**处置：未修（给方案）。** 本条**没有**像第三节那样落地代码，原因是判据不够硬：

- 根治要按**铁律 2**「A 步成功才入队 B 步 ⇒ B 的终态失败必须回写主对象」——
  `GiteeMemberTaskHandler` 失败时只把失败写到**成员行**（`SYNC_FAILED` + `lastError`）后重新抛出，
  **从不回写项目**；而调度器只按 `status = ACTIVE` 取项目 ⇒ 「失败是终态，但下一小时照旧重新入队」。
  所以正解是：SYNC_MEMBER 到达**终态**失败时，把项目自身的状态/同步标记改成非 ACTIVE。
- 但「哪个失败算项目级、哪个算成员级」目前只能**从错误文案里猜**（`Not Found Project` 算项目级，
  「该成员没绑托管方账号」算成员级）。没有 `provider` 列时，这个启发式一旦猜宽，就会把
  **健康项目**标成 FAILED —— 那是比现在这个噪声更严重的新缺陷（假红/误判）。
- ⇒ 先出**数据模型**（`gitee_project` 加 `provider` 列 + 回写规则），再动回写逻辑，
  并且必须在那 6 行桩时代残留上真机验证「回写只打中该打的」。
- 备选（更轻、不需要新列）：把校准入队改成按「同一 `(biz_type,biz_id)` 连续 N 次失败即退避/跳过」，
  先止住噪声，再谈根治。

**已做的只读确认**：本次没有改动这 6 行，也没有删除任何历史任务行 ——
统计（`FAILED 1475 / DONE 1871`）仍可复算。**是否清理这批残留请用户定**：
它们是本次缺陷的**证据载体**，清掉会让上面这组数字无法复现。

## 五、项目仓库：租户组织名写错也能保存并生效，导致建仓全线失败

**现象**：新建仓库受理成功（落 `CREATING`），但打工人跑完即失败：

```
在 Gitee 上找不到 AI-OA/dept11-sim--223222：该组织或仓库尚未在当前实例创建。
（Gitee 原始返回：Group）
```

**证据**：
```
gitee_tenant_config.org_name = 'AI-OA'      org_verified = NULL
GET /gitee/tenant-config -> configured:true, enabled:true, orgVerified:false,
                            verifyMessage:"未提供操作人，跳过组织可见性校验"
```
而同一租户在 09-17 成功建出来的仓库 owner 是 `yjiud`（`gitee_project` 现存行可查），
说明 `AI-OA` 是后来改上去的、且**从没被校验过**。

**根因**：`POST /gitee/tenant-config` 的保存路径只做**best-effort 可见性探测、不阻塞保存**
（代码注释自陈）。平台因此会以「已配置 / 已启用」的姿态对外，而把错误推迟到
**异步建仓任务**里才暴露 —— 用户点「新建项目」时看不到任何提示。
另有 `GiteeTokenService` 的「个人令牌优先、企业令牌兜底」兜底链：企业令牌为空
（`tokenConfigured:false`）也并不阻塞，进一步掩盖了「其实没配好」。

**处置：已修且已验证。** 通过该模块自己的管理接口把组织名改回真实存在的 `yjiud`：

```
POST /gitee/tenant-config {"orgName":"yjiud","enabled":true}
-> orgVerified:true, verifyMessage:"组织存在且当前账号可见"
```
改后重跑建仓：`CREATE_REPO` 任务 **DONE**，仓库真实建出
`https://gitee.com/yjiud/dept11-sim--1002-224429`。原值 `AI-OA` 已在此记录，可回滚。

**建议**：把 `orgVerified=false` 作为保存的前置拒绝，或在界面上以「未校验」显著标红；
建仓前若组织未校验，应在**同步路径**直接返回可读的 4xx，而不是落库后异步失败。

## 八、为什么本次不重启后端（这是环境约束，不是没做）

本次第三节那处后端代码修复（独立事务 + 哨兵值前置拦截）**只做到「源码已改 + 编译通过」**，
没做接口回归，原因是一条硬约束：

- 当前 :8080 是**用户在自有终端**启动的进程（PID 15040，命令行见第一节），自 16:50 起已连续运行 7 小时以上；
- 要出可验证的新 jar 必须走 `clean package`，而 `clean` 要删正在被该进程占用的
  `aioa-boot-*.jar` ⇒ **必须先停掉 :8080**；
- **不能由 agent 重启**：本环境里 agent 起的后台进程会被外部回收（见「用户级长期记忆」中
  「8080 只活 17 分钟 / 19h40m 后凭空不见」的实测），用户会得到「服务看着在跑、其实随时会停」
  的假象，比不重启更糟。

⇒ 正确做法：**由用户的终端重启**（`start-backend.bat` 或 `bash start-all.sh`），
然后重跑 `scripts/_check_pm_guards.py` / `_smoke_pm.py` / `_e2e_pm_ui.py` +
`scripts/_e2e_pm_simulated_project.py`，把第三节那 1 个 KNOWN-BUG 变成 PASS 即可收口。

> 顺带：`start-backend.bat` 本轮已修好（第一节「补充」），且它被 `.gitignore` 排除，
> 所以这次修复**只落在本机**，没有进仓库 —— 换机器要照第一节那张表重新对一遍。
