   `allowedUserIds`）、审计列与软删 `deleted_at`。
3. 存量平移（表刚建必为空，用 `DISTINCT` 防重号；只平移未软删且 `ENABLED` 的租户）：

   ```sql
   INSERT INTO connector_tenant_access (tenant_id, connector_code, enabled, enabled_by, enabled_at, created_by)
   SELECT DISTINCT t.tenant_id, 'scfy', 1, 0, NOW(6), 0
     FROM sys_tenant t
    WHERE t.deleted_at IS NULL AND t.status = 'ENABLED';
   ```

## 4. 判据统一：三处「恒真 / 平台级」逐一租户化

docs/92 §8 的核心判断被逐条兑现，判据唯一落点是新增的
`server/aios-resource/src/main/java/cn/aios/resource/connector/service/ConnectorTenantAccessService.java`：

| 原根因 | 改造点 | 改造后 |
|---|---|---|
| ① `config_keys='[]'` ⇒ `configReadyInternal()` 恒 `ready=true`（`ConnectorCatalogService.java:199-201`） | `configReadyInternal()` 开头先判 `requiresTenantAccess()` | TENANT 走 `tenantReady(code, tenantId)`（查本表 `enabled=1`），`config_keys=[]` 恒真分支只对 OPEN 生效 |
| ② `mcp_server.tenant_id=0` 平台行 + `trusted=1` ⇒ manifest 全员可见 | `McpRegistryService.manifest()` / `usableForAgent()` | TENANT 连接器一律再过 `decide(user, code, tool)`；平台行 `tenant_id=0` 不再是授权凭证；历史 `CONNECTED` / `API_KEY configReady` 短路对 TENANT 失效 |
| ③ hub `scfy/server.py` 零身份校验，绕过 manifest 直调仍通 | `_authorize()` 每次调用前回调 Java | fail-closed（见 §5），绕过 manifest 直调 hub 同样被拒 |

`ConnectorTenantAccessService` 关键方法（行号为当前文件实测）：

```text
requiresTenantAccess(code)   读 connector_def.access_mode（:74）
tenantReady(code, tenantId)  查 connector_tenant_access 行且 enabled=1（:91）
decide(user, code, tool)     租户启用 → CHAT_BASIC 粗闸 → 机构白名单 → 用户白名单（:114）
check(user, code, tool)      decide + 写 mcp_tool_audit，返回 CheckResult（:155）
list/view/enable/disable/configure  四态查询与管理动作（:166/:180/:211/:218/:230）
```

`decide()` 三层闸门顺序（缺一不可， deny 均回可执行中文 reason）：
1. 租户是否启用（无行/`enabled=0` ⇒ 未接入或已停用）；
2. 调用者是否具备 `CHAT_BASIC`（调用粗闸；避免把现网普通用户全拦掉）；
3. 机构白名单：`AuthUser.institutionId`（primary 机构，D3①）须在 `scope_institutions` 内（空 = 不限）；
4. 用户白名单：`config_json.allowedUserIds`（空 = 不限）。

## 5. 调用链路与双层闸门

```text
用户提问 → agent 拉 /api/v1/mcp/manifest
   [闸门1 · Java] TENANT 连接器先过 decide()（租户启用 / CHAT_BASIC / 机构 / 用户）
 → 注入 mcp__scfy__* → MCP tools/call（Authorization: Bearer <JWT>）
 → hub /mcp/scfy → scfy/server.py::_fn(ctx, **kwargs)
   [闸门2 · hub] _authorize() 实时回调 Java GET /api/v1/mcp/access/scfy/check?tool=...
      · fail-closed：无 token / Java 不可达 / 校验响应异常 一律拒绝，不发非遗 GET
      · 拒绝回 {ok:false, accessDenied:true, errors:"接入受控：..."}
      · 完全不缓存准入结果（见下）
 放行 → httpx GET 公网 /show/*（支持租户级 baseUrl 覆盖 _base_override）
```

要点：

- **闸门 2 是安全边界，不是「隐藏工具」**。绕过 manifest 直调 hub 也会被拒（端到端 A1-1/A4-2 实测）。
- `ctx: Context` 由 FastMCP 注入（与 `builtin.py` 通用代理同款），**不出现在 `inputSchema`**
  ⇒ 69 工具契约零漂移（hub 验收 T7：`ctx 不在任何 inputSchema`）。
- **准入不缓存**：每次 `tools/call` 实时回源 Java。曾实现 30s TTL 缓存，随即发现缓存 deny 会使
  管理员启用后 TTL 内仍被拒、缓存 allow 会使停用后 TTL 内仍放行 ⇒ 已完全移除。
  代价是每次调用多一次本机回环 HTTP（单轮同 server 调用上限 4 次，见 docs/89 §9），换来
  启用/停用**双向即时生效** + 逐次审计落 `mcp_tool_audit`（按 tenant 归属）。
- **文案区分两类故障**：Java 不可达时回「接入校验服务暂不可用，本轮未执行非遗查询
  （这是接入授权环节异常，不是上游接口返回错误）」——不误报数据源故障（hub 验收 T5 三连断言）。
- 回滚开关 `_access_check_enabled()`：`AIOS_SCFY_ACCESS_CHECK=0` 时 hub 不再校验，
  退回平台级统一接入（docs/92 风险 8 的回滚预案）。

## 6. 身份、权限与范围

- **身份**：所有 API 走 `AuthUserContext.require()`，tenantId/userId 从登录态取，
  路径/参数不透传（防止改个参数就查别人租户，与 `McpServerController` 同口径）。
  hub 回调带调用者 JWT（agent `tools/client.py` 透传 `Authorization`），Java 仍是唯一身份权威，
  hub 不持密钥、不解析 token。
- **管理权限**：新增 `PermissionCatalog.CONNECTOR_ACCESS_MANAGE = "connector:access:manage"`，
  仅系统/租户管理员（`requireManage` 手动 `holds()` 校验，沿用全仓无 `@PreAuthorize` 惯例）。
- **调用粗闸**：`CHAT_BASIC`；首期未新增 `connector:scfy:use` 类权限码（见 §10）。
- **范围**：`scope_institutions` 按 primary 机构判定；`config_json.allowedUserIds` 用户白名单；
  `config_json.baseUrl` 租户级数据源地址覆盖（自建 16060 场景）。
- **四态**：`NOT_CONNECTED`（无行）/ `CONFIGURED_DISABLED` / `ENABLED` / `DISABLED`；
  每态对 manifest 与调用的影响由同一 `decide()` 判定。
