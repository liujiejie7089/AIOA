## 二、架构：控制面 / 数据面 / 用户面

```
┌─────────────── 控制面：Java（唯一身份权威） ───────────────┐
│  管理端 /aios/web  「连接器配置」页                        │
│    GET/PUT/DELETE /api/v1/admin/connector-configs/{code}   │
│      → ConnectorTenantConfigService（schema 驱动 + 掩码）  │
│      → ConnectorCredentialGateway（原样转发调用者 JWT）    │
└───────────────────────────┬───────────────────────────────┘
                            │ HTTP/1.1（显式，防 h2c 吞 body）
┌───────────────────────────▼───────────────────────────────┐
│  数据面：mcp-hub :8099（连接器运行时，凭据的**权威存储**）  │
│    GET/PUT/DELETE /api/v1/connectors/{code}/credentials    │
│      → registry（连接器清单）→ provider 分流：              │
│          wecom ⇒ 企微原生加密表                            │
│          vault ⇒ 通用保险库 connector_credential           │
│          none  ⇒ 无应用级凭据（拒绝写入而不是假装成功）     │
│    /mcp/{code}  MCP 工具（原生 or 代理转发 Java）          │
└───────────────────────────┬───────────────────────────────┘
                            │ OAuth / IMAP-SMTP / 各应用 OpenAPI
┌───────────────────────────▼───────────────────────────────┐
│  用户面：H5 /aios/h5 「连接器」页                          │
│    用户用自己的账号授权（企微 OAuth / 邮箱授权码），        │
│    连接态按 tenant_id + user_id 隔离，互不可见             │
└───────────────────────────────────────────────────────────┘
```

**为什么凭据的权威必须在 hub**：工具是在 hub 进程里执行的。凭据写在别处 = 写了不生效。
早期实现就是「管理端写 MySQL、hub 读自己的库」，现象是「管理端显示已保存，用户端仍报未配置」，
本次把它作为**断链缺陷**修掉：Java 只做控制面（鉴权 + 校验 + 掩码），凭据落到 hub。
MySQL 的 `connector_tenant_config` 降级为**影子记录**（供 `configReady` 判定、列表展示、
hub 不可用时的只读兜底），影子写失败只告警、不影响「保存成功」（权威已落库）。

## 三、关键抽象：一份 manifest = 一个连接器

`mcp-hub/mcp_hub/connectors/manifest.py`

```python
ConnectorManifest(
    code="wechat_work", name="企业微信", group="协作与办公",
    auth_mode=AUTH_OAUTH2,     # OAUTH2 | CREDENTIAL | API_KEY —— 决定「谁来配凭据」
    provider="wecom",          # wecom | vault | none —— 决定「凭据落在哪」
    credential_fields=(
        CredentialField(name="corpId", label="企业ID（CorpID）", required=True, ...),
        CredentialField(name="corpSecret", label="应用 Secret", type="password",
                        sensitive=True, help="只存密文，永不回显"),
        ...
    ),
    tool_count=13,
    server_factory=_build_wecom_server,          # 非 None ⇒ 原生实装
    tool_catalog=lambda: wecom_catalog.TOOLS,    # 探测用同一份目录，杜绝漂移
)
```

- **网关主体不认识任何连接器**：`builtin.py` 遍历 `registry.all_manifests()`，
  有 `server_factory` 就交给它构建，否则按 `specs` 构建通用代理；`probe.py` 同样只问注册表。
当前注册的三个内置连接器（唯一清单在 `connectors/registry.py`）：

| code | auth_mode | provider | 凭据归谁 | 工具数 | 说明 |
|---|---|---|---|---|---|
| `wechat_work` | `OAUTH2` | `wecom` | 租户（应用凭据）+ 用户（OAuth） | 13 | 自建应用；需可信 IP/域名，见 §5.2 |
| `qq_mail` | `CREDENTIAL` | `none` | 用户（`connector_connection`） | 6 | 无应用级凭据，管理端不出现配置入口 |
| `wecom_group` | `API_KEY` | `vault` | 租户（webhookKey） | 2 | 零门槛通道，见 §5.7 |

- **管理端不认识任何字段名**：字段全部来自 manifest（hub）/ `connector_def.config_keys`（Java）。
- **敏感 = 不声明就不回显**：字段名命中 `(?i).*(secret|password|passwd|token|apikey|api_key|authcode).*`
  即视为敏感，GET 只回 `${key}Set: true|false`。
- **PUT 语义两端口径一致**：提交空串或掩码值（含 `*`/`•`）= 保留旧值。

新增一个第三方应用的标准动作为 5 步（不改网关主体、不改控制器、不改管理端表单）：

1. `connector_def` 插一行（`code` / `auth_mode` / `config_keys` JSON 数组）；
2. `registry.register(ConnectorManifest(...))`；
3. 有工具逻辑 ⇒ 提供 `server_factory`（否则把工具写进 `specs.BUILTIN_SERVERS` 走代理转发 Java）；
4. provider 选 `vault` 即自动获得加密存储与掩码（无需建表）；
5. 需要用户授权 ⇒ 在 H5 连接器页走既定 OAuth 流程（`docs/58`）。

## 四、凭据生命周期（含防伪判据）

| 阶段 | 行为 | 判据 |
|---|---|---|
| 保存 | 管理端 PUT → Java 校验角色 → 转发 hub → 加密落库 | 回查 hub `configured=true`（**第二源**，不信 Java 回话） |
| 回显 | GET 只回掩码 + `${key}Set` | 响应体不含明文（哨兵直接扫 body） |
| 生效 | hub 侧连接器立刻用新凭据 | 用户端 `configReady` 翻转 + 工具实调 |
| 清除 | DELETE → hub 清运行时 → 清影子记录 | hub `configured=false` 且 `configReady=false` |
| 落盘 | AES-256-GCM（`enc:` + base64(nonce+ct)） | 直接扫 SQLite 文件字节（db/-wal/-shm）无明文 |

失败语义（绝不含糊）：

- 运行时不可达 ⇒ **503 + 中文原因**，`配置未保存`，不写影子记录，不返回成功；
- 传了 schema 未声明的字段 ⇒ **400**（杜绝写任意键）；
- `provider=none` 的连接器被管理员写应用凭据 ⇒ **400**（QQ 邮箱属于此类）；
- 非管理员 ⇒ **403**；无 token ⇒ **401**。

## 五、如何连接企业微信

### 5.1 需要管理员在管理端填的配置项

| 配置项 | 必填 | 从哪来 | 说明 |
|---|---|---|---|
| `corpId` | 是 | 企微管理端 → 我的企业 → 企业信息 → 企业ID | 非敏感，回显前 4 位 |
| `agentId` | 是 | 应用管理 → 自建应用 → AgentId | 非敏感，回显前 4 位 |
| `corpSecret` | 是 | 同一页面 → Secret「查看」 | **敏感**：只存密文，永不回显 |
| `redirectUri` | 否 | env `WECOM_PUBLIC_BASE_URL` 推导 | 只影响 OAuth 回跳，不填则按 `WECOM_PUBLIC_BASE_URL + /api/v1/wecom/oauth/callback` 推导 |

> **两条回调路径都同域，所以企微「可信域名」只填一次根域名即可**：
> 用户端 H5 发起 → `https://<域名>/api/v1/connectors/wechat_work/callback`（Java，`aios.connector.public-base`）；
> MCP `connect` 工具发起 → `https://<域名>/api/v1/wecom/oauth/callback`（hub，`WECOM_PUBLIC_BASE_URL`）。
> 可信域名只校验**域名**，不校验路径/端口，填 `oa.example.com` 这一级即可。

> `redirectUri` 不在 `connector_def.config_keys` 里，因此管理端表单只出现前三个 —— 与
> `docs/61` 的「免域名」结论一致：**API 调用（发消息/通讯录/身份）从不需要域名**，
> 只有网页授权回调需要，由 env 兜底。

### 5.2 企微侧前置（管理员在 work.weixin.qq.com 做一次）

1. 建自建应用：应用管理 → 自建应用 → 创建，拿到 `agentId` / `secret`；「可见范围」必须包含要用的人。
2. 应用 → 企业可信 IP：把**服务器公网出口 IPv4** 加白（**仅支持 IPv4，不支持 IPv6/网段/`*`**，
   每应用上限 120 个；未加白则所有业务接口返回 `60020`）。

   > ⚠️ **这一步有硬前置，2026-10-30 用户截图证实、官方 path/90930 同样写明**：
   > 「配置企业可信 IP 前，请先设置可信域名或设置接收消息服务器 URL」。
   > 也就是说**没有备案域名就加不了可信 IP**（这两条路都要一个能通过企微校验的域名，
   > 备案主体须与企微企业主体一致或有关联）。这与本节第 3 条的「可信 IP 不要求企业认证」
   > 并不矛盾：**不要求认证 ≠ 不要求域名**。
   >
   > 由此得出一个必须早点讲清的判断：**自建应用这条路，没有备案域名就走不通**。
   > 若只是想「让 AI 能往群里发消息」，不要再在自建应用上加白折腾，直接用 §5.7 的群机器人。
3. 需要网页授权时：应用 → 网页授权及 JS-SDK → 填可信域名（要求企业已认证）；
   若不想认证企业，就只走「应用消息 + 通讯录 + 身份」这组 API。
   **注意**：即便不启用网页授权，第 2 步也仍需先有一个可信域名/接收消息 URL（见上）。

> **`gettoken` 不校验可信 IP**（易误判）：`cgi-bin/gettoken` 不带业务校验，
> 拿得到 token 只证明 `corpId/corpSecret` 正确；真正的 IP 校验发生在 `agent/get`、
> `user/list`、`message/send` 等业务接口。故「能取到 token」**不能**当作「配置已完成」的判据，
> 用 `scripts/wecom_ip_check.py` 两步自检（先 gettoken 再打 `agent/get`）。

### 5.3 平台侧步骤

1. 管理端 →「连接器配置」→ 选「企业微信」→ 填 `corpId` / `agentId` / `corpSecret` → 保存。
2. 保存后接口立刻回 `configured=true` / `configReady=true`，用户端卡片从「待管理员配置」变为「未连接」。
3. 用户端（H5）→「连接器」→ 企业微信 → 连接：
   - **A 模式**：企微 App 内 OAuth（`snsapi_privateinfo`），零填写，回跳后落库 `userid` + 企业邮箱；
   - **B 模式**：填企业邮箱地址 + 客户端专用密码（IMAP/SMTP 探活通过才落库）；
   - 先 A 后 B 自动合并为 **A+B**，工具白名单按模式收窄。
4. 断开：`disconnect(mode)` 单断某模式，`disconnect()` 全断并清凭据。

### 5.4 验证方式

```bash
# 1) 运行时是否已拿到凭据（第二源，绕过 Java）
curl -s --noproxy '*' -H "Authorization: Bearer <管理员token>" \
     http://127.0.0.1:8099/api/v1/connectors/wechat_work/credentials
#    期望：configured=true, values.corpSecretSet=true, corpSecret=""（无明文）

# 2) 一键哨兵：管理端保存 → 回查 hub → 用户端就绪 → 掩码 → 清除不残留
NO_PROXY='*' python scripts/_verify_connector_tenant_config.py
#    期望 9/9（前置：Java :8080 与 hub :8099 同时在线）

# 3) 双模式全链路（mock，20 项）
python scripts/_verify_wecom_dual_mode_p0.py
```

> ⚠️ 真机联调最常踩的一条：`60020 not allow to access from your ip`。
> 先确认**出口是 IPv4**（本项目已在 `wecom_api.py` 强制 `AF_INET` 解析 `qyapi.weixin.qq.com`，
> 因为双栈主机上 anyio 会优先 IPv6，而企微可信 IP 不支持 IPv6）。

### 5.5 企微管理端「可信域名」到底填什么

截图里那个框（应用 → 网页授权及 JS-SDK / OAuth2.0 网页授权 → **可信域名**）只填**域名本体**：

| 规则 | 说明 |
|---|---|
| 只填域名 | `oa.example.com` ✅ ｜ `https://oa.example.com` ❌ ｜ `oa.example.com:8443` ❌ ｜ `oa.example.com/api/v1/...` ❌ |
| 必须备案 | 备案主体须与企微企业主体相同或有关联（这是企微的硬门槛，截图已写明） |
| 企业需已认证 | 可信**域名**要求企业已认证；而可信 **IP** 不要求（这是「免域名」方案能服务未认证团队的原因） |
| 每应用 1 个 | 一个自建应用只能填 1 个可信域名，不支持通配/多个 |
| 与回调同域即可 | 回调路径 `/api/v1/connectors/wechat_work/callback` 与 `/api/v1/wecom/oauth/callback` 都在该域名下，填一次覆盖两条链路 |

**没有备案域名时（本机 `127.0.0.1` 就是这种情况）**：这个框**留空**即可，不启用网页授权。
此时可用的能力：`send_text_message`（应用消息）、`contact_search`（通讯录）、`check_connection`、邮箱模式 B；
不可用的只有 A 模式（`snsapi_privateinfo` 要网页授权，必须有可信域名）。
内网穿透域名一般未备案，**绕不过去**；要么补备案，要么就走上面这组 API。

### 5.6 相关环境变量与配置项（全量）

| 位置 | 键 | 必填 | 作用 |
|---|---|---|---|
| 企微管理端 | 企业ID / AgentId / Secret | 是 | 填进平台管理端 |
| 企微管理端 | 可信 IP（**仅 IPv4**） | 真机必需 | 未加白 ⇒ 全部业务接口 60020。**前置：须先设可信域名或接收消息 URL**（§5.2 第 2 条） |
| 企微管理端 | 可信域名 | 真机必需（自建应用） | 不仅网页授权要；它还是「加可信 IP」的前置条件。见 5.5/5.2 |
| 企微管理端 | 可见范围 | 是 | 同时是权限范围（决定能给谁发消息、谁能授权） |
| Java env | `AIOS_CONNECTOR_SECRET_KEY` | 生产必改 | 用户连接凭据加密（AES-256-GCM） |
| Java env | `AIOS_CONNECTOR_PUBLIC_BASE` | 有域名时填 | 拼用户端回调；留空回退请求 Origin |
| hub env | `WECOM_CONNECTOR_KEY` | `WECOM_MOCK=0` 时必需 | base64 的 32 字节 AES 密钥（`openssl rand -base64 32`） |
| hub env | `WECOM_MOCK` | 开发 1 / 真机 0 | 1 = 虚拟企业与虚拟邮箱，不连外网 |
| hub env | `WECOM_PUBLIC_BASE_URL` | 有域名时填 | 租户未配 `redirectUri` 时据此推导授权回调 |
| hub env | `AIOS_SERVER_BASE_URL` | 默认 `:8080` | hub 回打 Java `/api/v1/auth/me` 判身份 |
| hub env | `WECOM_DB_PATH` | 可空 | 凭据 SQLite 路径（默认 `mcp-hub/data/wecom.db`） |

### 5.7 零门槛通道：群机器人（`wecom_group`）

**为什么单独做一条通道**：自建应用的业务接口要过「可信 IP」，而可信 IP 又要先有备案域名
（§5.2）。当管理员手上**没有备案域名**时，自建应用这条路整体走不通 —— 但「让 AI 往群里发个通知」
这个最常见诉求，企微另有一条完全不同的入口：**群机器人 Webhook**。

官方 path/91770 只提了两条限制（仅群消息、20 条/分钟），**不提可信 IP、不提可信域名、
不提企业认证**。同一出口 IP 对照实验（2026-10-30 实测）：自建应用 `agent/get` 恒定 `60020`，
群机器人 webhook `errcode=0` 成功 —— 这就是判断依据，不是推断。

| 维度 | 自建应用（`wechat_work`） | 群机器人（`wecom_group`） |
|---|---|---|
| 可信 IP | 必需 | **不需要** |
| 可信域名 / 备案 | 必需（是加 IP 的前置） | **不需要** |
| 企业认证 | 网页授权要 | **不需要** |
| 凭据形态 | 租户级 `corpId/agentId/corpSecret` + 用户 OAuth | 租户级 `webhookKey`（**没有用户授权环节**） |
| `auth_mode` | `OAUTH2` | `API_KEY` |
| 能做什么 | 发应用消息、查通讯录、拿成员身份、企业邮箱收发 | 只能往**那一个**群发文本/markdown |
| 能给谁发 | 按 `touser` 指定成员 | 群固定，**没有收件人参数** |

**配置（两步）**

1. 企微里建群 → 群设置 → 群机器人 → 添加 → 复制 Webhook 地址：
   `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<这串就是 webhookKey>`
2. 管理端 →「连接器配置」→ 企业微信群机器人 → 填 `webhookKey` → 保存。
   凭据落 hub `vault`（`connector_credential` 表，AES-256-GCM，按 `tenant_id` 隔离），
   MySQL 只留影子记录供列表/就绪判定。

> 为什么它不需要用户在 H5 里点「连接」：凭据是**管理员**申请的，天然属于租户，
> 没有「用户把自己的身份授权给平台」这一环。故 manifest 闸门对 `API_KEY` 型走的是
> 「租户配置是否就绪」而不是「用户是否 CONNECTED」（`McpRegistryService.usableForAgent`）。
> 这是被真实 bug 逼出来的：早先只判 CONNECTED，导致群机器人在 hub 里能调、AI 却看不见。

**工具（2 个，工具目录唯一真源 = `mcp-hub/mcp_hub/wecom/group_server.py` 的 `TOOLS`）**

| 工具 | required | 说明 |
|---|---|---|
| `send_group_text` | `["content"]` | 纯文本，≤2048 字节 |
| `send_group_markdown` | `["content"]` | markdown（加粗/引用/链接/彩色字） |

两者都**没有**群参数、也没有收件人参数 —— 目标群由 key 决定。这个「没有」必须写进工具描述，
否则模型会反问「您要发到哪个群」：2026-10-30 实测，描述只写「往企业微信群发送消息」时，
MiniMax 拿到工具却不调用，直接反问群名；把「不需要群名称/群ID，不要反问」写进描述首句后才调通。

## 六、如何连接 QQ 邮箱

QQ 邮箱是 **`provider=none`** 型连接器：平台没有、也不需要「应用级凭据」，
`connector_def.config_keys = []`，因此管理端**不会出现**它的配置入口（`list()` 直接跳过），
尝试写应用凭据会明确 400。凭据由每位用户自己填，落在 `connector_connection.credential_json`（加密）。

### 6.1 用户侧步骤

1. QQ 邮箱网页版 → 设置 → 账户 → 开启 IMAP/SMTP 服务 → 生成**授权码**（不是 QQ 密码）。
2. H5 →「连接器」→ QQ 邮箱 → 填 `邮箱地址` + `授权码` → 连接（服务端先 IMAP 探活，通过才落库）。

### 6.2 验证方式

```bash
# 工具目录（6 个）与 required 断言
python scripts/_verify_mcp_hub.py
# 发信闭环：草稿 → 发送 → 幂等 → Sent 可见（判据取 DB status + IMAP 收件箱，不信模型文案）
python scripts/_verify_mcp_e2e.py
```

> 纪律：`langchain-mcp-adapters` 会丢 `isError`，客户端按 `"Error executing tool"` 前缀判失败；
> 模型（MiniMax）可能零工具调用却「谎报已发送」，所以发信必须回库/回收件箱复核。

## 八、已知边界

- `AIOS_MCP_HUB=false` 时连接器运行时不存在，管理端保存会**明确报 503**（而不是假成功）；
  企业微信/QQ 邮箱这类「工具跑在 hub 里」的连接器此时不可用，这是开关的应有语义。
- 影子记录只是缓存：hub 在线时以 hub 为准，`source=legacy` 会在管理端顶部红字提示。
- 企微可信 IP 必须是**固定公网 IPv4**；家宽动态 IP 会持续 `60020`，需换固定出口或走服务商代发。
- **没有备案域名 ⇒ 自建应用（`wechat_work`）真机不可用**（可信 IP 加不进去，§5.2），
  此时能用的只有群机器人（§5.7）与「邮箱模式 B」这类不需要企微业务接口的能力。
- 企微 OAuth 的 `redirectUri` 仍需域名（`docs/61` 已论证免域名只能免除 API 侧，不免授权形态）。
