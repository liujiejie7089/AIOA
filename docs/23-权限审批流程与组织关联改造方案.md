# 23 · 权限审批流程与组织关联改造方案（对标 O2OA）

> 需求来源：① 普通用户申请权限，由**部门负责人一级审批**即可；② **部门申请权限**同样向上级审批；
> ③ 当前「部门负责人 ↔ 普通用户」关联过少、业务衔接不紧密。
> 参考对象：开源 OA **O2OA**（https://github.com/o2oa/o2oa ，浙江兰德纵横，JavaEE 分布式 + 流程引擎）。
> 本文先给实测现状与 O2OA 模型梳理，再给可落地的改造方案。
> 所有现状数字均取自本机库（`aioa`）实测，代码位置精确到「文件 : 方法」。

---

## 0. 结论速览

| # | 问题 | 结论 |
|---|---|---|
| 1 | 普通用户申请权限只走部门负责人一级，现在能做到吗 | **引擎不支持**。`APPLICANT_SUPERIOR` 只实现了「一次展开整条上级链」，没有「向上几级」的深度参数。要一级审批必须给节点加 `levels` 语义。 |
| 2 | 「部门申请权限」现在能做吗 | **不能**。`approval_order` 的申请人只能是 `sys_user`（`ApprovalFlowService.submit` 的 `applicantUserId`），模型里没有「部门作为申请主体」。 |
| 3 | 为什么说「部门负责人与普通用户关联过少」 | 同一件事在库里**存在三套互不一致的口径**：`org_member.job_title` 标「负责人」的有 **27** 人、`org_department.leader_user_id` 配了的只有 **8** 个部门（共 39 个）、真正持有 `ROLE_DEPT_LEADER` 的只有 **3** 人。引擎只认第二个，所以「谁是负责人」在业务上根本不可靠。 |
| 4 | O2OA 最值得借鉴的是什么 | **「职务（Duty）」这一层中间件**：流程按「职务 + 所属组织」动态求值处理人，从而让**人员变动不牵动流程/权限配置**。我们缺的正是这层，改用自由文本 `job_title` 顶替。 |
| 5 | 一级审批有一个必须正视的后果 | 用户此前反馈过「机构管理员收不到成员申请」（正是 V39 改成整链递推的原因）。若改成一级，该诉求会**再次出现**。建议按 O2OA 的**「待阅 / 知会」**模式解决：机构管理员不审批但可见可督办。 |

## 1. 现状梳理（本系统实测）

### 1.1 组织与人员模型

```
平台(tenant 0)
└── 租户 sys_tenant(tenant_id ≥ 2)
    └── 机构 org_institution(tenant_id, admin_user_id)
        └── 部门 org_department(institution_id, parent_id, level, path, leader_user_id)
            └── 成员 org_member(user_id, department_id, job_title, is_org_admin)
                └── 账号 sys_user（角色挂在 sys_user_role，全局、不分机构）
```

关键局限：

| 维度 | 现状 | 问题 |
|---|---|---|
| 人员与组织的关系 | `org_member` 一张表，一人一行 | 无「身份」概念 —— 一人不能在机构 A 是负责人、在机构 B 是成员（兼职/借调表达不了）|
| 职务 | `org_member.job_title` **自由文本**（如「算法部负责人」） | 引擎**不读**该字段；它只是展示文案，却容易被误当成负责人依据 |
| 部门负责人 | `org_department.leader_user_id`（**单坑位**） | 只能一个负责人；无法表达「正职 / 副职 / 分管领导」；39 个部门只有 8 个配了 |
| 角色 | `sys_role` + `sys_user_role`，**全局** | `ROLE_DEPT_LEADER` 只挂了 3 人，与「谁实际是负责人」脱节 |

### 1.2 角色与权限模型

- 角色层级：`ROLE_ADMIN` > `ROLE_TENANT_ADMIN` > `ROLE_ORG_ADMIN` > `ROLE_DEPT_LEADER` > `ROLE_MEMBER`。
- 权限码目录 `PermissionCatalog`（`server/aioa-security/`）：`chat:basic` / `kb:read` / `doc:draft` /
  `worker:use|create|manage|edit:self` / `expert:manage` / `approval:leave`。
- 判权入口：`PermissionCatalog.holds(role, code)` —— **权限码 → 允许的角色集合**，与组织无关。
- 数据范围：`sys_role.data_scope` ∈ `ALL / TENANT / ORG / DEPT / SELF`。
- 权限申请：`POST /api/v1/org/permissions/apply`，请求体
  `PermissionGrantService.ApplyReq(permissionCode, targetWorkerType, reason, validDays)`
  —— **申请人恒为当前登录用户**，没有任何「代部门申请」的入口。

### 1.3 审批引擎（`ApprovalFlowService`，文件 : 方法）

```
submit()  → 建 approval_order → expandNodes() 解析节点 → 逐条插 approval_task(seq 升序)
decide()  → 当前节点 = 该单 seq 最小的 PENDING；通过则推进，末节点通过 → 单据 APPROVED + 回调
```

审批人类型（`approval_task.approver_type`）：

| 类型 | 求值方式 | 备注 |
|---|---|---|
| `DEPT_LEADER` | `resolveDeptLeader(institutionId, departmentId)` → `org_department.leader_user_id` | 解析不到时**兜底改派**给机构管理员，且 `approver_type` 同步改写为实际类型 |
| `ORG_ADMIN` | `org_institution.admin_user_id` | |
| `TENANT_ADMIN` | 本租户第一个 `ROLE_TENANT_ADMIN` | |
| `PLATFORM_ADMIN` | `tenant 0` 的第一个 `ROLE_ADMIN` | |
| `SPECIFIC` | `steps_json.approver_id` 或提交时传入 | |
| `APPLICANT_SUPERIOR` | `superiorLadder()`：从「申请人所在层级 +1」起，展开 **`[DEPT_LEADER, ORG_ADMIN, TENANT_ADMIN, PLATFORM_ADMIN]` 整条链**，跳过空位 / 申请人本人 / 重复人 | V39 新增。**只有租户 9 的 `PERMISSION_GRANT` 用了它**，其余租户仍是固定两级 |

流程定义解析优先级：**机构专属（`institution_id`）> 租户默认（`institution_id=0`）> 内置单级 `ORG_ADMIN` 兜底**。

### 1.4 实测数据（本机 `aioa` 库）

| 指标 | 数值 |
|---|---|
| 部门总数 / 已配 `leader_user_id` | **39 / 8**（20.5%）|
| `org_member` 行数 / 已挂部门 | 116 / 116 |
| `job_title` 含「负责人」的成员数 | **27** |
| 持有 `ROLE_DEPT_LEADER` 的人数 | **3** |
| 角色分布 | `ROLE_MEMBER` 97 · `ROLE_ORG_ADMIN` 19 · `ROLE_TENANT_ADMIN` 8 · `ROLE_DEPT_LEADER` **3** · `ROLE_ADMIN` 1 · `ROLE_USER` 1 |
| `PERMISSION_GRANT` 用 `APPLICANT_SUPERIOR` 的租户 | 仅 tenant 9；tenant 1–8 仍是 `[DEPT_LEADER, TENANT_ADMIN]` |

**三个数字（27 / 8 / 3）说明的是同一件事**：业务口径、引擎口径、权限口径各说各话。
「部门负责人与普通用户关联过少」的实质不是「配得少」，而是**根本不存在一个权威的、可被引擎和权限同时消费的『负责人』事实源**。

## 2. O2OA 模型梳理（对标学习）

O2OA 是 JavaEE 分布式架构的开源 OA / 协同办公平台，核心能力是「流程引擎 + 表单定制 + 组织管理」。

### 2.1 组织模型：五个正交概念

| 概念 | 含义 | 关键设计 |
|---|---|---|
| **组织 Unit** | 多级组织结构（集团 / 分公司 / 部门 / 小组） | 支持**多维组织**——多个公司组织结构同时并存，而非单棵树 |
| **身份 Identity** | 人员归属某组织的关系 | **一人多身份**：因兼职 / 借调，同一人可在多个组织各持一个身份；流程处理人**以身份记录**，因此「他是谁」与「他在哪个组织」不混淆 |
| **职务 Duty** | 组织中承担相同职责的职位总和（如「部门经理」「部门正职」） | **核心中间层**：实现「人员 ↔ 流程 / 权限」的解耦。人员调整只改职务的人员映射，**流程定义无需改动** |
| **群组 Group** | 同类人组合（项目突击组、各分公司领导…） | 可**嵌套群组**，也可**把组织加入群组** |
| **角色 Role** | 系统功能角色（系统管理员、流程平台管理员…） | 成员可为**个人成员**，也可为**群组成员**（含组织）→ 权限**继承** |

> 与「岗位」的区别：O2OA 明确把**职务**（工作类别，可多人）与**岗位**（与人强绑定，通常一人一岗）分开。

### 2.2 流程模型：活动 + 路由，处理人六类来源

流程由 **活动（Activity，节点）** 与 **路由（Route，连线）** 组成。人工活动的处理人求解支持六类来源：

1. **用户标识** —— 指定具体人员（张三、李四）；
2. **组织** —— 指定组织节点，支持嵌套（如「开发部」下的所有人）；
3. **群组** —— 指定群组，支持嵌套（如「各部门领导」）；
4. **职位（职务）** —— 按组织动态求值：**张三所在部门的领导是 A、李四则是 B**，同一流程模板适配全公司，无需为每个部门单独配置；
5. **流程数据** —— 引用表单 / 路由上产生的选择变量（常见套路：路由上设 `creatorLeader` 选择变量 → 活动处理人引用它）；
6. **脚本** —— 用脚本 `return` 最终处理人。

求解结果会做**递归解析**，得到一个**身份数组**（多人），再按节点的**处理模式**落地：
`单人(single) / 并行(parallel) / 顺序(queue) / 抢办(grab)`。

路由还可配：**条件脚本**（如按金额分流）、**选择范围**（按组织选 / 按职务选）、**默认选中人**。

### 2.3 权限与流程的挂接点

- 角色可挂**个人成员 / 群组成员**，从而「一个组织加入某角色 → 该组织所有人继承该角色权限」。
- 流程应用可配：**启动人 / 启动组织**（谁能发起）、**管理者 / 流程实例维护人**（后者的可选范围支持**身份、职务、角色、群组**四种）。
- 还有「**待阅**」概念：不需要审批但要知晓的人 —— 这是「知会 / 抄送」的标准做法。

### 2.4 对我们最有借鉴价值的四点

1. **职务是「人」与「规则」之间的唯一中间层**，流程与权限都以它为锚 —— 直击我们的 27/8/3 三口径分裂。
2. **处理人以「身份」而非「人」记录** —— 天然支持兼职与跨组织，且审批留痕能说清「以什么身份审的」。
3. **处理人来源可组合**（组织 / 职务 / 群组 / 脚本），而不是我们现在这种硬编码 `switch`。
4. **「待阅」**把「要知晓」与「要审批」分开 —— 恰好用来化解「一级审批后上级不知情」的副作用。

## 3. 差距分析

| 维度 | O2OA | 本系统现状 | 差距 |
|---|---|---|---|
| 人的组织归属 | 身份 Identity，一人多身份 | `org_member` 一人一行 | **缺身份层**，无法表达兼职 / 跨机构 |
| 职务 | 一等实体 Duty，多职务可选 | `job_title` 自由文本，引擎不读 | **缺职务字典**，负责人无权威事实源 |
| 部门负责人 | 职务 + 组织动态求值，可正/副职多人 | `leader_user_id` 单坑位，39 部门仅 8 个配 | **单点、覆盖率低、无多负责人** |
| 角色 | 可挂个人 / 群组 / 组织，支持继承 | `sys_user_role` 全局，仅个人 | **无组织维度、无继承** |
| 审批人求解 | 六类来源可组合 + 脚本 | 硬编码 `switch` 六种枚举 | **不可扩展**，新增口径必改代码 |
| 审批层级 | 节点 + 路由 + 条件，任意拓扑 | `steps_json` 顺序链 + 阈值跳级 | **缺分支 / 并行 / 知会** |
| 申请人 | 可为组织（启动组织） | 仅 `sys_user` | **缺部门申请主体** |
| 层级深度 | 由流程图决定 | `APPLICANT_SUPERIOR` 固定展开整链 | **缺「向上几级」参数** |
| 知会 | 待阅（不需要审批但要知晓） | 无 | **缺知会能力** |
| 处理模式 | 单人 / 并行 / 顺序 / 抢办 | 仅顺序单人 | 缺并行 / 抢办 |

## 4. 改造方案

### P1 · 审批层级：引入「申请人类型 + 层级深度」

**目标**：普通用户申请 → 部门负责人一级；部门申请 → 上一级（机构管理员）。

**做法**：给 `APPLICANT_SUPERIOR` 节点增加 `levels` 参数（**缺省 = 整链，向后兼容**），并引入申请人类型。

```jsonc
// 普通成员申请权限：只走部门负责人一级
{"seq": 1, "approver_type": "APPLICANT_SUPERIOR", "levels": 1}
```

引擎侧改动点（`ApprovalFlowService`）：

1. `parseSteps()` 增加解析 `levels`（默认 `null` = 整链）；
2. `expandNodes()` 的 `APPLICANT_SUPERIOR` 分支：`ladder = superiorLadder(...)` 后按 `levels` **截断**
   （`levels == 1` 取首个有效梯级）；
3. `superiorLadder()` 增加**申请人为部门**时的起算分支（见 P3）。

**语义表（改造后）**：

| 申请人身份 | `levels=1` 的审批人 | 说明 |
|---|---|---|
| 普通成员（本部门） | 本部门负责人 | 用户要求 ① |
| 部门负责人（代表本部门） | 机构管理员（企业管理员） | 用户要求 ② |
| 机构管理员 | 租户管理员 | 逐级向上 |
| 租户管理员 | 平台管理员 | 租户内已无上级 |

> **前置硬约束**：一级审批的前提是**部门负责人必须配全**。当前 39 个部门只有 8 个有
> `leader_user_id`，若此时切到一级，`resolveDeptLeader` 会走**兜底改派**给机构管理员 ——
> 表面上「能审批」，实际是兜底副作用（V39 已验证过这个陷阱）。
> 因此 **P2 的数据治理是 P1 的准入条件**，两者必须同批上线。

### P2 · 组织关联：补齐「职务 + 身份」，把「负责人」变成一等事实源

这是回应「关联过少、衔接不紧密」的核心。三步走：

**P2-1 职务字典（复刻 O2OA 的 Duty）**

新增 `org_duty`（租户级字典）：

```sql
CREATE TABLE org_duty (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  code VARCHAR(32) NOT NULL,          -- DEPT_PRINCIPAL / DEPT_DEPUTY / ORG_LEADER …
  name VARCHAR(64) NOT NULL,          -- 部门正职 / 部门副职 / 机构负责人
  duty_rank INT NOT NULL DEFAULT 1,   -- 排序：正职 1、副职 2，用于「取第一个"
  can_approve TINYINT NOT NULL DEFAULT 1,  -- 该职务是否可作为审批人
  status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  UNIQUE KEY uk_tenant_code (tenant_id, code)
);
```

给 `org_member` 增加 `duty_code VARCHAR(32) NULL`（**与 `job_title` 并存**：`job_title` 保留为展示文案，
`duty_code` 作为机器可读口径）。一个部门可有**多个** `DEPT_PRINCIPAL` / `DEPT_DEPUTY`。

**P2-2 身份（复刻 O2OA 的 Identity）**

`org_member` 本身就是「人 × 机构」的关系行，改造成本低：为它补 `is_primary TINYINT`
（主身份）与 `job_rank`，并把「部门内的职务」显式化（`department_id` + `duty_code`）。
这样一人可在多个机构各有一个身份行，审批留痕时记录「以哪个身份审的」。

**P2-3 审批人解析可组合化**

把 `expandNodes()` 里的 `switch` 抽成 `ApproverResolver` 策略接口，新增两类（对应 O2OA 的「职位」）：

| 新类型 | 语义 | 求值 |
|---|---|---|
| `DEPT_DUTY` | 申请人**所在部门**的某职务（如 `DEPT_PRINCIPAL`） | `org_member where department_id = 申请人部门 and duty_code = ?` |
| `UNIT_DUTY` | **指定组织**的某职务（复刻 O2OA 的「职务 + 组织参数」） | 同上，组织由参数给定 |

**兼容规则**：`DEPT_LEADER` 保留，但其实现改为**先查职务、再回落到 `leader_user_id`**，
从而让 27 人的 `job_title` 口径逐步收敛，而不是一次性推翻。

### P3 · 「部门」作为申请主体

**数据模型**：`approval_order` 增加两列

```sql
ALTER TABLE approval_order
  ADD COLUMN applicant_type VARCHAR(16) NOT NULL DEFAULT 'USER',  -- USER | DEPARTMENT
  ADD COLUMN applicant_department_id BIGINT NULL;
```

- `applicant_type='DEPARTMENT'` 时，`user_id` 仍记录**提交人**（部门负责人），
  但 `applicant_department_id` 标识「这是部门的名义申请」，审批链起点 = **该部门的上级**（机构管理员）。
- 权限申请入口扩展：`ApplyReq` 增加 `applyAsDepartment`（布尔）+ `departmentId`，
  仅**该部门负责人**可发起（`OrgGuard` 增加 `requireDeptLeader(departmentId)`）。

**审批链**：`superiorLadder()` 检测 `applicant_type='DEPARTMENT'` 时，起算层级取
**该部门所属机构**（而不是「部门负责人的个人层级」），从而实现「部门申请 → 向上级审批」。

### P4 · 知会（待阅）：化解「一级审批后上级不知情」

一级审批把成员申请止于部门负责人，机构管理员将不再收到（这正是 V39 要解决的问题）。
按 O2OA 的**待阅**做法，把「审批」与「知晓」拆开：

- `approval_task` 增加 `task_role VARCHAR(16)` ∈ `APPROVE | CC`（默认 `APPROVE`）；
- 节点可配 `"cc": ["ORG_ADMIN"]` —— 生成 `CC` 任务，**不阻塞流转**、只出现在「抄送我的」列表并推送通知；
- 用户端「待办」增加「抄送我的」分区；机构管理员因此**可见、可督办，但不需要审批**。

这比「把链拉长」更符合用户诉求：**审批要快，知情要全**。

### P5 · 数据治理（与 P2 同批执行）

把 27 / 8 / 3 三个口径收敛为一个，做法：

1. 新增 `V41` 迁移：建 `org_duty` + 给 `org_member` / `approval_order` 加列（DDL）；
2. 新增 `V42` 回填迁移：
   - `org_member.duty_code` ← 按 `job_title` 含「负责人」的规则回填（27 人 → `DEPT_PRINCIPAL`）；
   - `org_department.leader_user_id` ← 回填为空但部门内有 `DEPT_PRINCIPAL` 身份的行；
   - 为所有 `duty_code='DEPT_PRINCIPAL'` 的账号补授 `ROLE_DEPT_LEADER`（3 → 27）；
3. 迁移**只补空、不覆盖**已有显式配置（与 V26 播种器同一纪律）。

> 回填后 `ROLE_DEPT_LEADER` 从 3 人升到 27 人，会影响以角色为断言的既有套件

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **口径反转**：一级审批会让机构管理员收不到成员申请（与 V39 的结论相反） | 用户此前明确反馈过该问题 | 建 `CC` 知会节点（P4），做到「不审批但可见可督办」；并把层级深度做成**按租户 / 按业务类型可配**，而非全局写死 |
| 部门负责人未配全就切一级 | 兜底改派把审批悄悄转给机构管理员（伪装成能用） | P2 数据治理为 P1 准入条件；引擎对「兜底改派」保留 `task.note` 显式标记，并在待办列表提示 |
| 回填 `ROLE_DEPT_LEADER` 放大权限面 | 27 人获得部门级管理能力 | 角色与**数据范围**同时校验（`data_scope=DEPT` 已存在），授角色不改范围；回归 `e2e_admin_personnel_scope` / `e2e_worker_permission` |
| 三口径并存期 | 迁移途中「谁是负责人」仍可能不一致 | `DEPT_LEADER` 解析改为「先职务后回落」，两个口径取并集；迁移后跑一致性校验脚本 |
| `sys_user_role` 无组织维度 | 一人在两机构角色不同无法表达 | 短期用 `org_member.duty_code` 承载部门级差异；中期再把 `sys_user_role` 升级为「角色 × 机构」 |

## 7. 分期计划

| 期 | 内容 | 可独立验收 |
|---|---|---|
| **一期** | P2 数据治理（职务字典 + 回填 + 角色补齐）→ P1 层级深度 + 迁到一级 | 普通成员申请只到部门负责人；部门负责人申请到机构管理员 |
| **二期** | P3 部门作为申请主体 | 「以部门名义申请」落库并在审批链向上走 |
| **三期** | P4 知会 / 待阅 | 机构管理员在「抄送我的」看到成员申请，但不占待办 |
| **四期** | P2-3 解析器策略化 + `DEPT_DUTY` / `UNIT_DUTY` | 流程模板可跨部门复用，人员变动不改流程 |
| **五期** | 并行的处理模式（single / parallel / grab）与条件路由 | 复杂审批拓扑（如按金额分流） |

**分期依据**：一期同时解决「关联过少」（P2）与「一级审批」（P1），二者互为前提；
二 / 三期补齐用户明确提出的「部门申请」与「上级知情」；四 / 五期是把 O2OA 的通用能力补齐，属长期演进。

## 8. 验收标准

1. 普通成员提交权限申请 → `timeline` **恰有 1 个**有效节点，审批人 = 本部门负责人（不再出现机构管理员兜底改派）；
2. 部门负责人（或部门名义）提交 → 首节点 = 机构管理员，且 `applicant_type='DEPARTMENT'` 可查；
3. 机构管理员在「抄送我的」看到该单，`/workflow/tasks?scope=todo` **不**包含它（CC 不阻塞）；
4. 「谁是部门负责人」在职务 / `leader_user_id` / `ROLE_DEPT_LEADER` 三个口径下**一致**（一致性校验脚本 0 差异）；
5. 39 个部门的 `leader_user_id` 覆盖率 100%（或显式标记「本部门暂不设负责人」）；
6. 既有回归全绿，且新增用例覆盖：一级链、部门申请、CC 不阻塞、兼职身份。
