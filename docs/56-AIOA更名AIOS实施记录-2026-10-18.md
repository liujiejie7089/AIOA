## 三、三处技术陷阱（都已处理，勿重踩）

### 3.1 Flyway 历史迁移脚本**不能跟着改名**
批量替换改到了 32 个 `V*.sql`（多数只是注释里的「AIOA」），但 **Flyway 会对已执行的迁移做 checksum 校验**，
一旦内容变化，生产启动直接 `Migration checksum mismatch` 拒绝启动。

处理：把这 34 个文件（32 个 + 2 个被间接改动）**按 HEAD 逐字节还原**。
判据：`git diff --cached -M --numstat -- 'server/*/db/migration/*.sql'` 输出
`88 files changed, 0 insertions(+), 0 deletions(-)` —— 即 88 个迁移全是**纯路径改名、内容零变化**。
历史迁移里保留的旧品牌字样属「历史记录不可变」，新语义请写新迁移，不要回改老迁移。

### 3.2 运行中的后端会锁住 `server/aioa-boot/target/`
目录整体改名时报 `Permission denied`：`java.exe` 正持有 `aioa-boot-0.1.0-SNAPSHOT.jar`。
处理：不杀进程，改为**把 `pom.xml`/`src`/`uploads` 搬进 `server/aios-boot/`**，只留 `target/` 在旧目录。
收尾：停掉后端后删除空壳目录 `server/aioa-boot/`（目前仅剩 target）。

### 3.3 本环境 `git update-ref` 静默失效
`git checkout -b rename/aios` 得到的是**未出生分支**（HEAD 指向的 ref 没有写出来），
`git update-ref` 返回 0 但 `.git/refs/heads/rename/aios` 并未创建，导致 `git rev-parse HEAD` 报
`unknown revision`。手工写入 ref 文件后恢复：
```bash
mkdir -p .git/refs/heads/rename
printf '%s\n' <main-commit-sha> > .git/refs/heads/rename/aios
```
遇到「分支明明切了却说没有提交」先查 `git rev-parse HEAD`，不要怀疑工作区。

### 8.2 三个「以为要重建、其实不用」的结论

1. **`agent/.venv` 直接拷贝可用**。Windows venv 的 `python.exe` 是**按自身所在路径**推
   `sys.prefix` 的，`pyvenv.cfg` 里的 `home` 指向的是基础解释器（没搬）。
   只有 `Scripts/*.exe`（pip/uvicorn 这些 console script）的 shebang 写死了旧路径会失效 ——
   而 `start-all.sh` 用的是 `$ROOT/agent/.venv/Scripts/python.exe -m uvicorn`
   ⇒ **不受影响**。实测：`faster_whisper 1.2.1` 可导入，agent 启动日志
   `asr model loaded: D:\aios\agent\.models\small`，`/health` → `{"status":"UP"}`。
2. **`mvnw -o package` 离线成功**。`~/.m2` 在 C 盘没搬，依赖不用重下 ⇒ 13 模块全绿，
   jar 106M，启动 14.4s。
3. **`.git` 直接可用**，`HEAD=main`、`7fe7721` 在，工作区只报我改的那 7 个文件。
   `.git/config` 无绝对路径（`core.worktree` 没写死），无需 `git worktree repair`。

### 8.4 前端依赖的坑（`pnpm install` 三次未成，改整目录拷贝）

| 尝试 | 结果 |
|---|---|
| `pnpm install --offline` | `ERR_PNPM_NO_OFFLINE_TARBALL`（`@types/node-22.20.1` 等缺失） |
| `pnpm install`（默认 registry） | 9m50s 仅写 251K，`registry.npmjs.org` 元数据单请求 8.7s |
| `pnpm install --registry npmmirror` | 13m 仍停在 ~89M，放弃 |
| `pnpm install --offline --store-dir <C盘真实store>` | 19m 停在 72M，放弃 |

**根因**：pnpm 10 **把 store 默认放在「项目所在盘」** ⇒ 项目搬到 D 盘后默认 store 变成
`D:\.pnpm-store\v10`（空白）；真正的 store 在 `C:\Users\刘尖尖\AppData\Local\pnpm\store`（170M）。
指过去之后仍要跨盘 import（= 逐文件复制 + 重算索引），而本机 D 盘小文件写入仅 ~70KB/s。

**最终处置：`web/node_modules` 本次未恢复**（源码 + `dist` 产物齐备，管理端照常服务）。
需要重新构建管理端时在 `D:\aios\web` 自行装：

```bash
cd /d/aios/web && pnpm install --registry https://registry.npmmirror.com
```

为什么没有硬拷：pnpm 的 `node_modules` 是**符号链接森林**（`node_modules/<pkg>` → `.pnpm/<pkg>@<ver>/…`，
依赖之间再互相链），
- `/SL` 保留链接 ⇒ 逐条建链，本机 32 分钟只走了 41M 后停住；
- 跟随链接 ⇒ 同一份包被复制 N 次，体积爆炸；
- 先拷 store 再让 pnpm 硬链接 ⇒ 沙箱对大目录批量写有闸门（`cp -a files/` 直接被 SIGTERM，
  只有单分片能过）。

判据：`ls -A web/node_modules | wc -l` = 0 就是没有。**别再试第 4 遍**。

### 8.6 一条容易踩的坑：管理端临时 webroot 消失 ≠ 迁移弄坏了

`%LOCALAPPDATA%\Temp\aios-webroot` 会被系统清理，本次搬完就发现没了（`/aios/web/` 404）。
从 `web/apps/*/dist` 重新组装即可（`index.html` + `assets/` + `subapps/<name>/`）。

⚠️ **组装完必须重启后端**：静态目录是在**启动时**解析的，目录后建出来不会自动生效
（实测：组装后仍 404，重启后同样的 URL 立刻 200）。`start-backend.bat` 的前置检查
（缺 `index.html` 就打 `[WARN]`）就是为这个场景写的，别把它当成无关的啰嗦。
