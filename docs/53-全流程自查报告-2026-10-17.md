# 全流程自查报告（11 项痛点逐条判定）

> 日期：2026-10-17 · 范围：用户端 H5 / Python agent(`agent/aioa_ai`) / Java 后端(`server/`) / 管理端(`web/apps/shell`)
> 方法：**只读代码取证 + 活体接口实跑**。每条给「判定 → 依据（file:line 或真实返回）→ 方案」。
> 判定口径：**已解决**＝机制接通且有活体证据；**部分**＝有能力但没接到该业务上，或只覆盖了一部分场景；**存在**＝该能力在代码里找不到。

## 1. 数字人不会自动发起 OA 流程 —— 已解决（有活体证据）

**机制**：模型调 `request_form` → 图在 `clarify` 节点 `interrupt()` 暂停 → Java 补全字段发 `need_form` → 用户在卡里提交 → **后端自动建审批单** → 回执续跑。

- `agent/aioa_ai/tools/request_form.py:11-17`：agent 只产出 `{form_code, reason, prefill}`，**不发任何写接口**（HITL 纪律：确认归 UI）。
- `server/.../FormSubmissionService.java:112-121`：`submit_policy` 含 `APPROVAL` ⇒ `invokeApproval()`，回写 `approval_order_id` 与 `STATUS_APPROVING`；异常则回写 `FAILED` 并抛出（不静默成功）。
- `server/.../RunService.java:901,1013`：APPROVAL 模板的按钮文案是「提交审批」。

**活体证据（本次实跑 `scripts/_verify_form_flow.py`，24/24 通过，自清理 0 残留）**：

```
D1 提交进入审批中（APPROVING） — submissionId=15 status=APPROVING resume=true
D2 生成审批单（approvalOrderId 非空） — orderId=1058
D4 审批任务已生成 — (1488, 'DEPT_LEADER', 15, 'PENDING')
E3 驳回后 form_submission 回写 REJECTED（ApprovalOutcomeSink 真跑通）
G1 本套件数据已删干净 — 残留=0
```

**注意**：审计初查时 `form_submission` 是 **0 行**（从未有人真提交过），所以「不能自动发起」的印象可能来自「从没跑通过一次」，而不是机制缺失。

**方案**：无需改代码。**要补的是「让模型知道有哪些表单」**——见 §6 残留 A，这是当前闭环最脆的一环。

## 2. 业务规则校验偏弱，只有文字提醒 —— 存在

**判定：能力有，但没接到业务规则上。**

- `FormSchemaValidator.java:53-235`：只认 `type/required/min/max/maxLength/pattern/enum`。**无 if-then、无跨字段、无角色感知**。
- `FormTemplate.java:30-64`：`form_template` **没有 rules 列**，`schema_json` 只承载字段结构。
- `ask_user.py:24-53`：结构化单选分支**已具备**（`suggested_options`，`_as_options` 硬截断 6 个）。
- 但全仓 grep：`ask_user` **只由模型主动调用**，没有任何「检测到规则冲突 → 强制走结构化分支」的代码点。
- 「普通员工用部门章盖对外合同」这类语义冲突：**不在校验器、不在提示词、不在数据库约束**——三层都不拦。

**方案（P0）**：
在 `form_template.schema_json` 增加 `rules[]`，形如
```json
{"when": {"seal_scope": "DEPT", "counterparty": "EXTERNAL"},
 "then": {"block": true, "options": [{"value":"UPGRADE_ORG_SEAL","label":"改用机构章并走机构审批"},
                                     {"value":"CANCEL","label":"取消本次用印"}]}}
```
执行点**唯一**：`FormSubmissionService.submit()` 校验通过后、分流之前；命中 `block` 则返回 `code=400` + `options`，H5 直接把它们渲染成已有单选卡（复用 `ask_user` 的卡片，不新建 UI）。

## 3. 缺强制信息汇总确认节点 —— 存在

- `user-client/index.html:6595-6673` `mountFormCard`：点 `data-form-submit` → `validateForm` → `API.formSubmit`，**一跳到底**。
- `showReceipt` 在提交**之后**才出现（`:6614/6637`）——那是回执，不是确认。
- agent 侧 `nodes.py` 也没有 confirm 节点。

**方案（P0）**：提交按钮改两段式。`index.html:6624` 处先渲染 `formSummaryHtml(values)`（按字段 `title` 逐行列出「标签：值」），按钮文案改「确认提交」，二次点击才调 `API.formSubmit`。
判据：**汇总卡的每一行取自同一份 `values` 对象**，不得二次读 DOM（否则改了值不刷新，属铁律 12 的同源问题）。

## 4. 收集字段方式不稳定 —— 部分解决

- `request_form.py:28-59`：一次只请求一张表单，字段由 DB schema **整表渲染** ⇒ 「一次性抛一堆问题」这条在表单链上已不存在（整表本就该一次给全）。
- `ask_user.py:24-53`：强制「一次只问一个问题」，选项 2~6，代码硬截断。
- 残留：**同一轮可连续多次调 `ask_user`/`request_form`，没有次数上限**；提示词里没有「本轮至多一次」的硬约束（只有工具 description 的软约束）。

**方案（P2）**：在 `graph/nodes.py` 的 `clarify` 路由上加硬闸——本轮已发过澄清就丢弃后续澄清调用（与 `filter_intent_write_tools` 同款「确定性代码门」）。

## 5. 职责隔离/跨业务路由缺失 —— 部分存在

- **唯一跳转实现**（纯前端）：`_oa_app.js:2360 oaAfterOaAnswer` → `:1994 oaMaybeLeaveAction` → 命中 `APPLY_LEAVE` 且 `held===true` 时按 `intent.role` 找 worker → `:2010 oaPickWorker`。**不调任何后端路由接口**。
- 全仓 grep `handoff / next_worker / routeTo / switchWorker`：**0 条真实路由调用链**（`targetWorkerType` 是权限申请字段，不是路由）。
- 职责边界**有**：`intake.py:104-135` 每个角色带 `boundary`（如「不解答与请假无关的业务问题」），并由 `builder.py:156` 注入提示词。但只教「拒答」，**没教「转给谁」**（prompt 目录搜「转交/移交/另一个数字人」0 命中）。
- 影响面：**42 个模块（用印、报销…）完全没有路由能力**。

**方案（P1，与 §8 合并做）**：`intake.py` 的 `_ROLES` 增加 `routeTarget`（workerType），`classify()` 一并返回；H5 用通用分支替换 `APPLY_LEAVE` 硬编码；提示词 `boundary` 补一句「超出职责时请切换到对应数字人」。

## 6. 表单写死在提示词/Agent —— 基本解决，残留 3 处

**已解决的部分（有据）**：
- Schema 唯一事实源：`V85__form_domain.sql:15` `schema_json JSON NOT NULL`；现有 **516 张表单 / 43 个模块**（`LEDGER 504 + APPROVAL+RESUME 12`）。
- agent **零字段**：`request_form.py:11-13` 明确「agent 无此数据源，绝不生成 fields[]」；`intake.py:99-103` 注释写明「谁再写死字段就制造第二份真相」。实测 `_ROLES` 的 `formFields` 恒为 `[]`。
- 字段由 Java 补：`RunService.java:965-968` 单一补全点。
- 管理端**有**可视化设计器：`FormDesignerView.vue` + `router/index.ts:160` + `FormController`（`POST/PUT /api/v1/forms`，改表单**不用发版**）。

**残留 A（P0，最要紧）**：**表单清单没有下发给模型**。
`request_form.py:34,43` 的工具描述写着「form_code 必须来自当前可用表单清单」，但我在全仓搜 `form_catalog / available_forms / 表单清单`，**只有这 3 行描述本身命中**；`agent/aioa_ai/contracts.py` 的 `RunRequest` 也没有表单相关字段。
⇒ 模型只知道一个示例 `leave_request`。**结果是它要么不敢调、要么调错码**，而错码会走到 `RunService.java:990` 的「表单定义不存在」。**这条不补，§1 的闭环就只能靠运气。**
修法：Java 在 buildRequest 时注入 `available_forms: [{code,name,moduleCode}]`（按当前 worker/租户可见性过滤），agent 拼进系统提示；或 agent 启动时拉一个 `/internal/v1/forms` 清单（需新增内部接口）。

**残留 B（P2）**：`WorkerIntakeService.java:79-83` `ROLE_FORM_CODE` 硬编码 3 个 form_code（`leave_request/knowledge_upload/doc_draft`）。与库同源，风险低，但应下沉到配置。

**残留 C（P1）**：`FormSchemaValidator` 不校验 `additionalProperties:false` ⇒ AI 若传了 schema 之外的 key，**不报错、也不会入库**（被忽略）。要堵「编造字段」，需显式拒绝，而不是静默丢弃（静默丢会让人以为字段生效了）。

## 7. 跳转后上下文丢失 —— 存在

三处断点，缺一不可：

1. **换人就作废会话**：`_oa_app.js:1569` `if(!S.worker || w.id !== S.worker.id){ S.convId = null; oaAnswerSeq++; }` → 随后 `oaEnsureConv:1590` 按新 `workerId` **新建 conversation**，旧历史不带入。
2. **契约没有承载字段**：`agent/aioa_ai/contracts.py` `RunRequest:44-73` 只有 `run_id/conversation_id/text/attachments/context/user_context/history/scope/project/expert_settings/kb_on`，**没有** `upstream_summary / source_worker / prefill`。Java `CreateRunRequest` 同样没有。
3. **表单卡不支持预填**：`index.html:6595 mountFormCard(host,p,opts)` 只消费 `opts.standalone` 和 `state.conversationId`；全段搜 `prefill/initialValue/defaultValue` **0 命中** ⇒ 姓名、工号必须重填。

**方案（P1）**：
- 契约加三字段：`upstream_summary:string`（跳转时由 H5 用「用户原话 + 已收集字段」生成，**裁剪到 500 字以内**）、`source_worker:{id,type,name}`、`prefill:{k:v}`。
- Java `CreateRunRequest` 透传 → agent `builder.py` 把它注入系统提示（用已有的 `_wrap_field` 包裹，防注入）。
- `mountFormCard` 增 `opts.initialValues`，`collectFormValues` 以它为默认值。
判据：跳转后 B 数字人的**第一条回答**必须能引用 A 里的原话（不能只说「你好，请描述需求」）。

## 8. 没有统一调度中心 —— 存在（四项全无）

| 应有能力 | 现状 |
|---|---|
| 跳转中转层 | **0 命中**。`tools/orchestrator.py` 是**同一层工具子任务并发**编排（ADR-003），与数字人跳转无关 |
| 跳转审计日志 | **0 命中**。搜 `transfer/handoff/delegate` 只命中审批「转办」与机构管理员转移 |
| 次数限制/循环检测 | **0 命中**。搜 `max_hops/hop_count/visited` 只命中部门树 `depth`、HTTP `Transfer-Encoding` |
| 统一权限管控 | 只有会话创建层的 403 准入（`_oa_app.js:1600` 注释），非调度层 |

⇒ 「请假 ↔ 用印 来回跳」在代码上**没有任何东西能挡住**。

**方案（P1，建议与 §5/§7 一起做成一个 PR）**：
1. 后端新增 `WorkerRouter`（`aioa-chat`）：入参 `{fromWorkerId, intent, context}`，出参 `{toWorkerId, hop, routeId}`。**唯一判定点**。

3. 硬闸：`hop >= 3` 或 `to_worker ∈ visited` ⇒ 拒绝并回一条固定话术（不进模型，避免模型自己救场）。
4. H5 删掉 `oaMaybeLeaveAction` 里的 `APPLY_LEAVE` 硬编码，改调 `POST /api/v1/workers/route`。

## 9. 上下文无裁剪 —— 部分（有 10 轮硬上限）

- `RunService.java:128` `HISTORY_TURNS = 10`；`:605` `.last("limit " + HISTORY_TURNS)` ⇒ **只发最近 10 轮**给 agent。
- `agent/aioa_ai/llm/__init__.py:40` `max_context: int = 0  # 0=不限制`；`builder.py:282-296` 只有 `max_context>0` 才按字符预算（`max_context*2`）从最旧开始丢。
- 实库 `model_config`：只有 MiniMax(`is_default=1`) 是 `200000`，其余 6 个模型 `max_context=0`。
- 摘要压缩：搜 `compact/summary(历史)` **0 命中**。

**结论**：不是「几十轮全量透传」——**上限是 10 轮**。真实风险是「10 轮里全是长文档/长表格」时没有 token 预算，且系统提示会随 scope/action 规则膨胀。

**方案（P2）**：① 给默认模型显式填 `max_context`（机制已就绪，改配置即可）；② 若要更省，把 `HISTORY_TURNS` 从「轮」改成「token 预算」，并在超限时对最旧轮做一次摘要（新增一个 `compact` 节点，只在裁剪时触发）。

## 10. 字段 key 兼容 —— 部分（脏数据会入库）

- `FormSchemaValidator.java:53-110`：只遍历 `schema.properties` 校验，**从不遍历提交 data 的 key** ⇒ 多出来的 key 校验直接放行。
- `FormSubmissionService.java:96` `sub.setDataJson(objectMapper.writeValueAsString(data))` ⇒ **未知 key 原样入库** `form_submission.data_json`。
- 映射/别名机制：搜 `mapping/alias/fieldMap/keyMap/rename` 在**表单字段层 0 命中**（命中的都是 SQL 表别名、工具组别名）。
- H5 侧 `collectFormValues` 用 `data-field`（＝schema 字段名）构造 payload，无 UI 前缀 ⇒ **前端不会污染**，脏数据只会来自 API 直调或上游预填。

**方案（P1）**：在 `FormSubmissionService.submit()` **落库前**做一次白名单裁剪：`data.keySet().retainAll(schema.properties.keySet())`，并**记录被丢弃的键到日志**（静默丢会让人以为生效）。若要做「上下游字段复用」，再在 schema 里加 `x-alias`，由同一处解析——**不要**在 H5 或 agent 里各写一份映射。
