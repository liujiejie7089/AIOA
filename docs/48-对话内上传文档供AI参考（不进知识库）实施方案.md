### 与 docs/46 设计稿的关键偏离（务必分清）

`docs/46` §1 把「对话内上传文档」设计成**知识库通路**：普通对话 `POST /api/v1/kb/documents/upload`（scope=PERSONAL）、项目内双写「项目文档库 + 知识库登记」。本次**没有**按这条路走，而是改成了**不进知识库**的参考文档通路：

- 前端只把「通用文件上传」拿到的 **file id 数组**随 `CreateRunRequest.attachments` 下发；

- **全程零 KB 持久化**：不写 `kb_document` 等表、不参与任何 `/v1/kb/*` 检索。

## 0. 需求与边界

### 0.1 要做什么

用户在与 AI 对话时，通过对话栏「＋」上传一份文档，**本轮及本会话后续轮次**的 AI 回答都能参考该文档内容；**不写入知识库**，不污染其它会话与全局检索面。

### 0.2 边界（判据明确，避免「看起来像知识库」的误解）

- **不进知识库**（硬判据）：
  - 不写 `kb_document` / `kb_chunk` / `kb_vector` 等任何 KB 表（`RunService.resolveAttachments` 只用 `KbFileParser` 做**纯解析**，不调用任何 KB 持久化）；
  - 不参与 `/v1/kb/*` 检索（agent 的 `attachment_docs` 是 system 提示里的独立上下文块，**不走** `ToolGatewayService.searchKb`）；
  - 其它会话、其它用户**不可见**（落库在 `chat_message.attachments`，按 `conversation_id` 隔离，随会话走）。
- **可见性 = 该会话专属（重开本会话仍可用）**：解析快照随本轮 user 消息落 `chat_message.attachments`；历史轮回填时 `formatAttachmentDocs` 把正文**前置**到该轮 user content，所以「重新打开会话后 AI 仍看得到文档」成立。
- **两条不同通路（对照）**：这与「知识库上传」`/v1/kb/documents/upload` 是**完全两条路**——后者写 KB 表、进全局检索、跨会话可见；本功能不写 KB、仅会话内参考。

### 0.3 与 docs/46 的关系

`docs/46` §1 是原设计稿（KB 路由方案），**本次未采用**。本文是实际落地（不进知识库）。两者不要混淆：若有人照 docs/46 §1 去「双写进知识库」，与本实现正交且会带来 `docs/46` §5-Q4 的「删除联动」负担——本实现天然不需要，因为根本不落 KB。

## 1. 端到端链路（三层，各司其职）

```
用户浏览器(H5)                  Java aios-server (:8080)              Python agent (:8000)
─────────────────              ──────────────────────────           ────────────────────
点「＋」→ 选文件
   → 先走通用文件上传（FileController）拿到 file id
   → 暂存到 pendingFiles[]
   → send() 时把 id 数组带上
        │ POST /api/v1/conversations/{id}/runs
        │   body.attachments = [fileId,...]   （非空才写）
        └──────────────────────► RunService.start()
                                  │ 落 user 消息 + 调 resolveAttachments(ids)
                                  │  查 SysFile → 同源落盘路径读字节
                                  │  → KbFileParser.parse 抽正文
                                  │  → 每份截断到 VIEW_MAX_CHARS(20000)
                                  │  → 快照存 chat_message.attachments(JSON)
                                  │ subscribe()：当前轮把快照作为 attachment_docs 下发
                                  │  历史轮：loadHistory 用 formatAttachmentDocs 把正文
                                  │          前置回该轮 user content
                                  ▼
        ◄── SSE 流（AI 回答） ◄── POST /internal/v1/runs
                                  │   request.attachment_docs = 快照
                                  ▼
                              agent_runtime._build_messages：
                               无附件 → 逐字一致（不加块）
                               有附件 → 每份渲染成
                                 【参考文档】《name》
                                 {正文}
                                 【以上为参考文档】
                               正文经 _neutralize_injection() 中和（按不可信输入对待）
                               追加到 system 提示末尾
```

**为什么落盘路径要「同源」**：H5 上传走 `FileController`，存到 `aios.upload.dir`（默认 `./uploads`）下的 `storedName`；`RunService.resolveAttachments` 用**同一** `uploadDir`（`Paths.get(uploadDir).toAbsolutePath().normalize().resolve(storedName)`）读回字节——任何一边改了存储根目录，另一边必须同步，否则「文件已不存在」。

## 2. 契约

### 2.1 前端 → 后端

```
POST /api/v1/conversations/{id}/runs
{
  "text": "请解析我上传的文档",
  "context": { ... },                 // 页面上下文快照（既有）
  "attachments": [ 101, 102 ]         // ★ 新增：通用文件上传拿到的 file id 数组（Long）
}
```
- `attachments` 为 `List<Long>`（`CreateRunRequest.java:22`）；**非空才写进 body**，旧的三参 `createRun` 调用完全不变。
- 后端 `start()` 仍要求 `text` 非空；H5 侧在「只传文档不写字」时补默认话术「请解析我上传的文档」（`_backup_index_pre_oa.html:4551` / `_oa_app.js:1582`），**不是**放宽后端。

### 2.2 后端 → agent（结构化下发形状）

```
RunRequest.attachment_docs: [
  { "file_id": 101, "name": "报告.pdf", "text": "<解析正文>", "truncated": false },
  { "file_id": 102, "name": "数据.xlsx", "text": "", "error": "文件已不存在" }   // 失败项
]
```
- 正常项：`{file_id, name, text, truncated}`；单份失败：`text:""` + `error`，记 `log.warn`，**不上抛、不拖垮整轮对话**（铁律 2）。
- agent 侧 `AttachmentDoc`（`schemas.py:31-41`）字段一一对应；`RunRequest.attachment_docs` 为 `list[AttachmentDoc] | None`（`schemas.py:52`）。
- **历史轮不传 `attachment_docs`**：历史轮只能回填文本（agent 不回放结构化附件），故 `loadHistory` 在 Java 侧把正文前置进 `content`，agent 看到的只是「已含参考文档正文的 user content」。

### 2.3 截断常量（单一来源）

| 常量 | 位置 | 值 | 作用 |
|---|---|---|---|
| `KbController.VIEW_MAX_CHARS` | `aios-resource/.../controller/KbController.java:87`（`public`） | `20000` | 单份文档正文截断上限（Java 侧，被 `RunService` 复用，**单一来源**） |
| `_MAX_ATTACHMENT_CHARS` | `agent/app/core/agent_runtime.py:110` | `40000` | 所有附件正文**合计**上限，超出按顺序截断（agent 侧第二道保险） |

> `VIEW_MAX_CHARS` 改为 `public` 就是为了被 `RunService` 复用，避免「Java 侧又写死一份数字」的失真（吸取 `docs/42` 里 KB 大小限制「三处写死」的教训）。

### 2.4 支持的后缀（**10** 种，单一来源 = `KbFileParser.parse` 的 `endsWith` 分派）

`.pdf .docx .doc .xlsx .xls .txt .md .csv .json .log`

- 判据：`KbFileParser.java:53-69` 的 `endsWith` 分派**实际处理这 10 种**；H5 `accept`（`_backup_index_pre_oa.html:990` / `_oa_markup.html:47`）也列这 10 种——**前端与后端同源**。
- ⚠️ **计数提醒**：本功能相关简报里曾写「9 种」，但代码与 `accept` 均为 **10 种**（多了 `json`、`log`）；以本文 10 种为准。
- ⚠️ `KbFileParser.SUPPORTED` 常量串（`:41`）只列 8 种（漏 `json/log`），仅用于报错文案；不影响 `parse()` 实际支持 10 种（见「实施记录·未验证/遗留 3」）。

## 3. 两条投递路径的差异（当前轮 vs 历史轮）

| 路径 | 怎么做 | 为什么 |
|---|---|---|
| **当前轮**（结构化 `attachment_docs`） | `RunService.subscribe` 从已落库的 `ChatMessage.attachments` 取出，直接 `request.setAttachmentDocs(...)` 下发给 agent（`RunService.java:243-246`）；agent 渲染成独立 `【参考文档】《name》…【以上为参考文档】` 块追加到 system 末尾 | 当前轮消息刚落库，快照在手，最干净；agent 拿到结构化对象，便于做注入中和与总长截断 |
| **历史轮**（前置进 content） | `loadHistory` 对带附件的历史 user 消息，用 `formatAttachmentDocs` 把正文拼成 `【参考文档】《name》\n{正文}\n【以上为参考文档】\n\n` **前缀**，接到该轮 `content` 前（`RunService.java:474-479, 554-576`） | agent 的历史回放只收 `role/content` 字典，**不回放结构化 `attachment_docs`**；要让「重开会话后 AI 仍看得到文档」成立，只能在 Java 侧把正文回填进 content，让 agent 当普通 user 文本看到 |

**核心结论**：当前轮走「结构化 `attachment_docs`」，历史轮只能「回填文本」——这不是两条重复逻辑，而是 agent 历史协议（只回放 content）决定的必然分叉。两份渲染函数（`_build_attachment_block` 与 `formatAttachmentDocs`）都遵循同一套【参考文档】包裹格式，保证前后一致。

## 4. 安全性（文档正文按不可信输入对待）

- 文档是**用户上传的任意文件**，正文可能夹带「忽略前面的指令 / 你是…」之类的提示注入。agent 侧把每份 `attachment_docs.text` 经 `_neutralize_injection()` 中和（`agent_runtime.py:92-106` + `:131`）——命中 token-override 黑名单（`_OVERRIDE_PATTERNS`，`:60`）时剔除并记 `warn`，同时剥掉控制字符；**不拒绝请求**（保持产品行为），仅做降噪与越权防护。
- 这套 `_neutralize_injection` 与 user `text`、history `content` 用的是**同一道防线**（`agent_runtime.py:222, :243`），即「所有外部文本统一中和」的加固实践（同源防护，非为附件单独写判断）。
- Java 侧：`resolveAttachments` 单份失败**不 500、不拖垮整轮**（记录 `error` 项 + `log.warn`），符合铁律 2「不得静默，但也不上抛」。
- 不进知识库本身也是一道隔离：即使文档内容有误或含注入，也只影响「本次会话的这一轮上下文」，不会污染全局检索面或被其它会话读到。

> 背景引用：提示注入加固是本项目既有纪律；`_neutralize_injection` 的代码落点在 `agent/app/core/agent_runtime.py:92`，可对照阅读。

### 6.2 明确缺口（待办，**不要粉饰**）

1. **H5 端到端「＋」上传 → AI 真读到文档，没有自动判据**。上表只覆盖「后端解析」与「agent 注入」两段，没有一段把「前端选文件 → 上传拿 id → `createRun` 带 `attachments` → 后端解析 → agent 拼进 system → 回答确实引用」这条整链自动跑通。当前最可靠的判据仍是**人工**：在已重启后端（含本轮修复）的环境里，从 H5 真实点「＋」上传一份文档并提问，看回答是否引用其内容。
2. **`scripts/_check_dto_fields.py` 只保 DTO 口径**，不验证「id → 字节 → 正文 → 下发」的运行链路；它过了 ≠ 端到端过了。
3. **历史轮回填**（`formatAttachmentDocs` 前置进 content）只有后端单测覆盖，没有「重开会话后 AI 真看得到」的端到端判据。
4. **权限面**：上传走「通用文件上传」既有鉴权，本功能未引入新的越权面（不新增「指定 projectId 塞文件」之类入口），但也没有针对「跨会话/跨用户可见」的自动负向断言——依赖 `chat_message` 按 `conversation_id` 隔离的既有保证。
