# 92. 非遗能力按租户接入改造计划（2026-11-21）

> 本文是**方案设计**，不含具体代码实现。目标：把四川非遗（scfy）从「全系统统一接入」
> 改为「按租户维度接入」——只有租户完成接入配置后，该租户下的机构与用户才能调用对应非遗接口。
> 所有现状结论均来自本仓真实代码，带文件路径与行号，便于逐条回源核对（铁律 7/12）。

---

## 1. 现状与目标差异

### 1.1 现状：平台级单点接入，一次信任全员可用

非遗以原生连接器 `scfy` 接入，共 69 个只读工具。当前链路与判据：

| 环节 | 现状事实 | 位置 |
|---|---|---|
| 连接器目录 | `connector_def` 一行 `tenant_id=0`，`auth_mode='API_KEY'`，**`config_keys='[]'`**，`status=ACTIVE` | `V113__scfy_mcp_connector.sql:14-19`；V114 仅改文案 |
| MCP 服务器 | `mcp_server` id=5 `tenant_id=0`、`source=BUILTIN`、`trusted=0` 起步 | `V113:21-22` |
| 启用动作 | 管理员调一次 `POST /api/v1/mcp/servers/scfy/trust`，探测通过后 `trusted=1`、写工具快照 | `McpServerController.java:72-76`；`McpRegistryService.trust():262-278`、`syncTools():365-413` |
| manifest 下发 | 查 `tenant_id ∈ {0, 本租户}` 且 `trusted=1` | `McpRegistryService.manifest():77-108` |
| 可用判据 | `usableForAgent()`：用户 CONNECTED 放行；否则 `API_KEY && configReady()` | `McpRegistryService.java:125-138` |
| **配置就绪判定** | `configReadyInternal()`：**`config_keys` 为空 ⇒ 直接 `ready=true`**；scfy 恰是空 | `ConnectorCatalogService.java:194-218`（L199-201 是根因） |
| hub 侧调用 | 原生 server 直接 httpx GET 公网域名，**不校验任何身份/租户** | `mcp-hub/mcp_hub/scfy/server.py:62-`（全文无 Authorization/tenant/user 判定） |

**由此产生的效果**：scfy 一旦被 trust，所有租户、所有用户的 manifest 都包含 `mcp__scfy__*`——因为
（a）`mcp_server` 是 `tenant_id=0` 的平台行，对所有租户可见；（b）`config_keys=[]` 使
`configReady()` 恒真，人人放行；（c）hub 侧没有任何租户校验。这正是要消除的「全系统统一接入」。

### 1.2 目标：租户级接入，配置后才可见可调

| 维度 | 现状 | 目标 |
|---|---|---|
| 接入主体 | 平台管理员 trust 一次 | **每个租户**独立完成接入配置并启用 |
| 可见性 | 全员可见平台行 | 仅**已配置且已启用**的租户可见；未接入租户看不到工具 |
| 调用权限 | 无差别放行 | 租户开关 + 机构范围 + 用户权限三层闸门 |
| 调用链路 | agent → manifest → hub → 公网，hub 无鉴权 | 链路各层携带并校验租户身份，防绕过 |
| 数据/审计 | 公共接口、审计不区分租户 | 接入配置与调用审计按租户隔离，权限范围按机构收窄 |

### 1.3 关键认知：非遗数据本身是公开数据

非遗接口（`https://szbhpt.tsichuan.com/scfy/show/*`）是免登录只读公开接口，返回传承人、项目等
公共信息，**不含 aios 租户私有数据行**。因此本改造的「数据隔离」不是传统意义上的行级数据隔离，
而是三件事：① 接入配置（数据源地址/范围/配额）按租户隔离；② 调用权与可见性按租户+机构+用户隔离；
③ 调用审计与用量按租户归属。这一点决定了改造重点在**闸门与配置**，而非数据过滤。

## 2. 需要调整的五个方面

### 2.1 租户接入流程

现状只有两步：平台 trust + 全员可用。目标需要引入「租户接入」这一独立流程：

1. **租户申请/开通**：租户管理员在本租户发起非遗接入（管理端入口）。
2. **租户填写接入配置**：至少包含启用开关；按需包含数据源地址（公网域名或租户自建 16060）、
   允许调用的机构范围、调用配额。
3. **租户侧启用**：租户管理员在自己租户内完成「启用」，写入租户配置并置为生效。
4. **信任仍保留但下沉到租户维度**：工具目录探测与可信快照按租户（或平台探测一次、租户授权一次，
   见 §8 决策点 D1）。
5. **接入状态可查询/可撤销**：租户可查看「未接入 / 已配置待启用 / 已启用 / 已停用」四态。

可复用范式：`GiteeTenantConfigService.tenantEnabled()`（`aios-gitee/.../GiteeTenantConfigService.java:100-106`
无租户行=继承默认、显式 `enabled=0` 关闭）与 `ConnectorTenantConfig`（`V96:22-34`，租户+连接器唯一键、
`secret_json` 密文、`enabled`）已经提供了「租户级开关 + 配置」骨架，优先复用而非新建平行体系。

### 2.2 权限鉴权

现有四套机制，本改造要串成一条链：

| 机制 | 位置 | 在本次改造中的角色 |
|---|---|---|
| MCP manifest 闸门 | `McpRegistryService.manifest():77-108`、`usableForAgent():125-138` | **主闸门**：非接入租户根本拿不到工具 |
| 租户功能开关 | `GiteeTenantConfigService.tenantEnabled()`（范式）、`ConnectorTenantConfig.enabled` | 判定租户是否已接入/启用 |
| 权限码 | `PermissionCatalog.holds()`（`aios-security/.../PermissionCatalog.java:359-371`），手动校验（全仓无 `@PreAuthorize`） | 粗闸：谁有资格启用/调用（建议新增 `connection:scfy:use` 类权限码） |
| 工具级权限 | `tool_permission` 表 + `ToolPermissionService.java:62-122`（DENY 优先→ALLOW→白名单） | 细粒度：机构/角色维度限制具体工具子集 |

要点：
- 现有 `configReadyInternal()` 对空 `config_keys` 恒返回 true（`ConnectorCatalogService.java:199-201`），
  是「全员可用」的技术根因，**必须改造**（见 §8 D2），否则租户开关形同虚设。
- 权限校验沿用项目惯例：`PermissionCatalog.holds(user, code)` 手动调用，不引入注解；
  系统角色表达不了的「机构内范围」用服务层细判（参考 `PmProjectService.canManage` 模式，
  见 `PermissionCatalog.java:136-142` 注释）。

### 2.3 机构/用户关系

现状身份链路：

- `sys_user.tenant_id` 定租户（`V1__init.sql:25`）；
- 机构/部门**不在 sys_user 表里**，通过 `org_member(user_id, institution_id, department_id)` 关系行解析
  （`OrgMember.java:27-33`；`AuthService.java:317-326`、`404-413`）；一人可多机构兼职，`isPrimary` 为主身份；
- JWT 签发 claims `uid/tid/iid/did/roles`（`JwtTokenProvider.java:22-45`），每请求由
  `JwtAuthenticationFilter.java:55-123` 实时刷新角色与权限码并注入 `AuthUserContext`（`AuthUser.java:16-29`）。

目标要求「该租户下的机构和用户才能调用」，因此在上述链路中需要明确三层归属判定：

1. **租户层**：`AuthUser.tenantId` 必须命中一个已启用的 scfy 租户接入配置；
2. **机构层**：若租户配置了「允许机构范围」，用 `AuthUser.institutionId`（来自 `org_member`）判定是否在内；
   多机构兼职用户需明确以 primary 机构还是任一机构为准（见 §8 D3）；
3. **用户层**：用 `AuthUser.permissions` / 角色 / `tool_permission` 判定该用户能否调用。

注意：`AuthUser` 的字段是 `institutionId/departmentId`（对应 JWT 的 `iid/did`），**不是** `orgId`，
改造时别用错名字。

### 2.4 接口调用链路

现状链路：

```
用户提问 → agent 拉 /api/v1/mcp/manifest
        → Java 过滤 tenant∈{0,本租户} & trusted=1 & usableForAgent
        → agent 注入 mcp__scfy__*（ToolClient.list_mcp_tools, agent/tools/client.py:120-198）
        → 工具调用 → hub /mcp/scfy（mcp-hub/app.py:193-230）
        → scfy server httpx GET 公网域名（scfy/server.py:62-）
```

薄弱点：
- **hub 侧无鉴权**：`scfy/server.py` 不读 token/tenant。即便 manifest 层隐藏了工具，绕过 manifest
  直接请求 hub 仍可调——「隐藏工具」不是安全边界。
- `mcp_server` 的 `tenant_id=0` 平台行使所有租户共享同一份可信快照。

目标链路的加固方向：
- manifest 层按「租户接入配置」过滤（主闸门）；
- hub 层透传入站 token → 回调 Java 校验该 token 的租户是否已接入（可复用
  `builtin.py:60-101` 的 Authorization 透传模式，那个链路已能原样转发身份）；
- 调用审计 `mcp_tool_audit`（`V97:47-60`）写入 tenant_id，按租户归属。

### 2.5 数据隔离

| 隔离对象 | 手段 |
|---|---|
| 租户接入配置 | `connector_tenant_config`（租户唯一键）+ 可选 scfy 专用配置（机构范围/配额/base-url） |
| 工具可见性 | manifest 按租户过滤 + hub 回调校验 |
| 调用权限范围 | 机构白名单 + `tool_permission` 工具子集 |
| 审计与用量 | `mcp_tool_audit` 按 tenant_id 归属；配额按租户统计 |
| 数据源 | 公网域名全局共享（公开数据）；租户自建 16060 时 base-url 属于租户配置，需按租户隔离存放 |

明确不做的：非遗公开数据不做行级过滤（无租户私有数据行）；不为隔离而复制工具目录到每个租户
（工具目录仍以 Java `ScfyCatalog` 单一事实源为准，见 docs/89 §10.2）。

## 3. 分阶段实施步骤

### 阶段 0：判据固化与基线（无功能改动）
- 梳理并冻结现状判据清单（本文 §1.1 表）；为「租户未接入时工具不可见/不可调」写失败用例。
- 产出：判据矩阵 + 反向用例（证明当前全员可用是缺陷，而非预期）。

### 阶段 1：租户接入数据模型与配置
- 设计 scfy 租户接入配置：复用 `connector_tenant_config`（`enabled`）为最小骨架；
  若需机构范围/配额/base-url，新增 scfy 专用配置表（tenant 唯一键、审计列、软删）。
- 提供租户管理员配置入口（管理端 shell 的 connector-admin 通道，`web/apps/shell/src/api/connectorAdmin.ts:47-59` 现有凭据配置可参照）。
- 产出：迁移脚本 + 配置 CRUD + 接入四态查询。

### 阶段 2：接入流程改造
- 把「trust 一次全员可用」拆为「平台探测可信 + 每租户授权启用」。
- 定义状态机：未接入 → 已配置待启用 → 已启用 → 已停用，明确每态对 manifest 的影响。
- 产出：租户侧启用/停用端点；平台侧 trust 语义调整（D1 决策落地）。

### 阶段 3：权限鉴权闸门
- 改造 `configReadyInternal` / `usableForAgent`，让 scfy 走「租户接入配置」判据（D2）。
- manifest 过滤改按租户；新增权限码与 `tool_permission` 细粒度配置（如需限制工具子集）。
- 产出：主闸门 + 粗闸 + 细粒度三层联通。

### 阶段 4：调用链路加固
- hub 侧增加身份透传与租户校验（复用 `builtin.py` 透传模式），堵住绕过 manifest 的口子。
- `mcp_tool_audit` 按 tenant 归属；错误文案按「未接入 / 未启用 / 机构无权 / 配额用尽」分类。
- 产出：链路全程可追溯、不可绕过。

### 阶段 5：机构/用户范围与配额
- 落地机构白名单判定（多机构口径 D3）、用户权限、租户级配额与限流。
- 产出：范围判定服务 + 配额统计 + 超限提示。

### 阶段 6：灰度与验收
- 按租户灰度（先 1 个测试租户）；执行 §6 验收标准；旧行为回归对照。
- 产出：验收报告 + 回滚预案。

## 5. 风险与注意事项

1. **`config_keys=[]` 恒真陷阱（最高风险）**：不改 `ConnectorCatalogService.java:199-201`，租户开关完全无效，
   改造会「看起来做了、实际全员仍可用」。必须有反向用例证明未接入租户拿不到工具（铁律 7/12）。
2. **平台行 `tenant_id=0` 绕过**：manifest 查 `{0, 本租户}`，若保留 scfy 平台行且 trusted=1，租户隔离被平台行打穿。
   必须明确平台行是「目录/探测」还是「授权」，二者分离。
3. **hub 是旁路入口**：隐藏工具 ≠ 安全边界；直接 POST `/mcp/scfy` 可绕过。必须补 hub 侧校验，
   否则接口调用链路的租户控制只是「对老实用户有效」。
4. **不得编造/放宽判据**：沿用铁律 7——不为转绿放宽断言；「界面显示未接入」须回 manifest 与库双向核对。
5. **工具目录单一事实源**：不要为每个租户复制 `catalog.json`；目录仍由 Java `ScfyCatalog` 导出（docs/89 §10.2）。
6. **多机构兼职口径**：一人多 `org_member`（`OrgMember.java:56-61`），机构白名单必须定义 primary 还是任一，
   否则会误放行/误拦截。
7. **实时生效**：权限码每请求由 `JwtAuthenticationFilter.java:96-103` 刷新；租户接入态若缓存在 JWT，
   启用后要能即时生效（建议接入态走库实时查，不放 JWT claim）。
8. **历史行为回退**：现有租户已习惯非遗全员可用；改造后未配置租户将失去能力，需灰度与公告，
   并保留回滚开关。
9. **外部依赖抖动**：非遗公网域名/WAF 与上游数据库曾多次故障（docs/89 §8），改造要把「未接入/配置缺失」
   与「上游不可用」两类文案分开，避免把权限问题误报成数据源故障。
10. **上游原文不外发**：沿用统一错误载荷，上游错误只进日志（docs/87、pitfalls）。

## 6. 验收标准

按「可度量 + 判别力证明」设计，每条须能从库/接口回源核对，不只信界面：

| 编号 | 验收项 | 判定（须回源） |
|---|---|---|
| A1 | 未接入租户：manifest **不含** scfy，工具数 0；hub 直调被拒 | 查 `/api/v1/mcp/manifest` + `connector_tenant_config` 无行 |
| A2 | 已配置未启用：仍不可见；启用后立即可见（无需重新登录） | 切换前后各查一次 manifest |
| A3 | 已启用租户：该租户用户能调 69 工具，返回真实数据 | 真机提问，`agent_run_step` 有 scfy 成功调用 |
| A4 | 跨租户隔离：租户 B 未接入时，用 B 的 token 拿不到工具、直调 hub 被拒 | B token 双通道验证 |
| A5 | 机构范围：配置白名单后，名单外机构用户不可见/不可调，名单内可用 | 用两个机构账号对照 |
| A6 | 用户权限：无权限用户被拦，有权限用户放行 | 分配/撤销权限码后对照 |
| A7 | 审计归属：调用写入 `mcp_tool_audit` 且 tenant_id 正确 | 查审计表 tenant_id |
| A8 | 配额：超额后拒绝并给可执行提示，不误报「数据源故障」 | 压测配额 + 文案断言 |
| A9 | 非绘图/普通问答无回退：既有表格/图表功能（docs/91）不受影响 | 跑 `_check_answer_table_render.js` + 414 pytest |
| A10 | 判别力证明：把租户接入配置置空，原 A3 用例必须转 FAIL（证明判据不是恒真） | 反向用例 |
| A11 | 回归：既有连接器（wecom_cli 25、qq_mail 6）工具数不变 | hub `/health` + manifest 对照 |
| A12 | 上游故障时文案区分：模拟上游 500，报「数据源不可用」而非「未接入」 | 故障注入 |

## 7. 待决策点（实施前需拍板）

| 编号 | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | 平台 trust 与租户授权的关系 | ①每租户独立 trust（工具快照按租户）；②平台探测一次、租户仅授权启用 | ②——避免复制工具快照，符合单一事实源；租户开关作为授权层 |
| D2 | 空 config_keys 恒真怎么改 | ①给 scfy 设一个虚拟 config_key；②在 `configReady`/`usableForAgent` 增加「需租户接入配置」判据 | ②——虚拟 key 语义假、易被绕过；显式判据更清晰 |
| D3 | 多机构兼职口径 | ①primary 机构；②任一机构命中即放行 | 取①——最小权限原则；需要放宽再单独评审 |
| D4 | 接入配置存放 | ①复用 `connector_tenant_config`；②新建 scfy 专用表 | ①为骨架、②为扩展字段；避免两套开关源 |
| D5 | 配额是否首期做 | ①首期含；②二期 | ②——先做可见性与权限，配额依赖调用量统计，后置更稳 |

---

## 8. 结论

改造的核心不是「加一张表」，而是把当前三个「恒真/平台级」的判据逐一租户化：
`tenant_id=0` 的平台行、`config_keys=[]` 的 `configReady` 恒真、hub 侧零鉴权。
项目已具备成熟的「租户级 enabled + configReady」「权限码 holds」「tool_permission 细粒度」
三套范式，可直接串联复用，无需另起炉灶。风险集中在判据改造是否彻底（§5-1/2/3），
验收必须用反向用例证明「未接入即不可用」，而非只看「接入后可用」。

**本计划不含具体代码**；实施按阶段 0→6 推进，每阶段独立可验收、可回滚。
