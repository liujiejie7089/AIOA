# 57 · 全链路体检：OA 业务流程 与 数字人智能度

> 日期：2026-10-19　｜　对象：`D:\aios`（原 aioa，已更名 AIOS）
> 方法：**代码 + 文档 + 生产库**三层取证。本文所有结论都有 `file:line` 或 SQL 计数支撑，不做主观判断。
> 触发问题：「OA 流程业务类还是不够完善，数字人也还是不够智能，没有做到思考和决策」

---

## 0. 一句话结论

**审批引擎本身是国内 OA 里中上水平（会签/抢占/条件路由/加签/子流程/抄送/版本 diff 全都有），但它是空转的**——
真正让用户觉得「流程不完善、数字人不会思考」的不是引擎弱，而是**「表单 → 能力 → 工具 → 审批流」这条业务链在数据层就没有接上**：

| 体检项 | 实测 | 含义 |
|---|---|---|
| 43 个模块的表单模板 | **516 条**（43 × 12 租户） | 装好了 |
| 43 个模块的数字人 | **516 条**（`OA_*`） | 装好了 |
| 能力声明里声明了「审批走哪条流」 | **12 / 516**（且全部是 LEAVE） | **断点 1** |
| 能力声明里声明了「可调哪些工具」 | **0 / 516** | **断点 2** |
| 表单提交记录 `form_submission` | **0 条** | 从未有一张业务表单真正提交过 |
| 审批单 `approval_order` | 271 条，其中**员工侧只有 LEAVE 135 条** | 其余全是管理类或测试数据 |
| 已配置的审批流 `approval_flow_def` | **只有 LEAVE + 管理类**，无报销/用印/出差/采购 | **断点 3** |

即：**43 个模块目前是「有壳无肉」——数字人不知道怎么干活，流程不知道往哪走，所以用起来必然是"答得泛泛、办不了事"。**

## 2. 第二层：数字人——"不会思考"的五个机制原因

### 2.1 执行拓扑决定了它「只能一问一答，不能想」

```
START → prepare → agent →(有 tool_calls 且 <4 轮)→ tools → agent →(否则)→ finalize → END
                        └─(HITL 开)→ clarify（interrupt 挂起）
```

- 无 planner、无 router、无 critic、无 self-check 节点（`graph/builder.py:30-48` 只有 5 个节点）
- 工具回环硬上限 **4 轮**（`tools/client.py:21` `MAX_TOOL_ROUNDS=4`），第 5 轮直接摘掉工具
- `finalize`（`graph/nodes.py:509`）只负责收尾发事件，**不校验答案是否用了检索结果、数据是否自洽**

⇒ 机制上它是「单次 LLM + 可选工具调用」，不是「先规划、再取证、再自查」的 agent。用户感觉「不会思考」是**结构性的**，不是模型不够好。

### 2.2 上下文缺了最关键的一块：组织与权责

`prompt/builder.py:152-403` 实际拼进 prompt 的块只有：身份/职责边界、9 条行为规则、**用户名与角色**、当前页面、当前项目、动作提示、表单清单、参考文档、历史轮次。

**没有注入**：部门、组织架构、上下级关系、可审批人、我的权限清单、我的待办。
后果：它无法回答「我该找谁批」「这个金额要不要走总经理」「我还有几天年假额度」这类真正需要决策的问题，只能给通用话术。

### 2.3 能力表没绑工具，等于「有岗位没工具」

`worker_capability` 516 行的实测结果：
- `tool_names_json` **516 行全为空**
- `approval_biz_type` **504 行为 NULL**

而工具本身只有 5 个只读查询 + 1 个写操作（`ToolGatewayService.java:55-79`：`list_my_approvals` / `list_todo_approvals` / `search_kb_documents` / `get_my_quota` / `sql_query` / `apply_permission`）。

⇒ 一个「报销数字人」被启用时，它既不知道自己该调什么工具，也不知道提交后走哪条审批流——**它只能聊天**。

### 2.4 意图识别是正则打分，不是语义理解

`intent/intake.py:93-212`：`_ACTION_QUESTION`、`_DATA_HINT` 等正则 + 关键词评分，`best_score < 2.0` 就落到默认分支。
后果：换个说法就漏判；「帮我看看上个月报销到哪一步了」和「报销怎么弄」在打分上可能不可分。

### 2.5 专家配置（expert_settings）注入链断了

`RunService.java:382-391` 调 `resolveExpertSettings`，但 `:1030-1043` 靠 `findExpertForWorker` 命中 `ai_expert`，而 `:930-939` 的注释已写明：`worker_type`（`OA_*`）与 `expert_key` 命名不重合 ⇒ **恒返回 null ⇒ 永远不注入**。
Agent 侧 `graph/nodes.py:164`、`prompt/builder.py:172` 的解析逻辑因此永远落到默认值 ⇒ **专家配置页填什么都白填**。

### 2.6 模型与参数（本机实测配置）

`agent/.env`：
```
MODEL_DEFAULT=minimax        # MiniMax-Text-01（V61 种子），非推理模型
AIOS_HITL=true               # 本机已开（代码默认 false，config.py:71）
# 无 temperature / max_tokens 覆盖 → 温度取默认 0.3，无输出上限
```
⇒ HITL 在本机是开的（澄清卡/表单卡可用），但**工具筛选、规划、校验仍缺**；模型侧用的是非推理版，且未设输出上限。

## 3. 第三层：真正的根因是「四段断裂」

把三层证据叠起来，问题不在某一层，而在这条链上三处没接：

```
表单 form_template(43×12) ──✗── 能力 worker_capability(tool_names 全空)
                                      │
                                      ✗  approval_biz_type(504/516 为 NULL)
                                      ↓
                              审批流 approval_flow_def(只有 LEAVE)
                                      │
                                      ✗  业务回调 ApprovalCallback(员工侧仅 LEAVE)
                                      ↓
                              回写业务表 / 通知 / 待办
```

**三处 ✗ 就是「流程不完善 + 数字人不智能」的共同母因。**
修引擎没用，修提示词也没用——必须先把这三处接上，后面所有优化才有承载体。

## 4. 改进方案（按投入产出排序）

### 阶段一：接线（1～1.5 周，立刻能让用户感到"能办事"）

| # | 动作 | 落点 | 验收判据 |
|---|---|---|---|
| A1 | 把 `worker_capability.tool_names_json` 按模块填实（如报销→`get_my_quota,list_my_approvals,sql_query`） | V89 迁移 + 种子脚本 | `where tool_names_json is null or '[]'` 计数 = 0 |
| A2 | 把 `approval_biz_type` 按模块填实，**并为每个 code 建一条 `approval_flow_def`** | V89 + `ApprovalFlowProvisioner` | `form_template` 的 43 个 code 全部能在 `approval_flow_def` 找到同名 biz_type |
| A3 | 新增 3 条员工侧业务回调：**费用报销 / 用印 / 出差**（照 `LeaveService implements ApprovalCallback` 的写法，onApproved/onRejected 回写业务表） | `aios-project`、`aios-resource` | 提交后 `approval_order` 出现新 biz_type；驳回后业务单状态回 `DRAFT` 可重提 |
| A4 | 审批中心补「催办」+ 每日超时扫描（超 N 小时未处理 → 站内信 + 抄送其上级） | `ApprovalFlowService` 新增 `remind()`；`@Scheduled` | 手工造一条超时单，24h 内收到催办；日志可见 |
| A5 | 修 `HttpGatewayChannel` 钉 HTTP/1.1（`docs/55` P0-1） | `notify/HttpGatewayChannel.java` | 邮件/短信渠道不再 5s 超时全丢 |

> 阶段一完成后，用户能做：**报销 / 用印 / 出差 真提交、真审批、真催办**，数字人在这些场景里能查到「到哪一步了」。

### 阶段二：让数字人"会想"（2～3 周）

| # | 动作 | 落点 | 为什么有效 |
|---|---|---|---|
| B1 | 加 **planner 节点**：先产出「要查哪些工具 / 还需要问用户什么」的结构化计划，再进 agent 循环 | `graph/builder.py:33-41` 插 `plan` 节点；`state.py` 加 `plan/plan_index` | 把"一次性猜"变成"先列步骤"，多步业务（查额度→算天数→找审批人）才有解 |
| B2 | 加 **self-check 节点**：答案若引用了数据，必须能在 `tool_calls_log` 找到来源，否则退回重答 | `builder.py:42` finalize 前插 `self_check`；`state.py` 加 `self_check` | 直接消灭"编数字/编流程"这类最伤口碑的行为 |
| B3 | 注入**组织上下文**：部门、直属上级、可审批人候选、我的权限码、未办待办数 | `RunService.java:602-608` 扩参 → `prompt/builder.py` 新增块 | 才能回答「该找谁批」「我还有没有额度」 |
| B4 | 工具升级：把 5 个原子查询包装成 3 个**业务能力工具**（`prepare_leave`（算天数+查额度+选审批人）/ `track_my_request`（一个单号的完整旅程）/ `recommend_form`（按描述选表单）） | `ToolGatewayService` + `tools/` | 数字人从「查数据」升级到「办事」 |
| B5 | 接通 `expert_settings`：给 `agent_worker` 加 `expert_key` 或约定 `worker_type` 与 `expert_key` 同名 | `RunService.java:930-943` | 专家配置页立刻生效（现在填了全废） |
| B6 | 意图识别补语义层：正则打分保留为快速通道，低分时走一次小模型分类 | `intent/intake.py:212` 分支 | 换说法也能命中 |

### 阶段三：可持续（1～2 月）

- **流程设计器 UI**（管理端）：`TenantAdminController` 的 defs API 已就绪，只缺页面；让业务方能自己改流程，不必找开发
- **委托/代理 + 超时升级 + SLA 看板**：补齐成熟 OA 标配
- **长期记忆**：把用户偏好、常用审批路径沉淀成 profile，跨会话复用（当前只有本轮历史）
- **评测集**：给数字人建 50 条金标问答 + 20 条业务流程剧本，每次改 prompt/模型都跑一遍，避免"感觉变聪明了"的伪优化

## 5. 建议的下一步（最小可验证切片）

先做 **A1 + A2 + A3（只做报销一条）**，用一条端到端剧本验收：

> 员工说「我要报销上周出差的 1200 元」→ 数字人选 `expense_form` → 填单 → 提交 → 生成 `EXPENSE` 审批单 → 审批人收到站内信 → 审批通过 → 报销单状态变 `APPROVED` → 数字人能回答「已通过，财务将在 3 个工作日打款」

这条走通，就等于把「四段断裂」全部接上；其余 40 个模块照此复制即可。
