# 请假表单接真链路 / x-system 派生字段 / 错误建议并入（2026-11-06）

> 承接 `docs/84 §5`「留下未做」的三条。用户逐条纠偏后确认：三条都真实存在，
> 但根因与我原先的判断不同 —— 尤其第 ① 条「取消经典卡」这个方向是错的，
> 经典卡恰恰是当时唯一的真链路，删掉它只剩一条不落库、不扣余额的假链路。

## 1. 三条问题的真实根因

### ① 两条产出路径：不是「字段集不同」，是落库对象不同

|  | 经典卡 | 后端 `need_form` 卡 |
|---|---|---|
| 渲染 | `leaveFormHtml()` | `renderFormHtml(p)` |
| 提交 | `POST /v1/leave/requests` | `POST /v1/forms/leave_request/submit` |
| 后端 | `LeaveService.submit()` | `FormSubmissionService.submit()` |
| 落库 | `leave_request` + 余额占用 + 审批流 | `form_submission` + 审批流，**没有** `leave_request` |

`FormSubmissionService` 里没有任何 `LeaveService` 引用，`leave_request` 表只有
`LeaveService.submit()` 一处写入。所以后端卡提交的请假走不进业务链：

- 「我的请假记录」查 `leave_request` → 查不到
- 不占余额、不校验余额/假种有效期/提前天数/最长连续天数/证明材料
- 审批终态 `LeaveService.onApproved` 按 `order_id` 找单 → 找不到 → 静默 return，余额永不扣
- 传给审批引擎的 `days` 是 `null`，按天数的条件路由（`when.field=days`）在这条路上恒不成立

字段集差异的根源也在这里：V86 把 `leave_type` 写死成静态 enum，而 `leave_type` 表真值是
`CASUAL`（事假）/ `COMP`（调休）—— 表单里的 `PERSONAL` / `COMPENSATORY` 在字典里不存在，
选了必然失败。经典卡从 `/v1/leave/types` 取真码，所以没这个问题。

### ② 「请假天数」必填：用户可以自报少扣额度

`LeaveService.calcDays` 的口径是「优先用前端传的 explicit，为空才按起止算」。
前端填 1 天、实际休 5 天，后端就信 1 天 —— 余额按 1 天扣，`leave_request.days` 也是 1。

`x-system` 在当时代码里并不存在（全仓零命中，schema 扩展只有 `x-type` / `x-options-ref` / `x-rules`），
是需要新建的机制。前端侧另有一份硬编码白名单 `SYSTEM_FIELDS = ['days','hours',...]`，
后端加一个派生字段，前端就会漏一个。

### ③ toast 文案：问题不在 message 脏，在 suggestion 被丢了

H5 里 48 处 `toast('X失败：' + e.message)`，只有 2 处走 `errText()`。但后端
`GlobalExceptionHandler` 已经过 `ErrorText.sanitize()` + `ErrorCode.defaultMessage()`，
message 多数时候已经是人话。真正丢的是信封里的 `suggestion`（怎么办）——
`API.req` 已经把 `err.suggestion` 挂上去了，但 48 处 catch 只读 `e.message`。

管理端早就在拦截器里拼过一次（`web/apps/shell/src/api/index.ts` 的 `toApiError`），
H5 照抄即可。另：`errText()` 里那个「技术细节防漏」正则只对经过 `errText()` 的文案生效，
48 处裸拼完全绕过它 —— 改在 `API.req` 一处，两个问题一起解决。

## 2. 改了什么

### 后端

| 文件 | 改动 |
|---|---|
| `FormSubmissionService` | 注入 `LeaveService`；`bizType=LEAVE` 时委托 `leaveService.submit()`，不再自己调通用审批 |
| `FormSubmissionService.toLeaveBody()` | 字段名映射单点：`leave_type→leaveTypeCode`、`start_date→startDate`、`end_date→endDate`、`proof→proofFileId`；**刻意不映射 days** |
| `FormSubmissionService.fileIdOf()` | `proof` 兼容 `[{fileId}]` / `[12]` / `"12"` / `12` 四种形态 |
| `FormSubmissionService.onApprovalFinished()` | 不变，但因为 `sub.approval_order_id` = 请假单的 order，editing 终态会同步写 `form_submission` |
| `FormSchemaValidator` | `x-system` 字段跳过必填（值由后端回填，用户不填也算过） |
| `FormTemplateService.FormField` | 新增 `boolean system`，`resolveForRender` 置 `required=false` |

关键顺序：**先落 `form_submission` 再委托请假**。请假失败时把 submission 回写成 `FAILED` 再抛，
与既有 APPROVAL 分支一致 —— 最差情况留一条 FAILED 记录，不会留下「已占额度但对话里没痕迹」的单据。

请假服务抛的异常直接透出（余额不足/假种停用/需提前 N 天），不再套「提交审批失败：」前缀。

### 迁移

| 迁移 | 作用 |
|---|---|
| `V110__leave_form_real_chain.sql` | 平台默认行（tenant_id=0）：假种改 `x-options-ref: leave_types`、`days` 改 `x-system`、required 去掉 days |
| `V111__leave_form_tenant_copies.sql` | **各租户副本**同一修正（判据：假种枚举里还含 PERSONAL/COMPENSATORY，说明是从 V86 复制来没改过） |

为什么不能只改 V86：它已在所有环境执行过，改它会让 `flyway_schema_history` 的 checksum 与库里记录
不一致，只有带 `-Dspring.flyway.validate-on-migrate=false` 才能启动。启动脚本确实带了，
但那行注释写得很清楚 —— 它是「根因已在库里修好、只为两处入口一致」而存在的，不是改历史迁移的许可。

### H5（`user-client/index.html`）

| 位置 | 改动 |
|---|---|
| `renderFormHtml` | `f.system === true` 直接 `return`，不渲染派生字段 |
| `formSummaryHtml` | 判据改成 `f.system === true \|\| SYSTEM_FIELDS.indexOf(name)`，白名单降级为老后端兜底 |
| `uploadFormFiles()`（新增） | 提交前把 file 控件真上传，值换成 `[{fileId,name}]`；失败中断提交 |
| `API.req` | `message` 过 `safeErrMsg`（技术细节防漏），并并入 `suggestion`，原值留 `err.rawMessage` |
| `envelopeError()`（新增） | 三个裸 fetch（`fileUpload` / `kbUploadFile` / `asrTranscribe`）走同一口径 |
| `errText()` | 改用 `safeErrMsg` 单一口径；建议已并入 message 时不重复拼 |
| `dismissCard()` / `cancelLegacyLeaveForm()` | 卡片「取消」真的摘掉 DOM；`oaStop` 也能收掉经典请假卡 |

`uploadFormFiles` 这处是必须的：`collectFormValues` 对 file 只采**文件名**，
后端要的是 fileId。不补这一步，用户选了病历、界面显示着文件名，后端仍判「必须上传证明材料」。

## 3. 判据

新增 `scripts/_verify_leave_form_real_chain.py`（12 项，全部回库核，三方对照）：

| 判据 | 证伪方式 |
|---|---|
| P2a 天数 = 工作日数 | 提交时故意传 `days=99`；区间选「周四~下周一」= 工作日 3 / 自然日 5，三值必须不同 |
| P3 `leave_request` 真有这行 | 只落 `form_submission` 时这条必红 |
| P3c `leave_request.order_id` == 回执单号 | 不等则审批通过也扣不掉余额 |
| P4 `form_submission` APPROVING 且同单号 | 两表挂在不同的单上时必红 |
| P5 pending `+N` / 可用 `−N` | 「余额永不扣」时必红 |
| P6 `PERSONAL` 被拒 | 改回写死枚举时这条会变成「提交成功」 |
| P8 撤销后 pending 归零 | 反向验证额度是真的被占过 |

## 4. 这一轮踩的坑

1. **JSON path 里的连字符键必须加引号**：`$.properties.leave_type.x-options-ref` 报
   `Invalid JSON path expression`，Flyway 直接让后端起不来。正确写法 `'$."properties"...'` 不够，
   是 `'$.properties.leave_type."x-options-ref"'`。
2. **改平台行 ≠ 生效**：`getByCode` 是「本租户优先、没有才回退平台」。库里 10 个租户各有一份
   `leave_request` 副本，V110 只改 tenant_id=0，登录进来读到的还是旧定义。
   第一次跑 V110 后回归 V2d/V2c'' 原样报红才发现 —— 如果没有回归，这就是一次「改了却不生效」。
3. **Flyway 失败会留 `success=0` 记录**，下次启动直接报「Detected failed migration」；
   MySQL 的 DML 会回滚，所以 `schema_json` 没被改脏，只需删掉那条记录重跑。
4. **dev profile 不传 `--server.port` 会拿到随机端口**（本次 62170），
   报的是「Port 62170 already in use」——看着像端口冲突，其实是没指定端口。启动必须显式 `--server.port=8080`。

## 5. 仍然留着的

- **经典请假卡没有下线**。它是老链路，现在两条路都通到 `leave_request`（一条直连、一条经通用表单），
  不再是假链路。下线它要动 `oaEmitLeaveForm` 的触发逻辑，风险大于收益，本轮只补了「取消真能摘掉」。
- **`WorkerIntakeService.resolveFormFields` 仍会列出生日字段**（`days` 等）。它展示的是
  「这张表单有哪些字段」，语义上没错，但用户看到「数字人会填：请假天数」可能以为自己要填。
- **提交前的天数预览没有**：汇总面板不显示天数（它还没算出来）。要做到「填完就看见扣几天」，
  得加一个 `POST /forms/{code}/preview` 之类的接口 —— 本轮没做，避免多一次往返。
- **`toast` 文案只解决了「建议丢失」**：48 处前缀（「提交失败：」「上传失败：」）仍在各自 catch 里，
  这次没统一；但它们现在都带得上建议了。
