## 3. 已实现（本批）：文档域

### 3.1 迁移 V72
`pm_folder`（企业级公共 / 项目专属同表）+ `pm_document`（索引，字节落 `sys_file`）。
权限码只播 **`pm:doc:view` / `pm:doc:manage`**（已实现能力的码，见 §6.2 纪律）。

### 3.2 后端
| 文件 | 职责 |
|---|---|
| `entity/PmFolder.java` `entity/PmDocument.java` | 实体（生成列 `alive` 不映射，V24 约定） |
| `mapper/PmFolderMapper.java` `mapper/PmDocumentMapper.java` | MyBatis-Plus BaseMapper |
| `service/PmDocService.java` | 树 / 建文件夹 / 删空文件夹（BR-08）/ 登记文档（UPLOAD+AI）/ 删文档（BR-07 不删字节）；读写先过 `PmProjectService.requireVisible` |
| `controller/PmDocController.java` | `/api/v1/pm/projects/{id}/docs/**` + `/api/v1/pm/docs/enterprise` |

### 3.3 接口清单
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/pm/projects/{id}/docs/tree` | 项目文档树 = 企业级公共（只读挂载）+ 项目专属（可写） |
| GET | `/pm/docs/enterprise` | 企业文档树（跨项目） |
| POST | `/pm/projects/{id}/docs/folders` | 建项目文件夹（同名 409） |
| DELETE | `/pm/projects/{id}/docs/folders/{folderId}` | 删文件夹（非空 409，**无隐式递归**，BR-08） |
| POST | `/pm/projects/{id}/docs/documents` | 登记文档：`source=UPLOAD`(带 `fileId`) 或 `source=AI`(带 `contentText`) |
| GET | `/pm/projects/{id}/docs/documents/{docId}` | 文档详情（含 AI 正文） |
| DELETE | `/pm/projects/{id}/docs/documents/{docId}` | 软删索引（保留 `sys_file` 字节，BR-07） |

### 3.4 关键规则
- **BR-07**：项目软删级联软删 `PROJECT` 类文件夹，**不动** `ENTERPRISE` 类；文档删除只软删索引，不删 `sys_file` 字节。
- **BR-08**：文件夹只允许删空（子文件夹 + 文档计数 > 0 → 409）。
- 唯一键含 `alive` ⇒ 建文件夹前先查活行（V71 铁律），否则「删了再建同名」撞不上约束。

## 4. 未实现（已出表）：经费 / 合同 / 里程碑（批次 4）

表已在 **V73**：`pm_expense` / `pm_contract` / `pm_contract_payment` / `pm_milestone` / `pm_milestone_task`。
端点设计沿用 `docs/40 §6.3 + §7.2`，要点：

- **K4「不能修改」= 追加式账目**：`pm_expense` **不提供 update 端点**。写错只能**红冲**——
  新增一条**同方向、负金额**的「红字」流水（`reversal_of` 指向被冲销行），原行永不改、永不删；可完整审计。
  ⚠️ **不可用「方向翻转 + 正金额」实现红冲**：汇总是按方向分桶累加，翻转方向会让被冲销的支出仍留在支出桶
  （支出不减）、冲销额混进收入桶 ⇒「结余 = 预算 − 支出」回不去（用户看到「冲了但钱没回来」）。
  同方向负数入桶后自然抵消，且**红冲行本身不能再被红冲**、**同一原行不能重复红冲**（两条负向判据）。
  「分摊」= `alloc_ratio`（%）；「各项目成本」= 按 `project_id` 聚合；「不固定/增长」= 多行随时间累积。
- **BR-09**：合同收付款「确认实收/实付」时在**同一事务**内自动生成一条 `pm_expense`（`contract_payment_id` 溯源）——
  单一事实源，禁止两边各记一遍；已确认的收付款不可删，只能红冲。
- **BR-13**：里程碑达成需 `plan_date`；关联任务未全 `DONE` 时可强制达成，但必须记 `forced_by` + `forced_reason`。
- 审批复用既有引擎：`approval_flow_def.biz_type=PM_CONTRACT / PM_EXPENSE`（BR-11）。
- 权限码 `pm:budget:manage` / `pm:contract:manage` **随其实现在当次迁移里补种**（见 §6.2）。

## 5. 全新能力：项目数字人分配 + 项目上下文控制

### 5.1 复用前提（先查再建）
本平台**已有**「数字员工」子系统：实例在 `agent_worker`，会话经 `chat_conversation.worker_id` 绑定，
职责边界由 `WorkerRole` 唯一定义（`docs/10`、`docs/15`）。
⇒ 「分配项目数字人」= 把**已存在的数字员工**挂到项目上，**绝不新建第二套数字人**
（否则两套账号 / 两套职责，与「权限码单入口」纪律冲突，同 `docs/40` ADR-007 的取舍）。

### 5.2 数据（V74）
- `pm_project_worker`：`project_id ↔ worker_id`（M:N）+ `assign_role`（用途说明）+ `enabled`。
  唯一键 `(project_id, worker_id, alive)`。
- `pm_context_source`：项目数字人的**上下文来源**，一张表用 `source_type` 区分三类：
  | source_type | 含义 | 关键列 |
  |---|---|---|
  | `UPLOAD` | 后台上传 | `folder_id`（整目录）/ `file_id`（单文件） |
  | `WEB_SEARCH` | 网上搜索 | `config` JSON `{keywords,domains,maxResults}` |
  | `POLICY` | 政策 | `kb_document_id`（政策知识库文档） |
  `worker_id=0` = 项目级默认上下文（对所有已分配数字人生效）；否则仅对该数字员工。

### 5.3 「项目上下文控制」的语义
= 对上述来源的**开关与范围**：`enabled=0` 保留配置但不参与上下文组装；
`worker_id` 区分「项目级共享」与「数字员工专属」。
下发链路（未开工）：`RunService.buildScope`（`docs/10 §5 T3`）在组装请求时，
若会话绑定的数字员工属于某项目，则把该项目 `enabled=1` 的上下文来源一并下发 Agent。

### 5.4 权限码（未播种，随实现补）
`pm:ai:manage`（分配数字人 / 上下文控制）。

## 6. 与 docs/40 的有意差异（逐条给理由）

### 6.1 `pm_folder.parent_id` 用 `0` 而非 `NULL`（修正一个真缺陷）
`docs/40 §6.2` 草案写 `parent_id BIGINT NULL` + `UNIQUE KEY (tenant_id, COALESCE(project_id,0), parent_id, name, alive)`。
**MySQL 唯一键里 NULL 视为彼此不同** ⇒ 同一根下（`parent_id=NULL`）可插两条同名文件夹，唯一约束形同虚设。
修正：`parent_id BIGINT NOT NULL DEFAULT 0`（0=根，沿用本项目 `department_id=0`「机构直属」同款约定），
唯一键 `(tenant_id, project_id, parent_id, name, alive)`，根目录也受约束。

### 6.2 权限码播种纪律（V71 已写明，V72–V74 严格遵守）
**只为「已实现能力」播种 `sys_permission`**，否则该码会出现在「可申请权限」清单里、
用户申请到却无任何端点认它（能力事实上不可用）。故 V73/V74 **只建表、不播码**；
`pm:budget:manage` / `pm:contract:manage` / `pm:ai:manage` 随其实现在当次迁移里补。

### 6.3 V73/V74 先出表、端点分批实现
用户一次给出跨批次需求；表是纯增量、无回归风险，先出表可让后续批次不再改 schema。
端点按 docs/40 批次 3→4→数字人 顺序落地。
