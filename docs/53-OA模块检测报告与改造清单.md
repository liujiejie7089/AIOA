### 5.2 `approval_order.form_data` → 引用 `form_submission.id`

**目标**：消除 `form_submission` 与 `approval_order.form_data` 的双真源，统一为审批中心按需 join。

**涉及文件**：

- 新增 `server/aioa-boot/src/main/resources/db/migration/V88__approval_form_submission_ref.sql`
- `server/aioa-org/src/main/java/cn/aioa/org/entity/ApprovalOrder.java`（加 `form_submission_id` 字段 + 外键）
- 各业务 service（`LeaveService` / `OnboardingService` 等）写审批单时同步落 `form_submission`
- 审批中心查询 service（`ApprovalService.list / detail`）加 join

**改动要点**：

1. **迁移 V88**（0.3d）：
   ```sql
   ALTER TABLE approval_order ADD COLUMN form_submission_id BIGINT NULL
     COMMENT '关联 form_submission.id；为空表示历史硬编码 JSON';
   ALTER TABLE approval_order ADD INDEX idx_form_submission_id (form_submission_id);
   ```

2. **写侧改造**（1d）：
   - 各业务 service 调用 `ApprovalFlowService.submit(bizType)` 之前，先调用 `FormSubmissionService.submit` 落 `form_submission`（即使策略是 APPROVAL）；
   - 把 `form_submission.id` 写到 `approval_order.form_submission_id`；
   - `approval_order.form_data` 字段保留（标 @Deprecated）以兼容历史数据，但新增数据不再写入。

3. **读侧改造**（1d）：
   - `ApprovalService.detail(id)`：先查 `form_submission_id`；
   - 若非空，join `form_submission` 拿字段渲染详情页；
   - 若为空（历史数据），fallback 到 `form_data` JSON 解析 + 警告日志。

4. **单测**（0.5d）：
   - 新增 `ApprovalServiceFormSubmissionJoinTest.java`；
   - 断言：新建审批时 `approval_order.form_submission_id` 非空；
   - 断言：审批详情能 join 到 `form_submission`；
   - 历史数据回退路径要走通。

**验收**：

- 迁移执行成功（V88）；
- 新建请假单 / 报销单时 `form_submission` 与 `approval_order.form_submission_id` 一一对应；
- 审批中心能正常渲染详情；
- 历史数据审批详情仍能渲染（fallback 生效）；
- 新增测试绿。

**估时**：3–5 天。

**风险/回归**：

- 不要一刀切删除 `form_data` 列（历史数据回填成本太高）；
- 写侧改造要按业务逐个迁移（不要批量改），每个业务单测覆盖。
