# agent loop 完成判定闭环（2026-11-06）

> 用户现场截图：「帮我写一份周报」后，界面只有一句
> 「我先把本周的原始素材拉齐，再整理成周报。」+「数据来源 · 4 个」引用卡，
> 周报正文一个字都没有，run 却记 `SUCCEEDED`。
>
> 用户口径（原话）：**以 agent loop 为核心执行约束**，禁止任务只完成一半就停止；
> 保持目标、进度与完成判定的闭环；只要仍有需求未覆盖、错误未处理、输出不完整或
> 完成标准未达成，就不得结束、不得返回中间态、不得把剩余工作交给用户；
> 最终交付必须包含**完成状态、已覆盖的全部需求、完成依据**；
> 不得用「待续 / 稍后补充 / 剩余部分自行处理」收尾；
> 客观阻塞须在同一轮内穷尽可执行内容并精确列出未决项，阻塞说明本身不得充当交付。

## 1. 根因：结束判定答错了问题

旧 `route_after_agent()` 的结束条件只有一条：

```py
if calls and state.get("allow_tools"): return "tools"
return "finalize"          # 「本轮没调工具」⇒ 当作最终答案
```

它回答的是「模型还要不要调工具」，没有回答「**用户的目标达成了吗**」。

跨源聚合（`aggregate`）恰恰在 `prepare` 阶段由代码直连把素材注入 system，模型不需要再调
工具，于是「零 tool_calls ⇒ finalize」把一句导语当成交付，`run` 记 `SUCCEEDED`。
`chat_message#2966` 留有现场真实原文，一字未改：

```
我先收集本周的实际数据（日志、考勤、审批、业务产出），再据此起草周报。
```

同批 `chat_message#2970`（MiniMax 通道复现）则是另一种更隐蔽的中间态：

```
已完成的工具查询结果：
· list_todo_approvals：失败
· my_attendance：成功
…
```

工具结果清单 249 字被当成周报正文，界面停住，run 仍是 `SUCCEEDED`。

**提示词只能降低概率**（本项目已多次实测「写了 ≠ 模型会用」），所以完成判定必须做成
代码侧的确定性闸，不能只靠模型自觉。

## 2. 设计：软硬两层 + 确定性补齐自环

### 2.1 软约束（提示词）

- `agent/aios_ai/prompt/builder.py`：新增「【任务闭环 · agent loop 核心执行约束】」5 条 ——
  不得结束/不得返回中间态/不得把剩余工作推给用户；交付类任务末尾三行交代
  **完成状态 / 已覆盖的需求 / 完成依据**；禁用「待续」类收尾；客观阻塞先写完成稿再列
  「未决项 / 原因 / 当前状态 / 下一步可行路径」；不得把本该自己做的步骤改写成「请你自己…」。
- `agent/aios_ai/aggregate/plan.py` 的 `build_block()`：汇总要求从 5 条扩到 8 条，明确
  「**本轮就要给出成稿**」「素材已在上面，不需要再『先拉素材』」「界面会单独渲染
  『数据来源』引用卡，**那不是周报正文**」「某源失败不是停摆的理由」「末尾交代三要素」。

### 2.2 硬闸（确定性，新增 `agent/aios_ai/graph/delivery.py`）

| 常量 / 正则 | 作用 |
|---|---|
| `DELIVERY_RE` | 识别交付类诉求（周报/日报/总结/汇总/报告/方案/清单/台账…） |
| `UNFINISHED_RE` | 命中「待续 / 稍后补充 / 剩余部分自行处理」即中间态 |
| `PLAN_ONLY_RE` | 短句且只有「我先…再…」「正在整理」「请稍等」等计划句 |
| `SECTION_RE` | 成稿结构：小节 / 编号 / 条目 / 分节标题 |
| `DELIVERY_REQUIRED` | **完成状态 / 已覆盖 / 完成依据** 三项齐全（用户原话） |
| `MIN_DELIVERY_CHARS=140` | 交付类正文长度下限 |
| `MAX_DELIVERY_RETRIES=2` | 补齐轮上限，与工具轮分开计 |

`is_delivery_request(text, aggregated)`：聚合任务一律算交付类（代码已代拉素材，本就该成文）。
`assess_delivery(content, delivery)` 返回 `(是否达标, 未达标原因)`，原因写进补齐指令与日志。

**判据刻意收窄**：只对能客观判定的中间态动手；「你好」这类闲聊、以及
「我先说结论：这份周报可以直接交付。」这类**正在给内容**的短句不受影响
（`PLAN_ONLY_RE` 刻意不认裸的「我先」）。

### 2.3 补齐自环：`agent → agent`

`agent` 节点在「零 tool_calls 且未达标」时置 `delivery_pending=True`；
`route_after_agent()` 新增分支 `if state.get("delivery_pending"): return "agent"`；
`builder.py` 的条件边映射补 `"agent": "agent"`；`state.py` 声明
`delivery_pending / delivery_retries / delivery_reason` 三个写回键。

**不撤回已流出的导语**：流式 delta 已发给前端，界面没有撤回通道。因此追加一个 user 轮
`continuation_prompt()` 让模型「接着写完」，`content_parts` 累积拼接 ⇒
界面 delta、落库 content、后续上下文三者仍同源。补齐轮同时把本轮 assistant 导语并入
上下文（避免两条连续 user 消息、避免模型重复输出导语）。

### 2.4 收口诚实性

`finalize()` 不再以「补齐轮数用尽」为标注前提：**只要 `assess_delivery` 判不达标就追加
`exhausted_note()`**，列出「完成状态：未完成 / 未决项 / 当前状态 / 下一步可行路径」。
`run.completed` 新增 `delivery_complete` 字段，让「流程成功但交付未达标」可观测
（Java 侧仍按帧置 `SUCCEEDED`，表示链路正常收口，语义不冲突）。

## 3. 真机暴露的第二条缺陷链（比截图更深）

用 MiniMax 通道跑真机时，发现首版闸仍会漏：

1. 模型把工具轮跑满后**零正文**；闸触发第 1 次补齐；
2. **补齐轮模型惯性又吐 tool_calls** ⇒ `delivery_pending = not calls and …` 变假 ⇒
   补齐被跳过，直接 `finalize`；
3. `finalize` 的旧兜底「已完成的工具查询结果：…」把工具清单写进正文，
   且因 `retries` 未达上限，`exhausted_note` 不触发 ⇒ **中间态被记成 SUCCEEDED**。

三处修复（全部由真机证据驱动）：

- **补齐轮禁工具**：`agent()` 读 `continuation = state["delivery_pending"]`，
  `allow_tools = rounds < MAX_TOOL_ROUNDS and not continuation`；补齐轮仍返回的幻觉
  `tool_calls` 一律丢弃，并补一条纯文本 assistant 消息，避免留下没有 tool 消息回应的
  孤儿 `tool_calls`（上游会 400）或两条连续 assistant。
- **补齐轮不重新触发确定性开表/澄清短路**：两个分支都加 `not continuation`
  （它们原本都以 `not calls` 为条件，而补齐轮 calls 已被清空）。
- **`fallback_only` 标记**：`finalize` 里「零正文 + 工具结果汇总」和「空内容提示」两种兜底
  一律强制判为不达标，不许凑够 140 字就冒充成稿；`exhausted_note` 的触发条件改为
  `if not complete`（不再要求 `retries >= MAX`）。

## 4. 顺带修掉的两处既有回归（同一轮内穷尽可执行内容）

| 缺陷 | 根因 | 修法 |
|---|---|---|
| H5 纯文本 `run.failed` 帧的真实原因丢失 | `sseError()` 只在 `data` 能 `JSON.parse` 时取 `message`，纯文本一律丢成「生成失败，请稍后重试。」，`401/502` 永久不见 | 非 JSON 分支保留原文并过 `safeErrMsg()` 清洗；`_check_clar_no_silent_deadend.py` 的 S1 判据升级到当前 `errText(err,{withId:true})` 写法，并补 S1b 防回归 |
| 406 协商失败哨兵恒 FAIL | 判据硬钉旧词「不支持的响应类型」，后端 `ErrorCode.NOT_ACCEPTABLE` 早已改为「该接口不提供你要求的响应格式」 | 判据从 `ErrorCode.java` **回源**取官方文案，状态/信封/JSON 断言逐字不变 |
| 沙箱回归偶发 FAIL | 子进程 `import pandas` 冷启动实测 4.5–5.4s，卡在 `timeout=5` 边界，全量并发时偶发 5027ms 超时（单跑必过） | 只调**测试执行预算**到 20s，所有 `ok/data/拦截` 断言不变；另补 `test_sandbox_timeout_still_bites` 判别力证明超时闸仍有牙 |
| `test_disabled_connectors` 崩 | stub 只 yield `done` 不 yield `delta`，等于模拟「零正文」，被新闸正确拦下并触发补齐；补齐轮不挂工具使 `list(tools)` 崩 | stub 按真实流式协议补发 `delta`，**断言逐字不变** |

### 5.3 环境阻塞与绕行（如实记录）

默认通道 `deepseek-chat` 余额耗尽（`402 Insufficient Balance`），直连真机测试全部
`run.failed`，与本轮代码无关。处理方式：

- 验收脚本加 `--model` 参数，仅对**本轮 run** 指定 `model_ref=dashscope`（qwen-plus），
  不改全局默认配置、不改库、不改 `.env`；
- 为让不带该参数的既有活体哨兵也能跑完，用 `/internal/v1/models/apply` 做**进程级**
  热更新临时切默认通道，跑完立即 `apply(default=deepseek)` 恢复
  （日志两条可查：`00:08:19 → dashscope`、`00:19:07 → deepseek`）；
- 结论：**所有活体判据都真正跑过**，不是以「额度不足」为由 SKIP 了事。

## 6. 新踩的坑（已并入 `topics/pitfalls.md`）

- **106**：SSE 长 JSON 帧不要用 `str.splitlines()`（还会按 U+2028/U+0085 切中文正文）；
  也不要把非 `data:` 的续行并进 payload（会把 `id:null` 拼进 JSON，制造「delta 多 2 字」假故障）。
- **107**：`requests` 读 SSE 不带 charset 时按 latin-1 解码，中文成
  `å·²ä¸º…`、长度翻倍、中文判据恒假 ⇒ 必须 `resp.content.decode("utf-8")`。
- **108**：`mysql -N` 命令行把正文里的真实换行转义成字面 `\n`，造成「库里 699 字 vs
  SSE 674 字」的假不一致 ⇒ 回库核正文必须用 pymysql 取值。
- **109**：补齐轮若不显式禁工具，模型会惯性吐 tool_calls 让 `not calls` 变假，
  完成判定闸被绕过；`finalize` 的工具清单兜底更会被当成成稿还记 SUCCEEDED。
- **110**：`exhausted_note` 不能以「补齐轮数用尽」为触发条件 —— 补齐被幻觉调用中断时
  `retries` 可能仍是 0，旧条件会静默放行中间态。
