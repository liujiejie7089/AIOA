## §1 全部数字人逐个普查：43 个里有 43 个受同一个结构缺陷影响

**用户原话**：「每一个数字人都有这样的问题，你全部检查一遍」。
（承接 10-17 的「数字人不调用自定义表单」——那次只修了「调不调」的开关，这次查「调的是不是自己那张」。）

### 结论一：结构缺陷 —— 数字人绑定的表单从未参与下发（43/43 全中）

- `worker_capability` 表：**516 行 = 43 个 OA 模板 × 12 个租户，每个数字人恰好绑 1 张 `form_code`**；
  另有 4 个历史数字人（`86 政策快讯员` / `87 请假助手` / `88 办文助手` / `89 晨报员`）**0 条能力**。
- 但 `RunService` 下发 `available_forms` 走的是 `FormTemplateService.listAvailable(tenantId)`：
  **只按租户过滤，完全无视 worker_capability**。每个租户 43 张 ACTIVE 表单 ⇒ **每个数字人都拿到全部 43 张**。
- 出口也不校验：`buildNeedFormPayload` 拿到模型给的 `form_code` 只按租户查库，查得到就渲染。
- **实测证据（修复前，真实链路）**：
  - 用车助手（`vehicle_apply`）问「我要报销打车费」→ 弹 **`expense_form`（费用报销，别人的表）**
  - 会议助手（`meeting_book`）问「我要申请出差」→ 弹 **`travel_form`**
  - 会议助手在只下发 `meeting_book` 后仍产出 **`leave_request`**（提示词里 `leave_request` 是唯一示例）
- **判据要点**：`worker_capability` 是**只写不读**的元数据 —— 只被管理端 CRUD 和创建时校验用过，
  运行期一次都没被读。这与 10-17 的 `AIOS_HITL` 是同一类：**能力写了，但没有任何一条链路读它**。

### 修复（两道闸 + 一处去偏，都在确定性代码里）

1. **下发面收窄** `RunService.narrowFormsByWorker`：按会话 `workerId` 取能力，数字人绑几张就下发几张。
   未绑数字人 / 没配能力 / 读库异常 ⇒ **保持租户全量**（GENERAL 等历史数字人不受影响）。
   能力指向的表被停用 ⇒ 返回空 ⇒ 不下发清单（宁可说没这功能，也不让调停用的表）。
2. **出口闸** `RunService.buildNeedFormPayload`：`form_code` 不在该数字人能力内 ⇒ 直接回 error 帧，
   **不查库、不渲染**（`verify(..., never()).resolveForRender` 钉死拦截位置）。
3. **提示词去偏** `agent/aios_ai/tools/request_form.py`：工具描述原写「必须来自清单（**如 leave_request**）」
   —— 示例比清单更容易被照抄。改为只描述来源、不给具体 code。
4. `agent/aios_ai/prompt/builder.py` 强制使用规则 **+3 条**（都由实测失败样本反推）：
   - 规则 4「禁止把工具调用写成文字」（模型会把 `{"form_code":...}` 当正文输出，或列字段追问）
   - 规则 5「表单与项目无关」（模型答「请先进入一个项目」）
   - 规则 6「参数不全也要开表单」（枚举字段不该在正文里让用户先选）

### 可迁移教训

1. **「有绑定表」≠「按绑定表走」**：凡是「用户/管理员配置的绑定关系」，必须有一条运行期代码**真正读它**。
   判据不是「表里有数据」，而是「grep 这个 Service 的调用点，落在主链路上」。本项目已连犯三次
   （`AIOS_HITL`、`worker_capability`、`form_template.rules`）。
2. **下发面给宽 = 让模型合法地做错事**。43 张表全给，模型选错不叫「幻觉」，叫「界面允许它的选择」。
3. **提示词里的具体示例会被照抄，比清单更有权重**。工具描述里写 `leave_request`，模型就吐 `leave_request`，
   哪怕它不在本次 `available_forms` 里。示例要改成「逐字取自清单」这种不指向具体值的写法。
4. **两道闸要分别验证**：先证明「下发面收窄了」，再证明「出口能拦住兜底」。
   只验前者，会在模型编造 code 时漏掉后者（本次 1247 就是这样漏的）。
5. **SQL 侧判据**：核对「每个数字人绑几张表」用
   `select cnt,count(*) workers from (select w.id,count(c.id) cnt from agent_worker w left join worker_capability c on c.worker_id=w.id and c.deleted_at is null where w.deleted_at is null group by w.id) t group by cnt`
   —— 一眼看出「516 个各绑 1 条、10 个 0 条」，比逐个读代码快。
6. 12 个租户的 `(task_code,task_name,form_code)` 元组 **md5 完全相同** ⇒ 43 个模板全租户同构，
   实测一个租户即可覆盖 516 个数字人的行为差异。判据：
   `select tenant_id, md5(group_concat(concat(task_code,'|',task_name,'|',form_code) order by task_code separator ';')) from worker_capability ... group by tenant_id`。

## 二、第三道闸：确定性开表 + 全量普查收官（43/43）

### 2.1 为什么还要第三道闸

前两道闸（下发前按 `worker_capability` 收窄清单 + `buildNeedFormPayload` 出口校验）修完后，
普查仍有 7 个数字人不出表：1210 安全与权限 / 1213 财务 / 1226 工会 / 1227 党务 /
1228 文档管理 / 1242 费用报销 / 1247 会议 / 1249 公文。它们的 `task_name` 极泛
（「工会事项办理」「公文办理」），模型选择在正文反问「请问您要办理哪项业务？」而不调 `request_form`。
这不是绑定错，是模型-compliance 问题；再调提示词的边际收益已很低且有误触发风险
⇒ 改为**确定性代码判定**：每个数字人只绑一张表，用户原话点名了这项任务就直接开表。

### 2.2 两个走过的弯路（都别重犯）

1. **第一版把 need_form 帧放在 Java 流末补发**（`forward` 的 `message.completed` 之前 +
   `completeRun` 兜底）。红绿看着对（8 个 worker 全 PASS），但日志露馅：
   `resume (answer=None)` 之后 agent **立刻结束、零帧**。原因：补帧只在 Java 侧产生了一帧，
   **图里没有 `interrupt()`、没有 checkpoint**，用户提交表单后 `/resume` 无从恢复，
   模型拿不到回填数据。⇒ 判据：**「帧出现了」不等于「链路通了」**，必须验一次
   「提交 → 续跑」的续跑流是否真有内容。
2. **续跑会重弹**。第一版没区分首发/续跑，而 `lastUserText(run)` 按 `run_id` 取、续跑不落新
   user 消息 ⇒ 取到的仍是原话，判据必然再命中。虽然后来改成图内开表后 `clarifications` 非空
   天然挡住，但「首发/续跑」这件事当初就该用显式形参表达，而不是靠状态副作用兜。

### 2.3 最终架构（判定在 Java 一处，执行在 agent 图里）

- Java `RunService`（dispatch 期）：`uniqueCapability(workerId)` 取唯一启用能力行；
  `shouldOpenSingleForm(text, taskName, taskCode)`（纯函数，静态可单测）命中
  ⇒ 往 `AgentRunRequest` 塞 `form_hint = {form_code, reason}`。
- agent `nodes.agent`：模型本轮**没有任何工具调用** + `_hitl_enabled()` +
  `clarifications` 为空（= 不是续跑后的轮次）+ `form_hint` 存在
  ⇒ 造一条归一化控制调用 `{id,name,arguments}` 进 `pending_calls`，**同时**往
  `messages` 追加 OpenAI 形状的 assistant `tool_calls`（两种形状不能混：
  状态里是 `{id,name,arguments(dict)}`，消息里是 `function.name/arguments(str)`；
  混用会让 `route_after_agent` 认不出 request_form、直接走 `tools` 并 `KeyError: 'name'`）。
  然后走既有 `clarify` → `interrupt()` → `need_form`，**真实断点**，
  续跑后 `clarifications` 非空 ⇒ 不会再开第二次。
- 提示词不再承担这个判定（`request_form` 的 `form_code` 描述已删掉硬编码示例
  `leave_request`，模型曾逐字照抄它）。

  （26.6s，明细 `logs/proof/form_routing_census.json`）。修前 28 PASS / 15 R1_FAIL；
  两道闸后 36；三道闸后 43/43。NO_CAP 4 个是 86/87/88/89 历史数字人（无能力绑定）。
- 新增哨兵 `scripts/_verify_form_resume_no_reopen.py`（U1–U5）：首发开表 / resume 200 /
  **续跑帧里无 need_form** / 续跑非 run.failed / 问候不误触发。已登记进
  `_run_all_regression.sh`（与普查脚本同批）。
- 单测：Java `RunServiceFormFrameTest` 14（含 shouldOpenSingleForm 6 个）、
  `RunServiceHitlTest` 4；Python `test_aios_ai_form_hitl.py` 6（新增 form_hint 图级用例）、
  `test_aios_ai_hitl.py` 2、`test_aios_ai_graph.py` 8。变异测试都做过：

### 2.5 顺带修掉的真缺陷：`answer=null` 续跑必崩

用户关掉澄清卡/表单卡（后端透传 `answer: null`）时，LangGraph
`pregel/_loop.py:999` 的 `if resume_is_map := (...)` 不执行赋值，紧接着
`if not writes and not resume_is_map:` 抛 `UnboundLocalError`
⇒ `MODEL_STREAM_ERROR` + `run.failed`，整轮对话失败。
修在 `facade.resume`：`None → {"cancelled": True}`（唯一入口，含注释说明为什么不能传 None）。

### 2.6 哨兵自身踩的两个坑（写新哨兵时照抄结论）

- **读到 `need_form` 就断流** ⇒ 后端 `completeRun` 不执行、`markWaitingInput` 不落库，
  run 卡在 `RUNNING`，后续 `/resume` 报「不是等待澄清状态」—— 表现为「哨兵自己制造的红」。
  真实前端会读到流尾，哨兵必须同样读到终态帧。
- **把 `message.completed` 当终态** 也会早断（它之后还有 `run.completed`）。
  判据必须是 `run.completed` / `run.failed` 或连接 EOF。
- `markWaitingInput` 与客户端读尾有毫秒级竞态 ⇒ `/resume` 非 200 时短重试（≤6 次 × 1s）。

## 三、B-1 服务间令牌 + B-3 知识库静默降级（2026-10-18 下半场）

### 3.1 B-1：agent `/internal/v1/*` 此前**零鉴权**

审计结论（docs/45 C-1 同类）：同网段任何进程都能调 `models/apply`（把模型密钥热加载进进程）、
`runs`（烧额度 + 执行工具）、`runs/{id}/resume`（劫持挂起中的会话）。

落地：
- **agent 侧**新增 `aios_ai/security/service_jwt.py`（标准库 HS256，不引 PyJWT —— 少一个
  「容器里没装」的失败面）+ `app/main.py` 的 `_require_service_jwt` 中间件，**按路径前缀拦**
  （新增内部端点自动受保护，不必逐路由加依赖）。安全要点逐条落在代码里：alg 必须逐字 `HS256`
  （拒 `none` / alg-confusion）、`compare_digest` 常量时间、`exp` 必填、`svc ∈ {agent,server}`、
  **空密钥失败关闭**。
- **Java 侧全部调用方必须带票**（这是最容易漏的一半）：`RunService`（runs / resume / tasks，
  WebClient，原本就有）、`WorkerIntakeService`（worker-intent）、`WorkerScheduleService`（complete）、
  `KpiInsightService`（complete）、`AsrController`、`ModelConfigService`（3 处）。
- **兜底纪律**：漏票在 Java 侧**不会报错**。`WorkerIntakeService` 的 catch 分支把 401 当
  「agent 不可达」而**静默降级**为本地关键词推断；`WorkerScheduleService` 把 401 写进
  `error_msg` 像「模型不可用」；`KpiInsightService` 抛「AI 服务返回 HTTP 401」。三种症状都不指向
  「少一行 header」⇒ 新增静态哨兵 `scripts/_check_internal_service_auth.py`（含 `--selftest` 5 例）。

### 3.2 两个自伤，都值得记

1. **`_load()` 里写 `os.getenv("SERVICE_JWT_SECRET", "")` 让字段默认值永不生效**：
   pydantic 收到显式空串就覆盖 default ⇒ `verify()` 失败关闭 ⇒ **全站 401**。
   这正是铁律 21 的同族坑（「兜底写在默认值上，调用链却显式传空」）。修法
   `os.getenv(K) or DEV_SERVICE_JWT_SECRET`，并把这条写进铁律。
2. **并行 Edit 同一文件会静默丢改动**（同一条消息里两次 Edit 同一个文件）：
   本场 3 个 Java 文件的**字段声明全被丢掉、只有 header 那处落盘**，直到 `mvnw` 报
   「找不到符号 serviceTokenProvider」才暴露；两个测试文件的 import 也这样丢过一次。
   ⇒ **同一文件的多处修改必须串行**；批量改多个文件用「文本替换 + 命中计数」的一次性脚本更稳
   （本场就是这么补 5 个回归脚本的）。

### 3.3 部署口径：agent 容器变量名必须对

`agent/aios_ai/config.py` 读 **`SERVICE_JWT_SECRET`**（无前缀），Java 读 `AIOS_SERVICE_JWT_SECRET`；
`deploy/docker-compose.yml` 的 agent 服务此前只给了 `AIOS_` 前缀那个 ⇒ 容器内 agent 落到开发占位串，
与后端真实串不匹配 ⇒ 一上鉴权就**生产必 401**。已改成 `SERVICE_JWT_SECRET: ${SERVICE_JWT_SECRET:-…}`。
另加启动日志 `service jwt ready: fingerprint=<sha256 前 8 位> dev_placeholder=<bool>`，
两端对不上时能直接比指纹，不必抓包。

同时修 `_check_compose_env_wiring.py` 报出的两个真问题：`AIOS_ASR_ENABLED` / `AIOS_ASR_MAX_BYTES`
被 `application.yml` 引用但 compose 未透传（.env 里设是空转）——已补进 server 环境。

### 3.4 B-2（顺带可见化）：内存版挂起态

## 四、会话内跨数字人转交（handoff）+ 专家 AI 真能力（2026-10-18 晚）

### 4.1 用户需求（原话）

「数字人只能处理自己能力的事，如果在请假数字人上报销，会跳转到报销数字人，并且要同步上下文，
**不要让用户输入同样的问题**」+「管理端：表单设计器放到智能服务里面」。

### 4.2 为什么不能「换数字人 = 新开会话」

H5 原来的 `oaPickWorker` 换数字人就 `S.convId = null` ⇒ 新会话、历史全丢 ⇒ 用户必须重说。
**「不重述」的前置是「不换会话」**：所以在同一会话里改绑 `chat_conversation.worker_id`，
历史天然跟着走；agent 也拿不到跨数字人上下文（它只看到一个 `scope`），故**判定只能在 Java**。

### 4.3 判定：`matchHandoff` 纯函数（两级 + 四闸）

- **Tier A（强）**：候选 `task_name`（>=2 字）或 `task_code` 出现在用户原话里。
- **Tier B（弱，只在 A 全不命中时启用）**：任务名剥掉通用词（申请/办理/助手/设置/填报…）得核心词，
  与用户原话求**最长公共子串**，>=2 字才算命中。
  存在的理由（实测）：库里是书面语「费用报销申请」，用户说口语「我要报销差旅费」——

### 4.6 ★Tier B 上线后把 43 项表单路由打崩（43 PASS → 27 PASS）——两个自伤

**现象**：普查从 43 PASS 掉到 27 PASS / 16 FAIL，且失败形状诡异——模型把别的数字人的职责
**原文**当成自己的（「公文助手」说「我的职责范围是合同管理，包括合同起草要点…」）。

**定位**（不猜，打日志）：给 agent 临时加一行 `scope.duty=%r forms=%d` 打印，
三个 case 立刻看出 scope 全是**别人的**职责原文 ⇒ 说明会话被改绑了。
再打印交互帧：首帧就是 `worker.handoff`：

```
1249 公文助手（问「帮我办理公文起草」）→ 转给 1216 合同管理（重叠「起草」）
1216 合同管理（问「帮我办理合同起草」）→ 转给 1249 公文助手（重叠「起草」）
1208 数据分析（问「帮我办理看板配置」）→ 转给 1223 门户首页（重叠「配置」）
```

**两个根因（都出在我自己写的闸上）**：

1. **候选里排除了当前数字人**（`resolveHandoff` 里 `continue; // 排除当前 worker`）。
   而 `matchHandoff` 的闸 #1 是「当前数字人也命中 ⇒ 不转」，它的实现依赖候选里有当前那行
   （`Objects.equals(c.workerId(), currentWorkerId)`）⇒ 排除后**这道闸结构上永远不可能生效**。
   注释与实现自相矛盾：注释说「当前 worker 永不作为转交目标」，那只该影响「目标」，
   不该影响「是否与当前重合」的判定。
2. **通用词表漏了两字动作尾缀**（配置/起草/设置/填报/登记/录入/借阅/发起/发布/维护/添加/新建/申诉/
   报名/下发…）。`coreOverlap` 只把「整段片段」拿去查通用词，于是「起草」「配置」这种两字尾缀
   被当成业务重合 ⇒ 名字相近的任务互相转。

**修法**：① 候选恢复为「本租户全部启用数字人」（当前行的排除改由 `matchHandoff` 内部承担）；
② 通行词表补齐 19 个动作尾缀；③ 单测 H14（只差尾缀的两个任务双向都不得转）、
H15（`coreOverlap("帮我办理公文起草","合同起草")==""`、`coreTaskName("看板配置")=="看板"`）。

**收口**：`RunServiceHandoffTest` 15 项、`RunService*` 全量 **39 项**全绿；
表单路由普查恢复 **43 PASS / 0 CLARIFY / 4 NO_CAP / 0 FAIL**；
转交 e2e 仍 **10/10**、专家 e2e 仍 **7/7**。

**可迁移教训**：① 写「排除某元素」时先问「有没有别的判据要靠这个元素存在」——
    一个 `continue` 能让另一处的闸变成死代码，而单测（候选里带了当前行）根本发现不了；
② 两字中文后缀是**噪声不是信号**（起草/配置/申请/办理），弱匹配必须把它们列入黑名单，
    否则「相近」会退化成「相邻」；③ 全量普查的价值就在这：43 项里 16 项同时变红，比任何单测都早发现。

## 七、生产机 `git pull` 被挡 → 把 pip 源改成 build arg（`5e59652`）

**用户报的现象**：GitHub 上明明有新提交（`79b94fa`），生产机拉完「文件没变化」。
真因：`git pull` **abort 了**，一个文件都没落地 ——
`error: Your local changes to deploy/Dockerfile.agent would be overwritten by merge`。

**服务器本地改动到底是什么**：只有一行，把
`RUN pip install --no-cache-dir --upgrade pip && pip install --no-cache-dir .`
改成走清华源 `-i https://pypi.tuna.tsinghua.edu.cn/simple --trusted-host …`。

**判定**：这是**环境差异**，不是业务定制 ⇒ 不该留在工作区（会让每次 pull 都冲突），
也不该把它 commit 上去（会把国内镜像强加给所有环境）。
⇒ **参数化**：`ARG PIP_EXTRA_ARGS=`（留空=上游默认）＋ compose `agent.build.args` 透传
＋ 两个 `.env` 加「10 · 构建期」空键；生产在 `deploy/.env`（gitignored）里写镜像源即可。

**顺带确认的一处缺口**：服务器本地改动**没有** `COPY aios_ai` ⇒ 它构建出的 agent 镜像
缺 AI 内核（`ModuleNotFoundError: aios_ai`）。所以拉完**必须重建 agent 镜像**，不能只重启容器。

**哨兵**：`_check_agent_image_layout.py` 加 L8（禁止硬编码源、必须有 `${PIP_EXTRA_ARGS}`）、
**L8b 负向对照**（合成硬编码文本必须判红）、L9（compose 真透传）。实跑 **10/10 OK**。

**可迁移教训**：① 「pull 说没变化」先看**是不是被 abort**，别怀疑远端；
② `git status` 的一行 `M` 能让一条链路长期卡死，而它**不在**你正在看的那条错误里；
③ 生产与开发不一致的构建参数，**一律 .env / build-arg**，永不改受版本控制的文件。
