### ★ 关键语义：红冲 = 同方向负金额（红字冲销），不是「方向翻转 + 正金额」
- 首版实现写成「方向翻转 + 正金额」，实测发现**汇总回不去**：汇总是按方向分桶累加，
  翻转会使被冲销的支出**仍留在支出桶**（支出不减）、冲销额混进收入桶 ⇒「结余 = 预算 − 支出」不变。
  已改为**同方向、负金额**的红冲行 ⇒ 同桶自然抵消（`F5f` 支出回退、`F5g` 收入桶不受污染守住）。
- 两条负向约束：同一原行重复红冲 → 409；红冲一条红冲行 → 400。`append()` 仅允许红冲行取负。
- **教训**：我第一版把断言写成「方向翻转」——那是**照抄自己的实现**（同源谬误）。
  正确做法是先定「红冲应让经济效果归零」，再据此写断言，于是实现被迫改对。

## 九、Gitee「打通」收口（用户给出生产网络拓扑后）— 结论：公网入口已存在，阻塞解除

用户原话：「我的服务器是 `10.0.0.3:22`，通过隧道机 `219.151.186.24:22` 访问，但 `10.0.0.3` 能访问外网」。

- 这条信息**推翻了 §七 的旧结论**（「本机 127.0.0.1 不可能被回调 ⇒ 需要公网/内网穿透」）：
  生产**已经有公网入口**，只是当时不知道。
- 实测链路：`mall.egoaicloud.com` → A `219.151.186.24` → 其 `:443` 终结 TLS（证书 SAN 匹配）
  → openresty **原样不剥前缀**转发 `/aioa/...` 到 `10.0.0.3:8080`。
- 探活（走公网域名，非 IP）：`GET /aioa/api/v1/pm/projects` → **401**（后端可达）·
  `GET /aioa/api/v1/gitee/webhook/1` → **405**（路由存在，仅 POST）⇒ **webhook 回调面已就绪**。
- **★ 域名拼写是 `mall.egoaicloud.com`（ego**ai** 单 o+ai）**：双 o 的 `mall.egooaicloud.com`
  DoH 解析失败（不存在）。**拼错 ⇒ DNS 失败 + TLS 证书名不匹配 ⇒ 授权/webhook 静默失败**，

- `10.0.0.3 能访问外网` = **只有出方向**（AIOA→Gitee API 建仓/同步够用）；webhook 的**入方向**
  走上面那个公网入口，不走 10.0.0.3。**两个方向别混**。
- **改动**：`deploy/.env.production` Gitee 段启用（`ENABLED=true` · `SYNC_ENABLED=true` ·

## 十、Gitee 凭据落地 + 发现并修复「compose 未透传 = 静默空转」（2026-10-09 晚）

用户提供 Gitee OAuth `Client ID` / `Client Secret`（截图）。

### 落地（真值只进 `deploy/.env`，已 gitignore）
- `deploy/.env` Gitee 段：`ENABLED=true` · `CLIENT_ID/SECRET` 填真值 ·
  `REDIRECT_URI=https://mall.egoaicloud.com/aioa/api/v1/gitee/bind/callback` ·
  `WEBHOOK_BASE_URL=https://mall.egoaicloud.com/aioa` · `BIND_RETURN_URL=…/aioa/web/` · `SYNC_ENABLED=true`。
  **`TOKEN_ENC_KEY` 原本已有值（`zBvb1/…`），故意不动** —— 改了会让已存令牌解不开。
- **client_id 与 `2026-09-17.md` 记录的值逐字一致**（同一 Gitee 应用）。那次踩过「第 34 位是 b 不是 e」的
  转录坑；这次值第 34 位正是 `b` ✓（可交叉验证）。secret 从未入库。
- 核验：`git status` 仅 `docker-compose.yml` 变更；`deploy/.env` 仍被忽略；
  入库文件 grep 两段新密钥前缀**均无命中**（唯一命中是 client_id 出现在 `2026-09-17.md`——
  那是历史记录，client_id 属半公开标识，secret 才是机密，secret 不在库里）。

### 发现并修复：`AIOA_GITEE_SYNC_ENABLED` / `_SYNC_CRON` 未透传
- 本 compose **无 `env_file`**，`deploy/.env` 只作 `${}` 插值源；容器只收到 `server.environment`
  里**显式列出**的键。这两个键 yml 有引用（`${AIOA_GITEE_SYNC_ENABLED:true}` / `${…_SYNC_CRON:0 17 * * * *}`）
  但 compose 没列 ⇒ **在 .env 里把 sync 关掉是空转**，容器永远按 yml 默认 `true` 跑，且不报错。
- 修法：给 compose `server.environment` 补上这两键（默认值与 yml 一致，不改变现有行为）。
- 同类历史实例：`SPRING_DATASOURCE_*` 被 compose 现拼覆盖（`production-deploy.md` 已记）。

### 新增哨兵：`scripts/_check_compose_env_wiring.py`
- 判据：`application.yml` 里每个 `${VAR}` 必须 ① 被 compose 透传，或 ② 在 **BENIGN 白名单**里并写明理由
  （白名单是唯一豁免出口，逼着「为什么它不是空转」被写下来）。有**反恒真下限**（refs>60 / passed>50，
  解析器坏了必须报红，不许「0 个引用 ⇒ 恒绿」）。
- `--selftest` **7/7**：含 S6「把已修的 `AIOA_GITEE_SYNC_ENABLED` 从透传里摘掉 ⇒ 必须报 FAIL」。
- 运行结果：`application.yml 引用 74 / compose 透传 72`，PASS + 9 项白名单豁免（均注明理由）。
- 已登记进 `scripts/_run_all_regression.sh`。
- 顺带判定（**不是**缺陷，勿乱改）：
  - `SPRING_PROFILES_ACTIVE` 未透传**无害** —— `resources` 下**只有** `application.yml`，
    没有 `application-{dev,prod}.yml` ⇒ 激活任何 profile 都加载同一份配置。
  - `AIOA_SCFY_*`（四川法院集成未部署）、`AIOA_GITEA_*_TRUST_STORE*`/`_INSECURE_SKIP_VERIFY`
    （Gitea 默认 disabled）⇒ 白名单豁免。**启用 Gitea 前必须把这 4 个 TLS 键一并透传**（已写进白名单备注）。

### 交给用户执行的收口步骤（本机无 docker，跑不了 compose）

5. 重试一个 FAILED 项目 ⇒ `gitee_project` 应从 `FAILED` 转 `ACTIVE`。
