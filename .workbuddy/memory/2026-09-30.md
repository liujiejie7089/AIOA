## 二、请求 6：用户端新版复刻老版「推荐换人 + 表单直出」

用户原话：
> 用户端新版页面如果提问了其他的工作责任的，数字人会推荐相关责任的数字人，可以直接点击更换数字人，和老版一样，涉及需要填写的表单，直接由数字给出，和老版的逻辑一样。

### 先读老版口径（`_backup_index_pre_oa.html` = 重建的唯一基线）
- **推荐换人**：`afterAnswer()` → `guidanceBlock()`；`buildGuidance(experts, …, state.lastQuery)` 用
  `expertKeywords/scoreExpert` 给专家打分，点名称 `guidanceGo('chat:<key>')` → `startChat(i)`
  （**重置 conversationId**），另有「重新回答」`reAnswer()` = 换人 + 重发原问句。
- **表单直出**：`isLeaveRequest(q) && isLeaveCapable()` → 当场插 `leaveFormHtml()`。
  **两条件缺一不可**，否则「一边说不管请假、一边发表单」自相矛盾。
- 老版里「表单融入对话流」只有**请假**一条；技能参数卡（`openSkill`）是另一个入口。

### 新版实现（只改 OA 层，经典基线段一行未动）
`user-client/_oa_app.js` 新增 §9.5：
- 推荐判据**只认两个可核对来源**，别的一概不用：
  ① 后端职责分类器 `POST /v1/workers/intent`（与「新工作任务」**同一个判定点**；Java 侧 Agent 不可达时
  自动降级 `WorkerRole.infer`，故这条链路比 AI 推理可靠）；② 问句里**字面**命中员工名/职责名，
  或老版 `scoreExpert`（**逐字复用**，不另写第二套口径）。
  两者都拿不到 ⇒ **不推荐**（与老版同一取舍：宁可少推荐，也不给无关入口）。
- 推荐块作为数字人的**一条发言**落进对话坞 ⇒ 自动带上指向数字人的三角（`oaLayoutTails` 只认 `.bub`），
  不另写几何。点行 = 换人；「换他重答」= 换人 + 重发上一问（同老版 `reAnswer`）。
- **`oaPickWorker/oaPickExpert` 补 `S.convId = null`**：数字员工是在**创建会话时**绑定的
  （`API.ensureConversation` 带 workerId），沿用旧会话会让「换人」只换个称呼、回答仍出自原员工。
  老版 `startChat` 同样重置会话 —— 这是漏掉的一处口径对齐，不是新需求。
- 表单直出：同一份词表（`oaIsLeaveRequest`）+ 同一判据（`oaLeaveCapable`）→ `leaveFormHtml()` +
  `ensureLeaveTypes()`（假种来自后端配置，写死会打不到真实请假链路）。
- 样式：`_oa_extra.css` 段 2 追加 `.g-*`（推荐行/理由/「换他重答」按钮）。

### 本轮踩到并修掉的两个**真缺陷**（都不是测试问题）
1. **收口竞态 → 重复 id**。推荐/表单要等一次 intent 调用才落地，而这段是 `await` 之外的**异步尾巴**。
   首版为「不拖住下一次提问」写成 fire-and-forget ⇒ 若用户在等待期间切走形态，表单会在**切走之后**
   才塞进已隐藏的对话坞；经典侧再发一份 ⇒ 文档里出现**两份 `#leaveForm`**（E2E H8 实测 count=2）。
   修：加**收口代次** `oaAnswerSeq`，三处作废在途收口 —— 离开新版 / 换对话对象 / 新开对话；
   `oaAfterOaAnswer` 落地前同时判 `seq / mode / lastQuery`。
2. **两形态共用固定 id**：请假表单 id 写死（`leaveForm/lfType/lfStart…`，经典 helper 全靠它们取值）。
   同一文档里必须**至多一份**：新版发新表单前清掉经典遗留的那份（顺带作废其暂存附件，
   否则会带上一份表单的证明材料），离开新版时撤掉自己注入的那份。
   否则经典的「文档里已有表单就不再发」判据会被挡住 ⇒「经典问请假却不出表单」。
   —— E2E **H7/H8 就是这两条的双向断言**（切回经典 count=0；经典自发放后 count=1）。
