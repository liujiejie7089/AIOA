# 2026-10-03 · 信息架构调整：代码仓库并入「开发项目」，撤掉独立菜单「项目与仓库」

## 一、用户诉求（原话）

> 项目与仓库就是代码仓库， 当在项目管理中选择了项目管理-开发项目才会出现 ，你整合一下，不需要单独列一个菜单出来

拆成四条：① 撤掉「项目与仓库」一级菜单；② 代码仓库只跟**开发项目**出现（业务项目不得有 = BR-01）；
③ 整合不得丢能力；④ 验证。

## 二、结论：产品口径成立，按「入口收敛」实施（不改任何仓库能力）

原先 `GiteeProjectsView.vue` 一个页面**捆了两类能力**：租户级配置（企业初始化/组织/令牌/校准）
+ 仓库列表浏览。直接删菜单会让配置类能力**没有入口**（违铁律 4），也会打断两个钉住
`/gitee/projects` 的哨兵。故拆成两处：

| 面 | 变更前 | 变更后 |
|---|---|---|
| 一级菜单 | 「成果与项目 → 项目与仓库」 | **移除**（`MainLayout.vue`） |
| 日常使用 | 同上（全量列表，与项目无关） | 「项目管理 → **开发项目** → 代码仓库」页签（`v-if="isDev"`） |
| 租户级配置 | 混在同一页 | 「系统配置 → **仓库配置**」`/settings/repo-config`（同组件 + `meta.configOnly`，只渲染配置卡，不拉列表） |
| `/gitee/projects` | 菜单入口 | 降级为**不进菜单**的「仓库总览」，入口 = 开发项目页签的「仓库总览与配置」按钮（旧深链与 2 个哨兵继续可用） |

三处同源未破：菜单 / 路由 `meta.allowRoles` / 后端 `PermissionCatalog` 仍共用 `GITEE_VIEW_ROLES`。

## 五、可复用教训（下次别再踩）

1. **改菜单 / 路由要同步「后端用户可见文案」**：后端 5 处消息原本写「请先在「项目与仓库」中配置」，
   菜单撤了以后这些话会把用户指向一个不存在的页面。判据：`grep -r 项目与仓库` 全仓扫一遍。
2. **页头自称必须与路由 `meta.title` 同名**：原先 `/gitee/projects` 页头写「项目与仓库」、路由叫
   「仓库总览」，一个页面两个名字（违铁律 1 同源）。已统一为 `pageName` 派生。
3. **哨兵的精确匹配可能被"自身文案"误命中**：`verify_v48_ui.py` 新增的
   `get_by_text("项目与仓库", exact=True) == 0` 在 `providerLabel` 缺失时会被页头
   `headerTitle = pageName` 恰好命中 ⇒ 假红。改名后与 provider 状态无关，才真正稳健。
   **凡「某某不该出现」的断言，先想清「自身文案是否可能恰好等于它」。**
4. **`verify_v48_ui.py` 在本环境跑不了，且不是本次弄坏的**：账号绑定 `znkj*` 租户
   （`SELECT COUNT(*) FROM sys_user WHERE username LIKE 'znkj%'` = **0**，租户已不在本库），
   且入口写死 dev `:5173`。已在该脚本头部写明并给出可跑替代（见 `topics/e2e-suites.md`）。
   ⇒ **登录失败先查账号是否存在，别先怀疑自己刚改的代码**。
5. **构建残留**：`.dist-old-*` 被 `.gitignore:18` 显式覆盖（项目自有约定，属可弃物），
   但本机 safe-delete（genie-trash）对这两个目录 **fail-closed**（`Some operations were aborted`），
   删不掉 —— 未强删，留着无害（已 gitignored）。
