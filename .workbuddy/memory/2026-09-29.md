## v4：数字人换成用户给的真实图（抠图 + 去水印 + 位图动效）

用户原话：「去掉背景的数字人，直接把这张图作为数字人，去掉水印」（原文「去年」= 去掉）。

**做法**：`buddy-image-processing` 技能（`connect_cloud_service` 取 clientTempToken → `image-edit --operation matting`）。
- 输入 `clipboard-...-7fdf18a1.jpg`(170KB) → 输出 1536×1536 **RGBA**：完全透明 66.4% / 不透明 32.9%。
- **水印不用单独 erase**：「豆包AI生成」在背景上，抠图时随背景一起去掉（实测右下角区域 alpha 均值 **0.0**）——
  matting 一次搞定「去背景 + 去水印」两件事，省一次 API 调用。
- 后处理：按 `alpha>8` 的 bbox 裁掉透明留白（1536→**919×1295**）→ 缩到 560px 宽。
- **体积对比（决定了内联格式）**：同尺寸 PNG **379KB** / WebP **49KB** ⇒ 用 **WebP**（base64 仅 65KB）内联进 HTML，
  单文件仍可用（HTML 165KB）。另存 `user-client/assets/robot.webp`(49KB) / `robot.png`(379KB) / `robot-full.png`(1024px,461KB)。

**同时删掉上一版的 SVG 骨架**（挥手/眨眼是绑在 SVG 部件上的），`.r-wave/.r-blink/.r-ant/.r-pulse` 的
CSS 与 keyframes 一并清除，不留死代码；位图改做 **bob 浮动 + sway 轻微摇摆**（静态图只有动 transform 才「像活着」）。

**动效验证方法（照抄可用）**：静态截图证明不了「在动」。用 `getComputedStyle(el).transform` 隔 520ms 取两次比对；
再补一条 **`img.complete && naturalWidth>0`** —— 内联 base64 若损坏会**静默渲染成空白**，只看截图容易漏。
本轮 `robot motion: {img-loaded: True, bob: True, sway: True}`，console 0 / 横向溢出 0。

**复现的坑**：`present_files` 的预览面板**每次都会重新往 HTML 行内注入 `data-page-node-id`（本轮又 798 处）**。
⇒ 结论修正：这不是「注入一次」而是**每次 present 后都会回来**；`_*` 剥离脚本要**在每次 present 之后再跑一次**，
或干脆等到「入库/嵌入」那一步再统一剥离（预览态带这些属性不影响渲染）。

### 两个关键设计（写进计划的验收点）

1. **「不跳转」⇒ 不复用 `page-chat`**（它是满屏整页会话）。首页内做**对话坞**，但 SSE 处理**抽成共用函数**
   给两处调用，避免两套口径；对话坞用独立 `state.oaConvId` 与 `state.conversationId` 分账。
2. **「三角都对着数字人」⇒ 不能用 IM 左右分侧**。数字人作**坐标锚点 A**，对每个气泡：
   `θ = atan2(A.y-cy, A.x-cx)`（气泡中心→数字人），三角落位 = 该射线与气泡边框交点，
   绕自身中心旋转 `θ-90°`；用 CSS 变量 `--tail-x/--tail-y/--tail-angle` 承载，`rAF` 量测后写回，
   `ResizeObserver` 节流重算。**必须带 3 条降级**（reduced-motion / <360px / 数字人滚出视口→sticky 头像），
   否则极端情况会错位。

### 本轮真正的坑（两条已落 `topics/pitfalls.md` #98 / #99）

- **#98**：`display:none` 恢复时 `bub-in` 动画**重放**，布局在动画第 0 帧量 rect ⇒ 比终态低 8px

## 知识库：上传的资料「点开查看 + 删除」（双形态）

用户一句话需求：`上传的文档自己可以点开查看，与删除`。两种形态都要有。

### 先说清一件事：能看的是「入库正文」，不是原件

`kb_document` 存的是**解析后的正文 + 切片**（上传 = 解析 → 索引 → 存 `content`+`chunks`），
**原件从未落库**。所以「查看」= 展示 `kb_document.content`（与 RAG 检索同源的那份文本），
不是文件预览。要做真正的原件预览得重做上传链路（本轮**明确不做**），交付口径按实际能力说清。

### 后端：新增只读详情端点（读边界复用列表，不重写一份过滤）

- `GET /api/v1/kb/documents/{id}` → `DocDetailView(doc, content, contentLength, truncated)`。
- 可见性判据 **不另写一套**：私有方法 `listedFor(authUser, doc)` 直接问
  `kbService.list(...)` + `kbService.listTenant(...)`，即**复用列表的可见性判定** ——
  口径是「**看得见就能点开**」。这与写边界（PUT/DELETE = 本租户 + 本人/管理员）是两条不同的边界。
- 状态码：不存在 → 404；存在但不在可见列表 → 403（**不泄露「这份存在」**）。
- 正文超 `VIEW_MAX_CHARS = 20000` 截断并 `truncated=true`，同时给**完整** `contentLength`（截断可，静默不可）。

### 前端：两条渲染链，一个正文渲染器

- 经典（基线 `_backup_index_pre_oa.html`）：每行加「查看」按钮（**对所有可见行开放**，不按 owner 过滤），
  `openKbDoc(id)` 弹窗；行级「删除」按钮保持**仅本人**（`ownerUserId === meId`）。
- 新版（`_oa_app.js`）：整行可点开（`role="button"` + `tabindex="0"`，Enter/Space 也可），
  右侧加 `chevron` 提示；底部覆盖层 `.docview`（上滑入，`z-index:51` 在 `.doc-mask` 之上）；
  「删除资料」仅本人可见；`S.docId` 做 **last-wins** 守卫（后开的那份覆盖先返回的在途响应）。
- 共用 `kbDocBodyHtml(r)`：元信息（文件名/可见范围/状态/大小/切片/上传时间/失败原因）+ 入库正文块 +
  截断说明 + 空正文提示。两个形态一份实现，避免正文块两处漂移。
- 新增令牌 `--red-ink:#c62f34`（在 `--red-soft` 上 4.77:1，供危险按钮）。

### 顺手修掉两个真缺陷（都是拍截图才暴露的）

- **状态词表大小写不匹配（已落 `pitfalls.md` #101）**：`DocView.from` 小写下发 `ok/wait/failed`，
  而新版 `renderKb()` 比的是 `=== 'READY'/'FAILED'`（大写）⇒ 恒不成立。
  后果：徽标显示后端英文原文「ok」且一直是「处理中」的琥珀色；概览磁贴「已就绪 0 / 处理中 N」。
  接口全绿、console 干净、`state` 值本身正确 —— **只有截图能发现**。
  修法：`kbStateLevel()/kbStateText()` 作为唯一识别入口，经典 + 新版全走它。
- **概览磁贴标签与数字换行不一致**：`.kb-tile` 是 inline 流 ⇒ 「我的文档2」换行、「已就绪2」同行，
  四个磁贴长得不一样。改 `display:block`（图标 `margin:0 auto 6px`）+ 把数字的内联样式收进 CSS ⇒ 形态固定。

### 验收结果（重建后复跑，全绿）

- `_e2e_kb_doc.py`（**新增**，已登记进 `_run_all_regression.sh` SUITES）：**失败 0 项**。
  A 段 HTTP（404/401/403、正文逐字一致含换行、`contentLength`+`truncated`、可见列表每份都能点开）；
  B 段新版 UI（`role=button`、覆盖层、正文、共 N 字、本人可见删除、二次确认、
  删后列表消失且接口 404、共享资料不显示删除但可看、徽标中文、概览与列表同源）；
  C 段经典（查看按钮 + 弹窗正文 + 删后 404）；E 段 console 干净。
- `_e2e_oa.py` **连跑两次**（铁律 #8）0 失败；`_e2e_oa_approve.py` 0 失败；`_check_oa_visual.py` 0 失败。
- 题外：B5 第一版报 `tile=None list=3` 的**假失败**（已落 `pitfalls.md` #102）：
  用 `innerText.split('\n')[0]` 取标签，而磁贴标签与数字同行（`'已就绪3'`）⇒ 永远取不到。
  改为从 `span`/`b` 子元素读，并补 B5a「概览总数 == 列表渲染行数」前置（列表 `slice(0,30)`，截断则不可比）。

## 首页四张浮动卡的三角：改为「算出来的」指向数字人

用户口径：`图片中框出来的三角对着中间数字人，距离近一点`。

### 先量清楚，别猜

- `.kpi-float` 四张卡（待我审批 / 我发起的 / 知会未读 / 我的会话）绝对定位在 `.stage` 四角，
  数字人 `left:50%;top:50%` 居中 —— 二者的相对角度**逐视口宽度都不同**。
- 量到的实况：数字人静止盒 y 239.7~538.4（含 r-bob 上浮 8px），卡片贴 stage 左右两端；
  位图四周只有 4px 透明留白（不是我以为的「大留白」，所以视觉间距≈盒间距）。

### 真缺陷：四张卡的三角**全部背对**数字人

原实现是四组写死的静态 CSS 三角：k1/k2 在卡顶朝上、k3/k4 在卡底朝下 ⇒ 四张全指向外侧，
**尾巴尖离数字人约 81px**。用户圈出的正是「我的会话」那张朝下的尾巴。

### 改法：与对话坞气泡共用同一份算法（单一判定来源）

- 抽出 `tailPlacement(br, A, baseDeg)`：落点 = 宿主中心 → 锚点 的射线与宿主边的交点；
  朝向 = 该射线方向角 θ + 基准补偿。`baseDeg` 按宿主三角的基准态给：
  对话坞 SVG「顶点朝上」= −90° ⇒ +90°；浮动卡伪元素「顶点朝右下」= +45° ⇒ −45°。
- `oaLayoutTails()` 改成两段：① 浮动卡（不对话时显示）② 对话坞气泡（仅对话态）。
  变量一律写在**宿主**上（伪元素没有子节点可写），两者都靠继承拿。
- 量不到数字人时回退到 **stage 中心** —— 数字人本就是 stage 的 50%/50% 居中，与真值同源。
- CSS 侧删掉四组写死的 `::after` 覆盖，统一读 `--tail-*`（默认值只剩「脚本未跑」的兜底含义）。

### 距离「近一点」

竖向已贴到数字人盒边界（上两张下沿落 239.8、下两张上沿落 541.3，各比原来近 4px），
再靠就压到像素了。真正的「远」来自那根朝外的尾巴：改向之后尾巴尖到数字人中心
**从 261px 缩到 179px**（k4 实测）。

### 验收

- **新增 `_check_kpi_tail.py`（已登记进 `_run_all_regression.sh`）**：失败 0 项。
  逐卡断言 ①贴在朝数字人那一侧的边 ②顶点朝向误差 ≤0.5° ③尾巴尖不外飘；
  **并在 360/390/430 三个宽度各验一遍**（角度实测 59.2°/55.6°/51.4° 且误差均 0.00°
  ⇒ 证明角度是算出来的，不是写死的；同时覆盖 resize 重新落位）；
  另加「数字人上浮到波峰时与四张卡**零像素重叠**」（按位图 alpha 逐像素判定）。
- `_e2e_oa.py` ×2、`_e2e_oa_approve.py`、`_check_oa_visual.py`、`_e2e_kb_doc.py` 全 0。

### 本轮两条假失败（都已落 `pitfalls.md`）

- **#103**：为让伪元素复用算法，变量从三角节点改写到宿主 ⇒ `_e2e_oa.py` 读内联样式
  `t.style.getPropertyValue('--tail-angle')` 恒得 0，E1/E2 会双双变红。
  产品没回归，是**断言绑死了「变量存在哪个节点」**。改读 computed style。
- **#104**：新写的指向自检四张卡误差**整齐地全是 −90.00°** —— 与样本无关的常数偏差
  ⇒ 一定是我的基准角写反（顶点基准是 45° 而非 −45°），产品正确。
  拿「原实现 rotate(45deg) 顶点朝正下 90° = 45+45」验算即暴露。
