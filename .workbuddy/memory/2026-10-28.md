# 2026-10-28 企业微信双模式连接器（方案A OAuth / 方案B 邮箱授权码）评估

用户要求基于 LangGraph + FastAPI + MCP HTTP+SSE 实现两套可切换的企微连接器，并要求先评估选哪套方案。

**评估结论（已输出给用户，待确认后动工）**：
- 推荐「A 为主 + B 为必备 + 可叠加」，不做二选一。三条关键修正：
  ① OAuth 换不来邮件收发能力——getuserdetail 的 biz_mail 只是邮箱地址字符串，IMAP/SMTP 必须客户端专用密码，故「方案A 含邮件工具」不成立；
  ② 消息/通讯录工具实为应用级 API（access_token 即可），A 的真实价值是身份与审计（userid/biz_mail）；
  ③ snsapi_privateinfo 只能在企微内置浏览器弹授权框，PC/外浏览器只能走 qrConnect 兜底（仅 userid），H5 需 UA 分流。
- 架构：单一「企业微信」连接器 + 双授权形态 + 模式闸门（A/B/A+B 三种连接态，工具白名单按模式收窄），对齐 Octop catalog/auth_kind/allowed_tools/credential_fields 模式；JustAuth 只作流程参考（getuserdetail/UA 双分支不在其覆盖范围且为 Java 栈）。
- 分期：P0 脚手架+Mock E2E → P1 方案A 全链路 → P2 方案B → P3 LangGraph 双模式+模式闸门+SSE 重连 → P4 交付物收口（后台配置文档/URL模板+Scheme/错误清单/权限隔离）。

### 方案评估：免平台统一域名的「每用户绑定自己企业」（16:4x）

用户诉求：避开平台统一认证主企业域名的流程，让每个用户自行授权绑定自己的企业微信。
结论：可行，三条路线——①自建应用 API 直连（免域名，推荐）：用户填本企业
corpId/agentId/secret+本人 userid，服务端三连验证（gettoken→agent/get→user/get）后
加密落库，运行时 token 按 corp 隔离；②服务商第三方应用（中期）：域名在服务商后台配一次，
每企业管理员点一次授权安装，之后成员标准 OAuth；③每企自建+OAuth（现方案，负担最重：
每企业都要域名备案+校验，且可信域名要求企业已认证、每应用仅 1 个回调域名）。
支点事实（已核实）：域名/备案只服务 OAuth 回调；API 调用从不需要域名；可信IP 配置
不以企业认证为前提（与可信域名不同）；可信IP 仅支持 IPv4（本次实测）。
硬门槛：平台必须有固定出口 IP（所有接入企业加白它）；snsapi_privateinfo 只能授权
本企业成员 ⇒ 免不掉「每企业一份应用凭证」。
落地咬合点：store 扩 corp 凭据字段、connect 加凭证绑定分支（复用 B 模式 elicitation）、
gate 放行 A 组、identity 改 user/get、token 缓存 key=(corpId,secret)、H5 绑定表单。
