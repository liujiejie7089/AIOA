## 主题：用户报告的三个缺陷修复（Gitee 授权跳转 / 初始化令牌留空 / 菜单合并）

用户原话三问：① 跳转没有真实跳到 Gitee 授权；② 留空时初始化信息失败；③「人员管理」与「组织与员工」菜单功能重复，合并为一个且功能不丢。

### 一、缺陷 1：授权跳转没到真实 Gitee（**配置语义耦合**，非跳转逻辑坏）

**根因**（对照 `HEAD` 版代码确认，不是猜测）：`GiteeClient.authorizeUrl()` 用 `props.getWebBaseUrl()` 拼**用户浏览器**要去的 `/oauth/authorize`，而同一个键还被 `exchangeCode()`/`refresh()` 用来拼**服务端**调的 `/oauth/token`（HEAD: 80/100/111 三处读取同一个键）。于是「把服务端接口桩化以做端到端回归」的部署顺手把**用户浏览器**也送进了桩 —— 桩直接签发假身份（如 `gitee_dev_152`）并立刻回跳显示「绑定成功」，用户**从未**看到 Gitee 授权同意页。

**修复**：新增独立配置 `aioa.gitee.oauth-authorize-base-url`（默认 `https://gitee.com`，生产无需配置即正确）；`bindUrl` 回传 `authorizeHost`/`sandbox`/`warning`；`GiteeOauthController.okPage` 在非 `gitee.com` 域注入警示条；前端先弹 warning 再 `window.open`（**不能**在 features 写 `noopener` —— 按规范那样 `window.open` 恒返回 null，"是否被拦截"就无从判断；改打开后 `win.opener = null`），被拦截则回退整页跳转。
- 接线收进 `scripts/gitee-e2e-env.sh` + `start-all.sh` 的 `AIOA_GITEE_E2E=1` 显式 opt-in；默认打印"授权跳转 = https://gitee.com"。
- **验收（同一份 jar、只改配置，两个实例对照）** `scripts/_probe_authorize_host.py`：`:8080`（三项基址都指向桩）→ `authorizeHost=127.0.0.1`、`sandbox=True`+warning；`:8099`（未设任何 `AIOA_GITEE_*` 基址）→ `authorizeHost=gitee.com`、`sandbox=False`、URL `https://gitee.com/oauth/authorize?...` ✅
- 顺手改正 `scripts/gitee_stub.py` 里一句**错误文档**：它声称 `web-base-url` 是"死配置、全代码库从未被读取"，实际 HEAD 有三处读取，会把人误导成"改它没用"。

### 二、缺陷 2：令牌留空初始化失败（**契约本就要求必填**，代码只是报错了难看）

**根因**：DB 实况 `gitee_tenant_config` 该租户 `access_token=NULL`/`init_status='FAILED'`。留空时"复用已存令牌"分支不成立 → 走格式校验 → 旧代码 `String shown = accessToken == null ? "null" : accessToken` 把 `null` **拼进用户可见文案**（`…不合法：null`）。且平台**不存在**"共享企业令牌"可回落（`enterpriseToken` 只读本租户行）⇒ 在"从未配过令牌"的企业上留空**本就应当失败**（`docs/30` §1.3 明写"首次必填；`rotateToken=true` 或当前无令牌 → `accessToken` 必填`）。所以正确修法是"显式必填 + 文案可读"，**不是**让它静默成功。

**修复**：后端把空令牌按成因拆两句（无存量令牌 → 「请填写访问令牌：本企业尚未配置企业令牌，首次初始化必须提供」；开了轮换却留空 → 「访问令牌不能为空：本次提交开启了令牌轮换却未填写新令牌」），**不再回显 `null`**；前端令牌字段按 `initStatus.tokenConfigured` **动态必填** + placeholder/提示切换 + 提交前本地拦截。`docs/30` 补了这两句文案的对照表。

### 三、缺陷 3：合并「人员管理」与「组织与员工」（**菜单合并 ≠ 路由 alias**）

研究结论：两者**互补不重复** —— `/org-structure` = 机构/部门树+员工名册（`ORG_VIEW_ROLES`，**含 MEMBER**）；`/admin` = 人员名册+角色分配+账号启停+平台级卡片（`PERSONNEL_VIEW_ROLES`，**不含 MEMBER**）。后端模块（`aioa-org` vs `aioa-admin`）也互不重复。

**先踩到的坑（子代理限流前留下的半成品，已弃用）**：用 `alias: 'admin'` 合并 —— alias **继承** `ORG_VIEW_ROLES`（含 MEMBER），普通成员深链 `/admin` 就不再被拦截，等于顺手放宽了人员管理边界；且把「平台配置」拆成第三个页签后，平台管理员落到 `/admin` 只能看一个页签，E11/E12/E13「同页看全」的断言全碎。

**最终做法**：**2 路由 + 2 页签**。菜单只留一个入口（标签 `isPlatformAdmin ? '系统管理' : '组织与员工'`，可见性 `ORG_VIEW_ROLES` 即并集，因 `PERSONNEL ⊂ ORG`）；`/admin` 保留为**独立路由**、沿用原 `PERSONNEL_VIEW_ROLES`；`OrgAdminView` 两个页签**原样复用** `OrgStructureView.vue` 与 `AdminView.vue`（功能零裁剪，删掉子代理新建的 `panels/`）。默认页签由入口决定（`/admin`→人员管理、`/org-structure`→组织与部门），用 `watch(immediate)` 而非 `onMounted`（两条路由共用组件、实例会被复用），目标页签不可见时**回落组织与部门**（否则 active 停在不渲染的页签上 ⇒ 整页空白）。另修 `:default-active` → `menuActive`，让 `/admin` 旧书签仍能点亮合并后的唯一入口。

**结果：零断言改动** —— `e2e_admin_personnel_scope` **57/57**、`check_org_structure_render` ALL PASS，E14/E15（成员菜单无该入口 / 深链 `/admin` 仍被拦回 `/home`）**原样通过**。渲染实测：机构管理员侧边栏只剩一个「组织与员工」，平台管理员只剩一个「系统管理」。
