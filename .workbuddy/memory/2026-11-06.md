## 一、知识库「AI 总结不如网上资料」根因诊断（docs/74）

用户上传 5 个非遗名录 Excel（区/市/省/国家/联合国级），问「统计下四川省的省级非遗项目有多少个」，
数字人回「知识库暂未收录 —— 检索内部知识库返回 0 条」；另一个工具给出 1241 项等明细。
报告写在 `docs/74-知识库检索质量诊断与改进方案-2026-11-06.md`。

**量化结论（本地用线上同款算法复现，脚本 `.workbuddy/tmp/sim_kb_retrieval.py` / `sim_kb_fix.py`）**

| 环节 | 实测 |
|---|---|
| 切片 | 500 行表 → 503 块；**含列名的块 1/503**；`### Sheet1` 单独占一块 |
| 关键词腿 | 命中 501/503，最高分 0.2209，**几乎全部同分** ⇒ top5 = 表格第 1~5 行 |
| 向量腿 | cos 最高 **0.157**、中位 0.080，过 0.5 阈值 **0/503** ⇒ hybrid 退化为单路 |
| 降阈值反证 | threshold=0 → 过阈 503/503，top1 变成第 17 行（仍无关，只是噪声换位） |
| top5 覆盖 | **5/500 = 1.0%** ⇒ 聚合问题结构上不可能答对 |

**五个根因（都带文件行号）**
1. `KbFileParser.java:167,184` 每行一个 `\n` + `KbService.java:285,290` 按 `\n` 切段且 ≤500 字直接成块 ⇒ 表格一行一切片，列名只在 1 块里。
2. `nodes.py:394` `top_k = es.get("topK") or 5` + 无任何聚合能力 ⇒ 「有多少条」必错。
3. `EmbeddingProvider.java:68` local = FNV 哈希 char2gram 词频（**无语义**），配 `retrieval.py:23` threshold=0.5 ⇒ 向量腿 0 命中。注意 `bge-small-zh` 只是**预留扩展点，未实现**。
4. `KeywordScorer.java:52` 覆盖率 × `(1+ln(1+hit))`，**无 IDF、无长度归一** ⇒ 同分塌陷，RRF 后按 chunk_index 排序。
5. `retrieval.py:85` 整句当 keyword；`builder.py:175` 参考块只给 docName，不给"第 X/Y 段"；提示词无"命中是抽样"纪律 ⇒ 模型把"只看到 5 行"当成"库里没有"。

**方案**：P0-1 TableChunker（列名进块，块内 8–12 行）/ P0-2 统计切片 + 聚合意图**强制注入**（实测统计块与行块同分 0.01639 vs 0.01613，靠排序拿 top1 不可靠）+ `kb_table_query` + V108 `kb_row`/`kind` / P0-3 真语义向量 + `reembed-on-start` + 阈值按 P90 重标 / P1 BM25 + 单文档配额 / P2 入库自检。

**附带发现（会伪装成检索 Bug）**：本机 `kb_document` 存活 18 篇，其中 11 篇演示文档声明 `chunk_count=402`，
但 `kb_chunk` 里这 11 篇**一条切片都没有** ⇒ 页面显示"已索引"、检索命中 0，**无任何报错**。
→ `KbService.index()` 末加「声明数 vs 实际行数」自检，不一致置 FAILED。

**另外**：`KbController.java:212-214` 上传只存解析后的 text，**原始 xlsx 字节用完即弃** ⇒ 事后无法补做表格聚合，
必须入库时抽行（或新增 source-dir 落原件）。

**环境备注**：MySQL root 密码为**空**（`application.yml:12` `SPRING_DATASOURCE_PASSWORD:` 默认空串），
用 `pymysql` 直连要 `password=""`；`kb_document` 的列名是 `doc_name` / `chunk_count`（无 `char_count`），
`kb_chunk` 是 `doc_id` 而非 `document_id`。

## 第八轮：「62 门只返回 14 门」—— 枚举类问题三层修复 —— docs/76

用户怀疑「切片方式不合适」。核实：**对了一半**，只改切片修不好。

三层叠加：
1. **切片**：`split()` 对非表格内容「一行一块」（`p.length() <= size` 直接成块）⇒ PDF 1800 字切 **38 块**，
   每块 4 门课、无列名，还把真表格块挤掉。→ 改**段落合并**（累积到 chunkSize 落盘，空行/`#` 为界）：38 → **4 块**。
2. **取行**（直接原因）：`kb_table_query` 命中行**硬上限 10 行**且**无翻页参数**。→ 加 `offset`/`limit`
   （默认 50 / 上限 500）+ `hasMore`/`nextOffset`/`nextHint`。模型原话「接口每次只返回前 10 行」不是借口，是真的。
3. **口径**：明细 62 + 汇总 14 被并在一起数 ⇒ `matchedRows=76`，汇总键值行被当课程。→ 按表选（默认命中最多的表）
   + `sheet` 参数 + `otherSheets`/`sheetHint`。`matchedRows` 改为所选表口径。

**表格侧切片也改了**：小表（≤30 行且 ≤1800 字）**整表一块**（键值表切开会把标签与数值分家）；
大表 10 行 → **20 行/块**；前缀与首行同行（两条路径排版统一，否则「行数=换行段数」断言会错）。
同一份成绩单：切片 49 → **11**；汇总表 2 块 → **1 块**（含首末行）。

提示词第 8 条：枚举类必须按 `hasMore` 翻页取全；禁止只答第一页；禁止「接口只返回前几行，其余我没有」；
必须写明覆盖范围（「共 62 条，本页 1–50」）。

**验收**：`_verify_kb_grade_enum.py` **19/19**（切片 8 + 分页 8 + 端到端 3）；
回归 `_verify_kb_grade_sheet.py` 31/31、`_verify_kb_grade_answer.py` 5/5；
`aios-resource` 159/159、`aios-chat` 70/70。
端到端实际回答：**62 行课程全列**，带序号，末尾附「合计 62 门 / 134.0 学分 / 补考仅 1 门 / 等级制未换算」。

## 第十轮：数字人越界 ⇒ 一句话变成可点的跳转（请求 I，docs/82）

用户原话：「如果当前数字人无法处理，那就提示跳到合适的数字人处理」（截图里请假助手答
「超出我的请假办理职责范围，请改问文档解读数字员工」，**没有任何可点入口**）。

- **根因是判定位置错**，不是缺按钮：既有 `worker.handoff` 在 run **开始前**拿**用户原话**比任务名，
  而用户问的是「策划书里面说了什么」⇒ Tier A/B 全落空。越界是模型读完后才承认的 ⇒ 只能从**回答正文**取。
- 新增 `suggest.worker` 帧（**建议**，不改绑）+ `RunService.suggestWorker` 纯函数：
  两道硬闸（空/无当前数字人 ⇒ null，与 `matchHandoff` 同源）+ 越界话术正则 + **取名字最长**的点名者
  + 一个没点名 ⇒ null。把 `candidatesOf()` 抽出来与 `resolveHandoff` 共用（口径必须一致）。
- **真机核对发现截图里那个人在库里不存在**（全租户查无「文档解读数字员工」，只有
  「文档管理数字人/文档上传」；名字是模型编的）⇒ 若只按规则"不点名就不给"，截图场景**依然无入口**。
  于是补第二张卡 `kind:'pick'`「去挑一位能办的数字人」：不猜人（送错更糟），但点「去看看」进
  `#v-workers` 全量清单，并把原问句塞进 `setPendingTaskText()`，选完人自动回填。
- 点击链路：`POST /v1/conversations/{id}/handoff` → `rebindWorker`（三重校验在 `bindWorker`）
  → **只改 worker_id 不新建会话**（换会话丢历史）→ 原问题重发。
- 验收：单测 **11/11**（截图原文当用例）；`scripts/_verify_worker_suggest.py` **16/16**；
  回归 `_verify_leave_form_split` **13/13**。
- ★ 本轮最坑：**`time.sleep` 轮询会堵死 Playwright 的事件分发**（桩回调与 request 监听全排队），
  表现为「重发没触发」报红，而紧接着一次 `pg.evaluate` 后同一变量就变 2 条 ⇒ pitfalls 97。
  另：`S` 是 IIFE 闭包变量（只有 `window.oaState` 可见），会话 id 最终取**真实请求 URL**。
