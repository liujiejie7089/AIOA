## 用户端「创建数字人」无法创建 —— 根因定位（本轮用户提问）

**结论：意图识别与后端都不阻断，断在 H5 客户端 OA 形态没有 `CREATE_WORKER` 编排分支。**

- 实测 agent `/internal/v1/worker-intent`：`帮我创建一个数字人` → `action=CREATE_WORKER`、`actionName=创建数字员工`（识别是通的）。
- 但 `user-client/_oa_app.js` **全仓 grep `CREATE_WORKER` = 0 命中**；收口 `oaAfterOaAnswer`(:2081) 只挂
  `UPLOAD_FILE`/`REPORT_EXPENSE`（`oaMaybeProjectAction`:1909）与 `APPLY_LEAVE`（`oaMaybeLeaveAction`:1938）
  ⇒ 该动作被静默丢弃，界面无任何反应。
- 创建能力**只存在于经典形态**：`_backup_index_pre_oa.html:1085` 「＋ 创建数字员工」→ `createAgentFlow()`(:3286)
  → chips → `agentDemo()`(:3335) → `API.workerPrecheck`(:3379) → `confirmAgent()`(:3470，`state.intakeGate.ok===false` 则阻断)
  → `API.createWorker`(:3500)。它由**经典页面**的按钮/chips 驱动，与对话意图收口无关；`_oa_app.js` 从不调 `workerPrecheck`。
- 而 `MODE_DEFAULT='oa'`（`_oa_app.js:61`）⇒ **默认形态恰好就是没有创建入口的那个**；
  `_oa_app.js:1299` 自己就写着「在「专家与员工」（**经典形态**）里给数字员工设置执行时刻」。
- 权限**不是**阻断点：创建闸门 `requireCreate` 要 `worker:create`（`PermissionCatalog.WORKER_CREATE → ALL`）
  ⇒ 六个内置角色全员持有，且 ALL 型被 `applicable()` 过滤 ⇒ 不可申请、非稀缺。
  `intent()` 的 `held`/`pending` 指的是**数字人类型所需权限码**（如 `approval:leave`），**不是** `worker:create`。
- 附加缺陷（铁律 1）：`agent/aios_ai/prompt/builder.py:233-237` 让模型说「用户端「专家与员工」页有「＋ 创建数字员工」入口」
  —— 该入口**只在经典形态存在**，默认（OA）形态下不成立 ⇒ 模型给了**在默认形态下不成立**的指引。
- 解决方向：A) 在 OA 收口加 `oaMaybeCreateWorker(intent)`，并**复用**经典既有创建能力
  （把 `createAgentFlow`/`confirmAgent` + `workerPrecheck`/`createWorker` 提升为两形态共用），
  必填参数（`name`，`WorkerController.java:386-388` 空名即 400）由用户在卡里补；
  B) 让 `builder.py` 话术不再承诺默认形态下不存在的入口；C) 兜底给 OA「数字员工」页加「＋ 创建数字员工」按钮；
  D) **不建议**给 agent 加创建工具（创建是界面能力，含六项前置检查 + 可见范围，参数应由用户给）。
