## 二、坑：本机用 HTTP 码探活会骗人（本轮差点据此误判）
- 本机环境有 `http_proxy=http://127.0.0.1:63414`（沙箱代理，`HTTP_PROXY`/`HTTPS_PROXY`/小写同名都在）。
  它**时好时坏**：

- ⇒ **判定「服务在不在跑」只用两样 OS 级证据**：`netstat -ano | grep LISTENING | grep ":<port> "`
  + **服务自身日志**；HTTP 码只作辅助。

### ★ 顺手发现并修掉的自伤缺陷（死锁）
`GiteeProjectsView.vue` 里「平台参数（Gitee 应用）」卡**被渲染在 `moduleEnabled` 守卫之内**
（`<template v-else>` = configError 假 且 moduleEnabled 真那一支，跨行 42→533），
而它的注释、以及 `onMounted` 里 `loadPlatformConfig()` 的位置（第 1353-1356 行注释明写
「放在 moduleEnabled 守卫之后的话，模块一旦被关掉，用户就再也进不来把它打开了」）都声称它在守卫**之外**
—— **注释与结构互相矛盾**。后果：模块 `enabled=false`（生产默认即如此）⇒ 横幅显示、**这张「开总开关」的卡不渲染**
⇒ 管理端永远无法打开它（只能去改 env + 重启），整个「动态配置」需求落空。
**修复**：把卡片移出守卫，改成独立分支 `v-if="isPlatformAdmin && !configError"`；原来那支改成
`<template v-if="!configError && moduleEnabled">`（语义等价于旧 `v-else`，因 configError ⟹ !moduleEnabled）。
**编译期取证**：`@vue/compiler-sfc` 编出的渲染函数里卡片条件是
`(_ctx.isPlatformAdmin && !_ctx.configError) ? (_openBlock(), _createBlock(_component_el_card, { key: 2 …`
——**不含 moduleEnabled**，且是与两横幅同级的顶层 arm。
（Vue 3 会**跳过 v-if 分支之间的注释**，所以当时 `<template v-else>` 确实指的是 `moduleEnabled` 那支。）

### 教训（可复用）
1. **「我已经部署了」必须先证伪，别从现象往回猜代码**：直达生产取三样证据 ——
   ①部署的管理端入口 hash → 拉它的懒加载块 grep **本特性独有的中文字符串**；②新端点是否 404；
   ③既有端点是否出现**本轮新加的字段**。三者任一为「旧」即说明部署物不含该改动。
   （注意：**别用后端下发的文案做前端探针** —— 如「平台总开关」是 `FIELD_META` 里的后端标签，
   前端包里 grep 不到，第一版就因此误判为「本地也没这特性」。）
2. **未提交 = 未部署**（本仓库部署是 git 式）：任何「改了却没用」的现场，先看 `git status` 与
   `git rev-parse HEAD` vs `ls-remote <远端> main`。
3. **注释与结构矛盾时以结构为准**；`v-if/v-else` 链会把「注释里说在外面」的东西关在守内。
   凡「某卡片是开启某开关的唯一入口」，必须断言它**不被该开关自己的守卫挡住**（本轮即此坑）。


## 九、用户问「Webhook 回调基址填什么」——答案与预防复发

**答案**：**只填基址** = **`https://mall.egoaicloud.com/aioa`**（生产）。
依据（三处同源，非猜测）：`GiteeRepoTaskHandler.callbackUrl()` = `去尾斜杠(base)+"/api/v1/gitee/webhook/"+项目id`；
`deploy/.env.production:155` 本来就写着 `AIOA_GITEE_WEBHOOK_BASE_URL=https://mall.egoaicloud.com/aioa`；
该路径在 `SecurityConfig.PUBLIC_ENDPOINTS` 的 `permitAll` 里（`/api/v1/gitee/webhook/**`），Gitee 免令牌可回调。
本地留空即可（Gitee 到不了 127.0.0.1，Webhook 必然失败，属预期）。

**★ 顺手查到的关键事实**：生产 `GET /gitee/config` 的四个 flag
（`enabled` / `orgConfigured` / `webhookBaseUrlConfigured` / `oauthConfigured`）**全为 false**，
**尽管 `.env.production` 里 Gitee 段并非空** ⇒ **生产的 env 没真正传进容器**。
这解释了为什么「改了 .env 也没用」；而管理端页面（保存即生效、存库）正好绕开这个环境问题 —— 与用户诉求方向一致。

**本轮顺带改进（防复发）**：
- 后端字段提示改写：`webhookBaseUrl` 的 hint 由「必须是托管方能访问到的公网地址；填 127.0.0.1/localhost 必然配置失败」
  改为「**只填基址**：后端会自动在其后追加 /api/v1/gitee/webhook/{项目id}（结尾带不带 / 都行）。必须是 Gitee
  能访问到的公网地址，填 127.0.0.1 或 localhost 必然失败」——原提示不回答「填什么」，正是这次被问的原因。
- 指南 `deploy/GITEE-两套环境配置指南.md` §3.5 增「**`webhook-base-url` 到底填什么**」小节（生产/本地两档 + 白名单说明）。
