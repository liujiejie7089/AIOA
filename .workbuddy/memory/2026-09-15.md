## 权限申请「机构管理员收不到」根因定位（docs/21）

用户场景：租户 9（某某智能科技）→ 机构 29（研发中心，`znkjyf_admin` 3143）→ 部门 101（算法部 `ZN-SFB`），
以成员身份提交权限申请，机构管理员收不到。

### 实测根因（三条）
- **A 主因（结构性）**：`ApprovalFlowService.expandNodes()` 只按 `approval_flow_def.steps_json` 展开
  **固定模板**，**不按申请人层级递推「上一级」**。租户 9 的 `PERMISSION_GRANT` 定义（`id=31`）是
  `[DEPT_LEADER, TENANT_ADMIN]` —— **压根没有 ORG_ADMIN 节点**。
- **B 掩盖**：算法部 `org_department.id=101.leader_user_id` 为 **NULL**，`resolveDeptLeader` 返回 null →
  `expandNodes` L206-214 的兜底把第 1 级**改派给机构管理员**（还带着 `approver_type=DEPT_LEADER`
  的语义错误）。所以「有时像能收到」，纯属兜底副作用。
- **C 缺口**：`MainLayout.vue` 无任何 badge/红点，前端无待办计数接口 → 需求②完全未实现；
  `/tenant/approval-flow-defs` 有接口（`api/org.ts` 已封装）但**无视图引用** → 配置无界面。

### 复现证据（关键）
- 实验 A（负责人为空，`znsfb_m01` 提交）：`orderId=218`，seq1 `DEPT_LEADER→3143 机构管理员`（兜底改派），
  `znkjyf_admin` 的 `/workflow/tasks?scope=todo` **能查到**；`/approvals?scope=todo` 对他 **403**
  （legacy 单级池仅租户管理员可读，属预期）。
- 实验 B（把算法部负责人配成祁野 3144 后再提交）：`orderId=219`，
  `seq1=DEPT_LEADER→3144 祁野`、`seq2=TENANT_ADMIN→3142`，
  **机构管理员 3143 是否在链上: False** ← 复现用户描述。
- 造的两单（218/219 + task 216-219 + grant 51/52 + 2 条 notification）**已删除**，
  备份 `scripts/_diag_v40_backup.json`；`dept101.leader_user_id` 已还原为 NULL。
- 实验中途对 `org_department` 做过一次 UPDATE 后已还原（未留痕）。

### 顺带查实
- 祁野(3144)/路遥(3148)/简宁(3152) 三人均只有 `ROLE_MEMBER`，**未授 `ROLE_DEPT_LEADER`**
  → 「部门负责人」这一层在权限体系里不存在。
- 3142 与 3143 的 `nickname` **都叫「傅宸」**，待办里无法区分租户级/机构级，会加剧误判。
- 租户 9 只有 `PERMISSION_GRANT` 一条流程定义，`LEAVE`/`QUOTA_EXPAND`/`RESOURCE_OPEN` 全缺（即既有 D-8）。

### 产出
`docs/21-权限申请层级流转与待办红点设计.md`：
结论速览 / 现状事实 / 三条根因 / 需求应答（权限层级三层模型、传递路径现状与目标、红点四判据、

验收口径 / 风险兼容。

### 结论一句话
`expandNodes` 是「模板展开器」而非「层级递推器」，且模板缺 ORG_ADMIN 级 ——
要满足「所有人向上级申请」，必须让引擎按**申请人组织层级**推导上一级并加**自审防护**，
只改 `steps_json` 数据不足以覆盖「部门负责人自审」场景。

### 编写脚本时暴露的两个缺陷模式（可复用教训）
- `check()` 忘了 `return bool(cond)` → `if not check(...)` 恒真 → 脚本**静默 `sys.exit(1)` 且无堆栈**。
  诊断手段：`sys.exit` 抛 `SystemExit`，用 `except BaseException: traceback.print_exc()` 包一层即可现形。
  管道里 `| tail` 会**丢缓冲输出**，排查看门狗式静默退出时必须 `python -u` 或 `2>&1 | cat`。
- `permission_grant` 的 holdings 接口口径是 `byRole`/`byGrant` **分开返回**，不是 `held`。
- 渲染类脚本必须自建 `reset()`（直接删 tenant 9 测试账号的 `approval_order`/`approval_task`/
  `permission_grant`/`notification`），否则第二次跑被「你已有一条待审申请」挡住。

### 遗留
① tenant 管理员作为申请人的 `start=3` 分支无提交入口可触达（他持有全部可申请权限码），只有代码路径、无 E2E；
② **链长已选定为「整链逐级上报」**（4 级）。依据：用户报的缺陷是「成员申请，机构管理员收不到」——
   只审一级则成员的单只到部门负责人，机构管理员仍收不到，缺陷不闭环。
   某租户若要一层，把 `steps_json` 改成 `[{"seq":1,"approver_type":"DEPT_LEADER"}]` 即可（零代码改动）；
③ 3142/3143 昵称都是「傅宸」；④ `scxsyb_ldr`(3152) 仍未授 `ROLE_DEPT_LEADER`（故意，避免打破既有断言）。

### 补验：播种器（另一条代码路径）
`ApprovalFlowProvisioner` 只在 `TenantProvisionedEvent`（新建机构）时触发，且内部 try/catch
把异常吞成 warn —— **失败静默**，不实测等于没验。用可逆探针 `scripts/verify_v39_provisioner.py`
实测 **11/11**：删掉 tenant 9 的 `RESOURCE_OPEN` 默认流 → 以 `znkj_admin` 新建探针机构触发事件 →
断言补回 + 4 条各 1 条不重复 + `institution_id=0` 未被污染 → 软删探针回滚 →
`e2e_admin_personnel_scope` 57/57 / `check_org_structure_render` ALL PASS / `e2e_full_system` 152/152 确认零残留。

**结论：MyBatis 向 `steps_json`(JSON 列) 写 String 的插入路径实测通过**（此前只有 SQL 的 `CAST(... AS JSON)` 走过）。

## 登录报障修复：「机构/管理员账号 + User@123 很多都登不上去」

### 复现与归因（两个**互相独立**的根因，此前被混为一谈）
1. **租户名严格相等（主因，致「很多」账号登不上）**
   管理端登录框标签是「租户名称」，但机构/企业管理员按直觉填的是**自己的机构名称**
   （如把「某某智能科技有限公司研发中心」填进租户名称），`AuthService.assertTenantName`
   要求与租户全称**逐字相等** → 命中 1004「租户名称与账号不匹配」。
   实测 `znkjyf_admin` 填机构名 1004、填租户全称 0，同一账号同一密码两种结果。
2. **单账号口令孤例（致「User@123 登不上」）**
   全库 125 个启用账号：123 个 `User@123`、平台 `admin` 为 `Admin@123`、
   **`dsj_admin`(tenant2 租户管理员, id=3) 独为 `123456`**（V1/V24 遗留）。
   → `User@123` 对它必然 1001。判定为**遗留不一致而非有意设计**，三条独立证据：
   ① 其余全部租户侧账号（含 t3~t9 租户/机构管理员）一律 `User@123`；
   ② `scripts/verify_config_effect.py` 早已写死 `DEFAULT_PWD="User@123"` 并 `login("dsj_admin")`
      —— 该脚本因此**一直是坏的**（`KeyError: 'accessToken'`）；
   ③ `scripts/seed_worker_templates.py` 同样 `PWD='User@123'` 且把 `dsj_admin` 列在 `TENANT_ADMINS`。
   登录页演示提示也只对外宣告 `User@123`。

### 修复
- **`AuthService.assertTenantName` 改多形态匹配**（`tenantNameMatches`）：租户全称 / 租户编码 /
  **该租户名下任一机构名称** / 名称省略前缀（互为包含、两侧长度≥3）全部放行；归一化=去全部空白+小写。
  **只与本账号自身租户比对**，跨租户仍 1004（校验强度不变）。失败文案改为回显所属租户名 + 提示可填项。
- **`V40__normalize_dsj_admin_password.sql`**：把 `dsj_admin.password_hash` 归一化为 `User@123`
  （哈希取自本库已用 `User@123` 的既有账号，不落明文）。**追加迁移而非改 V24**（checksum）。
- **`LoginView.vue`**：字段标签「租户名称」→「**租户 / 机构名称**」，placeholder 与 tip 说明
  租户全称 / 租户编码 / 机构名称三种填法均可、可省前缀。
- 同步改测试基线：`e2e_full_system.py`(8 处 `'dsj_admin','123456'`)、`e2e_v32_org_scope.py` 改 `User@123`。

### 顺带修掉的两个真实缺陷（回归跑出来的）
- **`repro_logout_401.py` 未定义 `TENANT`**（`NameError`，此前一直跑不起来）→ 补 `TENANT="默认租户"`。
- **`login-view` 文案改动打挂两个脚本的 placeholder 选择器** → 统一改用稳定选择器
  `input[autocomplete="organization"]`（`e2e_admin_personnel_scope.py` 4 处、`repro_logout_401.py` 1 处）。
- **`AccountProvisioner.resolveOrCreate` 重建同名账号撞唯一键 → 500**（`verify_v39_provisioner` 暴露）：
  `sys_user.username` 唯一键**覆盖软删行**，而查询只认 `deleted_at IS NULL`，于是插入撞唯一键。
  真因是**运行真代码路径时暴露的产品缺陷**，非单纯数据漂移（软删行来自上次未跑完的探针）。
  修法：新增 `selectDeletedUserByUsername` + `reviveUser`，`resolveOrCreate` 先查软删行并**复活**
  （清 `deleted_at` + 复位归属/昵称/口令/启用态）再返回。实测探针连跑两次 11/11（`adminUserId` 复用旧 id 3156）。
  数据侧同时补回 tenant 9 缺失的 `RESOURCE_OPEN` 默认流（上一次中断的探针删了没补）。

### 验证（全部在停 JVM → `mvnw clean package` → 重启后实测）
`e2e_login_tenant_name` **15/15**（新增：四种填法 8/8 ×4、跨租户 1004 零漏放、空白/平台/H5 省略/1001 边界、
无头 Edge 真机填「研发中心」登录成功）· `e2e_full_system` **152/152** · `e2e_admin_personnel_scope` **57/57** ·
`e2e_v32_org_scope` **51/51** · `e2e_v39_applicant_superior` **69/69** · `verify_v39_provisioner` **11/11**（连跑两次，
幂等）· `verify_config_effect` **11/11**（此前因孤例口令是坏的）· `repro_logout_401` PASS · `vue-tsc --noEmit` 0 错。
未启用/离线核实：`dsj_admin/User@123`→0 且 `123456`→1001；tenant9 默认流回到 4；探针机构/账号均无存活残留；Flyway 至 v40。

### 结论/坑
- **1001(口令错) 与 1004(租户名不匹配) 必须分开判**：写套件时按 `password_hash` 反查真实口令，
  否则单账号口令孤例会被误判成「租户名校验有问题」，得出完全错误的结论。
- **`sys_user.username` 唯一键覆盖软删行**：凡「软删 + 唯一键」组合，插入前必须先查软删行。
- 触及登录表单文案时，E2E 选择器要绑 `autocomplete` 等稳定属性，**别绑 placeholder**。

## 权限审批流程 + 组织关联改造方案（对标 O2OA，产出 `docs/23`）

用户诉求：① 普通用户申请权限 → 部门负责人**一级**审批即可；② **部门申请**同样向上级审批；
③ 「部门负责人 ↔ 普通用户」关联过少、业务衔接不紧密；④ 参考 O2OA 梳理权限模型/审批层级/角色关联并提改造思路。

**交付物**：`docs/23-权限审批流程与组织关联改造方案.md`（现状梳理 + O2OA 对标 + 差距分析 + 五期方案 + 落地清单 + 风险）。

### 关键实测数字（本次新查，构成「关联过少」的硬证据）
`org_department` 39 个，仅 **8** 个配了 `leader_user_id`；`org_member` 116 行全部已挂部门；
`job_title` 含「负责人」的成员 **27** 人；真正持有 `ROLE_DEPT_LEADER` 的只有 **3** 人。
→ **27 / 8 / 3 三套口径互不一致**，「谁是部门负责人」没有权威事实源（业务口径、引擎口径、权限口径各说各话）。
另：`PERMISSION_GRANT` 用 `APPLICANT_SUPERIOR` 的**只有 tenant 9**（其余 tenant 1–8 仍是固定两级 `[DEPT_LEADER, TENANT_ADMIN]`）。

### 核心结论（引擎层面）
- `APPLICANT_SUPERIOR` 只实现「一次展开整条上级链」，**没有「向上几级」参数** → 一级审批必须给节点加 `levels`（缺省=整链，向后兼容）。
- 申请人只能是 `sys_user`，**没有「部门作为申请主体」** → 需 `approval_order` 加 `applicant_type` + `applicant_department_id`。
- **口径反转警示**：一级审批会让机构管理员**收不到**成员申请，这正是 V39 改整链的原因。建议按 O2OA 的**「待阅/知会」**解决（`approval_task.task_role` ∈ APPROVE|CC，CC 不阻塞流转）——「审批要快，知情要全」。
- **一级审批的前置硬约束**：部门负责人必须先配全，否则 `resolveDeptLeader` 会**兜底改派**给机构管理员（表面能用，实为副作用，V39 已验证过该陷阱）→ 数据治理(P2)是层级改造(P1)的准入条件。

### O2OA 可借鉴要点（本次抓取官方资料所得）
组织 = Unit / **Identity 身份（一人多身份，处理人以身份记录）** / **Duty 职务（人员与流程·权限解耦的中间层）** / Group 群组（可嵌套、可含组织）/ Role 角色（成员可为个人或群组→权限继承）。
流程 = 活动 + 路由；处理人六类来源（用户标识 / 组织 / 群组 / **职务（按组织动态求值）** / 流程数据 / 脚本），递归解析为身份数组；
处理模式 single / parallel / queue / grab；路由支持条件脚本与选择范围；另有**待阅**概念。
→ 我们最缺的是 **Duty 这一层**（改用自由文本 `job_title` 顶替），以及**处理人来源可组合**（现在是硬编码 switch）。

### 方案骨架
P1 审批层级（申请人类型 + `levels`）· P2 职务字典 `org_duty` + 身份 + `DEPT_DUTY`/`UNIT_DUTY` 解析器 · P3 部门作为申请主体 ·
P4 知会(CC) · P5 数据治理回填（27/8/3 收敛，`ROLE_DEPT_LEADER` 3→27）。分期：一期 P2+P1，二期 P3，三期 P4，四期解析器策略化，五期并行/条件路由。

### 状态
本次为**方案交付**（用户明确要求「提出具体改造思路」），**未改动任何生产代码/数据**。
后续若要落地，注意回填 `ROLE_DEPT_LEADER` 会影响以角色为断言的既有套件（`e2e_admin_personnel_scope` 档位分组等），需同批回归且**不得为转绿放宽断言**。
