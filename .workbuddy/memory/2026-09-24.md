### ① 管理端「新增机构」后不显示

**根因（数据级，铁证）**：`org_institution` 里存在 `id=87, code='ttt', tenant_id=0`。
平台管理员（`ROLE_ADMIN`）的 `tenantId` **恒为 0**（平台自身租户），而
`InstitutionService.create` 用的是**裸** `actor.getTenantId()`，
列表/详情用的是 `OrgGuard.resolveRequestTenant(u)`（平台管理员→「机构最多的启用租户」= 2）。
⇒ 建出来的机构挂 tenant 0，**任何租户的列表都查不到它**。

同一文件里 4 处都犯了这个错：`create` / `update` / `changeStatus` / `assignAdmin`（行 118/167/216/250）。

**修复**：4 处统一改为 `guard.resolveRequestTenant(actor)`。
**数据修复**：`V64__fix_institution_tenant_scope.sql` 把 `tenant_id=0` 的存活行回填到默认租户（=2）。

> ⚠️ **V64 第一版直接挂**：`UPDATE org_institution SET tenant_id=(SELECT ... ORDER BY (SELECT COUNT(*) FROM org_institution ...))`
> ⇒ MySQL **Error 1093**「You can't specify target table for update in FROM clause」。

### ② 资源与授权管理「停用」无效

**根因**：前端 `toggleGrant(id)` → `POST /tenant/grants/{id}/toggle` **不带 body**；
后端 `TenantAdminController` 写的是
`boolean enabled = body == null || !Boolean.FALSE.equals(body.get("enabled"))`
⇒ `body == null` 恒等于 `enabled = true` ⇒ **点「停用」永远变成「启用」，记录永远是已启用**。

**修复**：
- 后端：不传 `enabled` 时**真翻转**（`explicit != null ? explicit : !TRUE.equals(g.getEnabled())`），
  显式传值仍按值设置（幂等）。
- 前端：`toggleGrant(id, enabled)` **显式传目标状态**（`!isOn(row)`），避免依赖后端默认值与连点抖动。
- 补成功回执（此前静默成功，用户无法区分「生效了」和「没反应」）。
- 错误文案：业务失败是 HTTP 200 + `code≠0`（异常体是 `ApiError`，**没有 `.response`**），
  原写法 `e.response.data.message` 永远取不到 ⇒ 统一走 `errText()`。

## 专家「启用 / 停用 / 删除」缺陷修复（用户报 ③②①）

**用户报的三件事**：① admin 新建专家、其他机构靠「导入模板」获取；② 要「删除专家」功能；
③ **缺陷**：新建的 `test` 专家**没有启用**，用户端还是能用。

**③ 根因（铁律 #1 违例：同一决策点两处判定）**
- 管理端停用 → `POST /expert-config/experts/{key}/config {enabled:false}` ⇒ **只写 `expert_config`（配置层）**
- 用户端目录 → `GET /api/v1/experts` → `CatalogService` **只按 `ai_expert.enabled` 列过滤**，从不读配置层
- 而 `ai_expert.enabled` 列**从来没有任何代码写过 false**（`importTemplate` / `saveTemplate`
  均硬编码 `setEnabled(true)`，`defaults()` 也是 true）⇒ 用户端**根本没有能生效的关闭开关**。
- **本机库实证**：`test` 的两条片段 `id=172 GLOBAL{"enabled":true}`、`id=173 TENANT{"enabled":false}`
  （均 APPROVED）；修复前 admin 的 `GET /api/v1/experts` 里 `test` 仍在，**修复后消失**（已在运行态复核）。

**修复**（backend 6 文件 + frontend 2 文件 + 单测）
- `ExpertConfigService.isEnabled(tenantId, institutionId, deptId, userId, expertKey)` = 「是否启用」的
  **唯一判据**（= 配置层 resolve 结果）；新增 `deleteAll(tenantId, key)`、`deleteAllExceptTenants(key, keepTenantIds)`。
- `CatalogService.experts(AuthUser)` 取代 `experts(Long tenantId)`；`availableExperts` 走**两道闸**：
  SQL `ai_expert.enabled=true` + `configService.isEnabled(...)`；`defaultExpertKey` 提为 public 供删除守卫复用同一判据。
- `CatalogController` 传整个 `AuthUser`（INSTITUTION/DEPT/USER 层需要）。
- `ExpertConfigController`：新增 `DELETE /api/v1/expert-config/experts/{key}`；守卫①默认 AI 不可删

- **两个前端不用重新打包**；nginx **只监听 80**（`81` 仍然不存在）。

### 卡点 1：宿主 8000 被占 ⇒ `port is already allocated`（agent 起不来）
- 证据：用户 host-check 里 `0.0.0.0:8000` **已被别的容器占用**；而 compose 把 agent 固定发布
  `127.0.0.1:8000:8000` ⇒ 绑不上，`docker compose up -d server agent` 会失败。

  （**默认 8000，行为不变**）；并在 `.env` / `.env.production` **声明**该键（也顺带消掉
  compose-lint 的「引用了未声明键」警告 —— 铁律：compose 引用的每个 `${VAR}` 都要在 env 里有出处）。

  容器内仍监听 8000，server 走服务名 `agent:8000`，与宿主映射无关。
