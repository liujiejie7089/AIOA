### 一、盘点结论（实测数字）

- `server/aioa-gitee`：**42 文件 / 6683 行**；`GiteeClient` **592 行 / ~25 个 API 方法**，**无接口抽象**（具体类被 **8 处**服务直接注入：Account/Content/Member/MemberTaskHandler/RepoTaskHandler/TenantConfig/TenantInit/Token）。

- 9 张 `gitee_*` 表 + 5 个 Flyway 迁移（V48/V49/V50/V51/V53）。

- 配置：`application.yml` 里 **15 个** `AIOA_GITEE_*` 环境变量。
- 测试：4 个套件 **252 条断言**（v48 116 / v50 54 / v51 50 / SMOKE 32）+ `verify_v51_repo_urls` 23。

### 二、兼容性判定：约 19/25 个端点**同形**

Gitea 刻意对齐 GitHub API，而 Gitee V5 骨架也是 GitHub 风格 ⇒ `/user`、`/user/orgs`、`/orgs/{org}`、
`/orgs/{org}/members`、`POST /orgs/{org}/repos`、`POST /user/repos`、`/repos/{o}/{r}`、
`contents`（`content` base64 / `message` / `branch` / `sha`）、`branches`/`commits`、`collaborators`
**路径与字段名都一致**；`Authorization: token xxx` **Gitea 同样接受**。

### 三、★ 五个硬分歧点（按「会不会静默出事」排序）

1. **⚠⚠⚠ 仓库命名：Gitea 没有独立 `path`**。我们用 `name`(中文显示名) + `path`(slug) 两个字段，
   Gitea `POST /orgs/{org}/repos` **不认 `path`**，`name` 即 slug ⇒ `path` **被静默忽略**，
   仓库 URL 变中文名、与平台 `repo_name` 不一致。**需产品决策**（唯一的破坏性语义变更）。
2. **⚠⚠⚠ Webhook 签名**：Gitee 是 `X-Gitee-Token` **明文比对**；Gitea 是 **原始报文体的 hex HMAC-SHA256**
   （`X-Gitea-Signature`，另有兼容头 `X-Hub-Signature-256` 带 `sha256=` 前缀），**必须先缓存原始报文再解析 JSON**。
   不改 ⇒ Webhook 全被平台拒收，且排障方向容易走反。
3. **⚠⚠ Webhook 请求体与事件名**：Gitee `{url, password, push_events, merge_requests_events, issues_events, note_events, encryption_type}`
   vs Gitea `{type, config:{url, content_type, secret}, events:[...], active}`；事件名 Gitee `Push Hook`/`Merge Request Hook`/`Issue Hook`/`Note Hook`
   vs Gitea `push`/`pull_request`/`issues`/**`issue_comment`**。
   **★ 现有 `classify()` 是「按子串顺序判断」（push → merge/pull request → issue → note），
   Gitea 的 `issue_comment` 含 `issue` 子串 ⇒ 必被误判成 Issue 事件，永远进不到 note 分支** ⇒ 必须改**精确映射表**。
4. **⚠⚠ OAuth 端点与 scope 整表不同**：Gitee `/oauth/authorize` + `/oauth/token`（网页域）；
   Gitea **`/login/oauth/authorize` + `/login/oauth/access_token`**。
   scope 词表**没有一个同名**：Gitea 是 `repo`/`read:repository`/`write:repository`/`read:organization`/`notification`/`issue`…；
   且**官方文档版本间口径矛盾**（老文档「不支持 scope，第三方应用获得用户全部资源」，
   新文档「支持按路由分组的 read:/write:」）⇒ **必须锁 Gitea 版本并实测**。
   另：Gitea 文档明确 **改 scope 会导致整个流程失败、用户须重新授权**；回调 URI **建议 `127.0.0.1` 而非 `localhost`**（RFC 8252）。
5. **⚠ 分页参数 `per_page` → `limit`**：Gitea `ListOptions` 只有 `page`+`limit`，`per_page` **被忽略**（回落默认页大小）
   ⇒ 成员/协作者列表**静默少一截**，约 6 处要改。与我们刚在 Gitee 上踩的「桩不校验 scope」**同一类陷阱**。

**无对应物**：仓库级团队（Gitee `/repos/{o}/{r}/teams` + `PUT /repos/{o}/{r}/teams/{team}`；
Gitea 只有组织级 `/orgs/{org}/teams` + `PUT /teams/{id}/repos/{org}/{repo}`，语义反转 ⇒ 建议砍掉或重设计）；
企业(enterprise)层级（Gitea 只有 org）。

  但**仓库/组织/用户级写操作全要令牌**，这是真机验证的唯一硬阻塞。

#### 10.1 探针又抓出一个真缺陷：**设置面没有中立化**

`provider=gitea` 起实例后 `POST /api/v1/gitee/bind/authorize` 返回
`code=400`「Gitee OAuth 应用未配置（缺 aioa.gitee.client-id / client-secret）」——
**gitea 接线根本绑不上**。根因：`RepoProviderClient` 只覆盖了「怎么调平台接口」，
没覆盖「**平台侧的配置长什么样**」，而 `GiteeAccountService` 等 **8 个业务类 + 2 个控制器**
仍直读 `GiteeProperties`。切 gitea 后这些点会读到**空组织 / 空 Webhook 回调基址 /
错的签名密钥 / 错的令牌密钥**，且**编译期毫无提示** —— 属于「不报错、值不对」类缺陷。

**做法（#273）**：新增 `RepoProviderSettings` 端口 + `RepoProviderSettingsAdapter`。
**访问器方法名刻意与 `GiteeProperties` 的 getter 同名** ⇒ 11 处调用点**一行未改**，
只把字段声明从 `GiteeProperties` 换成 `RepoProviderSettings`，改动面小且可审计。
适配器里把设置分成三类取数：
① **平台协议类**（org / webhook-base-url / webhook-secret / redirect-uri /
oauth-authorize-base-url / token-enc-key / repo-name-max-length）**随 provider 切**；
② **平台运行参数**（sync-enabled / purge-repo-on-delete / max-attempts /
task-batch-size / bind-return-url，Gitea 段未重复定义）**仍取 gitee 段**，避免行为漂移；

#### 10.5 把「靠纪律守」的风险改成「靠代码守」：沙箱覆盖真实绑定的守卫（#274）

从 2026-09-17 起交付说明里一直写着「⚠️ 别在此时跑 Gitee 桩套件：`GiteeAccountService.callback()`
对已有绑定行没有保护，桩接线下会把真实绑定覆盖成假身份」。**这是条靠人的记性守的纪律，

**为什么必须拦**：覆盖后真实令牌被换成桩签发的假令牌，而**两条路径的返回都叫「绑定成功」**，
事后无法分辨 —— 不可逆的数据损坏。

**做法**：`GiteeAccountService.clobberRealBinding(existingUid, incomingUid, sandbox)` 纯函数 +
常数 `STUB_UID_CEILING = 1_000_000`。判据来自实测：**桩签发 5 位 uid（42040–42891），
真实账号 8 位（14032724）**。四种组合逐一钉死（`GiteeAccountClobberGuardTest` 6 例）：
- 沙箱 + 既有是真实账号 + uid 不同 ⇒ **拦**（唯一要防的场景）
- 沙箱 + 同一账号重新授权 ⇒ 不拦（否则桩套件重跑必红，**桩 uid 每次重启会变**）
- 沙箱 + 既有也是桩身份 ⇒ 不拦
- 真实授权域换号重绑 ⇒ 不拦（合法操作，不能因噎废食）

**失效方向刻意选 fail-open**：若某个真实老账号 uid 在 7 位以下则不受保护 —— 与改造前一致，
不会比原来更糟。彻底修法是给绑定行加 `sandbox` 列如实标注来源（列为后续项）。

**桩接线实测（用「假真实行」验证，不碰真实绑定）**：把行 11(9/3145) 的 uid 临时改成 14032724 →
走完整授权码流程 → 回调返回失败页

原 uid=14032724，本次 uid=42364」→ **行 uid 未被改写** → 已还原为 42489、state 行已删。

#### 11.1 抓到并修掉的 5 个「真机才炸」缺陷

1. **切 provider 后建项目 500（阻塞级）**：`gitee_account` 里是**写入时那个托管方的密钥**加密的

   企业令牌，**解密失败不回落** → 500。修法：解密失败按「本平台下没有这条绑定」处理 → 回落

### 12. Gitea 流程第二轮：界面文案面 + 失败原因面（#283~#285）

承接 §11，补做**「用户看得见的部分」**：界面文案（§11 已做）之外，还有两个从没被看过的面 ——

#### 12.1 缺陷 6（界面级）：同步失败原因把托管方原文抛给用户

- 现象：`gitee_repo_member.last_error` / `gitee_project.error_msg` = `GetUserByName`(6)/`Not Found`(4)/
  `Rate Limit Exceeded`(18)/`401 Unauthorized: Access token does not exist`(2)。
- **这两个字段直接渲染给租户管理员**：`GiteeProjectDetailView.vue:209`（成员表 FAILED 态 tooltip）、
  `:54`（项目详情红字告警）、`GiteeProjectsView.vue:270`（列表红字）。
- 两条独立成因：
  1. `GiteaProviderClient.extractMessage()` **只取错误体的 `message`** 就返回 ——
     而 Gitea 在协作者用户不存在时 `message` 恰恰是**内部操作名**：
     `PUT /repos/{o}/{r}/collaborators/dsj_admin -> HTTP 404 msg=GetUserByName`，
     真正的人话在 `errors[]`（`user does not exist [name: dsj_admin]`），被整段丢弃。
  2. 落库前不做本地化与归因。
- 修：`errors[]` 优先、`message` 附后；新增纯函数 `support/ProviderFailureText`
  （401→重新绑定 / 403→补令牌权限 / 404→仓库或账号不存在 / 422→账号在当前实例不存在 /
  429→限流会自动重试 / 5xx→稍后自动重试），**中文归因+动作在前、托管方原文附尾部括号**；
  托管方名由 `label` 传入，不写死。两个落库点（`GiteeMemberTaskHandler.failedMember`、
  `GiteeRepoTaskHandler.markFailed`）改走它。
- 防回归：单测 20 条 + 真机 `G9.4~G9.6`。

#### 12.2 缺陷 7（正确性级·最危险）：422「用户不存在」被当成「已是协作者」→ 成员假绿

- **怎么发现的**：为缺陷 6 写真机探针时探针**拿不到 FAILED**，成员反而被标 `SYNCED`，追下去才是产品判错。
- 直连 Gitea 实测：
  - `PUT .../collaborators/no-such-gitea-user-xyz` → **422** `{"message":"user does not exist [uid: 0, name: ...]"}`
  - `PUT .../collaborators/liujiejie`（已是协作者）→ **204**（幂等成功，根本不走异常分支）
- 成因：`isAlreadyCollaborator()` 把 **422 一律**当「已在协作者中」（注释依据是 Gitee 的行为）。
  ⇒ 权限根本没加上，管理端显示绿色「已同步」。G8 段创建者用例恰好走「未绑定⇒PENDING」分支而绕开了它。
- 修：判据改为「状态码属 400/409/422 **且**文案明确说已是协作者」
  （`already`/`已存在`/`已是`/`已在`/`has been added`/`repeated`）。单测 6 条 + 真机断言必须落 FAILED。
- 现状：库中 `SYNCED` 且带登录名的成员行 82 条，其登录名在真机 Gitea 上**都不存在**
  （含桩时代演示行，桩对任何登录名都回 204）。**刻意不改这些历史行**（那是改演示数据、不是修缺陷）。
- **真实缺口**：定时校准只补「非 SYNCED」成员（`ne(sync_status,'SYNCED')`）⇒ **不复核已 SYNCED 的行**，
  托管方账号被删/改名后平台不会自己发现。未引入「按 synced_at 老化重验」的原因：每轮多出与成员数
  同量级的外部调用，而该实例**已在返 429 限流**（新增失败面 > 收益）。属待评估项。

#### 12.3 同轮修掉的静默失效：**「清空失败原因」这句代码一直是空转**

- 证据：**17 个 `status=ACTIVE` 的项目**仍挂着 `error_msg='Rate Limit Exceeded'` ——
  说明「建仓成功 → `setErrorMsg(null)`」实际没写进去。
- 成因：MyBatis-Plus 默认 `update-strategy=NOT_NULL` 会把 **null 字段整段排除在 `SET` 外**
  ⇒ `setErrorMsg(null)` / `setLastError(null)` 这类「清空」写法**看着成功、一个字节没写**。
  与 `GiteeMemberTaskHandler.softDeleteMember` 注释里记的 `deletedAt + updateById` **同一族**。
- 修：`GiteeProject.errorMsg` / `GiteeRepoMember.lastError` 显式
  `@TableField(updateStrategy = FieldStrategy.ALWAYS)`（字段级，不影响其他列）。
- 为什么之前没暴露：界面只在配合 FAILED 态时渲染这两个字段 ⇒ ACTIVE 行上的残留不可见（**潜在**缺陷）。
- 防回归：真机 `G10.5~G10.7`（写脏 → 走重试 → 回读为空 → 回 ACTIVE 后仍为空）。

### 13. Gitea 账号绑定「闭环」：`unauthorized_client` 根因定位与修复（14:17–14:50）

#### 13.1 根因：**托管方登记的 OAuth 应用密钥形态不对，怎么传都过不了校验**

单变量对照 `POST {web}/login/oauth/access_token`：

| 入参 | 响应 |
|---|---|
| 现役 client_id + 登记页显示的密钥 | `unauthorized_client / invalid client secret` |
| 现役 client_id + **故意写错的**密钥 | **同上，逐字节相同** |
| 不存在的 client_id | `invalid_client / cannot load client with client id: ...` |
| 现役 client_id + 空密钥 | `unauthorized_client / invalid empty client secret` |

判读：client_id 被识别（与不存在时不同）、密钥字段被读到（与空时不同），
但**正确值与错值无法区分** ⇒ 库里存的密钥与登记页显示的**不是同一回事**。

决定性：**新建**一个应用（API `POST /user/applications/oauth2`）→ 同一条请求变成
`client is not authorized`（**凭证校验通过**，才轮到授权码被拒）。
新密钥是 **`gto_` 前缀 56 字符**，旧的是 **`qto_` 前缀 55 字符** ⇒
**Gitea 1.26 生成/校验 `gto_`；那个 `qto_` 值永远通不过**。
编辑页把库里失效值**原样显示** ⇒ 「截图里看着复制对了」这个直觉是错的。

#### 13.2 第二个缺陷：我们把 `error_description` 丢了

Gitea 的换令牌错误体 `{error, error_description}` 里 `error` **恒为通用码**：
正确密钥+无效码 → `client is not authorized`；密钥错 → `invalid client secret`；两者 `error` 都是 `unauthorized_client`。
而 `GiteaProviderClient.firstDetail()` 只 `return n.get("error")` ⇒ **页面两种故障同一句话**，用户看不懂。
**修**：`error_description` 优先、与 `error` 组合保留（→ `client is not authorized（unauthorized_client）`）；
`errors[]` 优先级不变。抽成 `static`（包内可见）后加单测 6 条。
