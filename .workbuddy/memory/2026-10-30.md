## 企微「接收消息服务器配置」与「可信域名」的关系（13:50 澄清）

结论（已核代码，不是推测）：
- **本项目没有实现企微消息回调端点**。全仓 grep `echostr` / `msg_signature` / `WXBizMsgCrypt` / `wx_crypt`
  在 `mcp-hub/` 与 `server/`（排除 target）**零命中**；`ConnectorController` 只有 OAuth 白名单的
  `/{code}/callback`，与消息推送无关。
- 因此「接收消息服务器配置」里的 URL/Token/EncodingAESKey **填了必然保存失败**：
  企微会立刻 GET 校验（要求 1 秒内回明文 echostr），我们的服务没有该端点。
- 两块配置**互不依赖**：可信域名（网页授权）+ 接收消息（事件推送）是两个独立模块。
  用户看到「要先设接收消息」，实际是同页保存时被非法的回调 URL 拖累 ⇒ **URL/Token/AESKey 全留空**即可。
- 同时：企微回调 URL **不支持写 IP**，且域名要备案 ⇒ 无备案域名时这条路上限就是"留空"。

路线：无备案域名 ⇒ 放弃 A 模式（OAuth 网页授权），只走 应用消息 / 通讯录 / 身份 + 邮箱 B 模式，
这三类**都不需要域名**，只差可信 IP 加白（当前出口 116.169.10.253，家宽会漂）。

## 纠正：可信 IP 有前置门槛（14:05，昨日判断有误）

企微「企业可信 IP」弹窗原文：**「配置企业可信IP前，请先 设置可信域名 或 设置接收消息服务器URL」**。
两者是**二选一**，但**都必须有能通过企微校验的域名**（页面原文：备案主体与当前企业主体相同或有关联）。
⇒ 无备案域名时，自建应用的**业务接口（发消息/通讯录/身份）根本开不了**，不是"只差加白"。
昨日说「只差 IP 加白」是错的，已在回复中纠正。

**对照实验（决定性证据，同一 IP 116.169.10.253）**：
- 自建应用 `agent/get` → `60020 not allow to access from your ip`
- 群机器人 webhook → `93000 invalid webhook url`（只是 key 错，**没有 60020**）
⇒ **群机器人 Webhook 不受可信 IP / 域名 / 企业认证限制**（官方 path/91770 只提 key 与 20 条/分钟）。
已做 `scripts/wecom_webhook_send.py`（--text / --markdown / --at-mobile，强制 IPv4 + 绕代理）。
这是当前唯一"今天就能用"的真机通道（仅群消息，不能给个人发、不能读通讯录）。

三条出路：① 群机器人 Hook（零门槛，限群消息）② 备案域名+云服务器（7~20 天，全功能）
③ 服务商第三方应用（需资质，个人不可行）。

**93000 排查口径**（实测踩到）：`invalid webhook url` 且 errmsg 带 `from ip: x.x.x.x` ⇒ 请求已到达企微，
**与网络/代理/可信 IP 全无关**，纯粹是 key 不被认。别往 IP 白名单方向查。
常见成因：①建的是「智能机器人」（新版带对话，无 webhook，走另一套 API）②复制了创建页的示例占位 key
③UUID 大小写被改 ④机器人被删/未建完。已在 `wecom_webhook_send.py` 内置这套提示。
（key 属敏感，勿落库/勿写进文档。）

## 群机器人接入体系 + 三个必修 bug（15:10 收口）

**1. MCP 闸门只判 CONNECTED ⇒ API_KEY 型连接器永远进不了 manifest。**
`McpRegistryService.manifest()` 对 BUILTIN 只认 `connector_connection` CONNECTED；群机器人是租户凭据型、
没有用户授权环节 ⇒ 「hub 里能调、AI 看不见」。修：新增 `usableForAgent()`，CONNECTED 之外允许
`auth_mode=API_KEY && configReady(tenant)`。`getTrusted=1` 仍在查询里，信任闸门没被绕过。

**2. 工具描述决定模型调不调。**
描述只写「往企业微信群发送消息」时，MiniMax 拿到 2 个工具却**不调**，反问「请提供群名称或群ID」；
把「目标群由 Webhook Key 决定，本工具没有也不需要群名/群ID，用户说发群里就直接发」写进描述**首句**后才调通。
另：HITL 开了 `ask_user` 会放大反问倾向（实测直接弹 `need_clarification` 问「发到哪个群」）。

**3. 凭据泄漏的第二条路径：依赖的日志。**
自己 logger 只打 key 尾 4 位，但 **httpx 在 INFO 级别把整条 `?key=…` URL 打出来**（验收时靠日志取第二源才发现）。
修：`group.py` 装 `_RedactKeyFilter` 到 `httpx` logger，把 `key=/access_token=/corpsecret=/secret=` 抹成 `***`
（只改 record 文本、不改级别 ⇒ 并发安全）。哨兵 G7 直接扫日志文件本体复核。

## 按用户跳转授权方案评审（15:40，产出 docs/63）

用户要「像 WorkBuddy 那样每人跳转授权、Agent 用该用户自己的数据」。已把官方口径核实一遍并对照代码，
结论：**骨架已在，不需要重做**；但有 2 个 P0 缺陷（都是 mock 掩盖的）。

### 前提纠正（最重要，已写进 docs/63 §1）

**企微没有「用户级 access_token」**。只有应用级 token（corpId+corpSecret 换），OAuth 产出的是
`userid`（长期）+ `user_ticket`（1800s、一次性）。所以「以该用户身份调 API」= 应用 token + userid 当参数；
敏感字段之所以能拿，是因为**本人点过授权**，不是因为存在用户 token。
⇒ 隔离不能靠 token 天然保证，必须自己在「谁在调」层做；`userid` 绝不能作为工具入参（否则越权读他人）。

### 官方硬口径（检索核实，附链接见 docs/63 附录）

- `snsapi_base` 静默仅 UserId；`snsapi_userinfo` 静默无手机/邮箱；**`snsapi_privateinfo` 手动授权**含手机/邮箱，
  且 **`agentid` 必填否则报错**、**成员须在可见范围内否则不返回 `user_ticket`（不报错）**。
- `auth/getuserinfo` → `userid` + `user_ticket`；code 一次性、5min 过期；域名不匹配回 `50001`。
- `auth/getuserdetail`（POST body `{"user_ticket"}`）→ name/mobile/email/**biz_mail**；成员须在可见范围。
- **2022-06-20 20:00 起 `user/list` 不再返回头像/性别/手机/邮箱/企业邮箱/二维码/地址**；
  2022-08-15 起「通讯录同步」新增 IP 不能调 `user/list`。⇒「必须让用户点一下」是官方结构，不是我们的选择。
- 可信域名须**完全一致**（含端口、不支持泛域名/IP）；**配可信 IP 前必须先有可信域名或接收消息 URL**。
- 敏感授权有 **30 天记忆**（首授权后 30 天内不再弹），用户要改得自己去企微「个人敏感信息授权管理」。
- 上下游/企业互联**不支持** `user_ticket`。

### P0-1 `exchange_code` 与官方不一致（mock 把它藏住了）

`wecom/wecom_api.py:177` 调 `/cgi-bin/user/getuserinfo` 并读字段 `ticket`；官方是
`/cgi-bin/auth/getuserinfo` + `user_ticket`。真机上 ⇒ `user_ticket` 为 None ⇒ `complete_oauth` 跳过
`getuserdetail` ⇒ `a_credential` 只有 userid，name/biz_mail 为 null，**且不报错**。
20 项双模式哨兵测不出来，因为 mock 的 `exchange_code` 直接返回 `user_ticket`（`wecom_api.py:91`）——
**这是「mock 当判据」的教科书案例**，与本项目铁律 7/12 同源。

### P0-2 用户连接态两个源，闸门读的与执行读的不是同一个

- Java `connector_connection`（`WeComOAuthService.callback` 写）→ **manifest 闸门读它**；
- hub `wecom_connection`（`server.complete_oauth` 写）→ **工具执行读它**（gate + payload）；
- 两处**无任何回写**（hub 只回打 `/auth/me`）。
⇒ 走 Agent 的 `connect` 工具连上后，Java 表仍 NEED_AUTH ⇒ 下一轮 manifest 判未连接 ⇒ **工具从模型手里消失**。
反之走 Java 回调则 hub 无凭据 ⇒ 执行报「凭据缺失」。已核对实际库：Java 侧只有 qq_mail 的 CONNECTED 行，
hub `wecom_connection` 为空 —— 因为 A 模式真机从未跑通，所以这个断裂一直没被撞到。

### P1/P2

- `send_text_message(touser, content)` 让模型自选收件人 ⇒ 在「按用户授权」语义下属越权（可给任意同事发）。
- `contact_search` 用 `user/list?department_id=1` 读全员可见范围（非「用户自己的数据」），
  且 `bizMail` 自 2022-06-20 起恒为 null —— 又是 mock 里有值、真机没有。

### 外部前置

A 模式真机唯一阻塞仍是**备案域名**（否则加不了可信 IP）。绕法：只上群机器人 + 邮箱模式 B，

## 评估 wecom-unified skill（npx skills add WecomTeam/wecom-unified）

### 它是什么

不是「企业微信对接 SDK」，而是 **`@wecom/cli`（官方 CLI，本机已装 1.3.4）的命令行套件**：
133 个 reference，覆盖 13 个业务域（消息/邮件/文档/在线表格/智能表格/智能文档/PPT/日程/会议/待办/微盘/通讯录/媒体），
外加 10 套 slide 模板与 6 个 python 脚本（build_docx / build_page / recalc 等）。
鉴权 = `wecom-cli auth init` **本机扫码一次**，凭据加密落在 `WECOM_CLI_CONFIG_DIR` 下的
`personal/credentials.enc` + `.encryption_key`（本机已有这套文件，说明已授权过）。

### 安装状态的两个坑（实测）

1. **`~/.workbuddy/skills/wecom-unified` 是空目录**（0 字节）⇒ WorkBuddy **不会加载**它
   （本会话可加载 skill 列表里没有它）。有内容的是 `~/.agents/skills/wecom-unified`，
   靠 `~/.claude/skills/wecom-unified` 软链给 Claude Code 用。要在这里用得重新装或同步过去。
2. 本会话 **WeCom 连接器是关闭的**（系统级约束），所以 CLI 与 skill 都不可调用；
   要启用得在左下角 + 菜单打开连接器。分析只读文件、未运行 CLI。

### 结论（关键判断）

它**不能**替代本项目的企微能力，因为两者的部署模型根本不同：

| | wecom-unified skill | 本项目 |
|---|---|---|
| 执行载体 | 本机 CLI（要 Bash） | MCP 服务 :8099 + Java 控制面 |
| 身份 | 单授权人（一套 credentials.enc） | N 个用户各自 OAuth，tenantId+userId 隔离 |
| 鉴权 | 本机扫码一次 | 跳转授权 + state + 回跳 + 库内加密凭据 |
| 按用户裁剪 | 无（有 Bash 就能全调） | manifest 闸门 + A/B 模式闸门 |
| 消息发送面 | 只有授权人 / 机器人最近会话 | 应用 token 可发可见范围任何人（已加 confirmed 闸门） |

⇒ **不能删任何现有模块**。我们那 10 个 A/B 工具（send_text_message / contact_search /
get_my_profile / mail_*6 / check_connection）在「单人单机」场景下与 skill 能力重叠，
但承载了 skill 没有的东西（租户隔离、闸门、审计、邮件幂等草稿表）。

### 它真正的价值（两条）

1. **证明「扫码授权」能绕开备案域名** —— 我们 A 模式唯一的外部阻塞。但它是官方机器人的授权通道，
   SaaS 无法复用（拿不到别人的 credentials.enc）。
2. **补齐 9 个我们完全没有的域**（文档/表格/智能表格/智能文档/PPT/日程/会议/待办/微盘/媒体），
   这份清单可直接当 roadmap，按 docs/63 的模式做成新连接器。

### 不建议的用法

在 agent 服务端 shell 调 `wecom-cli`：每用户需独立 `WECOM_CLI_CONFIG_DIR` + 各自扫码，
无法自动化；且加密密钥与密文同目录，多租户下等于弱隔离。

## 决定：AIOS 走 wecom-cli 接入 → 计划见 docs/64

用户拍板用该 skill/CLI 作为企微通道。出计划（`docs/64`），未动代码。

### 实测六条（决定架构，均已验证）

1. CLI 1.3.4，满足 skill 要求。
2. **隔离靠配置目录**：`WECOM_CLI_CONFIG_DIR=$(mktemp -d) wecom-cli auth show --status` → `unauthorized`；
   现用目录 → `authorized`。⇒ 多用户 = 每人一个目录。
3. **授权可程序驱动**：`auth init --noninteractive --no-browser --output-qrcode <png>` ⇒ 可做 H5 二维码 + 轮询。
4. `identity whoami` 返回**两段身份**：机器人（名/ID）+ 授权真人（名/ID），且声明
   「CLI 调用一定由机器人身份代用户执行」。**顶层 --help 里没有 identity，但它存在**。
5. 写入权限：读真人数据 OK；写只有 doc/sheet/smartsheet/smartpage 四类可跨身份，
   其余只能写机器人创建的数据（`todo --help` 自称「机器人视角」）⇒ 逐域实测前不要承诺"替用户发邮件/建待办"。
6. **skill 与 CLI 有命令漂移**：skill 写 `contact search`，CLI 实际 `contact users search`，
   且 CLI 直接回「该接口不存在……请更新到最新 skill」。⇒ 命令一律以 `--schema`/`--doc` 现取。

额外：`chat messages list` 可按时间范围拉会话消息 ⇒ **入站消息可读**（我们原先完全没有接收能力）。

### 计划的骨架

P0 Spike：**一个 Bot 能否挂多个真人**（两个空目录 + 同一 Bot ID/Secret + 两个同事扫码）。
不通过就停，退回 docs/63 的 MCP 路线 —— 这是整个方案的前提，必须先验。

结论性判断：旧代码**不能整体废弃**。可废的只有 A 模式 snsapi_privateinfo 链路
（`wecom/oauth.py`、`wecom_api` 的 exchange_code/get_user_detail、`admin_api` 的 oauth 两接口、
Java `WeComOAuthService`、`_connect_a`/`_wait_connected`）；
必须留：群机器人 webhook（CLI 发不了指定群）、store/crypto/identity/gate、sync、Java 控制面、前端面板、哨兵。

废弃顺序钉死：Spike 通过 → P1 验收 → 切入口 → 观察一迭代 → 才删。P1 前删 = 把回滚路径也删了。

## 企微「扫码」连接器（wecom_cli）· 连接器入口 + 数字人读数全链路打通

目标（用户原话）：一个人一个账号，各自只看到自己绑定的企业微信；且必须先在「连接器」里选企业微信
完成扫码绑定，之后才能在数字人里提问企微数据。

**实装**
- hub `mcp_hub/wecom_cli/`：`profiles`（目录即身份）/`runner`（子进程+剔除 `WECOM_CLI_ADDITIONAL_HEADERS_*`）/
  `auth`（status/whoami/start_qr/bind）/`catalog`（5 只读工具）/`identity`（有 Authorization 必走真实身份）/
  `server`（原生 FastMCP）/`admin_api`（`/api/v1/wecom_cli/{status,qr,bind,disconnect}`）。
- `app.py` 前缀分流：`/api/v1/wecom_cli` 必须在 `/api/v1/wecom` **之前**（包含关系）。
- Java：`WeComCliGateway`（专用，契约 `{code,message,data}`）+ `ConnectorController` 的 `qr/qr-status/qr-bind`
  与 `start→mode=QR`、`disconnect→先删 hub 目录再改库` + `ConnectorDef.AUTH_MODE_QR` + `V102`。
- H5 `index.html`：`openConnector` QR 分支 + `openQrModal`（出图→2s 轮询→bind→关闭）+ `.oa-qr-*` 白底样式。
- `start-all.sh`：`unset SERVER__PORT` + `--server.port=8080`；WECOM_MOCK=1 时给
  `AIOS_WECOM_CLI_SHARED_PROFILE` 演示兜底（生产必须清空）。

**验收**：`_verify_wecom_cli`(15/15) · `_verify_oa_qr_modal`(10/10) · connectors 19/19 · mcp_registry 13/13 ·
state_sync 7/7 · agent_wiring 6/6 · oa_connector_ui 17/17 · oa_mcp_panel 19/19。
真实对话（MiniMax-Text-01）：问「我绑定的企业微信是哪个账号」→ 调 `mcp__wecom_cli__whoami` → 答「刘洋」；
问「刘洋在哪个部门」→ 调 `mcp__wecom_cli__contact_search` → 答「成都易构部门」。

**四个坑**（明细已进 `topics/pitfalls.md`）：credentials.enc 层级 / ASGI helper 忘 await /
`SERVER__PORT` 劫持端口 / H5 生效文件是 index.html 而非 `_oa_app.js`。

**未做**：一 Bot 挂多真人（原 P0 Spike）仍无第二份真机授权可验；写操作（F5 权限边界）未开放；
旧 A 模式（`wechat_work` 的 privateinfo 链路）尚未物理删除。
