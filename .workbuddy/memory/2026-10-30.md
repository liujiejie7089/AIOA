## 企微「接收消息服务器配置」与「可信域名」的关系（13:50 澄清）

结论（已核代码，不是推测）：
- **本项目没有实现企微消息回调端点**。全仓 grep `echostr` / `msg_signature` / `WXBizMsgCrypt` / `wx_crypt`
  在 `mcp-hub/` 与 `server/`（排除 target）**零命中**；`ConnectorController` 只有 OAuth 白名单的
  `/{code}/callback`，与消息推送无关。
- 因此「接收消息服务器配置」里的 URL/Token/EncodingAESKey **填了必然保存失败**：
  企微会立刻 GET 校验（要求 1 秒内回明文 echostr），我们的服务没有该端点。
- 两块配置**互不依赖**：可信域名（网页授权）+ 接收消息（事件推送）是两个独立模块。
  用户看到「要先设接收消息」，实际是同页保存时被非法的回调 URL 拖累 ⇒ **URL/Token/AESKey 全留空**即可。
- 同时：企微回调 URL **不支持写 IP**，且域名要备案 ⇒ 无备案域名时这条路上限就是"留空"。

路线：无备案域名 ⇒ 放弃 A 模式（OAuth 网页授权），只走 应用消息 / 通讯录 / 身份 + 邮箱 B 模式，
这三类**都不需要域名**，只差可信 IP 加白（当前出口 116.169.10.253，家宽会漂）。

## 纠正：可信 IP 有前置门槛（14:05，昨日判断有误）

企微「企业可信 IP」弹窗原文：**「配置企业可信IP前，请先 设置可信域名 或 设置接收消息服务器URL」**。
两者是**二选一**，但**都必须有能通过企微校验的域名**（页面原文：备案主体与当前企业主体相同或有关联）。
⇒ 无备案域名时，自建应用的**业务接口（发消息/通讯录/身份）根本开不了**，不是"只差加白"。
昨日说「只差 IP 加白」是错的，已在回复中纠正。

**对照实验（决定性证据，同一 IP 116.169.10.253）**：
- 自建应用 `agent/get` → `60020 not allow to access from your ip`
- 群机器人 webhook → `93000 invalid webhook url`（只是 key 错，**没有 60020**）
⇒ **群机器人 Webhook 不受可信 IP / 域名 / 企业认证限制**（官方 path/91770 只提 key 与 20 条/分钟）。
已做 `scripts/wecom_webhook_send.py`（--text / --markdown / --at-mobile，强制 IPv4 + 绕代理）。
这是当前唯一"今天就能用"的真机通道（仅群消息，不能给个人发、不能读通讯录）。

三条出路：① 群机器人 Hook（零门槛，限群消息）② 备案域名+云服务器（7~20 天，全功能）
③ 服务商第三方应用（需资质，个人不可行）。

**93000 排查口径**（实测踩到）：`invalid webhook url` 且 errmsg 带 `from ip: x.x.x.x` ⇒ 请求已到达企微，
**与网络/代理/可信 IP 全无关**，纯粹是 key 不被认。别往 IP 白名单方向查。
常见成因：①建的是「智能机器人」（新版带对话，无 webhook，走另一套 API）②复制了创建页的示例占位 key
③UUID 大小写被改 ④机器人被删/未建完。已在 `wecom_webhook_send.py` 内置这套提示。
（key 属敏感，勿落库/勿写进文档。）

## 群机器人接入体系 + 三个必修 bug（15:10 收口）

**1. MCP 闸门只判 CONNECTED ⇒ API_KEY 型连接器永远进不了 manifest。**
`McpRegistryService.manifest()` 对 BUILTIN 只认 `connector_connection` CONNECTED；群机器人是租户凭据型、
没有用户授权环节 ⇒ 「hub 里能调、AI 看不见」。修：新增 `usableForAgent()`，CONNECTED 之外允许
`auth_mode=API_KEY && configReady(tenant)`。`getTrusted=1` 仍在查询里，信任闸门没被绕过。

**2. 工具描述决定模型调不调。**
描述只写「往企业微信群发送消息」时，MiniMax 拿到 2 个工具却**不调**，反问「请提供群名称或群ID」；
把「目标群由 Webhook Key 决定，本工具没有也不需要群名/群ID，用户说发群里就直接发」写进描述**首句**后才调通。
另：HITL 开了 `ask_user` 会放大反问倾向（实测直接弹 `need_clarification` 问「发到哪个群」）。

**3. 凭据泄漏的第二条路径：依赖的日志。**
自己 logger 只打 key 尾 4 位，但 **httpx 在 INFO 级别把整条 `?key=…` URL 打出来**（验收时靠日志取第二源才发现）。
修：`group.py` 装 `_RedactKeyFilter` 到 `httpx` logger，把 `key=/access_token=/corpsecret=/secret=` 抹成 `***`
（只改 record 文本、不改级别 ⇒ 并发安全）。哨兵 G7 直接扫日志文件本体复核。

### 端到端踩的两个「看起来没问题」的坑

- `POST :8000/internal/v1/runs` 必须带 **`user_token`**（body 字段，用户 accessToken）。缺了
  ⇒ `ToolClient.enabled=False` ⇒ MCP 通道整段跳过；此时日志 `tools=2` 是 HITL 的 `ask_user`/`request_form`，
  **不是**连接器工具。我一开始就把它当成「群机器人 2 个工具」误判过一次 —— 判据要回真源。
- hub 用 `&` 起在「会退出的 shell」里 **必被回收**（本次实测 1 分钟内消失，agent 随即 `mcpDegraded=true`）。
  必须同任务内 `起服务 + sleep 100000`。同理 `SERVER__PORT=61302` 要把后端顶到错误端口，启动前 `unset`。

### DB 工具目录只是快照（会旧，别当权威）

`mcp_server_tool` 在 **trust 那一刻**从 hub 的 `list_tools` 覆盖写；hub 后续扩工具而没人重新信任，
界面数字就一直是旧的（实测 `wechat_work` 已 13、DB 留 3）。**重跑 trust 即自愈**；`_verify_mcp_registry.py`
新增 M13 用「DB vs hub 实装数」双向比对盯着它。

### 哨兵自身的坑：断言依赖外部状态

`_verify_mcp_registry.py` 的 M1/M2/M3/M8/M9 都以「库里 trusted 全 0」为前提，但脚本从不保证这个前提
⇒ 真实环境里别人 trust 过就 5 项一起假失败。改成「快照 trusted → 复位 → 跑 → **按快照恢复**」。
不能无脑复位：`wecom_group` 一取消信任，AI 那边的工具就没了。
