### 关键现状（盘点结论）
- 已有好底子：`KbFileParser` 支持 PDF/Word/Excel/MD/CSV；`KnowledgeStore` 接口 + `MysqlKnowledgeStore`，
  **已预留 `aioa.kb.store=vector` 切换点**（`@ConditionalOnProperty`）；`kb_document`(54) / `kb_chunk`(792)；
  `ai_expert`(4，全 tenant_id=0 全局模板)；`tool_definition`(**0 条**，表已建模未填充)；
  agent 侧有完整 OpenAI 兼容调用 + function-calling 循环 + citations 溯源。
- 缺：向量化与检索（现为 `LIKE`）、租户级配置内核、工具实例、意图路由、参数生效链路。
- **温度在 `agent/app/core/agent_runtime.py` 的 `_post_non_stream` 里硬编码 0.3** → 参数不生效的典型点。
- agent 总代码仅 1152 行；依赖只有 fastapi/uvicorn/pydantic/pyyaml/httpx/pytest（无 numpy/ES 客户端）。

### 环境约束（重要）
- **本机无 ES、无 docker**。`aioa` 库 57 张表，企业模拟数据只有 `approval_order`(82)/`payment_order`(8)/`biz_kpi`(9)。
- 方案设计为「双实现」：默认 `local`（零依赖跑通闭环）+ `elasticsearch`（dense_vector + HNSW + 客户端 RRF，
  rank_constant=60；注意 **ES 原生 RRF retriever 需 Enterprise 许可**，免费版只能客户端融合）。

### 2026 同类方案对标要点
- 混合检索 BM25+向量+重排是标配；RAGFlow 强在复杂文档解析与溯源，Dify 强在编排，MaxKB 开箱即用。
- RRF 只按排名融合（绕开 BM25 与余弦量纲不一致问题），k=60 是 ES 生产默认；cross-encoder 重排是二阶段，
  先取 top-100~1000 再重排。
- 借鉴的验证手段：每次 run 回传 **`effective_params` 生效参数快照**（含每个参数最终值与来源层级），
  这是验证「配置真实生效」的核心；另提供 resolve 接口返回每层覆盖来源。
